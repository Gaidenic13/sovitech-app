# packages/engine/src/bodies

One file per production formula body, named `<id>@<version>.ts`. `../manifest.json` records, for each, the SHA-256 of the body together with everything it loads, transitively (`../manifest.ts` `bodyHashInputOf`, reached as `@sovitech/engine/manifest`: each file of that closure, sorted by its path from the repository root, as its path, its length and its bytes, then each allowed package by its locked version; docs/adr/0047 decision 3 as amended in phase 5 part B and after the final verification; guardrails 2.4 "Formula versions are immutable"; case G9-11; `../manifest.test.ts` checks this folder against the manifest and the catalogue).

Empty in phase 5: no source defines the method of any declared formula (points, CAPEX at stage 1 and 2, annual energy, savings, the measures' order all wait for SOVITECH datasets that no one has approved), so the app shows "Not available yet" naming what is missing (prompt 3, phase 5: "Write no production formula for a method no source defines"). TEST bodies live in `packages/engine/test-formulas/bodies/`, with their own manifest, and load only inside the test runner.

What the hash covers, and what fails the check (it fails closed):

- Every import and export-from, found by the TypeScript parser however it is laid out (two on one line, one split over lines, after a comment), and every `import()` and `require()` with a plain string literal. Each relative module is hashed with its bytes, and theirs in turn (an engine helper such as `../interval.ts`, and `../errors.ts` behind it). A helper changed under the same version fails the check, as a changed body does; the fix is a new version of each body that loads it, never a re-recorded entry.
- One package by name: `decimal.js` (`PRODUCTION_IMPORT_POLICY`), hashed by its exact version in `pnpm-lock.yaml` for the engine, so a new locked version fails the check too. Any other import by name fails: a workspace package such as `@sovitech/registry` (its `link:` is no version), a Node built-in, any other package.
- An `import()` or `require()` whose module is not a plain string literal (a template literal, a variable, a concatenation), `require` used any other way, a source that does not parse, or an import that names no file fails the check; it never passes it.
- `import type`, `export type` and type positions load nothing at run time and are left out (an `import { type X }` still loads its module and is kept).

Keep a body's imports to the engine's own modules (`../interval` for values, `../catalogue` for types), so the closure stays small and every file in it is one the engine owns. (Phase 5 part A wrote here that a body's file hash covered everything that decides its figures; with helpers imported, it did not: part B's V-7. Part B's reader then found imports with a pattern at the start of a line and left packages out; the final verification of phase 5 showed it missed a second import on one line, a template-literal `import()` and every package, and the parser and the policy above replaced it.)

# tests/guardrails

One file per code-test case (T) of `docs/guardrails.md` section 7, at the top level of this folder. Vitest's `guardrails` project runs them (`pnpm test`).

- **File names.** The case id as section 7 writes it, then `.test.ts` (or `.test.tsx` for a case that renders JSX): `G1-4.test.ts`, `G7-2a.test.ts`, `GS-1.test.ts`.
- **Titles.** Every test title starts with the ids it proves, for example `'G1-4 · …'` or `'US-INTAKE-03 · F-QUESTION-02 · G7-6: …'` (prompt 3 section 12). The index check fails a file in which no string names its id.
- **Support code** goes in `_support/`, which Vitest does not collect. No other subfolder.
- **Pending cases.** A case written before the code it tests starts with the marker line `// @pending-until: phase <n> <feature>[, <feature>]` and registers its test through the pending wrapper, `_support/pending.ts` (`const pending = pendingCase(import.meta.url); pending('<ID> · …', body)`). A file that imports the wrapper, directly or through another `_support/` module, is pending: the index check lists its id as "pending: no automated check yet", never as passing. The import and the marker go together; either one alone, or a malformed marker, fails the index check (ADR 0003, ADR 0004). Both come out in the phase that builds the code under test: the wrapper fails the test as soon as it passes.
- **Never hold a case out any other way.** `test.skip`, `.todo`, `.only`, `.fails`, `.skipIf`, `.runIf` and `context.skip()` in a case file fail the index check, and so do an options object with `skip`, `todo`, `fails` or `only` on a test or a describe (`test('…', { skip: true }, fn)`), a computed modifier (`test['skip']`), a destructured one (`const { skip } = test`), and `test.extend`. The index check reads case files with the TypeScript parser, and a file with any of these is malformed: it counts neither as real nor as pending. At run time the guardrail run guard (`tools/vitest/guardrail-run-guard.ts`) fails the run when a guardrail test is skipped, todo, filtered by `.only` or `-t`, or in fails mode other than by the wrapper, or when a case file runs no test.
- **Never throw the stub's error yourself.** A case file that names `NotImplementedError` or `declareNotImplemented` fails the index check: only a domain stub throws that error, and `new NotImplementedError(...)` outside the domain throws a `TypeError` (ADR 0004). Call the domain function under test instead.
- **Every test asserts, and each assertion checks something.** A test with an empty body fails the index check (`[empty]`), and the `guardrails` Vitest project sets `expect.requireAssertions`, so a test whose body asserts nothing fails the run. Since the phase 0 review round 2 the index check also refuses (`[vacuous]`) an `expect(...)` with no matcher called after it (Vitest counts the `expect` call itself as an assertion), `expect.assertions(0)` or a count computed from code, and `.toThrow()` or `.toThrowError()` naming no error: any error passes them, the domain stub's `NotImplementedError` included.
- **Test the code, not a stand-in.** `vi.mock`, `vi.doMock`, `vi.stubGlobal`, `vi.stubEnv`, `vi.resetModules`, `vi.importActual`, `vi.importMock`, a computed or destructured member of `vi`, and a `vi.spyOn` given its own implementation or placed on project code (`@sovitech/*` or a relative import) fail the index check (`[test double]`). A `vi.fn()` passed in as a dependency is allowed. A case that truly needs a double gets an entry in `tools/checks/index/reviewed-test-doubles.json` (empty today): the file, the call, its target and why the case still tests the code under test. Each entry is a loosening the owner reviews (it is in the loosening check's exception-list snapshot), and an entry that matches no use fails the check.
- **A stub reached is not a pass.** The `guardrails` project's stub guard (`tools/vitest/guardrail-stub-guard.ts`) fails any test that reached an unbuilt domain stub, caught or not, unless the pending wrapper held it out (`[stub] case exercises an unbuilt stub`). So `expect(() => derive(...)).toThrow()` against a stub fails; write the case behind the pending wrapper until the code exists.
- **Support code is read like a case file.** Modules in `_support/` must not swallow errors: a `catch` clause, `.catch`, a two-argument `.then`, `Promise.allSettled`, a hold-out, a vacuous assertion, a test double, or naming `NotImplementedError` is a `[support]` problem, and a case that imports such a module, directly or through another, is malformed. The pending wrapper alone may catch the stub's error and skip.
- **No stubs.** While D-33 is open, no placeholder file is written for a case that does not exist yet (`docs/adr/0003-index-check-convention.md`). A file carrying the `@guardrail-stub` marker never counts as a case.

The index check (`tools/checks/index/`, run by `pnpm checks`) fails when a T id of section 7 has no file here, and when a file here is not named `<ID>.test.ts`, names an id that is not in section 7, or names an E id (evals go in `evals/guardrails/`).

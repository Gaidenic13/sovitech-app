# 0026. The analysis queue and upload sessions: two tables in schema `sovitech_work`

- **Status:** Accepted: default, reversible. Supersedes ADR 0020 (pg-boss), which was not built.
- **Date:** 2026-09-26

## Context

- **ADR 0020** chose pg-boss 12.34.0 in its own schema, created by a committed copy of pg-boss's construction plans. Building phase 2 showed three costs: pg-boss's job rows hold a JSON payload and an `output` column where a thrown error is serialised with its message (rule 13 then depends on every caller never passing text); creating a queue in pg-boss 10 and later creates a table partition at run time, which is DDL by the app's role; and its dependency tree (cron-parser, rrule-temporal, serialize-error, type-fest, luxon) serves features the worker does not use.
- **ADR 0019:** resumable uploads need a place to keep an upload in flight (its project, user, declared size and format) across requests and restarts.
- **Prompt 3 section 8 and ADR 0018 / 0024:** one sandboxed container per file; the extractor's command line and exit codes are ADR 0024's.
- **Rule 13:** neither the queue nor its logs may hold document text.

## Decision

1. **Schema `sovitech_work`**, created by migration 0010 as `sovitech_db_owner`, outside schema `sovitech`, so the value store's append-only guards and `unguarded_tables()` are untouched. The app role gets `USAGE`, `SELECT`, `INSERT`, `DELETE` and `UPDATE` on named columns only; it runs no DDL.
2. **`analysis_jobs`** holds ids and codes only: project id, document id, content hash, state (`queued`, `running`, `done`, `failed`), attempts, `run_after`, the worker that holds it and since when, and an error code checked by a pattern (`^[a-z][a-z0-9_]*$`), so no text can land in it. A partial unique index allows one open job per document.
3. **The worker** (`apps/api/src/jobs/worker.ts`) claims a job with `FOR UPDATE SKIP LOCKED` (a job held longer than `staleAfterSeconds` is reclaimed), writes `request.json` into the job's work folder, runs the extractor through `DockerExtractorRunner` with ADR 0024's flags, mounts and command line (`--request /job/request.json --document /input/document --out /output [--ids /ids/requirements.ids]`), reads `output.json` with the YAML reader restricted to JSON (no aliases, unique keys, 256 MiB ceiling), checks it with `parseExtractionOutput` and `outputAnswersRequest`, and stores only what the output holds (ADR 0027). A failure retries after `retryAfterSeconds`; the last attempt records "Analysis failed". The work folder is removed whatever happens. Exit codes map to error codes: 2 `extractor_refused_request`, 3 `extractor_refused_job`, 137 `sandbox_memory_limit`, 125 `sandbox_unavailable`, a timeout `sandbox_time_limit`, anything else `extractor_failed`.
   **Amended in the phase 2 review (the output place).** A container compromised by a document could make `/output/output.json` a link to `/dev/zero` or a FIFO, which the host then followed (reading without bound, or waiting for ever), could run programs from `/output` (a noexec `/tmp` notwithstanding), could fill the host's disk for the whole wall clock, and could leave folders the host cannot remove. Now:
   - `/output` is a volume of the job's own, a tmpfs of `outputBytes` (the 256 MiB output limit and room for the writer's temporary file), `noexec,nosuid,nodev`, owned by the sandbox's account; no host folder backs it. A holder container (the same image running `sleep`, with the same confinement) keeps it mounted while the job's container runs and after it ends.
   - Every container runs with `--user 10001:10001`, so an image override cannot run as root.
   - After the job, the runner copies `/output/output.json` out through the Docker daemon as a tar entry (`docker cp`, which never follows a link): only one regular file named `output.json` within the output limit is taken, into a host file the runner creates (O_EXCL, never through a link); anything else is refused as `sandbox_output_refused` (not retried) and nothing is written on the host (`apps/api/src/jobs/copy-out.ts`). The holder, the container and the volume are removed whatever happened.
   - The worker reads the host file once, with `O_NOFOLLOW | O_NONBLOCK`, checks the open descriptor is a regular file within the limit, and reads at most that from the same descriptor (`read-output.ts`); the job's folders are owner-only, and a folder that will not go is logged by code rather than ending the worker.
   Proven by `apps/api/src/jobs/jobs.test.ts`: a container-made link to `/dev/zero` and a container-made FIFO at `output.json` are refused with nothing on the host; writing past the volume and running a file from it both fail in the container; host-made links, FIFOs and folders are refused by the reader.
   **And the models** (the orchestrator's ruling on PRD R-023 and R-024; ADR 0025 decision 4): a model's job ends with `model_reading_not_decided` before any sandbox runs, unless the worker carries the tests-only switch.
   **Superseded in part by ADR 0034** (2026-09-30): the 256 MiB ceiling and the 272 MiB volume above no longer hold. An output with no IFC section is read within 4 MiB, and the volume is 5 MiB, for every job that asks for no IFC values (every job while `ifc-values` is closed); only a job that asks for IFC values gets a 517 MiB volume, and its gated section is read line by line within 1 MiB a line and 512 MiB in all (ADR 0034 decisions 3 and 4).
4. **Nothing the container prints is read or logged.** Only its exit status, as a code.
5. **`upload_sessions`** holds an upload in flight: project, user, file name, format and declared size, and (migration 0011) its state (`open`, `appending`, `completing`), the lease of the request that holds it, and when it last saw an append or a completion (ADR 0019, "One writer at a time"). The app may update only the state, lease and activity columns, never the file name. A session is deleted when the upload completes, is refused or is aborted. An abandoned one (no append or completion for 30 minutes, no lease held) is removed with its staged bytes by `sweepAbandonedUploads` (`apps/api/src/uploads/service.ts`), which the API process runs when an upload is opened, at most once a minute, and the worker runs too (`worker-main.ts`, the same function). Since the fix round of 2026-09-30 the sweep takes the session under a lease, removes its staged bytes and sealed copy first, then deletes the session with its file name; a removal that fails gives the session back still abandoned, and the next sweep removes the bytes (`UploadSweepIncomplete` is logged as a code). The file name is held here only while the upload is in flight; once registered it moves to the document's text (ADR 0025).
6. **pg-boss and `@fastify/multipart` are removed** from `apps/api/package.json`: nothing imports them (ADR 0019 item 3 said the integrator would remove multipart if unused).
7. **The worker process** is `pnpm --filter @sovitech/api worker` (`src/worker-main.ts`). It acts as the extraction service account (`SOVITECH_EXTRACTION_ACCOUNT_ID`, created by `pnpm --filter @sovitech/api extraction-account`), which the owner's upload adds as a project member when it queues a job.

## Consequences

- No new dependency. The queue's semantics are a few SQL statements, tested against a real database (`packages/db/src/ingestion.test.ts`, `tests/api/analysis.test.ts`).
- Finished job rows stay until something deletes them; they hold ids and codes only. A retention sweep is not built.
- The worker is one process; several can run against the same table, since claiming skips locked rows.
- Each job costs a few more docker commands than one `docker run` (the volume, the holder, the copy, the removals): about a second on the development machine. The Python extractor's test harness no longer mounts a host folder at `/output` either (ADR 0034 decision 5): its sandbox definition, `services/extractor/src/sovitech_extractor/sandbox.py`, takes the job's volume and names the sandbox account since 2026-09-30.
- An upload's lease is held only for one request's append or completion; nothing holds a database connection while a chunk streams.

## How to reverse

- **Back to pg-boss or to graphile-worker:** the job carries `{ projectId, documentId, contentHash }` and nothing else; replace `enqueueAnalysis`, `claimAnalysisJob`, `finishAnalysisJob` and `failAnalysisJob` and drop the two tables by migration.

## Amended in the viewer step (2026-10-07, part 1; ADR 0051)

The plan named ADR 0020 for this amendment; ADR 0020 is superseded by this one, so the amendment is recorded here.
- **A second queue, for conversions:** `sovitech_work.model_view_jobs` (migration 0017), beside `analysis_jobs` and on its pattern: ids and codes only (project id, document id, content hash, state, attempts, `run_after`, the worker that holds it and since when, an error code checked by pattern), one open job per project and content hash (a second document of the same bytes in the same project reuses the conversion), claimed with `FOR UPDATE SKIP LOCKED`, failed and retried after `retryAfterSeconds`, the last attempt recorded as a `failed` conversion event with its code. The erasure drops a queued job of the erased bytes and ends a running one (`failed` with `erased`), so its worker, which checks under the project's write lock that it still holds the job before recording or keeping anything, stores nothing, and the bytes uploaded again get a job of their own (part 1's review, V-3 and A-1). Like `analysis_jobs`, it is working state without row-level security; the conversion record itself is the append-only `sovitech.model_view_events` (ADR 0051 decision 6; G13-14).
- **One worker loop for both:** `worker-main.ts` runs one analysis step and then one conversion step in turn (`ModelViewWorker.runOnce`), sleeping only when both are idle, so at most one sandbox runs at a time (each conversion container may take 4 GB on the 8 GiB Colima VM) and neither queue waits on the other's backlog. A conversion step that throws is logged as `worker_error` and the loop goes on. At start the worker queues the conversions current IFC models still need (`apps/api/src/jobs/model-view/backfill.ts`), and reads the hash of the converter's sources the image's label must match.
- **The worker acts as the extraction service account** for conversions too (decision 7). An IFC upload now adds that account as a project member when it queues the conversion, as an analysed upload already did; the account cannot add itself (SVR03), so the backfill does not reach an IFC-only project stored before the viewer step until its next IFC upload.
- **How to reverse:** stop queueing conversions and drop the loop's conversion step; `model_view_jobs` can then be dropped by migration.

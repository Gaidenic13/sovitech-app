# 0003. Index-check convention: no pending stubs while D-33 is open

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25 (amended 2026-09-25 at the end of phase 1)

## Context

`docs/guardrails.md` section 7 (v1.5) says: "The CI index check. It fails when an id below has no case file, or a case file's id is missing from this table." Section 7 indexes 104 ids at v1.5: 84 code tests (T) and 20 evals (E). T cases live in `tests/guardrails/<ID>.test.*`; E cases in `evals/guardrails/<ID>.yaml`.

Two sources disagree on unbuilt cases:
- **Prompt 3 section 5.2, row "Index-check convention"** (source: build-readiness decision 5) defaults to "Unbuilt cases exist as pending stubs, reported as 'no automated check yet', so CI is green from the first commit", and phase 0's exit asks for `pnpm check` green "with the stubs counted".
- **The PRD's D-33** (build-readiness decisions 5, 11 and 12) is open, with this "Until decided" line: "No pending stub is created: under v1.5 the index check fails for each section 7 id with no case file (guardrails section 7; R-156), and the harness reports each such case as 'no automated check yet', never as passing." Its impact column notes that a stub satisfying the index check with no test behind it "must never read as a working check", and PRD section 11 adds that such a stub "may count as a loosening (section 10, 'When unsure, treat the change as loosening')". Whether a stub counts as a case file is for the approver, who is not yet named.

Prompt 3 section 4: where a 5.2 default and the PRD's "Until decided" line differ, follow the stricter and log it. The orchestrator ruled on 2026-09-25, under that section, that the PRD line is the stricter one. The owner decided no D row as of 2026-09-25.

## Decision

This build follows the PRD's interim line, not prompt 3's default.

1. **No pending stubs are created.** No file exists under `tests/guardrails/` or `evals/guardrails/` unless it holds a real case.
2. **The index check** (`tools/checks/index/check.ts`) parses the section 7 table and:
   - fails for each id with no case file, and lists each one in `noAutomatedCheckYet`; `run-all` prints them under "No automated check yet";
   - fails for each case file whose id is not in the table;
   - counts a real case file whose test is held out of the green run by the pending wrapper as present, and lists it in `pending`; `run-all` prints it as "pending: no automated check yet", never as passing. The field-state and evidence tests are such files until phases 1 and 2 remove the wrapper.
3. **`run-all` enforces it too.** A check result whose `noAutomatedCheckYet` list is not empty never passes, whatever the check returned (`tools/checks/runner.ts`).
4. **A stub generator exists but is not run.** `tools/checks/index/generate-stubs.ts` can write one pending stub per id with no case file. Nothing runs it while D-33 is open.
5. **Everything else in `pnpm check` must be green.** Only the index check is expected to fail, and only for ids with no case file.

## Conventions the index check enforces

Recorded 2026-09-25 when the checks were integrated. Phase 1 onwards follows them; a change to any of them is a change to this ADR.

- **The count.** At v1.5 the section 7 table holds 104 ids: 84 T and 20 E. The index check's parser and an independent line count agree, and a unit test pins 104/84/20 while the version is 1.5 (`tools/checks/index/guardrail-index.test.ts`). The parser is importable (`tools/checks/index/guardrail-index.ts`: `loadGuardrailIndex`, `parseGuardrailIndex`), so no other check parses the table again.
- **Layout.** T cases are `tests/guardrails/<ID>.test.ts` (or `.test.tsx`) and E cases `evals/guardrails/<ID>.yaml`, at the top level of those folders. Support code for T cases lives in `tests/guardrails/_support/` only; eval support data in a folder starting with `_`. Any other nested file, and any top-level file that is not a case file, `README.md` or a dotfile, fails with `[layout]`. `.spec.ts` and `.yml` are refused. Two files for one id fail.
- **Titles.** Every T case file names its id in a string, in practice its test titles (prompt 3 section 12), or it fails with `[title]`. `G1-1` is not found inside `G1-10`, nor `G7-2` inside `G7-2a`.
- **Holding a case out.** The only way to hold a case out is the pending wrapper. Since the phase 0 review (finding 9) the check reads T case files with the TypeScript parser, not a regex, and raises `[held out]` for: `.skip`, `.todo`, `.only`, `.fails`, `.skipIf` and `.runIf` on any receiver (`test`, `it`, `describe`, a context, an import or local alias); an options object that sets `skip`, `todo`, `fails` or `only` on a test or a describe (a literal `false` is allowed); a computed modifier (`test['skip']`, `test[name]`); a destructured one (`const { skip } = test`, `({ skip }) => …`); `test.extend`; and `context.skip()`.
- **Empty tests.** A test registered (through `test`, `it`, an alias or the wrapper's `pendingCase`) with a body that does nothing is an `[empty]` problem. A body that runs but asserts nothing is caught at run time instead: the `guardrails` Vitest project sets `expect.requireAssertions`.
- **Vacuous assertions** (phase 0 review, round 2). `[vacuous]`: an `expect(...)` with no matcher called after it (also `expect.soft`, `expect.poll`, a test context's `expect`, an alias or a namespace import), which Vitest counts as an assertion so `expect.requireAssertions` lets it through; `expect.assertions(0)` or a count computed from code; and `.toThrow()` or `.toThrowError()` naming no error, which passes on any error, an unbuilt stub's included.
- **Test doubles** (round 2). `[test double]`: `vi.mock`, `vi.doMock`, `vi.stubGlobal`, `vi.stubEnv`, `vi.resetModules`, `vi.importActual`, `vi.importMock`, a member of `vi` that is computed or destructured, and a `vi.spyOn` given its own implementation (chained, or later through the spy variable) or placed on project code (`@sovitech/*` or a relative import). A `vi.fn()` passed in as a dependency is allowed. The only way past is an entry in the reviewed list `tools/checks/index/reviewed-test-doubles.json` (file, call, target, reason); it is empty, an entry that matches no use or a malformed list fails the check, and the list is in the loosening check's exception-list snapshot, so an added entry fails until the approver approves it (guardrails section 10).
- **Support modules** (round 2). Modules under `tests/guardrails/_support/` are read like case files. `[support]`: a catch clause, `.catch`, a two-argument `.then`, `Promise.allSettled`, a hold-out, a vacuous assertion, an unreviewed test double, or naming `NotImplementedError`; the pending wrapper alone may catch and skip. A case file that imports such a module, directly or through another, is malformed.
- **Run configuration** (round 2). On the repository only, the index check also runs the config-integrity check (`tools/vitest/config-integrity.ts`) and reports `[run config]` for any setting that loses a guard of the guardrail run: the run guard missing from the reporters; the `guardrails` project missing, renamed or doubled, or its include, `_support` exclude, `expect.requireAssertions` or stub-guard setup file changed; `passWithNoTests` or `allowOnly`; a `test` script other than `vitest run` with no flag outside `ALLOWED_TEST_SCRIPT_FLAGS` (empty, and in the exception-list snapshot); `pnpm check` or CI not running it as written. It holds even when a broken config would keep the unit tests from running.
- **Malformed files never count.** A T file with a `[held out]`, `[empty]`, `[vacuous]`, `[test double]`, `[support]` or naming `[pending]` problem, and an E file with an `[eval]` problem, is malformed: it counts neither as real nor as pending, and its id is listed as "no automated check yet" (in `noAutomatedCheckYet`). Before the review such a file counted as real with a problem.
- **Pending.** A T case file is pending when both hold: it imports the pending wrapper `tests/guardrails/_support/pending.ts` (directly, or through another `_support/` module), and its first line is the domain's marker `// @pending-until: phase <1-7> <feature>[, <feature>]`, as `parsePendingMarker` in `@sovitech/domain` reads it (ADR 0004). The wrapper and the index check read the same grammar. The import without the marker, the marker without the import, and a malformed marker are each a `[pending]` problem, and the file still counts as pending, never as real. A case file that names `NotImplementedError` or `declareNotImplemented` is a `[pending]` problem and malformed: only a domain stub throws that error (ADR 0004, decision 4), so a case file that throws it itself would stay pending forever (phase 0 review, finding 2).
- **Stubs.** A file carrying the marker `@guardrail-stub`, or an eval with `status: stub`, is a stub. A stub never counts as a case: its id stays in `noAutomatedCheckYet`, so running the generator can never make the check pass.
- **Evals.** An eval file is a YAML mapping with an `id` key equal to its file name. The optional `status` key accepts only `pending` or `stub`. Since the phase 0 review (findings 3 and 10), an eval counts only with the full case body of guardrails section 7: `fixture` (a path, or list of paths, under `fixtures/evals/<ID>/` that exists), `task` (text or a mapping), `assertions` (a non-empty list) and `samples: 5`. A file with less (an `id` line alone, say) is an `[eval]` problem and malformed. Whether a full eval may count as real is read from evidence, not a switch (`tools/checks/index/eval-runs.ts`; round 2 replaced the hand-set `EVAL_RUNNER_EXISTS`): the runner module must exist (`packages/ai/src/evals/runner.ts`, phase 2), and a results record `evals/guardrails/_results/<ID>.json` must name the id, `samples: 5` and `passed: 5`, with a prompt hash (every file under `prompts/`), model id (`MODEL_ID` in `packages/ai/src/model.ts`) and schema hash (every file under `packages/ai/src/schema/`) equal to the current ones. A change to any of the three after the run turns the case back to pending, with a problem (`CLAUDE.md` definition of done item 2). Until the runner exists no E case is real. The paths are the phase 2 contract; phase 2 may move them with the seeds and tests. If the runner's own schema check replaces the body check, the results-record rule stays.
- **An empty scope fails.** A section 7 table with no id, or a missing `tests/guardrails/` folder, is a `[scope]` problem (phase 0 review, finding 17).
- **The run-time half.** The guardrail run guard (`tools/vitest/guardrail-run-guard.ts`, a Vitest reporter registered in `vitest.config.ts`) reads what the run did and fails it when a guardrail test was skipped, todo, `.only`-filtered or in fails mode other than by the pending wrapper, when a case file ran no test, when a test did not finish, when a test's full name does not name its case id, when a passing test carries no stub-guard record (`[unguarded]`) or one showing it reached an unbuilt stub (`[stub]`), and, on an unfiltered run, when a case file on disk was not collected. A wrapper skip counts only with the wrapper's meta record, its note word for word, and the marker and wrapper import in the file. Its JSON report puts each case file in exactly one of `failed`, `heldOut`, `notCounted`, `pending` and `real`, so a test in fails mode is never listed as real (round 2). The stub guard (`tools/vitest/guardrail-stub-guard.ts`, a setup file of the `guardrails` project; ADR 0004, decision 7) fails a test that reached an unbuilt domain stub unless the wrapper held it out. `tools/vitest/README.md` records the limits of both.
- **Counts.** `run-all` and `pnpm check` print "Guardrail cases (docs/guardrails.md section 7): N real, N pending (no automated check yet), N no automated check yet", and a green run reads "passed with N pending … (no automated check yet)" while any case is held out (phase 0 review, finding 18). A run whose counts cannot be read is not green. Since round 2, `pnpm check` runs its Vitest step with `SOVITECH_RUN_GUARD_OUTPUT` set, and a code-test case counts as real only when its file reads as real and the run passed it as one (`tools/checks/index/run-evidence.ts`, `run-counts.ts`); a missing report, a run that saw no guardrail case file, and a case that reads as real but did not run and pass are `[run]` problems, and the run is not green. CI does the same in its `checks:run-evidence` job (`reconcile-run.ts`). `run-all` alone reads the case files only, and says so under its counts.
- **Versioned ids.** An id such as "G4-2 v2" (section 7, "Existing ids keep their expected result") has no file-name form yet. A row like that fails the check with a `[table]` problem until a form is agreed, rather than being skipped.
- **Report order.** Problems other than missing ids are printed first, as `problem: <file>:<line>: [<kind>] ...`, so a new fault never hides behind the expected missing ids.

## Consequences

- `pnpm check`, and CI once it exists, fail until every section 7 id has a real case file or D-33 is decided. Phase 0's exit item "pnpm check runs green with the stubs counted" does not hold while D-33 is open. This is reported in each phase report, not worked around.
- Every guardrail case with no automated check is named on every run, so a change summary can list them (`CLAUDE.md`, definition of done items 1 and 5).
- A failing index check can hide a new failure inside the same check. The index check's details therefore separate "no case file" ids from any other problem (an unindexed case file, an unparsable table), and the integrator reads the details, not only the table row.
- The conventions are proven on seeded inputs, 85 in all in the index self-test (`pnpm check:selftest -- --only index`): 45 bad inputs and one control under `tools/checks/index/seeded/`; 24 bad seeded case files and 2 controls in `tools/vitest/seeded/run/`; three roots that Vitest alone passes and the guards fail (`held-out-only`, `not-collected`, `unguarded`) and a root with a test that asserts nothing (`no-assertion`); and 12 settings under `tools/vitest/seeded/config/` that each lose a guard of the run. Each seed added after a review is one the earlier check let through. `run-evidence.test.ts`, `run-counts.test.ts` and `eval-runs.test.ts` prove the run reconciliation and the eval evidence.
- **Known residual.** A case file that carries the marker, imports the wrapper, and forges the wrapper's meta record and note by calling `context.skip` itself passes the run guard; the index check fails it statically on the `.skip` access or the destructured `skip`. Review is the last line.
- **Known residuals after round 2.** An assertion on a literal subject (`expect(true).toBe(true)`) is not flagged statically, and a case file that catches its own assertion failure is caught only while the stub it calls is unbuilt (the stub guard sees the stub error); once the code is built, review is the last line (phase 1 review). A mocked domain throws nothing, so the stub guard cannot see it; the static `[test double]` rule is the only line. The `_support/` module list and hashes are not pinned (phase 1 adds the fast-check helper there).
- **Not yet covered: a fast-check edge** (phase 0 review, finding 16). When a property throws the stub's error for one input and fails an assertion for another, fast-check reports one error, which may be the stub's; the wrapper then skips the case. No current pending case can do this (each calls the stub before any assertion). Phase 1 adds a `tests/guardrails/_support/` helper that wraps property predicates and rethrows any error that is not the stub's.

## How to reverse

Once the owner decides D-33 for pending stubs, and the approver (guardrails section 10) rules that a pending stub counts as a case file under section 7:
1. Run `tsx tools/checks/index/generate-stubs.ts --write` once (without `--write` it is a dry run). It writes a pending stub for each id with no case file: `tests/guardrails/<ID>.test.ts` for T cases and `evals/guardrails/<ID>.yaml` for E cases.
2. Change the index check to report stub ids as "no automated check yet" through a list that does not fail the run: move `report.stubs` out of `noAutomatedCheckYet` in `reportToResult` (`tools/checks/index/index-check.ts`) into a new field of `CheckResult` (`tools/checks/types.ts`) that `tools/checks/runner.ts` prints and does not fail on, keeping the rule that an id with no file at all fails. `tools/checks/index/README.md` gives the same steps.
3. Change this ADR's status to "Accepted: owner decision <date>", naming the approver's ruling.

## Phase 1 amendment (2026-09-25)

The round 2 residuals and the phase 1 items of the build log's "Next" were closed in the index check. Each is a tightening; the conventions above hold, with these additions.

- **`[process]`** (round 2 residual: a stub reached from a child process, which the stub guard cannot count, and a case asserting only on the exit status). A case file that imports or loads `child_process`, `worker_threads`, `cluster` or `vm` (with or without `node:`; statically, by `import()`, `require()` or a re-export), `execa`, `tinyexec`, `cross-spawn`, `tinypool` or `piscina`, uses `new Worker(...)`, loads a module by a path computed from code, or uses `createRequire`, is malformed. The rule is static and reads case files and `_support/` modules only: a module a case reaches outside `_support/` is not read (the render cases G2-1 and G2-8 start Chromium through Playwright), and the run guard cannot see a child process at run time.
- **`[swallow]`** (round 2 residual). A case file whose `finally` block leaves by `return`, `throw`, `break` or `continue`, which replaces whatever the `try` block threw, is malformed. `[support]` flags the same `finally` exits, and process use, in `_support/` modules.
- **Modules that may catch the stub's error** (the reviewed route of the build log's phase 1 item). `tools/checks/index/stub-aware-support.json` lists the two support modules that must catch an error to tell the domain stub's from every other: `tests/guardrails/_support/pending.ts` (role `pending-wrapper`) and `tests/guardrails/_support/property.ts` (role `stub-aware`), each pinned by the SHA-256 of its reviewed content and each reading the error through `notImplementedFeature`. A listed module whose content changed is held to the full `[support]` rule, with a problem, until its hash is recorded again; an entry that matches no module fails. The list is the exception list `index.stub-aware-support-modules`, recorded in unapproved baseline v0 on 2026-09-25, so an added entry or a changed hash waits for the approver. The other support modules (the builders) are not pinned: the `[support]` rule reads each of them on every run, and pinning them would make each new helper wait for the approver.
- **The fast-check edge** (phase 0 review, finding 16) is closed by `tests/guardrails/_support/property.ts` (`assertProperty`, `assertAsyncProperty`; ADR 0004, phase 1 amendment).
- **Seeds.** The index self-test runs 91 seeded bad inputs (85 before): 51 static seeds under `tools/checks/index/seeded/` (45 before; new: `process-child-process`, `process-worker-threads`, `swallow-finally-in-case`, `support-finally-return`, `support-pin-changed`, `support-pin-stale`), the run seeds in `tools/vitest/seeded/run/`, the four roots and the 12 config seeds. When phase 1 built `derive`, the harness tests and seeds that need an unbuilt stub moved to `verify-proposal`; run seed G2-7 is now a stale marker (a pending case still naming `derive`, which must fail to load), and `tools/vitest/stub-probe.ts` finds whichever stub still throws. When phase 2 builds the last stub, those tests say so and skip, and the pending wrapper can go.
- **The count at v1.6.** Guardrails 1.6 adds G4-20, G10-8 and G13-5: 107 ids, 87 T and 20 E. `guardrail-index.test.ts` pins the count per version (1.5 and 1.6); a later version adds its own pin.
- **A reading of the parser, recorded** (registry builder, phase 1): a local name in a case file that shadows a Vitest API (a variable named `suite`) is read as that API, so `suite.fixture.values[key]` read as a computed modifier and the case as held out. Renaming the variable fixed it; `tests/guardrails/README.md` notes it. This errs on the safe side (the case counted as malformed, never as real).
- **Known residuals, unchanged:** an assertion on a literal subject (`expect(true).toBe(true)`) is not flagged statically, and once a stub is built a case that catches its own failure is caught only by review.

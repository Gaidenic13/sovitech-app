# 0022. The extraction contract: one JSON Schema, zod and Python dataclasses, a sealed IFC section

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-26

## Context

- **Prompt 3 section 6, "services/extractor":** the extractor emits text blocks, cells and IFC facts with locators, raw strings and typed STEP literals, coverage and findings as JSON, plus the gated table-driven IFC candidate proposals. It never parses numbers out of text, never maps PDF or XLSX content to fields, and never writes the database. The extractor and the AI propose; the API verifies and writes.
- **Prompt 3 section 8, "Output per file" and "No locator shortcuts":** candidate proposals with IFC evidence (content hash, schema, GlobalId, STEP ids, path, the verbatim STEP text), a coverage record, IDS results (spec ids, counts, failing GlobalIds, never report text), findings (rule 14), viewing derivatives under project id plus content hash. While `ifc-values` is closed, no GlobalId, STEP id or property path is encoded into `page`, `sheet`, `cell` or `bbox`.
- **Guardrails v1.6:** 2.4 `Evidence.locator` has page, sheet, cell and bbox only; ifc-input 6.2.1 (the IFC locator) and 6.2.2 (document records for models) are proposals. G1-13 (phase 2) needs a strict runtime check of the locator; G12-5 needs an IFC file never to read as analysed. Rule 13: logs and error reports never contain document text. Rule 14: hidden text is reported and never used.
- **PRD:** R-015 (PDF and XLSX read with evidence checked by code), R-022 and R-023 (models stored "Not analysed"; the engineer-only record of header and schema errors), R-024 (model text reported as findings), R-027 and R-030 (model values and mapping tables, gated; "Until decided": no mapping table is consulted), R-025 (viewing files keyed by project id plus content hash). No D row decides the format of the exchange.
- **Dependencies at hand:** zod 4.6.5 in the workspace; the extractor's locks (ADR 0018) hold no pydantic and no jsonschema library.

## Decision

1. **One source.** `packages/extraction-contract/src/extraction-contract.schema.json` (JSON Schema 2020-12) defines the three entry points: `ExtractionRequest`, `ExtractionOutput` and `EvidenceLocator`. A generator in the package (`src/generator/`) writes the zod schemas and types (`src/generated/`), the Python dataclasses (`services/extractor/src/sovitech_extractor/contract/_generated.py`) and a byte copy of the schema beside them, which the Python validator reads. A drift test fails when a generated file differs from what the generator writes now.
2. **A closed subset.** The loader accepts only the keywords both sides implement with the same meaning (closed objects, anchored patterns without `\d`-style classes, code-point string lengths, integer and number bounds, arrays, `$ref`, `oneOf` with a const discriminator) and stops on anything else. Rules JSON Schema cannot express are named invariants (`x-invariants`), implemented once in `src/invariants.ts` and once in `contract/_invariants.py`; the rule tables they read (`x-format-rules`, `x-mechanism-rules`, `x-ifc-locator-keys`) are schema data. A shared corpus (`src/samples/corpus.json`, 104 cases and 5 request-output pairs) holds both languages to the same verdicts and to lossless round trips.
3. **Strict is the only mode.** Every object refuses unknown keys, in both languages, at every level. There is no lenient mode: stripping would hide an extractor that writes a locator where it does not belong.
4. **No engineering value is a JSON number.** PDF text, XLSX cached values (as stored, with the number format as written) and STEP literals (as tokens, with their IFC type) stay text for the rule 8 parser and the API. The only JSON numbers are page numbers, character offsets, STEP ids, IDS counts, PDF coordinates and job limits; a test pins the list.
5. **Status lines in the 2.8 terms.** `analysis` is `analysed`, `partly_analysed` (pages read of total for a PDF; sheets read of total for a workbook), `stored_only` with the word for the G12-1 slot (a closed list: IFC model, RVT model, DWG drawing, DOCX file, JPG image, PNG image, ZIP archive, PDF scan), or `failed` with a code. An IFC file is always `stored_only` with "IFC model" (G12-5); what the extractor could process is `ifcModel.processing`, for the engineer. **Amended in the phase 2 review:** a workbook with a sheet not read (a chart sheet, a sheet over the cell limit, a read error) is `partly_analysed` with `unit: "sheets"`, never `analysed`; the format rules name each format's unit (`partlyAnalysedUnit`), and the `sheet_coverage` invariant holds the status to the sheet coverage (analysed: every sheet read; partly analysed: the sheets read of the sheets listed; failed: none read), in both languages, with the shared corpus. The status is data; the owner-facing line for sheets waits for the approver (build log, P-2-XLSX-SHEETS), so the API keeps showing the workbook's coverage as recorded.
6. **The IFC section is sealed.** IFC facts (with the IFC locator of ifc-input 6.2.1) and the candidate proposals live in `ifcValues`, a separate structure. `parseExtractionOutput` returns it as an opaque handle (JSON `{"sealed":"ifc-values"}`); `openIfcValues(handle, gateSource)` reads `ifc-values` through the registry's `readGate` and opens nothing while it reads closed, then withholds each proposal whose mechanism's gates (`x-mechanism-rules`: `ifc-identity`, `ifc-code-inference`, `ifc-areas`, `ifc-geometry`, `dataset-asset-taxonomy`, `dataset-glossary`) or declared gates do not all read open. The request's `ifcValues` follows the gate, and while it is false no dataset may be mounted. The engineer-only record (`ifcModel`: header, classes present, schema-check outcome, IDS results) and the findings stay readable while the gate is closed, as the gate's closed behaviour says.
7. **Findings and problems carry codes, never text.** A finding is a kind, a code and a location (an IFC finding names GlobalIds and STEP ids for the engineer; this is not `Evidence.locator`). A refused value gets JSON Pointers and codes only.
8. **Evidence.locator.** `parseEvidenceLocator` (and `evidenceLocatorSchema`, for the AI's structured-output schema) accepts `{ page, bbox? }` or `{ sheet, cell? }`; an IFC key is refused with `ifc_field`, any other unknown key with `unknown_key`. `evidenceTexts` gives the per-page and per-cell text excerpts are checked against, without hidden text.
9. **Python models are dataclasses,** frozen, with slots, over a hand-written validator of the same subset (`_validate.py`), a codec and `dump_output`, which refuses to write what the API would refuse. No new Python dependency.
10. **The package** is `@sovitech/extraction-contract` (zod, `@sovitech/registry` for the gate read, `@sovitech/domain` for types), server-side only: `.dependency-cruiser.cjs` adds it to the code that never reaches the browser. The domain keeps depending on no package; the verifier gets the locator check from the API (injected, as `readQuantities` is).
11. **An output answers its request in the declared format** (phase 2 review). `outputAnswersRequest` (and `output_answers_request`) refuse an output whose `format` is not the request's `declaredFormat`, unless it is `other` and failed (the file is not what was declared, or could not be placed: the extractor's `format_mismatch`). A workbook uploaded as a PDF can then never be stored with its sheets' text, coverage and status under a PDF record.

## Consequences

- The extractor builder and the API builder write against one definition; a change to it is a schema edit, a regeneration and a contract version bump (`contractVersion` is a const, so mismatched versions refuse each other).
- The IFC value path can be built and tested end to end in `tests/proposed/` without any production code being able to read a model value while the gate is closed.
- Two implementations of the invariants must be kept equal by the corpus. A rule added to one side only fails the other side's corpus test, or the id-parity tests.
- The contract adds wording for the approver to review: the G12-1 slot words other than "RVT model" (prompt 3 section 5.3 names IFC, DWG and DOCX), and "PDF scan" for a PDF with no text layer on any page (5.2 stores scans "Not analysed").
- The phase 2 review's two changes (decision 5's sheets and decision 11) kept `contractVersion` at 1.0.0: both languages, the corpus and the extractor changed together, nothing outside this repository reads the contract, and an output written by a reader built before them is still read, except a workbook with a sheet not read stored as `analysed`, which is refused (as it should be). The sandbox images must be rebuilt from the current sources for the extractor's side of both changes to run in the sandbox.
- Hidden text is kept in the output (flagged) for the engineer's view; the API must build verification text with `evidenceTexts` or the same rule, and never send hidden blocks to the AI.
- An output is one JSON text, as this ADR describes, for every job that asks for no IFC values. A job that asks for IFC values gets its IFC section as lines after the output (ADR 0034, 2026-09-30: `packages/extraction-contract/src/ifc-values-stream.ts`, TypeScript only), read by `readIfcValuesStream` into the same sealed handle; the shared JSON Schema and the Python side are unchanged.

## How to reverse

- **To pydantic:** add pydantic to `requirements.in` (MIT; a new hashed pin, ADR 0018), generate `BaseModel` classes with `model_config = ConfigDict(extra='forbid', frozen=True)` from the same schema, and drop `_validate.py` and `_codec.py`; the corpus test stays.
- **To an open IFC section:** remove the seal only when `ifc-values` opens under section 10 of the guardrails; until then the gate reading is the way in.
- **To a lenient mode:** not recommended; it would need the approver, because it lets more through (guardrails section 10).

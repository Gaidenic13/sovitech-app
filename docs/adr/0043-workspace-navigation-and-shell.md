# 0043. Workspace navigation and shell: the PRD's D-02 "Until decided" lines over prompt 3's 2.5 default

- **Status:** Accepted: default, reversible
- **Date:** 2026-10-02

## Context

- **Prompt 3 5.2, "Navigation"** (dashboards 8.3, 2.5): "The dashboards-spec 2.5 structure (wizard, then the workspace with the grouped sidebar, Overview landing, one editor per decision), without its 'SOVITECH's proposed design' label on Topology (proposal 7.2.10; section 9) and without its scenario selection (proposal 7.2.4). Tab order as the approved screenshots show it (TOPOLOGY · SYSTEM SCOPE · METRICS)." Prompt 3 phase 4: "The workspace shell (header, grouped sidebar, tabs, inspector, 48px status footer with the demo line on the demo project) and navigation per the ADR."
- **Prompt 3 section 4:** a requirement blocked by an open question builds the PRD's "Until decided" behaviour; "Where a 5.2 default and the PRD line differ, follow the stricter and log it."
- **PRD R-146** (D-02), "Until decided": "Each built workspace page is reachable from the project sidebar, and no tab, sidebar item or link leads to a page that is not built (US-ADMIN-13 AC1). The tabs, tab order, grouped sidebar, back links and one editor per decision of dashboards-spec 2.5 are not adopted, and every option in dashboards 8.3 stays open."
- **PRD 10.2**, "Until dashboards 8.3 (D-02) is decided": "no separate Overview or Property page is built, and after Generate the owner sees the stored proposal (US-PROPOSAL-05; US-REVIEW-15); the header menu holds only the account item, an entry to the project list and sign-out (US-ADMIN-07)."
- **PRD R-050** (D-02), "Until decided": "no Property page is built, and no navigation item leads to an empty page." **R-144** (D-10, D-02): the header menu holds only the account item, the project list and sign-out. **R-145** (no gate, S2): the sidebar's project switcher lists only the user's projects, loads only the chosen project, under the name entered on step 1. **R-049** (no gate, S2): the project card beside each dashboard. **R-139** (no gate): no live element; a drawn status footer "carries only 2.8 status lines, rule 7's 'Still reading <n> files…' notice and, on a project flagged demo, 'Demo data, not an assessment of the real building'"; what else a footer's "data status" says is D-90.
- **The approved links the PRD keeps:** R-052 "Until decided": System Scope "reached from the project sidebar (R-146) and from '← Back to System Scope' on Equipment and Zones; its 'Save and Continue →' opens Zones, and its '← Back to Topology' link is shown only once Topology is built"; R-061, R-066: Zones' and Equipment's "← Back to System Scope"; R-066: Zones' "View Equipment in Zone →".
- **R-009 "Until decided"** (D-10): "a project with a generated proposal opens its stored proposal, not the wizard"; no proposal is stored before phase 5 (ADR 0039 decision 4). **R-012 "Until decided"** (D-14, D-02): no menu offers a way back to the intake after Generate; a "Not available yet" action "opens a built page".
- **The approved screens** (15 to 18 and 20) draw one flat project list: Overview · Property · System Scope · Topology · Zones · Equipment · Alarms · Documents · Reports, with the PROJECT selector above it and the project card below it (dashboards-spec 2.4.2, "Project"). Screens 15, 18 and 20 draw no tabs; 16 and 17 draw TOPOLOGY · WIREFRAME · METRICS.

## Decision

1. **The PRD's lines are followed where they are stricter than 5.2** (logged under "Product doc issues" in the build log): no tabs in this phase; no grouping of the sidebar; no Overview or Property page; no "back to intake" entry; the header menu as phase 3 built it (R-144). The 5.2 default's grouped sidebar, tabs and tab order wait for D-02.
2. **The project sidebar** (208px) is the approved flat project list in its drawn order, keeping only built pages (`WORKSPACE_PAGES`): Proposal, System Scope, Topology, Zones, Equipment, Documents. Overview, Property, Alarms, Reports and the Metrics pages are not listed (R-050, R-146; the `operations` gate; phases 5 and 6). Above the list, the project switcher (UD-32; R-145): a button naming the current project (its step 1 name, bound) that opens a list of links to the user's projects (`projects.list`: only projects the user is a member of, rule 13), never a dialog; choosing one opens the same page of that project and remounts the frame, so nothing of the previous project remains (US-ADMIN-06 AC2). Below the list, the project card (R-049; decision 5).
3. **The landing after Generate is phase 3's proposal page, now in the workspace frame**, in the slot the approved list gives Overview, labelled "Proposal": PRD 10.2 ("after Generate the owner sees the stored proposal") with no Overview built; phase 5 replaces its content with the stored proposal. Generate leads there, as in phase 3. A project reopened from the project list still opens at step 1 while no proposal is stored (R-009); every workspace route is addressable directly. Whether the list should open the workspace before phase 5 is a question for the owner (D-02, D-14).
4. **Links inside pages are the approved ones the PRD keeps**, each to a built page: "← Back to System Scope" on Equipment and Zones, "← Back to Topology" and "Save and Continue →" (to Zones) on System Scope, "View Equipment in Zone →" on Zones (Equipment filtered by the zone), Topology's "View in System Scope", Equipment's row "›" to the asset detail (UD-08) and "← Back to Equipment" there. A "Not available yet" line's action opens a built page (`WorkspaceAction`: Documents' upload surface, step 3's floors row, System Scope). Links with no built target are removed and listed (UD-23, UD-24 and System Scope's "Edit Scope", which repeats the row's switch).
5. **The shell's parts:** the 64px header of phase 3 (logo, the project's bound name, the date, the menu); the sidebar of decision 2 with the project card at its foot (the building's key facts through the Value component, the same value ids as step 3 and step 8; no photo, Status or BMS Platform line; R-049); the page, with a 360px right inspector where the page has one (Documents, Equipment, Zones; System Scope's detail panel per screen 16); and a **48px status footer, always visible** (sticky at the bottom), carrying only the demo line on the demo project (the served `project.demoLine`, never the app's copy; rule 10, GS-1, G10-12) and rule 7's "Still reading <n> files…" while analysis runs (R-139). On workspace pages the demo line sits in the footer and not under the header, so it shows once. No live element: no "BMS LIVE", "Last sync", timeline or playback bar (R-139; 7.1-r27). **Landmarks** (WCAG 2.4.1, 1.3.1, 2.4.3; amended in part B, below): the page column is the page's one `main` (`#main`, the skip link's target and where each page puts the focus on mount), the sidebar sits beside it in an `aside`, and the status footer after it is the page's contentinfo; the header stays the banner.
6. **One floor selection** (prompt 3 phase 4, "Shared floor selection"): the `level` search parameter, read by System Scope, Topology, Zones and Equipment and kept by the sidebar's links; a view state that writes nothing (R-077). Its options are the level register's (ADR 0045).
7. **Titles:** each page names itself in the document title ("<page> – SOVITECH"; WCAG 2.4.2), never a project name or a figure. Page titles in the approved title slot; an eyebrow only where the approved screen draws one (Documents).

## Consequences

- Every built page is one click from the sidebar, and no control leads to an empty or unbuilt page (US-ADMIN-13 AC1).
- The screens differ from the mockups where the PRD's lines hold: no top tabs on 16 and 17, a shorter sidebar list, no photo on the card, no "BMS Live · Last sync" footer; the build log lists them.
- An owner who leaves the workspace returns to it through the proposal page (Generate) or a direct link until phase 5 stores a proposal.

## How to reverse

When the owner decides D-02: add the tabs (and their order) to the header slot, group the sidebar as 2.5 proposes, add Overview and Property to `WORKSPACE_PAGES` once built, and point the project list's rows at the workspace landing. Each is a change to `WorkspaceLayout` and the contract's `WORKSPACE_PAGES`; no page changes.

## Amendment: how the shell is built (the shell builder, phase 4 part A, 2026-10-02)

Decisions 1 to 7 stand. What the build added, each reversible on its own:

1. **Where the frame is drawn.** The workspace group's route (`apps/web/src/routes.tsx`) carries a handle (`apps/web/src/workspace/handle.ts`), and the project's layout (`apps/web/src/wizard/ProjectLayout.tsx`) draws the frame (`apps/web/src/workspace/WorkspaceFrame.tsx`) around every screen under it: the proposal page (moved into the group as the landing, decision 3), System Scope, Topology, Zones, Equipment with the asset detail, and Documents. The frame stays mounted while the owner moves between pages and is keyed with the project, as the wizard's state is, so switching project drops everything of the previous one (US-ADMIN-06 AC2). A project the user cannot reach shows its not-found page with no frame (rule 13). The wizard's steps and UD-45 keep phase 3's shell; there the demo line stays under the header.
2. **The kit's layout pieces.** The frame uses the UI kit's `WorkspaceFrame` (sidebar beside the page, the 48px footer sticky across both; the landmarks as part B amends them, below), `SideNav`, `StatusFooter`, `PageHeader`, `InspectorLayout`, `Inspector`, `RegisterTable`, `InlinePanel`, `MenuButton`, `ChipGroup`, `Pager`, `SelectionList`, `ActiveFilters` and `ValueName`. The app adds only the data and the copy.
3. **One readiness for two requests.** The frame (`workspace.frame`) and the page each read their own route; the page never waits for the frame. `data-render-ready` is set only while every mounted part that asked for data has rendered it (`apps/web/src/shell/render-ready.ts` keeps one entry per caller; with one caller it behaves as in phase 3).
4. **The frame follows the analysis.** It reads `workspace.frame` again every 5 s while its footer's "Still reading" line is served, and a page that changes what it shows (an upload stored, a revision declared, a document deleted) reads it again at once.
5. **The project switcher reads `projects.list` each time it opens** (a project created or shared meanwhile is listed), and passes the chosen row's demo flag in the router state, as the project list's Open does, so the chosen project's screens show the demo line from their first render (G10-12's reading). It never shows the demo line itself: on another project's screen that would label that screen (G10-10).
6. **The floor selection** is the `level` search parameter in the contract's key form (a malformed one is ignored, never sent), kept by the sidebar's links to System Scope, Topology, Zones and Equipment only, and dropped when the project changes. `useLevelSelection` (`apps/web/src/workspace/navigation.ts`) reads and sets it with a history replace; it writes nothing.
7. **Owner actions beside a "Not available yet" line** link to built pages (`workspaceActionPath`): `upload_document` opens Documents with `?upload=open`, `enter_floors` opens step 3, `choose_systems` opens System Scope. `?document=<id>` opens a document's inspector (for links and the render screens).
8. **The sticky footer never covers the focus** (WCAG 2.2 2.4.11): on a workspace screen the page scrolls things into view with a bottom scroll padding of the footer's height plus the gutter (`apps/web/src/styles.css`).
9. **Replace on Documents** goes through the project's uploads (`apps/web/src/wizard/UploadsProvider.tsx`, `addFiles(files, { revisionOf })`): once the new file is stored, its revision declaration (`documents.revisionOf`) is sent from there, at project level, so it completes even if the owner leaves the page; a refused declaration is shown on Documents with how to declare it from the new document's menu. **Download** is a link to `documents.file` (served after the project access check); nothing is fetched into the page.

How to reverse: each item is local to the file named; removing the handle returns the workspace pages to phase 3's shell.

## Amendment: landmarks, page failures and the frame's parts (phase 4 part B, 2026-10-02)

Decisions 1 to 7 and the part A amendment stand, except where this one replaces them. Each is reversible on its own.

1. **One main, beside the sidebar** (DR-3, V-7; WCAG 2.4.1, 1.3.1, 2.4.3). Part A wrapped the whole frame in the app shell's `<main id="main">`, so "Skip to content" and each page's focus on mount landed before the switcher and the six sidebar links, and the footer was not a contentinfo landmark. Now the kit's `WorkspaceFrame` draws the page column as `<main id="main" tabIndex={-1}>`, the sidebar in an `aside` and the footer as the page's `<footer>`, and the app shell takes `landmark?: 'main' | 'none'` (`apps/web/src/shell/Shell.tsx`, default `main`): the workspace frame (`apps/web/src/workspace/WorkspaceFrame.tsx`) passes `none`, so exactly one main exists on a workspace page, outside which the sidebar sits. The skip link keeps `href="#main"`, now the page column, and the pages keep focusing `#main` on mount. The wizard's steps, UD-45, the project list and sign-in keep the shell's own main. Proven by the component test "DR-3 · V-7 …" in `apps/web/src/workspace/WorkspaceFrame.test.tsx`.
2. **A page that fails to render keeps the frame** (A-1; rule 7; rule 10 "Labelled everywhere"). The workspace group's route has its own error element (`WorkspacePageFailed`, `apps/web/src/workspace/WorkspaceLayout.tsx`): the page's failure state ("This page could not be loaded. Nothing you entered is lost." with "Try again", which opens the same address again) inside the frame the project's layout keeps drawing, so the sidebar stays reachable and the footer keeps the demo line on the demo. Before, React Router's default boundary replaced the whole app.
3. **The project card's failure says what failed** (DR-9): "The building facts could not be loaded. Try again." (`workspace.frame.cardLoadFailed`), never the page's failure sentence beside a page that loaded.
4. **The switcher's list stops above the footer** (DR-4; rule 10 with 2.8 "Prominence"; WCAG 2.4.11): its height runs from its top to a gutter above the status footer's top, measured on opening and on scroll and resize, and a longer list scrolls inside it, so the demo line is never covered.
5. **The proposal page takes the workspace page layout** (DR-7): the kit's `PageHeader` in the page column with the frame's padding, and "Back to review" as a 40px secondary button (R-012 "Until decided" keeps a way back to the intake out of the menus; phase 3 built this button).

6. **One floor control, drawn one way** (DR-5; decision 6; dashboards-spec 2.5 rule 6 and 3.5, "Fixed order: view mode, floor, system filter"; ADR 0040 decision 6, DR-24). System Scope, Topology, Zones and Equipment draw the shared floor selection with one component, `FloorFilter` (`apps/web/src/workspace/pages/topology/ViewFilter.tsx`), in the page header's actions slot, before the system filter. With a known level register it is the "Floor" dropdown ("All floors", the levels by their bound labels, the unstated line under the list). With no floor structure, or the floors in conflict, the same slot shows the served line ("Not available yet: floor structure", or "Not available yet: two values for floors" beside the floors field's own display with its two readings, their sources and rule 4's routing line, V-4, G7-16) and the served actions as underlined links, and no list. Topology's and Zones' notice bar, System Scope's level picker and Equipment's floor entry inside Filters are gone (Equipment's chip for a chosen floor stays). A `level` the served register does not hold is dropped from the address once the register is in (`useHeldLevel`), so the control never reads "All floors" while a hidden filter applies.
7. **System Scope's system filter** (V-10; approved screen 16's "All Systems"; R-052's "Until decided" takes DB-16's layout as the base): "All systems" and the eight systems, after Floor in the header, held in the page's own state, so `?system=` keeps its meaning (it opens that system's panel, Topology's "View in System Scope"). The detail panel follows the rows shown, and "Save and Continue" reports only the suggestions on the rows the filter shows (rule 3, "Nothing hidden, collapsed or on another step is accepted this way"; G3-22).
8. **The focus after an action that removes its own control** (A-6; WCAG 2.4.3). After Delete on Documents the focus moves to the next row's "Show details" (the previous row's when the deleted one was last), and with no row left to the register's region while it is a tab stop, else to the page column (`main#main`, tabIndex -1); after "Looks right", "Something's wrong" or "Clear the selection" on Equipment, to the first previously selected row's checkbox, else to the status line (tabIndex -1). Never to `<body>`.

How to reverse: item 1 by passing `landmark="main"` from the frame once the kit's frame draws no main; item 2 by removing the group's `errorElement`; items 3 to 8 are local to the files named.

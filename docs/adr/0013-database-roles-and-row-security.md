# 0013. Database roles, the request scope and row-level security

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25

## Context

- **Prompt 3 section 5.2, rows "Database"** (row-level security on `project_id`) **and "Authentication"** (a roles table, the database guard and a development login; no production identity provider). Sources: `docs/build-readiness.md` 3 "Now" items 4 and 10; guardrails rule 13 ("Isolation": "Every document, excerpt, embedding and cache entry is keyed by project id"; "Project boundary").
- **Prompt 3 section 10**, app roles: `owner`; `sovitech_engineer`, the only role the guarded function accepts; `sovitech_commercial_reviewer`, who co-signs stage 3 records; `sovitech_admin`, for users, roles and projects, which "never permits verification", and "granting any role is an audited event".
- **PRD:** R-158 (isolation; test ids G13-1, G13-2, G13-4), F-AUTH-02, F-AUTH-03. D-13 is open (which sign-in replaces the development login; who may grant the engineer role; "is each grant recorded?"; its note: "Recording who granted a role changes no guardrail rule"). The owner decided no D row as of 2026-09-25.
- **New case G13-5** (prompt 3, "New case ids"): a session scoped to project B reads candidates, evidence and documents; no project A row is returned.

## Decision

1. **Database roles** (migration 0000, run by the database administrator):
   - login roles: `sovitech_db_migrator` (runs ordinary migrations; may `SET ROLE sovitech_db_owner`, nothing else), `sovitech_db_app` (the API), `sovitech_db_admin` (the operator's tools);
   - roles nobody logs in as and nobody is a member of: `sovitech_db_owner` (owns the schema and every table but those below), `sovitech_db_guard` (owns the guard functions, ADR 0014), `sovitech_db_verifier` and `sovitech_db_eraser` (own the two guarded functions, ADR 0015), `sovitech_db_access` (owns the account, role and project functions, and the relations they trust for who a user is and what they hold: `app_users`, `app_role_events`, the view `app_user_roles`, `projects`, `project_members`, and the two request views of decision 6; migration 0009 gives them to it and registers them in `sovitech_guard.relation_owners`). The migrator acts only as `sovitech_db_owner`, so no ordinary migration can alter, replace or redefine what the definer functions trust.
   Only the two definer roles that read across projects by design, `sovitech_db_access` (membership and role lookups) and `sovitech_db_guard` (existence checks), bypass row-level security. No role of the store is a superuser. The invariant check (ADR 0014) keeps all of this true.
2. **App roles are events.** `app_role_events` holds each grant and revoke, with who acted (the app user, or the operator's login), when and why; the latest event per user and role decides. `sovitech.user_holds_role` reads the events directly, not through a view; the view `app_user_roles` lists the current roles for the operator's login. Rows are written only by `sovitech.grant_app_role` and `sovitech.revoke_app_role`, which also write an `audit_events` row; a guard refuses any other writer. They accept the operator's login (`sovitech_db_admin`), or an app request by a person who holds `sovitech_admin`, with two limits:
   - **nobody grants or revokes their own role** (`SVR03`): holding `sovitech_admin` never permits verification (prompt 3 section 10), and an admin who granted themself `sovitech_engineer` could verify;
   - **`sovitech_engineer` and `sovitech_commercial_reviewer` are granted on the operator's login only** (`SVR04`), never from an app request, until PRD D-13 decides who grants them. This is the stricter reading while D-13 is open: an admin could otherwise make an account they created an engineer. Revoking either role from an app request stays allowed.

   Accounts (`app_users`, of kind `person`, `service` or `seed`) are created the same way, audited. No page creates accounts or grants roles yet (US-ADMIN-16 AC1); the TEST accounts of the tests are created and granted on the operator's login.
3. **The request scope.** The data-access layer opens every request in one transaction and sets, for that transaction only, `sovitech.user_id` (the authenticated user) and `sovitech.project_id` (the project in scope) (`withRequest`, `packages/db/src/request.ts`). `sovitech.current_project_id()` returns the project in scope only when that user is a member of the project or holds `sovitech_engineer` or `sovitech_commercial_reviewer`; otherwise it returns nothing.
4. **Row-level security**, enabled and forced (so it binds the table owner too), with one policy `project_scope` (`project_id = (SELECT sovitech.current_project_id())`, for reading and writing) on every project-scoped table: subjects, documents and their events and texts, candidates, evidence locators and excerpts, candidate and field events, asset identities, appearances and events, guardrail events, opened items, stage 3 records and their inputs, proposal snapshots and their parts, project members, the project row itself, and project audit events. Audit events with no project (accounts and roles) are read only by the operator's login.
5. **Readings recorded for the owner:**
   - **Who reads a project.** Its members, and holders of the two SOVITECH review roles (engineers review every project). Holding `sovitech_admin` alone gives no access to a project's documents and values: the admin manages accounts, roles and projects, and a project's own data needs membership. This is the stricter reading; relaxing it is the owner's call (D-13).
   - **Who creates a project and who is a member.** Any known user creates a project through `sovitech.create_project` and becomes its member (the demo flag follows the creator's account, ADR 0015). A person who holds `owner` and is a member of the project, in an app request, or the operator's login adds members (`sovitech.add_project_member`), and nobody adds themself (`SVR03`); both are audited. An admin who is not a member therefore cannot make themself one, which would undo the reading above in one call; and a job's service account, the demo seed or a member who does not hold `owner` never decides who belongs to a project (rule 13, "Project boundary"): the operator's login adds a job's account to the projects it works on.
   - **What a job's account acts for.** A service account writes as the system, and writes document, AI, calculated, estimated and reference values, only in a project it is a member of (`sovitech.request_user_acts_as(project, 'system')`), even when it also holds a review role that would let it read every project. It never withdraws a document: 2.3's deletion is the owner's, and a job erases only through the audited erasure function (ADR 0014 decision 4, ADR 0015; phase 1 review, round 4).
6. **What the app reads about accounts** (rule 13, project boundary: other clients' identities stay on their side). The app holds no read on `app_users`, `app_role_events` or `app_user_roles`, and cannot call `sovitech.user_holds_role`. It reads two `security_barrier` views owned by `sovitech_db_access`: `request_accounts` (id, display name, kind) and `request_account_roles` (user, role, since), each limited to the request's own account and the members of the project in scope (`readVisibleAccounts`, `readUserRoles`). The guard triggers ask about the request's own user only, through `sovitech.request_user_acts_as` (ADR 0014). The operator's login reads the tables in full.

## Consequences

- G13-5 passes: a session scoped to project B reads no project A row through the data-access layer, through direct SQL on the app role's connection, or by asking for A's ids; a user of B who scopes a session to A reads nothing at all; an admin who is not a member of A cannot add themself and reads nothing of A. G10-3 carries the self-grant routes. `packages/db/src/access.test.ts` carries the rest: self-grant and self-revoke of every role, admin grants of the review roles, member rules, the request views, and the closed role lookup.
- **The trust boundary, stated plainly.** The API authenticates; the store trusts the API to name the authenticated user. A caller that holds the app role's password can name any user, and so act as any engineer. Every check the store makes (role, account kind, opened item, demo flag, project membership) holds for the user the API names. Closing this gap needs sessions the database can check itself, such as tokens signed by the production identity provider and checked in the database; that belongs with D-13 (the production sign-in). Until then the app role's password is a secret of the API alone, `.env` is git-ignored and `.env.example` holds no value.
- A later feature that reads across projects (the engineer's queue, UD-15) runs one request per project, or goes through a new definer function that is reviewed as a guard.

- **The phase 1 review (2026-09-25)** found, each confirmed against real Postgres: an ordinary migration replaced `app_user_roles` (owned then by `sovitech_db_owner`) so that every account read as an engineer, which let a user with no role read another project and verify a value; an admin granted themself `sovitech_engineer` through the app and then verified; an admin added themself to a project and read it; and the app read every account and every role holder. Decisions 1, 2, 5 and 6 changed as above; ADR 0014 records the guard side.
- **The phase 1 review, round 3 (2026-09-25)** found, reproduced on a TEST database: a service account added by an owner added an outsider, who then read and wrote the project as a member (probe R5); and a service account holding a review role could write system events on a project it was not a member of. Decision 5 changed as above; `packages/db/src/access.test.ts` proves both (a service account, the demo seed and a member without `owner` each refused, with the controls).
- **For the owner (D-13):** the review roles are granted on the operator's login only for now. Which sign-in replaces the development login, and who may grant those two roles, decides whether an app request may grant them again.

## How to reverse

- **Isolation by the API only:** drop the `project_scope` policies. That loosens rule 13's enforcement to one layer; the invariant check fails until `sovitech_guard.project_tables` changes in an admin migration, which is a visible, reviewed step.
- **Admins read every project:** add `sovitech_admin` to `sovitech.current_project_id()` in an admin migration, after the owner decides D-13.
- **Admins grant the review roles from the app, or add themselves to projects:** remove the `SVR04` check from `sovitech.grant_app_role`, or the self check from `sovitech.add_project_member`, in an admin migration, after the owner decides D-13. Each lets more people act, so it waits for the approver's own words (guardrails section 10).
- **Another role model:** the app roles live in `app_role_events` and the functions of migration 0006; the database roles in migration 0000.

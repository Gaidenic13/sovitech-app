# 0037. The end-to-end setup: a TEST database, the API and the worker behind the built web app

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-30

## Context

- **Prompt 3 phase 3 exit:** Playwright flows pass: (a) the demo project from step 1 to step 8; (b) a new project with fixture uploads; (c) a new project with no documents that skips everything and still reaches step 8. On every step and state: the render test, axe with zero violations, the reserved-term scan and the demo line (demo project); no `question_for_known_field` event in (a).
- **Until now** Playwright's one web server is the built web app (`vite build && vite preview` on 127.0.0.1:4173, never reused: ADR 0006), shared by the `render` and `e2e` projects; no API ran. Phase 3's screens read the API, which reads Postgres.
- **The store's TEST machinery** (`@sovitech/db/testing`: `startTestDatabase`, TEST accounts; reachable only from `tests/`) starts a Postgres container with Testcontainers (images pinned by digest, approved downloads), applies the migrations and opens stores per login. The demo seed (ADR 0029) builds the demo project through the upload protocol and, with a sandbox runner, drains the analysis queue through the extractor's image (ADR 0018; the images are built locally, `sovitech-extractor:dev` and `sovitech-ifc-reader:dev`). Docker runs in Colima, which mounts only folders under the home folder.
- **Playwright** starts its `webServer` before `globalSetup`, so the API cannot be a `webServer` entry if it needs a database the global setup starts.
- **The owner's decisions in force:** uploads accept fixture hashes only (ADR 0028); the demo keeps the fixture's `test` profile (2026-09-30); no `ANTHROPIC_API_KEY`, so no AI runs and no document value exists.

## Decision

1. **Global setup** (`tests/e2e/setup/global-setup.ts`, named in `playwright.config.ts` for both projects; teardown in `global-teardown.ts`):
   1. starts a TEST database with `startTestDatabase()`;
   2. on the operator's login creates the extraction service account and the development accounts ("Development owner", role `owner`; ADR 0038), with `createAppUser` and `grantAppRole`;
   3. runs the demo seed (`seedDemo`) with the `DockerExtractorRunner` over both sandbox images and a data folder created under the home folder (as `tests/api/demo-seed.test.ts` does for Colima), then adds the development accounts as members of the demo project on the operator's login (`addProjectMember`), so the demo project is listed for every development account (PRD R-136, "Proposed (PRD interim, reversible)"). The setup fails with a message naming the image build commands when an image is missing; it never runs without them, so the demo shows its real analysed state;
   4. spawns the API (`apps/api/src/index.ts` through tsx) on 127.0.0.1:4174 and the analysis worker (`apps/api/src/worker-main.ts`), both with the TEST database's app login, a random 48-character session secret, the extraction account, the data folder, the sandbox images and `SOVITECH_DEV_ACCOUNTS`, and waits for `/health`;
   5. writes `test-results/e2e/state.json` (the development account ids and the demo project id; no secret, no password), which specs read to sign in and open projects.
   Teardown stops the worker, the API and the database and removes the data folder.
2. **The API's database settings in tests.** The API and the worker read their connection strings from `SOVITECH_DB_APP_URL` and `SOVITECH_DB_OPERATOR_URL` when set (a whole URL, as `TestDatabase.url(role)` gives it), else from the port, name and passwords as today (`apps/api/src/config.ts`; the API builder adds the two settings to `SETTING_NAMES` and `.env.example`, empty).
3. **One origin.** The web build is still Playwright's `webServer` on 4173; `vite preview` proxies `/api` to 127.0.0.1:4174 (`apps/web/vite.config.ts`), and `vite dev` proxies it to 127.0.0.1:3000, the API's default port. Cookies are same-origin, `SameSite=Strict`, with no CORS.
4. **What each spec uses.** Specs sign in through the sign-in page (the development login), never by setting a cookie by hand; they create their own projects through step 1. A spec that needs a stored finding while the owner is on another step (G7-4's flow) writes it with the store's TEST helpers from `tests/` (never through an app route that does not exist), in the extraction account's request, as the ingestion path would.
5. **The render test** (`tests/e2e/render/screens.ts`) lists every route of `apps/web/src/routes.tsx` (`APP_PATHS`) and every state phase 3 adds, each with `displayObjectsFromApi()` and an `arrange` that signs in and brings the screen into its state.
6. **Accessibility:** `@axe-core/playwright` (4.13.0, already a devDependency) on every screen and state, zero violations, WCAG 2.2 AA tags (prompt 3 5.2 "Accessibility level").
7. **Ports:** web 4173 (e2e) and 5173 (development); API 4174 (e2e) and 3000 (development). `strictPort` everywhere: a taken port stops the run.

8. **Amended 2026-10-01 (the integrator), as built:**
   - The global setup (`tests/e2e/setup/global-setup.ts`) starts the stack as its own process (`tests/e2e/setup/stack.ts`, through tsx), so Testcontainers, the store and Docker run in plain Node rather than in Playwright's test loader; it waits for `test-results/e2e/state.json` (up to ten minutes) and returns the teardown, which stops the stack with SIGTERM. The stack's log is `test-results/e2e/stack.log` (codes and ids only). A cold stack is ready in about 20 s on the development machine (the seed's eight PDF and XLSX documents through the sandbox; the two models stored, not read).
   - The stack refuses to start when something already answers on 127.0.0.1:4174 (it would otherwise check another API's screens), and when either sandbox image is missing (naming both build commands).
   - The API and the worker get no `ANTHROPIC_API_KEY` and no `SOVITECH_` setting from the shell, only the stack's own: the e2e run stays the no-key build the owner's answers describe, whatever the shell holds (a `.env` at the repository root is still read by the worker for the key; none exists).
   - **One TEST-only control route**, on the loopback interface in the stack's process: `GET /guardrail-events?projectId=<uuid>[&type=<type>]` answers the project's guardrail events (type, field key, subject id) as the throwaway database's administrator reads them. Flow (a) uses it for "no `question_for_known_field` event". It answers GET only, exists only while the stack runs, and `state.json` names its address; no app route was added for it.
   - `.dependency-cruiser.cjs`'s `db-only-from-api` lets `tests/e2e/setup/` reach `@sovitech/db` (the stack imports only `@sovitech/db/testing`); no spec imports the store.
   - **Screens with a project** (`tests/e2e/render/screens.ts`): `path` is the app route of `APP_PATHS`; a route with parameters is reached from `/sign-in` by the entry's `arrange` (sign in through the page, then open the demo's screen or create a TEST project through step 1). The render spec fails when a route of `APP_PATHS` has no entry. Names typed into forms hold no digit and no number word, because the typed text shows unbound until it is stored.
   - **Flows** (`tests/e2e/flows/`): `demo.spec.ts` (exit (a)), `fixture-uploads.spec.ts` (exit (b)), `no-documents.spec.ts` (exit (c)), and `screen-states.spec.ts` (axe and the demo line on every entry of the render screen list). `screen-checks.ts` runs on each screen and state a flow reaches: the render check (a new observation per screen, with its reserved-term scan), axe under the WCAG 2.2 AA tags, and the demo line (on the demo's screens, on the demo's row of the project list only, nowhere else). `SOVITECH_E2E_SCREENSHOTS=<folder>` also saves each checked screen as a full-page PNG at 1440 wide.
   - The render project's canaries now include the UI kit's pages (must pass), so the components' render test runs in `pnpm check`; the kit's axe and keyboard checks stay in `tests/e2e/pages/ui/ui-kit.spec.ts` (e2e project).
   - A display-object response that arrives while its page is navigating is still collected, and its delivery to the replaced document is dropped (the next document's harness receives everything collected at its first response; a value shown unannounced still fails as an unknown value id). Any other failure to read or deliver is a problem that fails the check. (Found by a render screen that opens step 5 while step 2's late-findings poll is on its way.)
   - Test timeout 90 s per test (a wizard screen signs in, reads the API and runs the render check's settle windows); the global timeout is 30 minutes.

9. **The screen states the settled list missed** (amended 2026-10-01, phase 3 part B, V-1): `screens.ts` also lists the loading, load-failure and in-between states, each checked by the render test (with its reserved-term scan) and by `flows/screen-states.spec.ts` (axe under the WCAG 2.2 AA tags, the demo line on the demo's screens and on no other). They are reached through the page's own requests (`tests/e2e/support/network.ts`, page actions only): a step's view **held** for a few seconds after the page asks for it, so the render check reads the loading state and then the loaded screen, and every digit either one shows (a placeholder figure while loading fails as a transient digit, G2-1); a view and the project list **aborted** as a failed network request, so the page shows its load failure with "Try again"; an upload's chunk held, so a file shows as uploading with "Stop uploading". The screen-states spec runs axe and the demo line while a hold stands, then releases it. Nothing is answered from the test: every display object still comes from the API through the render adapter. A held view is opened only once the project list has answered, so a fresh page knows whether the project is the demo. The adapter drops a request still in flight when its test has ended (a poll, or a hold released at the end of a test): no check reads that page any more; before, its error stopped a Playwright worker, and the test queued on it did not run. A fetch that fails while its page's check still runs is still an error. The adapter also reads the display objects a refusal carries (the contract's `RefusalBody.displayObjects`; the fixtures-only guard's refusal names the refused file, bound to `upload:<id>.fileName`, DR-10): a refusal of a request that is not a GET is fetched and, when its JSON body holds `displayObjects`, they go to the harness before the page has the refusal. The global timeout rises to 45 minutes (from decision 8's 30): many of these states hold a request or have a poll due, so the render check waits out its settle windows on them.

10. **The state checks on the demo flow** (amended 2026-10-01, part B, V-3): flow (a) keeps the control route's event check (no `question_for_known_field`, no `confirmation_budget_exceeded`, whichever detector logs them) and also reads the rendered steps 4 to 7: each answer the demo seed stores (its input, `fixtures/demo/owner-answers.json`) shows as that question's chosen option, and no "Skip for now" and no "You can provide this later." renders there, so a question the page asks for a known field fails the flow even if no detector logged it.

11. **The control route writes TEST states** (amended 2026-10-01, part B, V-1). Besides `GET /guardrail-events`, the stack's loopback control route answers `POST /test-states/<name>?projectId=<uuid>`, which writes one named TEST state into a TEST project a spec created through step 1 (204), and refuses the demo project (403 `demo_project`), an unknown project (404 `project_not_found`) and an unknown name (400). The states (`tests/e2e/setup/control.ts`): `document-being-read` (one TEST document registered and queued, with no job behind it, so it stays "being read"); `owner-conflicts` (two TEST documents each for the building type and the occupancy: two conflicts put to the owner, and with the two missing first-estimate inputs more than three "For you" items, so "and <n> more" shows); `building-type-inference` (one TEST inference of the building type: rule 5's confirmation, "Yes, it's a hotel"); `floors-conflict` (two TEST documents with two upper-floor counts, written while the owner is on step 6: G7-4's late finding, its dot and its one quiet notice, in the browser; in phase 4 part B also the floors conflict on the workspace's floor control, V-4, G7-16); `assets-listed` (phase 4: one TEST equipment list writing three tags and one untagged fan coil, as asset subjects, identities, appearances and their evidence); `assets-numbered` (phase 4 part B, A-1: one TEST equipment list numbering its equipment, with the tags "101" and "1.2", so a tag written as a number reaches Equipment's inspector and the asset record).
   - **How it writes:** only through the store's TEST machinery (`@sovitech/db/testing`): a TEST extraction service account made a member of the project on the operator's login (`createTestService`), then one statement per call on the app's own login in that account's request scope (`TestDatabase.as('app', …, { userId, projectId })`). Row-level security, the author and source guard, the document and analysis-event rules, the evidence check and the excerpt rule of the store all apply, as they do to the ingestion path; a value's excerpt occurs on its page's stored text. It reads the project's demo flag and its building subject as the throwaway database's administrator, as the event route reads; nothing is written as the administrator, and no app route was added.
   - **What it writes:** synthetic values marked TEST (file names, page text, excerpts, the counts 6 and 8, the choices); no figure from the mockups, `company/` or a real building; never into the demo.
   - **Boundary** (part B, V-13): `.dependency-cruiser.cjs` now lets `tests/e2e/setup/` past `db-only-from-api` only for the TEST machinery: the separate rule `e2e-setup-reaches-db-only-through-testing` refuses any other `@sovitech/db` import from there (decision 8's "imports only `@sovitech/db/testing`" is now enforced, not only stated). The stack still imports the API's seed and account modules, which reach the store as the API does.
   - The specs reach the route through `tests/e2e/support/control.ts` (a `fetch` to the address `state.json` names); no spec imports the store.

## Consequences

- `pnpm e2e` and `pnpm test:render` (inside `pnpm check`) need Docker, the Postgres and reaper images, and the two sandbox images built locally; the setup adds about a minute (the seed's ten documents through the extractor). CI needs docker-in-docker (D-33, already listed).
- The demo is shown as the seed builds it, with its documents' real status lines; with no API key it holds no document value, so its step 3 facts read Unknown and its outputs "Not available yet".
- One database serves every spec; specs never depend on another spec's project.

## How to reverse

Replace the global setup with a fixed local stack (docker-compose's Postgres, the seed CLI, `pnpm dev:api`), keeping the proxy; or run the API in-process inside the global setup with `buildServer` (as `tests/guardrails/_support/api.ts` does) instead of spawning it.

## Amended in the viewer step (2026-10-07, part 1; ADR 0051)

The stack needs a third locally built image, the model conversion sandbox `sovitech-model-converter:dev` (`services/model-converter/build.sh`), beside the two analysis images: `tests/e2e/setup/stack.ts` checks for it, names its build command when it is missing, and passes it to the API and the worker as `SOVITECH_CONVERTER_IMAGE`. The demo seed queues the conversions of its two IFC models, and the worker runs them (one sandbox at a time, about a second each); nothing visible changes in part 1, since no page mounts the view. Without the image, the stack refuses to start rather than letting the conversions retry and record `sandbox_unavailable`.

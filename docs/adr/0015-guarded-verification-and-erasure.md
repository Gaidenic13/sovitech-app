# 0015. The two guarded functions: engineer verification and erasure

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25

## Context

- **Rule 10, "Engineer verification is an authenticated action":** "Only the engineer review endpoint writes `engineer_verified`. The caller must be an authenticated user with the `sovitech_engineer` role, who has opened the item. No script, migration, seed, AI output or service account can write it." **Rule 10, "Demo data":** "Demo values never carry `engineer_verified`, and never name a real person as verifier."
- **Rule 13, "Erasure":** one audited erasure job removes the file, its extracted text and its embeddings; replaces the excerpt text in every evidence entry that cites it with "[erased]"; writes an `erased` document event; withdraws the affected candidates, which keep their ids and values. "This is the only path that alters stored evidence, and it cannot change a value." Guardrails 2.3: "Deleting a document withdraws each candidate whose evidence comes only from that document. A candidate or asset with evidence from other active documents keeps that evidence."
- **Prompt 3 section 5.2, row "Database"**, and section 10's app roles; `docs/build-readiness.md` 3 "Now" item 4 ("one guarded function that is the only writer of `engineer_verified` (G10-3)").
- **PRD:** R-157, F-AUTH-04 (inputs: session, candidate id, the item-opened record, the project's demo flag), F-INGEST-07 (outputs, including `withdrawn` events with role `system`), US-ADMIN-23 AC3 (the erased event names the owner who asked or the system), US-DOCS-21 AC8 and traceability 10.3 near miss 5 (the same file uploaded twice to one project: deleting one leaves the other's file, text and evidence). **D-55** is open ("What is one item the engineer must have opened"); its interim: "One item is one candidate the engineer has opened with its evidence, and bulk checkboxes never verify." **D-13** and **D-20** are open. The owner decided no D row as of 2026-09-25.
- **Cases:** G10-3 (a non-engineer account calls the verify endpoint: rejected) and the new G10-8 (an engineer calls it on a candidate of the demo project: rejected).

## Decision

1. **`sovitech.open_review_item(open_id, candidate_id)`**, owned by `sovitech_db_verifier`, records that the requesting engineer opened one candidate (`review_item_opens`). It accepts only an app request by a person holding `sovitech_engineer`, on a candidate of the project in scope. One item is one candidate (D-55 interim).
2. **`sovitech.verify_candidate(event_id, candidate_id, reason)`**, owned by `sovitech_db_verifier`, the one writer of `engineer_verified`. It refuses, each with its own code:
   - any login but the app's (`SVV01`), and a request with no user (`SVV01`);
   - an account that is not a person: a service or seed account, even one holding the engineer role (`SVV02`);
   - a user who does not hold `sovitech_engineer` now: an owner, a commercial reviewer, an admin, a revoked engineer (`SVV03`);
   - a candidate outside the project in scope (`SVV04`);
   - a candidate of a project flagged demo (`SVV05`; G10-8);
   - an engineer who has not opened that candidate (`SVV06`).

   Only then does it write one `engineer_verified` event naming the engineer, one candidate per call; a verification never carries a bulk id (a check constraint), so bulk checkboxes never verify. The review endpoint (phase 7) calls it through `verifyCandidate` in the data-access layer. EXECUTE is granted to the app role alone.
3. **`sovitech.erase_document(audit_id, event_id, document_id, role, reason)`**, owned by `sovitech_db_eraser`. For a document of the project in scope, and only from an app request:
   - the erased event names the owner who asked (a member of the project holding the `owner` role) or the system (a service account that is a member of the project), as US-ADMIN-23 AC3 reads 2.3; anything else is refused (`SVE03`); a second erasure is refused (`SVE02`); its reason is the function's own code, `document_erased`, whatever the caller gave (the caller's reason goes to the audit event), so the value model can tell the erasure path from any other system event (ADR 0016 decision 21; phase 1 review, round 4);
   - it runs in a READ COMMITTED transaction only (`SVE12`), and holds the **erasure lock** of the document's (project, content hash) exclusively from before its erased event to its commit (a transaction-level advisory lock; its key is `sovitech_guard.erasure_lock_key`);
   - every excerpt citing the document becomes `[erased]`, with the time;
   - the extracted text of the document's content hash is deleted, unless another document of the same project with the same bytes is not erased; then it stays for that document (2.3; US-DOCS-21 AC8);
   - each candidate whose evidence now comes only from erased or withdrawn documents gets a `withdrawn` event, role `system`, reason `document_erased`; candidates themselves are never touched, so their ids and values stay. This is the one system event written in a request whose user is not a service account: the event-actor guard (ADR 0014) lets the erasure function, and nothing else, write it;
   - one `document_erased` audit event records who asked, in which role, which document, and the counts, with ids and counts only.
   - **Nothing of the document comes back** (rule 13: the erasure "removes the file, its extracted text"; "replaces the excerpt text in every evidence entry that cites it"). Guards on `document_texts`, `evidence_locators` and `evidence_excerpts` (ADR 0014) refuse, with `SVE11`, extracted text for a content hash no document of which is left unerased in the project, and an evidence entry or excerpt citing an erased document, whether of a candidate or of an asset appearance. Each takes the erasure lock shared before it looks, in READ COMMITTED only (`SVE12`): a write that got there first commits before the erasure reads the excerpts and texts, so the erasure erases what it wrote and withdraws what it supported; a write that comes later waits for the erasure to commit and is then refused. The same bytes uploaded again as a new document take text and evidence (US-DOCS-21 AC8).

   The files and derived files are removed by the erasure job in the API (phase 2) around this call; the embeddings table does not exist yet.
4. **The demo flag follows the creator's account** (rule 10, "Demo data": "Demo projects are flagged `demo`"; "Demo values never carry `engineer_verified`"). `sovitech.create_project` refuses (`SVR05`) a project created by the demo seed account without the flag, and one flagged demo by any other account, person or service. The flag was the caller's word alone: a seed that left it off would have made the demo's values verifiable, since `verify_candidate` reads the flag (`SVV05`). No source lets an owner set the flag, so the refusal follows from rule 10 as written and takes nothing from an owner.
5. **Readings recorded for the owner and the approver:**
   - **Verification and the other roles.** A user holding both `sovitech_engineer` and `sovitech_admin` can verify: the rule forbids admin alone from permitting it, not an engineer who also administers. Whether one account may hold two roles is D-20 (new Q36) and US-ADMIN-03's note; requiring separate accounts would be a tightening for the approver.
   - **The stage 3 record** has the rule 10 fields but no writer (D-20: where it is created is open). Nothing in the store requires the reviewing engineer and the commercial reviewer to be different people: that is new Q36, a tightening for the approver.
   - **Erasure by an engineer or an admin** is refused for now: rule 13 describes the erasure job "When an owner deletes a document or asks for erasure", and US-ADMIN-23 AC3 names the owner who asked or the system. How an owner asks for erasure other than by deleting a document is new Q14. An engineer's own withdrawal of a document holds since round 5 (2.3's `DocumentEvent`; ADR 0014 decision 4; ADR 0016 decision 21); it removes the document and withdraws the values only it supports, but it starts no erasure: rule 13 names the owner's deletion or request.

## Consequences

- G10-3 and G10-8 pass through the data-access layer, each with a control that shows the same engineer accepted on a project that is not a demo, after opening the item. G10-3 also refuses the admin's self-grant route and an admin's grant of the engineer role to an account they created (ADR 0013); G10-8 also refuses a seed account's project without the flag, and a person's project with it (decision 4). `packages/db/src/store.test.ts` shows the erasure: two excerpts erased, text kept while a duplicate upload holds it and deleted with the last one, only the candidates that lose their last active source withdrawn, every candidate row unchanged, the audit event free of document text, and the domain's `derive` reading the withdrawn candidates as withdrawn.
- **What the store cannot know.** "Authenticated" means the user the API names (ADR 0013, "The trust boundary"). The store checks that user's account kind, role, opened item and project, and refuses every other login.
- Demo values are refused by the store, whoever calls; the demo seed never needs an `engineer_verified` event (rule 10).

- **Found by the phase 1 review (2026-09-25):** `create_project` trusted `p_is_demo` from any caller (decision 4 added); an admin could verify after granting themself the engineer role (ADR 0013, decision 2).
- **Found by the phase 1 review, round 3 (2026-09-25),** reproduced on a TEST database (probe E0 to E4): after the owner erased a document, the extraction job, still running or retried, stored its extracted text again, a new document value whose evidence cited it and an asset appearance citing it, each with its text in clear; `erase_document` then refused a second erasure, so the text could never be erased; and a write committing just after the erasure's snapshot kept its excerpt in clear. Decision 3 changed as above. `packages/db/src/store.test.ts`, "nothing of an erased document comes back", proves it: E1 to E3 refused and no text of the erased document stored; an excerpt written after an erasure in the same transaction refused; a value written while the erasure waits erased and withdrawn; a write while the erasure has not committed waiting, then refused; READ COMMITTED required on both sides; and the re-upload control. The runner's self-check (ADR 0014, decision 7) performs one verification and one erasure after each migration, so a migration that stops either path fails the run. Indexed at integration as G13-8 (guardrails 1.6): E1 to E4 and the re-upload control; the concurrent writes and the isolation level stay in `store.test.ts`.
- **Found by the phase 1 review, round 4 (2026-09-25):** the erased event carried the caller's reason, so derive could not tell the erasure function's erasure as the system from a system event of any other kind; a document `withdrawn` event from a job's service account or an engineer was read as a deletion (ADR 0014, ADR 0016 decision 21). The erased event now carries `document_erased`, and the CHECK `document_events_erased_by_erasure` keeps it so. Proof: `packages/db/src/access.test.ts`, "the erased event is the erasure function's, with its own reason". Still open, for the approver: the system erases through this function with no record of the owner's request (proposal P-1-SYSTEM-ERASURE-REQUEST, build log phase 1).
- **Round 5 of the phase 1 review (2026-09-25)** changed nothing here: the erasure function and its erased event are as round 4 left them. The document withdrawal rule changed around it (ADR 0014 decision 4): the system withdraws a document only as the job carrying out the owner's or an engineer's own withdrawal, which it names; the system's erasure through this function still needs no record of the owner's request (P-1-SYSTEM-ERASURE-REQUEST).
- **Erasure and the store's writers:** the extraction and erasure jobs (phase 2) write in READ COMMITTED transactions, the database default and the data-access layer's.

## How to reverse

- **Several candidates per opened item** (if D-55 settles on an asset or a document place): change `review_item_opens` and the check in `verify_candidate` in an admin migration; the guard registry names the functions, so the invariant check keeps their owner and definer rights.
- **Erasure by other roles:** widen the role check in `erase_document` after the owner decides new Q14.
- **Removing either function or its checks** lets more through; it is a loosening under guardrails section 10 and waits for the approver's own words.

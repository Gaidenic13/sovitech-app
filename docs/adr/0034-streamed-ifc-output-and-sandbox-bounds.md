# 0034. The streamed IFC section, the bounds on sandbox outputs, the test harness's output place, and the API server's waits

- **Status:** Accepted: default, reversible. The per-line IFC section is gated code: it is written only when a request asks for IFC values, which the API does only while `ifc-values` reads open, and read only while it reads open (prompt 3 5.4). Building it approves none of ifc-input 6.2.1, 6.2.2, 6.2.3 or 6.2.10.
- **Date:** 2026-09-30
- **Supersedes in part:** ADR 0026 decision 3 as amended ("a tmpfs of `outputBytes` (the 256 MiB output limit ...)") and ADR 0033 "Consequences" ("Not built here: the streamed writer for large gated outputs"); ADR 0022 and 0031 describe the one-text output, which stays the form of every output that carries no IFC section.

## Context

- **The phase 2 review** (verifier V0 and adversarial A11, and the build log's "Next"): the `perf` model's gated output (741,528 facts, 46,754 proposals) failed as `output.too_large`, because its JSON passed V8's longest string, and the streamed writer had to exist before `ifc-values` can open; every sandbox output was parsed at once in the worker's process, bounded only at 256 MiB; the Python test harness (`services/extractor/src/sovitech_extractor/sandbox.py`) still bind-mounted a host folder at `/output`, unlike the API's runner; and Fastify's `requestTimeout` and `connectionTimeout` were not set.
- **Reproduced first** (scratchpad `build/fix3b/stream-sandbox/`): the reader's command line on the `perf` model with IFC values and a TEST table exits 4, `output.too_large`, after 29 s at 1.60 GB peak RSS; a 206 MB output within the 256 MiB bound, read by the worker's reader, stops the worker's process with "JavaScript heap out of memory" (the YAML reader holds about 20 times what it parses); a container run through the Python harness leaves a link to `/dev/zero` at `output.json`, a FIFO, an executable, a 64 MB file and a folder with mode 0000 in the host folder; and a request whose body stalls is held open by the API with no end.
- **Prompt 3** section 8 (every job that opens an owner document runs in a container with limits; one writable place), section 11 (the extraction budget: 5 minutes and 4 GB; security basics) and 5.4 (gates; nothing gated reachable except through the test-utils override in `tests/proposed/`). **Guardrails** rule 13 (logs and errors never carry document text), rule 12 (a file that could not be read says so: "Analysis failed").
- **The Python extractor has no IFC role** since the owner's decision of 2026-09-26 ("web-ifc instead"; ADR 0031): it refuses a model (`job.ifc_read_by_ifc_reader`). So the per-line form is written and read in TypeScript only.
- **Owner decision 2026-09-25:** uploads accept fixture hashes only, so the only documents the live app reads are the generated fixtures.

## Decision

1. **The per-line IFC section** (`packages/extraction-contract/src/ifc-values-stream.ts`, TypeScript only; the shared JSON Schema and the Python side are unchanged). When a request asks for IFC values of a model (`ifcValuesStreamExpected`: `ifcValues` true and format `ifc`), the IFC reader's command line writes `output.json` as lines, each ending with a line end:
   1. the extraction output without its IFC section, one JSON text, parsed by the contract's `parseExtractionOutput` as any output;
   2. the stream header, `{"ifcValuesStream":{"contractVersion","section","statements","facts","candidateProposals"}}`: `section` is `present` or `absent` (no section: the model could not be opened), with the number of lines of each kind that follow;
   3. each quoted STEP statement once, `{"statement":{"stepId","text"}}`, its verbatim text from `#<stepId>` to `;` (the `perf` model's relation statements were repeated once per element they relate: 1.27 GB in a prototype of the build log's "Next", 248.8 MB now);
   4. the facts, `{"fact":{"id","globalId","stepIds","path","value","declaredUnit"?}}`: an `IfcFact` without what every fact shares or repeats. Its locator's content hash and schema are the output's (`ifc_value_locators`), and its excerpt is its statements' text joined by line ends, rebuilt by the reader;
   5. the proposals, `{"proposal":IfcCandidateProposal}`.
   The line schemas are built from the generated defs (`IfcFactSchema.shape`, `IfcLocatorSchema.shape`, `IfcCandidateProposalSchema`), so a line holds what the in-memory section holds, under the same rules. The writer (`ifcValuesStreamLines`) is a generator: one line at a time, through a file stream to a temporary file and a rename, so no text of the whole section is built. It throws `output.not_streamable` when a fact's excerpt is not exactly its statements, and `output.line_too_long` when a line would pass `IFC_VALUES_LINE_MAX_BYTES` (1 MiB). The reader keeps every value below that: a list value longer than 256 KiB as JSON is not representable (`value.not_representable` in coverage, as for any value the contract cannot hold), and every other part is bounded by the contract (strings of 20,000 code points, names of 255). Every other output (PDF, XLSX, a model with no IFC values asked for) stays one JSON text, as before.
2. **Reading it** (`readIfcValuesStream`): it takes no line while the request asked for no IFC values (`not_asked`) or while `ifc-values` reads closed in the worker's gate source (`gate_closed`), and none from an output that does not carry the form (`unexpected`). Otherwise it checks each line as it arrives: its kind in order (statements, then facts, then proposals), its schema, the whole-output invariants for its part (`ifc_value_locators`, `ifc_proposals`, `format_sections`), and the form's own checks (`stream:*`: the header, a statement once and its own, a fact's statements written before it, no statement unquoted, a joined excerpt within 20,000 code points, and exactly the counts announced). Any failure refuses the whole output; nothing of it is returned. What it reads comes back as the same sealed handle as the in-memory form, and only `openIfcValues` opens it, through the gate (ADR 0022, ADR 0033: the gated value path needs no change). Problems are paths under `/lines/<n>` and codes, never values (rule 13).
3. **The worker's reading and the bounds** (`apps/api/src/jobs/read-output.ts`, `output-file.ts`). The output file is opened once (`O_NOFOLLOW | O_NONBLOCK`), checked to be a regular file within the whole bound, and read from that descriptor:
   - the first line within **4 MiB** (`OUTPUT_LIMITS.outputBytes`; the largest fixture's output, the 40-page specification's, is 1,173,042 bytes, so the margin is 3.6 times; the YAML reader holds about 265 MB while it parses 4 MiB, against 4 GB and a crash before). For a job that asked for no IFC values this is the whole output, with or without a line end; a larger one is refused `output_too_large` and not parsed. This replaces the 256 MiB bound on every output;
   - the later lines only when the job asked for IFC values, and only while the caller iterates them: each within **1 MiB** (`lineBytes`, the contract's `IFC_VALUES_LINE_MAX_BYTES`; the `perf` model's longest is 6,739 bytes), all within **512 MiB** (`gatedBytes`; the `perf` model's section is 248,792,524 bytes, so a margin of 2.2 times), each decoded as strict UTF-8 and parsed alone, then handed to the contract. A line past its bound (`output_line_too_long`), a last line with no line end or a file shorter than it said (`output_truncated`), a line that is empty, not UTF-8 or that the reader below refuses (`output_line_malformed`), or a section past its bound (`output_gated_too_large`) refuses the whole output; so do the contract's refusals (`ifc_values_truncated`, `ifc_values_excess`, `ifc_values_invalid`, `ifc_values_not_asked`, `ifc_values_gate_closed`, `ifc_values_unexpected`).
   - **The reader of the first line and of each later line is the YAML reader with its JSON schema** (`yaml`'s `parse` with `schema: 'json'`, no aliases, unique keys; `jsonValue` in `read-output.ts`), not a strict JSON parser (corrected on 2026-09-30 after the closing verification of the second fix round, `verify2d/stream/lines.out`; this decision first said a line must be "one JSON value"). It accepts, where strict JSON would not: single-quoted strings, a trailing `# comment`, a leading `---` document marker, explicit tags (`!!str`; `!!binary` gives a byte array), a byte-order mark, raw tabs and NUL characters inside strings, a whitespace-only line (read as null), an anchor with no alias, and a lone surrogate escape. It refuses unquoted keys, a line ending in CR LF, duplicate keys, two values on one line, aliases, hexadecimal numbers, a number written with a leading `+`, `.inf` and an unquoted word. Whatever it returns, the first line still goes through the contract's strict parser and **every later line through the contract's strict line schemas**, which refuse any key, shape or type they do not name (a null, a byte array where text is due): so nothing unvalidated is taken, and only this decision's wording was imprecise. Replacing the reader with a strict JSON reader is proposal P-2-STREAM-JSON-READER (the build log).
   The worker checks the whole output before it stores anything, so a refused line stores nothing of it; the job ends failed with the code (not retried), and a model keeps its G12-1 line.
4. **The sandbox's output place follows what was asked** (`apps/api/src/jobs/sandbox.ts`): the output volume is 5 MiB (the 4 MiB output, its line end and 1 MiB) for a job that asked for no IFC values, which is every job while `ifc-values` is closed, and 517 MiB only for a job that asked for IFC values (`SandboxJob.ifcValues`); the copy out of the container takes at most the same file bound. Before, every job had 272 MiB.
5. **The Python test harness's output place is the worker's** (`services/extractor/tests/job_sandbox.py`). The tests no longer bind-mount a host folder at `/output`: every sandboxed job of `services/extractor/tests/test_sandbox.py` writes into a volume of its own, a tmpfs of 5 MiB, `noexec,nosuid,nodev`, owned by `10001:10001` with mode 0700, kept mounted by a holder under the same confinement; the container runs with `--user 10001:10001`; the one regular output file within the bound is copied out through the Docker daemon into a new host file; containers and volume are removed whatever happened. `job_sandbox.command` swaps the bind that `sovitech_extractor.sandbox.docker_argv` still writes for the volume, and refuses a command with any other writable mount. `docker_argv` itself (in `src/`, outside this change's files) keeps its `out` folder parameter: its only user is these tests. Changing it to take the volume, so the harness and the definition agree, is left to the integrator (the diff is in the fix round's report). **Applied by the integrator on 2026-09-30:** `docker_argv` and `run` take the job's output volume (`output_volume`) and name the sandbox account (`SANDBOX_USER`), so the definition itself mounts no host folder; `job_sandbox.command` now checks rather than swaps (one writable mount, the job's volume; the sandbox account named) and refuses anything else; `output_place` and `copy_out` stay in the tests' module.
6. **The API server's waits and parsed-body bound** (`apps/api/src/server.ts`, `SERVER_LIMITS`):
   - `requestTimeout` 150 s: a whole request, body included, must arrive within it. That is past a chunk's own deadline (`APPEND_DEADLINE_SECONDS`, 120 s), so an 8 MiB chunk that arrives in time is never cut, and one that does not gets the upload's own 409 `chunk_timeout`, which the client resumes from.
   - `connectionTimeout` 660 s: a socket quiet this long is closed. That is past a completion's lease (`COMPLETE_LEASE_SECONDS`, 600 s), during which the server copies and hashes up to 500 MB and writes nothing.
   - `keepAliveTimeout` 10 s; `headersTimeout` 60 s (Node's default, stated); Node checks both waits every 30 s (its default, stated).
   - `bodyLimit` 16 KiB for parsed (JSON) bodies: the routes that take one carry a file name and a size, or a document id. A chunk is handed to its route as a stream, never parsed, and the upload bounds it.
   The request and headers waits are also given to Node's server at its creation (Fastify's `http` option). Set only afterwards, as Fastify sets `requestTimeout`, Node 22.17 checks no request wait shorter than its headers wait (measured: a stalled body stayed open until the socket wait closed it). The production values (150 s over 60 s) did not depend on it; the scaled-down test did.

## Consequences

- The `perf` model, refused as `output.too_large` before, now goes through the whole path with the gate open (tests/proposed): the reader's command line, the worker's line-by-line reading, and the gated value path's storing. The live app is unchanged while `ifc-values` is closed: requests ask for no IFC values, the reader writes one JSON text, and the worker reads nothing after the first line (a test proves it with a section of megabytes behind it: at most one read of 64 KiB past the first line, and none of its lines parsed).
- **Both sandbox images must be rebuilt** from the current sources (`docker build --target extractor -t sovitech-extractor:dev services/extractor` and `docker build -f services/ifc-reader/Dockerfile -t sovitech-ifc-reader:dev .`): the IFC reader's image carries the new command line (the per-line form, the list bound); the extractor's source is unchanged here, but its tests now run through the worker's output place. Outputs that carry no IFC section are byte for byte as before, so the images of 2026-09-30 still pass every blocking test.
- **Throughput of the gated path is slow and measured, not tuned.** The YAML reader parses about 15,000 lines a second (68 to 73 s for the `perf` model's 1,033,071 lines), because `JSON.parse` is reserved for the reviewed readers of `JSON_PARSE_REVIEWED`, which waits for the approver. The gated value path stores the model's 291,541 statements and registers 22,635 spatial elements one at a time (about 50 s on a quiet machine, 225 s beside other test runs): its per-element writes are the store's (`packages/db`), not batched. Neither is a live path.
- A real PDF of a few hundred pages would pass the 4 MiB output bound and read "Analysis failed" (rule 12's line). No such file reaches the app while uploads take fixtures only; when real uploads are allowed, the bound is revisited, or PDF pages get a per-line form too.
- The contract's inline `ifcValues` stays valid (the in-process runs of the tests and the corpus use it); an output file carrying both forms is refused (`unexpected`).
- The problem codes gain `stream:<id>` (TypeScript only).

## How to reverse

Delete `packages/extraction-contract/src/ifc-values-stream.ts` with its exports and the two helpers it made of `invariants.ts`, the per-line branch of `packages/ifc-reader/src/cli.ts` and the list bound in `values.ts`, `apps/api/src/jobs/output-file.ts`, and restore `read-output.ts`'s one-value reader and the worker's call of `checkedOutput`; set the volume back to one size. A large model's gated output then fails as `output.too_large` again. The test harness's output place and the server's waits are independent of the rest and are reversed by restoring `test_sandbox.py`'s calls of `sandbox.run` and removing `SERVER_LIMITS` from `buildServer`.

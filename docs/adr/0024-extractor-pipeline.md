# 0024. The extractor: its readers, the IFC data pass, the entry point and the sandbox runner

- **Status:** Accepted: default, reversible, for the entry point, the PDF and XLSX readers, format detection, logging and the sandbox runner. **Superseded by the owner's decision of 2026-09-26 ("web-ifc instead"; ADR 0018; ADR 0031)** for the IFC data pass: the schema tables this ADR proposed (decision 6) and the Python IFC data pass on them (decisions 6 and 7) are removed, and IFC models are read by the IFC reader on web-ifc (`packages/ifc-reader`); only the STEP reader of decision 6 stays, for word-for-word excerpts. Decision 10 (STEP ids) went with the IFC output. **Proposed, for the approver,** still: the rule 14 thresholds (decision 3).
- **Date:** 2026-09-26

## Context

- **Prompt 3 section 6** (services/extractor): Python, sandboxed jobs; emits text blocks, cells and IFC facts with locators, raw strings and typed STEP literals, coverage and findings, plus the gated table-driven IFC candidate proposals; never parses numbers out of text; never maps PDF or XLSX content to fields; never writes the database. **Section 8**: code reads IFC, not the AI; the pipeline order (header and schema, units, spatial tree, groups and systems, elements with types and property sets, geometry last); `ifcopenshell.validate` first; a file with schema problems is read where it can be; validator and IfcTester logging captured and emitted as codes, GlobalIds and STEP ids only; IDS results as spec ids, counts and failing GlobalIds; storeys never floors; no IfcConvert option that prints names or areas. **Section 10, phase 2**: PDF through pypdfium2 (native text layer, anchor ids, character boxes, hidden-text flags), XLSX through openpyxl (cached value and number format, locators), coverage recorded by code, other formats stored "Not analysed", G12-3 built with 3 pages with no text layer. **Section 11**: the extraction budget (a `perf` IFC4 file of about 100 MB: data pass within 5 minutes and under 4 GB), the sandbox as a security basic.
- **ifc-input** 2.2 (stack and order), 4.1 (principles: the verbatim STEP line is the excerpt, units from the file), 4.4 (life-safety signals), 5.3 to 5.5 (fixtures, cases, the IDS), 6.2 (proposals, none applied).
- **ADR 0018**: IfcOpenShell 0.8.5 and IfcTester 0.8.5 are withheld (their wheels bundle CGAL packages published under the GPL); options (a) to (d) are the owner's. **ADR 0020**: the job worker runs `docker run` with ADR 0018's flags; jobs carry ids only. **ADR 0022**: the extraction contract; an IFC file is always `stored_only` with "IFC model"; the IFC values are sealed.
- **PRD**: R-013 to R-015, R-022 to R-042 (E-DOCS, E-IFC). D-01 (build-readiness decision 4, parsing scope; the 5.2 default "IFC parsed, values behind `ifc-values`" applies, per the orchestrator's instruction for this run), D-36 (the IDS check), D-37 to D-43, D-49, D-50, D-56, D-59, D-63 (the ifc-input 6.2 proposals).
- **Guardrails v1.6**: rule 1 (the five evidence checks; content hash), rule 8 (the one number parser is in `packages/registry`), rule 12 (coverage by code; "not found" never covers what was not read), rule 13 (logs never hold document text; documents stay with their project), rule 14 (embedded instructions and hidden text are findings and change nothing).

## Decision

1. **Entry point.** `python -I -m sovitech_extractor --request <file> --document <file> --out <folder> [--datasets <folder>] [--ids <file>]`. The request is read strictly (`contract.parse_request`); the output is written only through `contract.dump_output` and only when `contract.output_answers_request` finds nothing, as `output.json`, atomically. Exit status: 0 output written; 2 request refused; 3 job refused (`job.content_hash_mismatch`, a named dataset or IDS not mounted or not matching); 4 internal error. The extractor refuses a file whose SHA-256 is not the request's content hash: it never writes an output about bytes it did not read.
2. **The format comes from the content** (`formats.py`): PDF, ISO 10303-21 (IFC), a ZIP container (XLSX, DOCX, or any other archive, stored whole and not opened further), an OLE compound file (RVT only when RVT was declared; the container alone does not say RVT), DWG, JPEG, PNG. What cannot be placed is `other`, failed, with `format_mismatch` (something else was declared) or `unrecognised_format`. RVT, DWG, DOCX, JPG, PNG and ZIP are stored with their G12-1 word and nothing is extracted. **Amended in the phase 2 review:** a file the extractor can place, but as another format than the one declared (a workbook uploaded as a PDF), is not read either: `other`, failed, `format_mismatch`, so nothing describes it as a format its record does not have; a file declared as a ZIP archive is stored as one whatever its container holds (R-014). The contract refuses any other output of another format (ADR 0022 decision 11).
3. **PDF** (`pdf_reader.py`, pypdfium2 5.13.0, PDFium 153.0.7999.0). A text block is one line of the page's text layer (split where part of the line counts as hidden and part does not), so a document that places each glyph as its own object still reads as lines and an excerpt is found in the text the verifier checks. Each block has an anchor id (`p<page>-b<n>`), its raw text, its box and the loose box of every character the text layer places. Hidden text (rule 14), judged per text object: invisible render mode; a fill (or, for stroke-only text, a stroke) that matches what is painted behind it (the topmost filled path under it, or the white page; unknown, so not flagged, over an image or a form); tiny text; text outside the page. Coverage: a page with no text layer is not read (`no_text_layer`; no OCR); pages past the page limit or the time limit, and a page PDFium cannot load, are not read with that reason; a PDF with no text layer on any page is stored as "PDF scan"; an encrypted PDF fails as `encrypted`.
   - **Proposed, for the approver (rule 14 thresholds):** text whose characters stand under **2.0 points** (loose box height) is tiny; two colours match within **8 of 255** per channel. The guardrails name "white or tiny text" and set no threshold. A higher threshold hides more (stricter on Truth, and legitimate small print would give no values).
   - **Not detected**, listed for the engineer: text hidden by a clipping path, and text on an optional-content layer switched off; PDFium exposes neither to this reader. The `clipped` and `hidden_layer` reasons of the contract are never set today.
4. **XLSX** (`xlsx_reader.py`). The parts are read with lxml, streaming, with entity resolution, DTD loading and network access off; a part that declares a DOCTYPE is refused. A cell's `raw` is the text of its value as the sheet XML stores it (a number cell's "93.59999999999999", not the 93.6 a display would show), because openpyxl's reader turns number cells into floats and loads whole workbooks into memory; openpyxl supplies its table of built-in number formats and its date-format test, and the tests read every fixture with openpyxl to cross-check sheets, states, number formats, formulas, merged ranges and hidden rows and columns. This departs from "XLSX through openpyxl" in the letter, to keep the contract's "raw is the cached value exactly as the file stores it" and the cell limit. A formula is kept as written, with a leading "=", never evaluated. Hidden: hidden and very hidden sheets, hidden rows and columns, a font colour that matches the fill (white on no fill included). A sheet over the cell limit, a chart sheet, or a dialog or macro sheet is not read, with the reason, and none of its cells is emitted. **Amended in the phase 2 review:** the workbook's status follows its sheet coverage: every sheet read, `analysed`; some, `partly_analysed` in sheets; none, `failed` (`unreadable_file`), with each sheet's reason kept in the coverage for the engineer.
5. **Embedded instructions** (`instructions.py`). PDF blocks, XLSX string cells and IFC free text (Name, Description, ObjectType, LongName, text property values, the header) are matched, case folded and without diacritics, against English and Romanian patterns for text that addresses the reader: telling it to ignore its instructions, to mark values verified or confirmed, to issue a quotation, or speaking to the AI. Each text gives at most one `embedded_instruction` finding, with a code and a location. A finding changes nothing; a miss changes nothing either, because document text never sets state (rule 14).
6. **IFC: the data pass** (`ifc/`), in ifc-input 2.2's order. **Superseded (2026-09-26):** the owner chose web-ifc (ADR 0018, option (c)); the data pass below is now the IFC reader's (`packages/ifc-reader`, ADR 0031), which keeps its stages, codes, output and ground-truth tests, reads the model with web-ifc instead of these schema tables, and was checked to give the same outputs on the four synthetic models. `ifc/` keeps only `step.py`, the in-house reader of word-for-word excerpts, which the reader's TypeScript copy is checked against (`tests/test_step_text_parity.py`); an IFC job sent to this extractor is refused (`job.ifc_read_by_ifc_reader`). As written on 2026-09-26:
   - **The STEP reader** (`step.py`) reads the header and indexes every instance in one pass (where each statement starts and ends), and parses an instance's attributes only when something asks; values stay tokens (`Real("430000.")`), strings keep their token and their decoded text (ISO 10303-21 escapes, including `\X2\`), and an instance's verbatim statement is its excerpt. A statement it cannot read is recorded with its STEP id, and the rest of the file is read. This reader is needed whichever way ADR 0018 is decided: the contract carries STEP tokens as written and the verbatim line as the excerpt (ifc-input 4.1 item 3), which a parsed model does not give back.
   - **Proposed, for the owner (ADR 0018):** the entities the data pass reads are named through **schema tables written here** (`schema.py`: project and spatial structure, zones and systems, relationships, property and quantity sets, units, presentation layers, element occurrences and type objects, for IFC2X3, IFC4 and IFC4X3), written separately from the fixture generator's tables so each checks the other. They serve the data pass while IfcOpenShell is withheld; they are not a schema validator. If the owner takes ADR 0018's option (a), (b) or (d), IfcOpenShell's schema can replace the tables behind the same access (`model.py`), and `ifcopenshell.validate` runs. If the owner reads this as option (c) ("a different parser for the data pass") and declines it, the IFC half of the extractor records the header only and marks the rest not read. Either way nothing from a model becomes a value while `ifc-values` is closed.
   - **Stages**: header and schema; the project's unit assignment and the units values name themselves; the spatial tree (aggregation); zones and systems with their members and the buildings a system serves; elements with containment, their type objects, their property and quantity sets (on the occurrence and through the type), and control links; then geometry: presentation layers switched off mark their elements as hidden content (a `hidden_content` finding), and shapes are **not processed** (recorded in coverage as `geometry.not_processed`): a geometry kernel is withheld (ADR 0018), and reading coordinates would mean reading numbers out of text. So "placed outside the site's extent" (ifc-input 6.2.13) is not detected.
   - **The engineer's record** (`ifcModel`): the header schema as written, the authoring tool, the IfcProject GlobalId, the classes present (named as the schema names them; a keyword the reader does not know is listed in coverage as not recognised, never guessed into a name), `processing: partial` (the geometry stage did not run), and the schema check `not_run` (`ifcopenshell.validate` 0.8.5, withheld). No IDS result is recorded while IfcTester is withheld; no home-made evaluator stands in for it (`ifc/checks.py` holds adapters for both tools, written against their 0.8.5 APIs, which have not run).
   - **The register** (`register.py`): one row per element, with its engineering tag (the Tag when it holds a letter), its class as IFC4 names it (an IFC2X3 generic occurrence is named by its type object, IfcElectricDistributionPoint by its function, per the IFC4 change log: a schema correspondence, not an app type), its predefined type resolved from the occurrence or its type, its storey and its systems. It is the extractor's view for the engineer and the tests (IFC-11); it counts nothing.
   - **Storeys are never floors.** Nothing counts storeys or elements; the only storey count in an output is a file's own property value, as written.
7. **IFC values, only when asked** (`ifc/values.py`, `ifc/proposals.py`, `ifc/datasets.py`; **superseded 2026-09-26**: now `packages/ifc-reader/src/values.ts`, `proposals.ts` and `datasets.ts`, reading the same dataset format). When the request asks for IFC values (the API does so only while `ifc-values` reads open), the output's sealed section holds a fact for each attribute, property, quantity and relation of each readable object, with its IFC locator (content hash, schema, GlobalId, the STEP id of the quoted line, the path, through the type object where it comes from there), its token and the unit the file declares, and the verbatim line. Elements on a switched-off layer give no fact and no proposal. **Every proposal comes from a rule of a mounted dataset** (`<id>@<version>.json`, kind `ifc-mapping`, read strictly): the extractor holds no mapping table and no field key of its own, so with no dataset there is no proposal. A rule names its mechanism, field key, subject kind, source claim (document or ai_inference with a confidence), extra gates, a match (object kind, IFC4 class and resolved predefined type, an attribute, a property or quantity, a tag prefix, a name term, a relation and its group, properties that must be true) and its value (the matched fact, or a choice). Each proposal waits for its mechanism's gates at least (the contract's x-mechanism-rules) and names its dataset. The life-safety signals of ifc-input 4.4 are rules of such a table (ifc-input 6.2.10 counts that list among the tables to approve); the TEST tables in the tests add `dataset-asset-taxonomy` to them. No `geometry` rule is accepted.
8. **Logs carry codes only** (`logs.py`). While a job runs, the process's standard output and standard error point at /dev/null, so nothing a native library prints leaves the sandbox; the extractor's JSON log lines go to the original standard error and hold a level, a code, and at most a name matching `[A-Za-z_][A-Za-z0-9_.]*`, a count, STEP ids and GlobalIds. Library logging becomes `library.log` (logger name and level), warnings `library.warning` (category), an exception `job.internal_error` (class name).
9. **The sandbox runner** (`sandbox.py`) is the one definition of the flags: `--network none`, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit 256`, `--memory 4g` with `--memory-swap` equal, `--cpus 2`, a 64 MB `noexec` tmpfs at /tmp, the document and the request mounted read-only, the datasets and the IDS read-only when named, one writable output folder; the container runs as uid 10001 and is killed at the wall clock (`docker kill`). The API's worker (ADR 0020) runs the same command. Folders shared with the container must sit where the Docker machine mounts them (with Colima, under the home folder), and the output folder must be writable by uid 10001. The phase 4 Node conversion (That Open's IfcImporter) has a spec with no image yet (`CONVERSION`).
10. **STEP ids** (**superseded 2026-09-26**: `step_ids.py` went with the IFC output; the IFC reader takes each STEP id as web-ifc's integer, an identifier it reads, never digits turned into a number, so no exception to the bans is needed and the proposal below is withdrawn). The extractor kept STEP instance names as their digits and turns them into the contract's integers in one function (`step_ids.as_step_id`), which refuses anything that is not an instance name. It does not call `int()`, because the Python bans refuse `int()` on text anywhere in the extractor with no inline switch; it is written out digit by digit instead. **Proposed, for review:** an identifier, not a value, passes here outside the bans' sight; the reviewer may prefer `int()` in this one function under a reviewed exception to the bans, which would change the bans and waits for the approver.

## Consequences

- The four synthetic models, the six PDF companions and the two XLSX companions are read to their ground truth (`services/extractor/tests/`), and every output parses under the contract in both languages. The IFC2X3 copy gives rev A's register except the limits its ground truth lists (IFC-11).
- While IfcOpenShell and IfcTester are withheld: no schema validation, no IDS results, no geometry, no viewing derivatives. The engineer's record says so (`not_run`, `processing: partial`, `geometry.not_processed`).
- The hidden-text reasons `clipped` and `hidden_layer` (PDF) and "outside the site's extent" (IFC) are not detected; a hidden run the reader misses is treated as visible text, so a value could be read from it. Listed for the engineer and the approver.
- A real, large IFC file gives a large sealed section when IFC values are asked (on the perf model: 741,528 facts, 1.24 GB of JSON). The output limits of the contract (100,000 findings; 10,000,000 facts) hold; a relation line over 20,000 characters gives no fact and is recorded as not representable.
- The TypeScript guardrail cases cannot call the extractor: the index check refuses a case file that runs code in another process (phase 1, `[process]`), while prompt 3 section 6 says extractor-level cases call the extractor from the TypeScript test. The extractor-level halves of G12-1, G12-3, G12-4, G12-5, G14-1, G14-2 and G14-3 are pytest tests titled with their ids; the TypeScript halves (status lines, the verifier, "not found" coverage) wait for the API and the integrator. The IFC value path runs end to end in the proposed suite, since phase 2's integration `tests/proposed/ifc-input-5.4-reader.test.ts` (the IFC reader; ADR 0031) and `tests/proposed/ifc-input-5.4-api.test.ts` (the API).

## How to reverse

- **To the Python data pass for IFC** (if the owner reverses "web-ifc instead"): take option (a), (b) or (d) of ADR 0018, rebuild the data pass of decisions 6 and 7 on IfcOpenShell (the stages, codes and output are the IFC reader's, whose tests and ground truth carry over), and route IFC jobs to the extractor again (ADR 0031, "How to reverse"). The Python data pass on its own schema tables was removed before any commit; its stages survive in `packages/ifc-reader/src/reading.ts`.

- **To IfcOpenShell for the data pass** (after the owner's decision on ADR 0018): keep the STEP reader for tokens and excerpts; read the entities through `ifcopenshell` in `model.py` instead of `schema.py`; `ifc/checks.py` then runs `ifcopenshell.validate` and IfcTester.
- **To openpyxl's reader for XLSX:** replace `xlsx_reader.py`'s part reading with `openpyxl.load_workbook(read_only=False, data_only=True)`; `raw` then comes from the float openpyxl returns and is no longer the stored text, which is a change to the contract's description of `raw`.
- **To blocks per text object:** restore one block per PDFium text object in `pdf_reader._segments`; an excerpt then no longer matches across glyph objects.
- **Thresholds:** `pdf_reader.TINY_TEXT_POINTS` and `_COLOUR_TOLERANCE`.
- **STEP ids through `int()`:** a reviewed exception in `tests/test_bans.py` for `step_ids.py`, then `int(digits)` there.

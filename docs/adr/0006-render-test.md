# 0006. Render test: the reading of rule 2 and the harness

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25. Revised 2026-09-25 after the phase 0 adversarial review and verifier: the value ids a screen holds are required, step numbers are tied to one registered stepper, pixels the test cannot read fail unless reviewed, the allowlist self-test checks each seed's reason, the web server is never reused, and the harness pages carry TEST values. Revised again 2026-09-25 after the second review (round 2): a value element is compared with the display object the screen was served, not only its id; an app screen's display objects come only from the API through one registered adapter; the rendered page is scanned for reserved terms (decision 8); the check waits for a readiness marker, the network and the page's timers, and reads again with every hover and focus state forced; stepper items carry their registered titles; large inline SVG drawings with no text are unreadable pixels; number words count as numbers; `.only`, skipped and fixme tests fail the Playwright run.
- **Note on the status.** The reading of rule 2 in decision 2 is listed for the approver as a clarification of rule 2, under "Proposals (not applied)" below. It is not written into `docs/guardrails.md`. (Moved out of the Status field at integration, so the field holds one of the three values prompt 3 section 15 allows.)

## Decision

### 1. The contract: value ids and the display objects the screen was served

- A value renders inside an element carrying `data-value-id="<subject kind>:<subject id>.<field path>"`, for example `document:<id>.coverage` or `project:<id>.openItems.owner`. The pattern is `VALUE_ID_PATTERN` in `tests/e2e/render/contract.ts`. Phase 3's view-model may narrow it; it never widens it.
- The nearest element carrying `data-value-id` decides. An empty or malformed id ties nothing and fails (`malformed-value-id`).
- **Every check is given the display objects the screen and state was served** (value id to what it shows: `text`, the formatted value or range; `lines`, its badge, source line and status lines; `parts`, pieces of the text or a line that a component renders in separate elements, such as the figure and its unit; `evidence`, the excerpts shown with it, each with its document id and content hash). Types in `contract.ts` (`ServedDisplay`), validation in `display-objects.ts`.
  - A `data-value-id` the screen was served no display object for fails (`unknown-value-id`), whether or not the element shows a number.
  - **Inside a value element, every text holding a number must be made of what its display object declares** (`display-mismatch`): the declared strings are cut out of the text, longest first, and no number may remain. A served id around a whole card, a literal in place of the value, and the value with a figure typed beside it all fail. An `aria-label` such as "TEST 123 guest rooms" on a value whose text is "TEST 123" passes: the words left over hold no number.
  - **A value element inside another value element fails** (`nested-value-element`).
  - A run of adjacent text nodes is read as one text, so a framework that splits "TEST " and "12,345" into two nodes is read as it is shown.
- **Where display objects come from.** Nothing a test types binds a number on an app screen:
  - An app screen (`tests/e2e/render/screens.ts`, from phase 3 on) names `displayObjectsFromApi()` (`api-display-objects.ts`), the one registered source. The check intercepts every response of the display-object route the page requests, reads its display objects, puts them into the in-page harness, and only then lets the page have the response, so the harness knows each id and its text before the page can render it. A screen that shows no value names `{}`. A function (whatever it returns), a hand-typed map, an object that only looks like the registered source (it is registered by identity, not by shape), and the earlier `knownValueIds` field are refused by `screens-schema.ts`, which `tools/checks/render` applies in `pnpm checks` and the render spec applies before it visits a screen.
  - A harness page (`tests/e2e/pages/`) declares its display objects in one `<script type="application/json" data-render-display-objects>` tag. `harness-pages.ts` reads it from the file before the page loads; the in-page harness never reads it.
  - Typed display objects are accepted only on the harness's own pages: `runRenderCheck` refuses a check prepared with a non-empty typed set on any other URL. An empty set (a screen with no value) is accepted anywhere.
  - An e2e flow prepares with `displayObjectsFromApi()`, and after an owner action calls `resetRenderCheck(page)`: the display objects keep coming from the API, and a typed set is refused.
- `prepareRenderCheck` and `checkUrl` refuse to run without display objects, or with invalid ones.
- The display-object route (`DISPLAY_OBJECT_ROUTE`, `/api/display-objects`) and the response shape (`{ displayObjects: [{ valueId, text, lines?, parts?, evidence? }] }`) are phase 0 placeholders for the harness: phase 3 points them at the API's route and the view-model's display-object type. `tools/checks/render/api-display-objects.test.ts` proves the mechanism against a TEST server on the loopback interface.

### 2. The reading of rule 2 (prompt 3 section 7)

1. **Digits the guardrails require are tied to a value id, never allowlisted.** Every 2.8 status line and every rule 7 count ("Partly analysed (<n> of <m> pages)", "Provisional: depends on <n> equipment items not yet checked", "<n> things for you to check", "and <n> more", "Rev B changed <n> values", "Still reading <n> files") renders through the StatusLine component, and each number in it sits in an element whose value id the view-model derives from stored state, for example `document:<id>.coverage` or `project:<id>.openItems.owner`, as that display object serves it.
2. **File names, revisions, tags and room or storey names** are document or field values, and render inside a value element.
3. **Digits with no stored-state meaning are not shown:** no upload percentages, no file sizes, no page numbers or totals in pagination, and no numeric chart ticks (the chart's table view carries the values). Showing them tied to a value id is proposal 7.2.30 (D-54), a loosening, and is not applied.

### 3. What the test reads

- Text nodes of the document, including the document title, open and closed shadow roots (the harness records roots as they are attached) and every frame of the page.
- Hidden content too: a collapsed section, a closed `<details>` and an element with `display: none` can be opened, and 2.8 "Prominence" forbids holding the only copy of anything there.
- The attributes a browser shows or announces: `aria-label`, `aria-description`, `aria-roledescription`, `aria-valuetext`, `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-placeholder`, `aria-braillelabel`, `aria-brailleroledescription`, `title`, `alt`, `placeholder`, `label`; and `value`, `max`, `min`, `low`, `high`, `optimum` on `<progress>` and `<meter>` (`SCANNED_ATTRIBUTES`, `RANGE_ELEMENT_ATTRIBUTES`). Removing one is a loosening of the test.
- The shown value of text-like inputs, button inputs and textareas.
- CSS generated content: `::before` and `::after` strings, `attr()` values and counters, and numbered list markers. **Generated content never carries a number**, inside a value element or not, because a value's digits must be its formatted text in the DOM.
- **What hover and focus show** (new in round 2). After the page has settled and been scrolled, the check forces `:hover`, `:focus`, `:focus-within` and `:focus-visible` on every element (Chrome DevTools Protocol, `CSS.forcePseudoState`), and dispatches pointer, mouse and focus entry events (never leave or blur) on every element a hover or focus could change: interactive elements, elements with a title or a description, inline handlers, and every element under a hover or focus listener (the harness records `addEventListener` calls from document start, so a framework that delegates from its root reaches every element). Content that stays is read by the snapshot; content that comes and goes is caught by the mutation observer as a transient number. So the render project runs in Chromium only.
- Not read: `<script>`, `<style>`, `<template>` contents, and pixels. **An element that draws pixels the test cannot read fails (`unreadable-pixels`) unless it is on the reviewed `unreadable` list of `allowlist.ts`:** `<canvas>`, `<img>`, `<video>`, `<embed>`, `<object>`, an SVG `<image>`, an `<input type="image">`, CSS images (a `url()` in `background-image`, `border-image-source`, `mask-image`, `content`, a list marker image, or the same on `::before` and `::after`), and, new in round 2, **an outermost inline `<svg>` larger than an icon (`ICON_MAX_PX`, 32 px on a side) that draws shapes (path, `use`, polygon, polyline, line, rect, circle, ellipse) and holds no text** (`svg-graphic`): its shapes could spell digits the test cannot read. An icon of 32 px or less passes; an SVG with text is read as text. A reviewed element carries `data-render-unreadable="<entry id>"`, must be of the kind its entry names and, when it loads a file, must load the file its entry names; the report lists it as unreadable. What a reviewed element draws is still not read (ifc-input 6.2.15, D-46).

### 4. What counts as a number

- Any Unicode number character (`\p{N}`): ASCII digits, digits of other scripts, fractions such as ½, and superscript or subscript digits such as the 2 in m² and CO₂. A unit label shown outside a value element therefore fails unless it is reviewed fixed copy. This is the strict reading of "digit sequence".
- **Number words** (new in round 2), so a rule 7 count written as words ("Two things for you to check") or a figure in words ("thirty floors") fails like digits: English cardinal words from zero to twenty, the tens, hundred, thousand, million, billion and dozen, with their plurals; Romanian cardinal words (zero, unu, doi, două, trei ... douăzeci ... sută, sute, mii, milion, milioane, miliard, miliarde), whole word, case and diacritics ignored (`NUMBER_WORDS` in `contract.ts`). English words apply where the nearest `lang` is not Romanian, Romanian words where it is, since Romanian "opt" (eight) is English "opt". Left out because they are also common words: English "one"; Romanian "un", "o", "una", "nouă" (nine, and "new") and "mie" (thousand, and "to me"). This goes beyond rule 2's "digit sequence"; it follows rule 7's counts, which must be bound.

### 5. The allowlist

One file, `tests/e2e/render/allowlist.ts`, with rule 2's four categories only. Each entry names its category, the reason its digits carry no stored-state meaning, and its source. Each category is recognised by structure, not by guessing from the text:

| Category | Accepted only when |
|---|---|
| Dates and times | The number sits in a `<time>` element whose `datetime` attribute is a valid date or time and whose text is that same moment in an allowlisted format |
| Step numbers | The number sits in an element marked `data-render-allow="<entry id>"` whose whole text matches the entry's anchored pattern, inside the one stepper container that registers the entry (`data-render-stepper="<entry id>"`). That container is an `<ol>` whose children are exactly the entry's `steps` `<li>` items; the marker is the only one in its item, its number equals the item's position, and **the item shows nothing but that number and the registered title of its step** (new in round 2: "6 air handling units" in item 6 of a valid stepper failed nothing before). A second registered container on the page fails every marker in both |
| Character counters | The number sits in an element marked `data-render-allow="<entry id>"` and tied to a text field by `data-counter-for`, whose text is the field's own character count and maxlength |
| Fixed interface copy | A text node, an enclosing element's whole text, or an attribute reads the entry's text, character for character |

The same file holds the reviewed `unreadable` list (decision 3): each entry has an id, the kind of element (`canvas`, `img`, `video`, `embed`, `object`, `svg-image`, `input-image`, `css-image`, `svg-graphic`), a reason saying why its pixels hold no number, and a source. An entry for an element that loads a file (every kind but `canvas`, `css-image` and `svg-graphic`) also names that file: `src`, a pattern anchored with `$` that the path of the element's URL must match, so a marker cannot carry another image through the entry. The owner reviews each entry through the build log, as for the allowlist. It holds one entry at phase 0:

| Id | Element | Why its pixels hold no number | Source |
|---|---|---|---|
| `brand-logo` | `img`, file path matching `(?:^\|/)logo-white(?:-[A-Za-z0-9_-]+)?\.svg$` (the file, or its build output `assets/logo-white-<hash>.svg`) | The SOVITECH logo from `packages/ui/src/brand/logo-white.svg`: the letters SOVITECH CONTROL, a fingerprint and a building, drawn as paths, with no text element and no number | Prompt 3 section 6 ("Brand assets"); `packages/ui/src/brand/README.md`; both logo files rendered and looked at on 2026-09-25 |

The brand work of phase 0 put the logo on the placeholder page, so the entry was added then, not in a later phase. The model viewer's canvas, and a drawing such as step 2's 64 px upload icon, are added by the phase that builds them. ### 6. Timing, count-ups and animation (G2-8)

- The harness is injected before the page's own scripts and records every value element from document start: on each DOM mutation, each animation frame and every 100 ms, it notes the element's value id and what it shows and announces, or nothing while it is hidden or removed.
- **A value id fails when one text holding a number stopped being shown while that id showed a different text holding a number.** That catches a count-up in place, a count-up that swaps elements, a flip-book of hidden elements, and an announced value (`aria-valuenow`) that counts. It lets through a pending value that later shows its one number, and one value shown in two forms that both stay.
- **No value animates** (prompt 3 section 11): any running CSS animation, CSS transition or script animation on a value element, or inside one, while it shows a number fails. That catches an odometer roll and a CSS counter, and also a fade-in. This goes beyond G2-8's situation (a count-up) and follows the prompt's own tie of "no value animates" to G2-8. A hover style that transitions a value element fails too, now that hover is forced.
- An unbound number shown at any moment after DOMContentLoaded and gone by the end fails G2-1 (`transient-digit`). A value element whose numbers differ from its display object while it changes is left to the G2-8 timeline; the snapshot reports what stays.
- **When the check reads** (round 2; the late count-up probe, 2.5 s after load, passed the earlier 1.5 s window):
  1. It waits until the page has loaded; the readiness marker `data-render-ready` is on `<body>` (required when the screen was served display objects: an app screen that shows values sets it once it has rendered the data it asked for, and a screen that never sets it fails, `not-ready`); no network request is in flight; no `setTimeout` the page scheduled is due within the budget (the harness wraps `setTimeout` from document start, so a count-up started from a delayed timer is waited for); at least the minimum window (1.5 s) has passed since the last of the call, the readiness marker and the last network response; and the value elements have been quiet for 500 ms. The budget is 10 s; a page unsettled then is read as it is, with a note.
  2. It scrolls the document and every scroll container through their extent, so values that animate when scrolled into view do so while observed, and waits again.
  3. It forces hover and focus (decision 3), and waits again.
- The harness is timing-based. What starts later than every wait (an animation gated on a clock read inside an animation-frame loop, long after the readiness marker and every timer) is still outside it, and is reported as a known gap.

### 7. Where it runs

- `tests/guardrails/G2-1.test.ts` and `G2-8.test.ts` are the indexed case files. They are Vitest files that drive the Playwright-based checker through Playwright's library API (`chromium.launch()`), on the harness pages in `tests/e2e/pages/` loaded from `file://` URLs, each with the display objects it declares: 45 G2-1 pages, 11 G2-8 pages and one clean page. Each bad page must fail with exactly its expected violation kinds, and with the stated count where it holds several faults of one kind; the clean page must pass. G2-1 also proves that a display object left out of the clean page's set fails, that a check without display objects, with a malformed id or with a function is refused, that typed display objects are refused off the harness pages, and that a screen entry without `displayObjectsFromApi()` or `{}` is refused.
- `tools/checks/render/rendered-copy.test.ts` (Vitest, unit project) runs the five reserved-term pages in `tests/e2e/pages/reserved-terms/` and the clean page in Chromium, and proves the marker rules without a browser (decision 8). Their indexed cases, G10-1 and G11-6, have no case file yet.
- `tools/checks/render/api-display-objects.test.ts` proves the registered adapter against a TEST server: a screen that shows what the API served passes; an id or a number the API did not serve fails; typed display objects on that screen are refused.
- The harness pages hold only visibly synthetic TEST values in a digit pattern (`TEST 1`, `TEST 12`, `TEST 123`, `TEST 1,234 m³/h`, `TEST 12,345 m²`), keeping each character class a page exercises (grouping commas, superscripts, Arabic-Indic digits, a vulgar fraction, a digit column). Prompt 3 section 5.4 forbids plausible-looking engineering data anywhere else, placeholders included. Step numbers, dates, the character counter and the reviewed fixed copy keep their own digits, which are interface, not engineering, values. The TEST evidence excerpts are synthetic.
- `tests/e2e/render/render.spec.ts` (Playwright project `render`, `pnpm test:render`, part of `pnpm check`) runs the render test on every screen listed in `tests/e2e/render/screens.ts`, served by the Playwright web server, each with the display objects it takes from the API. In phase 0 that is the placeholder page, which shows no value. It checks the screen list against `screens-schema.ts`, and fails when `playwright.config.ts` would reuse a server that is already listening: `webServer.reuseExistingServer` is `false`, so every run builds and serves the current code, and a port already taken stops the run with an error. It also runs canaries in that runner: a bare digit, a transient digit, an unknown value id, a served id around a card, number words, a step number outside the stepper, a misused stepper item, a canvas, an SVG drawing, a number shown only on hover, three count-ups (one late), two reserved-term pages and the clean page.
- **The Playwright run guard** (round 2, finding 6(d)): `playwright.config.ts` sets `forbidOnly: true` for every run, local or CI, and registers `tests/e2e/render/run-guard-reporter.ts`, which fails the run when a test is skipped (`test.skip`, `test.fixme`, or a skip while running) or marked to fail (`test.fail`), and when the render project ran but not one passing test per screen of `screens.ts`. Three seeds under `tools/checks/render/seeded/run-guard/` run in a render project under the repository's own config (its reporters and `forbidOnly`, with no web server and no browser); each run must fail.
- Every later phase adds each screen and state it builds to `screens.ts`, with `displayObjectsFromApi()`. An e2e flow that changes a value through an owner action calls `resetRenderCheck(page)` after the action, then `runRenderCheck(page)`.

### 8. Reserved terms on rendered pages (2.8; new in round 2)

- The in-page harness hands back every unit of shown copy: the text of each block of the page (a block's inline content joined, split where a block or a marked element breaks it, so a term split across inline elements is one phrase), each marked element's whole text, each shown attribute (the scanned attributes of decision 3, `alt`, `title`, `placeholder` and `aria-label` included, and the value of button inputs), and each `::before` and `::after` string. `tests/e2e/render/rendered-copy.ts` matches each unit with the one matcher, imported from `@sovitech/registry/reserved-terms` through the package's exports (`scanCopy`, `createAllowanceSet`, `registeredAllowances`). A unit holding a reserved term where 2.8 does not allow it fails (`reserved-term`, rule 2.8).
- 2.8's allowed places are honoured only through markers the app sets on the element that holds the whole text, `data-copy-kind`:
  - `badge`, `status-line`, `action-label`, `registry-qualifier`, `generated-sentence`: the unit passes only when a registered allowance of that same kind covers the whole unit. A marker cannot borrow another kind's entry, and a marker alone allows nothing. None is registered at phase 0, so every marked unit with a reserved term fails until its phase registers the allowance with its registry entry.
  - `evidence-excerpt`, with `data-document-id` and `data-content-hash`: the unit is verbatim document text only when the display objects the screen was served declare that excerpt with that document id and content hash.
  - Unmarked copy and a marker naming no place of 2.8 are matched as plain copy.
- This reads what is shown, whatever the source: capitalised terms held as object keys and rendered through `Object.keys`, copy from tagged templates or `String.raw`, attribute values on custom components, JSON copy files. Those forms escaped the source scan (round 2 finding "The source scan skips copy in common forms"); the source-scan half of that finding belongs to `tools/checks/reserved-terms`.
- Not scanned: text inputs' and textareas' values, which are the owner's own text (rule 14: material, not app copy); comments; `<script>`, `<style>` and `<template>`.

## Consequences

- Phase 3's Value, Price, StatusLine and Badge components must put every number inside an element with `data-value-id` whose id and text come from a display object the API served, and show only what it declares; the view-model must serve `parts` for any piece a component renders apart. The Stepper must render one `<ol data-render-stepper="wizard-step-number">` of eight `<li>` items, each with its number marked `data-render-allow="wizard-step-number"` and its registered title, nothing else; the character counter must emit `data-render-allow` and `data-counter-for`; dates must render in `<time datetime>`; the app shell must set `data-render-ready` on `<body>` once a screen has rendered the data it asked for; badges, status lines, action labels, qualifier labels and generated sentences that carry a reserved term must be marked with `data-copy-kind` and registered as allowances; evidence excerpts must be marked with their document id and content hash and served in the display objects. Phase 3's API must serve display objects on one route for each screen and state, and point `DISPLAY_OBJECT_ROUTE` and `parseServedDisplayObjects` at it. A lint or grep that keeps `data-render-allow` inside the Stepper and the counter would add a second guard; it is not built yet.
- Icons and images: Lucide icons render as inline SVG paths at 24 px and pass. A larger drawing with no text, and any raster or `<img>`, needs a reviewed `unreadable` entry first; the brand logo has one (`brand-logo`).
- The web server is shared by the two Playwright projects, so `pnpm e2e` also builds and serves afresh and stops if port 4173 is taken.
- The strict readings cost build effort, not owner time: unit labels such as m² need a value element or reviewed copy; list markers and generated content cannot carry numbers; a value cannot fade in; hover transitions on value elements fail; number words outside a value element need rewording or binding. None of them adds a question, a gate or a blocked state.

## How to reverse

- **The harness mechanics** (Chromium through Playwright, the attribute names, the window lengths, the scroll and hover passes, the timer wrapper): change `tests/e2e/render/`, update the harness pages and the case files in the same change, and keep every bad page failing.
- **The reading in decision 2:** it stands until the approver rules on the clarification below. If proposal 7.2.30 is approved (D-54), add its three classes (record-tied digits, scale-tied ticks, page numbers inside a pagination role) to the scanner, each with a harness page that passes and one that fails ("page buttons pass; an unbound 512 fails"), as a new case; that is a loosening and waits for the approver's own words.
- **The strict readings** in decisions 1, 3, 4, 5, 6 and 8 (display objects compared with what each value element shows, display objects only from the API on app screens, pixels and SVG drawings failing unless reviewed, hidden content, hover and focus forced, number characters of every script and number words, generated content, the one registered stepper and its titles, the readiness marker, "no value animates", reserved terms on rendered pages with markers honoured only through registered allowances): relaxing any of them lets more digits or terms through, so it is a loosening under guardrails section 10 and needs the approver.
- **The web server:** setting `reuseExistingServer` back to `true` lets the render test pass against a server that is not the current build; the render spec fails if it is. To allow reuse again, first make the page serve the build id of the current build and have the render spec compare it.
- **The run guard:** `forbidOnly: true` and the reporter stay; removing either lets a held-out screen read as a pass, and the run-guard seeds fail the self-test.

## Phase 1 amendment (2026-09-25)

The two remainders of adversarial finding 10 (round 2) were built; both tighten the allowlist schema.

- **Unreadable entries confined to their component.** An entry for an element that loads no file (a canvas, a CSS image, an inline SVG drawing) must name the one component file that draws it (`component`, a path under `apps/` or `packages/`). The in-page harness cannot tell which source file drew an element, so the confinement is static: a source scan (`tools/checks/render/unreadable-markers.ts`, run by the render check) accepts a `data-render-unreadable` or `renderUnreadable` marker only as a literal entry id, and for a component-named entry only in that file; it fails a computed value, the DOM dataset form, an unknown id and a stale component. It flags any mention of the marker names in `apps/` and `packages/`, comments included, unless it is a literal entry id or a CSS selector. An entry for a file-loading element stays confined by its `src` pattern.
- **Fixed copy that reads as a quantity is refused.** An allowlist entry of fixed interface copy fails when a number stands next to a unit of guardrails rule 8 ("TEST 12 kW", "12kW", "34.500mp") or next to a word that names what a count counts, in English or Romanian ("TEST rooms 212", "12 camere"). An engineering value renders bound, never as fixed copy. "Max file size 500 MB" passes. The check is a heuristic over closed lists (rule 8's units with their ASCII and Romanian spellings; count nouns in both languages), and a unit test reads rule 8's table in `docs/guardrails.md` and fails when one of its units is unknown there.
- **Seeds.** The render self-test runs 51 seeded inputs (39 before): 7 new allowlist seeds (a canvas, a CSS image and a component outside app code without their component; four fixed-copy quantities) and the marker seeds under `tools/checks/render/seeded/markers/`.
- **Reserved terms on rendered pages.** Since phase 1 the registered allowances are 2.8's own texts ([ADR 0011](0011-verbatim-2-8-allowances.md)), so the harness page `tests/e2e/pages/reserved-terms/marked-without-allowance.html` now marks texts that are not 2.8's ("Verified by SOVITECH engineers" as a badge, "Formal quotation issued" as a status line), and `tools/checks/render/rendered-copy.test.ts` shows the 2.8 badge passing and a near miss failing with the registered allowances.
- **Phase 1 review (2026-09-25).** A marked badge, status line or generated sentence passes on a rendered page only when a display object the screen was served carries it among its `lines`, with its slots typed, and the stage 3 label only with its stored quotation record ([ADR 0011](0011-verbatim-2-8-allowances.md), decision 13; `ServedDisplay.quotationRecordId`). Two reserved-term harness pages were added for the new indexed cases: `reserved-terms/stage-3-label-without-record.html` (G10-9) and `reserved-terms/sentence-slot-with-words.html` (G3-11); each must fail with one reserved-term finding, and `tools/checks/render/rendered-copy.test.ts` runs them with the other reserved-term pages.

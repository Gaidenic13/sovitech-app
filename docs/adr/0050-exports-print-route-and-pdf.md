# 0050. Exports: the print route, its PDF printed with Playwright in the API, generated outputs and the Equipment CSV

- **Status:** Accepted: default, reversible
- **Date:** 2026-10-05

- **Prompt 3** phase 5: "a print route rendered to PDF with Playwright, with badges, ranges and sources inline, the appendix ..., the open items ('What we still need'), the demo line, and `logo.svg` on light pages. Every other export the PRD scopes ... carries the demo line ... shows Unknown as text, never as 0 or blank, and keeps each value's badge and source beside it, as columns in a tabular export (7.1-r25, rule 1). Only the exported proposal carries the appendix ... Every export passes the reserved-term scan." Exit: "The exported PDF passes the render test and the reserved-term scan on its print route." ## Decision

1. **The print route is a web page** (`/projects/:projectId/print/proposals/:snapshotId`): a light page on white paper outside the app's shell, reading `proposals.print` like any screen, so the render test, axe and the reserved-term scan check it as they check every screen (the phase's exit). It carries the cover (the project's bound name, "Preliminary proposal"; the logo only once proposal P-5-PRINT-LOGO-UNREADABLE is approved, decision 7), the proposal's sections with each badge on its figure's line and every range and source line inline, "What we still need" once, and the appendix (every value with its source line, its badge as its verification, and for calculated and estimated values the formula, version, assumptions and range; excerpts as stored, "[erased]" after erasure). On the demo project the demo line is a fixed element that the print layout repeats on every page, and on the cover. Print tokens are the brand's light values (white paper, the brand's dark green-black ink, green #1F6B4A as the accent on light, borders at the brand's 10-12% on light), in `tokens.css` under a print scope, marked as Brand values in their brand roles; AA contrast on white. The page sets `data-print-ready="true"` on the document element once its view has rendered, `"failed"` if it could not load.
2. **The API prints it** with `playwright-core` 1.63.0 (Apache-2.0; added to `apps/api`'s dependencies, pinned, already in the lockfile: no new download; it drives the Chromium build the e2e setup installed): one headless browser, launched on the first export and closed with the server; one print at a time; each print in a fresh context carrying only the requester's session cookie for the web origin (`SOVITECH_WEB_ORIGIN`, the API's config; the dev and e2e origins proxy `/api` to the API, ADR 0037), refusing every request off the web origin, waiting for the ready marker, printing A4 with backgrounds, then closed. A timeout or a failed page answers `503 export_unavailable`; the web says the PDF could not be prepared and the owner can try again (rule 7). No new secret, token or account is minted for printing.
3. **Exports are produced from stored records when they are downloaded; no export file is stored.** A proposal PDF is a generated output: `generated_outputs` (migration 0015) records its kind, its snapshot, who started it and when; Reports lists these records (R-119's "stored file" read as this record and the snapshot it prints, from which the same figures are printed every time). Each download prints the snapshot again, so: erasure reaches every later download ("[erased]"; rule 13; G13-12) and no copy of a document's text outlives its erasure in a stored file; a figure whose inputs changed carries "Out of date, recalculating" (US-REPORTS-02 AC5); a stale quotation record's "Superseded" shows (G10-2). The PDF's bytes are not promised identical across downloads (the generation date and every figure are; a reading listed for the owner with proposal 7.2.25).
4. **The Equipment export is a direct CSV download** (`exports.equipment`), not a generated output: the register as the page's filters narrow it, every row, UTF-8 with a header row; for each cell three columns (the shown text, its badge, its source line); a missing value as its missing wording ("Unknown"), never 0 or blank; the demo line as the file's first line on the demo project; the counts' "Not available yet" line where the page shows it; no count outside the engine. A cell whose text starts with `=`, `+`, `-`, `@`, a tab or a carriage return is written with a leading apostrophe, so a spreadsheet never runs it as a formula (CSV injection; the shown value is otherwise as served). Its fixed copy (column heads) is the view-model's server copy, checked by the reserved-term check. It is not listed on Reports: a register exported from current state has no stored record to print again, and storing its bytes would keep document-derived text past an erasure (rule 13).
5. **Every export passes the reserved-term scan** (corrected in part B, V-5): the print route through the render test's scan, and the downloaded PDFs' text in the e2e flows (g) and (h) (amended by the integrator, part A; flow (i) downloads the PDF without reading it) and the printed PDFs' text in the print cases G10-5 and G10-13; the Equipment CSV by its case G10-14, which scans the produced text of the demo's export and of another project's, and by the e2e flow (d), which downloads the seeded demo's CSV and scans it (part B). Both read the file after its optional byte order mark and match each cell with the one reserved-term list, 2.8's allowances applied by column as the header row names the columns: a badge column passes a registered badge label whole; every other cell outside the source columns (the shown text, the header row, the demo line, the count line) is matched as plain copy. A source column holds the source line, which quotes the cited document's name as uploaded: both set apart the cited files' names as verbatim source text and match the rest of the line, the app's own words, as plain copy (G10-14 with the names its case stored, `tests/guardrails/_support/csv.ts`; flow (d) with the fixture files' names, a superset of the demo's uploads, `tests/e2e/support/csv.ts`; aligned by the integrator in part B, where flow (d) had passed a source cell whole).
6. **No other export is built in phase 5**: the phasing plan (DB-11) is phase 6's; Export Scope is not built (R-122 "Until decided"); report templates, the generator and the viewer are not built (R-123 "Until decided").

7. **No logo on the print route until the approver accepts its review entry (found by the planner).** The render test cannot read an image's pixels; the logo on screens passes only through the reviewed `render.unreadable` entry `brand-logo`, whose `src` pattern covers `logo-white.svg` alone (tests/e2e/render/allowlist.ts; packages/ui/src/brand/Logo.tsx: "The light logo ... is for exports on white (phase 5) and is not reviewed for a screen"). Covering `logo.svg` widens an exception list the loosening check records by content hash, which section 10 counts as a loosening and prompt 3 section 13 stops ("widening the render allowlist beyond rule 2's categories"). So the print route and Reports' cover preview draw no logo, never a typeset wordmark in its place (OD-2), and the change is proposal P-5-PRINT-LOGO-UNREADABLE in the build log; once approved, `logo.svg` goes on the cover and the page header of every printed page, as app-alignment and prompt 3 phase 5 ask.

## Consequences

- One more runtime dependency in the API (playwright-core), and a headless Chromium process while the API serves exports (about 150-300 MB while printing). The machine already holds the browser; nothing is downloaded at run time.
- The PDF is exactly what the print route shows, so the render test of the print route is the PDF's check; the per-page demo line is checked on the PDF by its case (G10-13).

## How to reverse

Printing moves to the worker or to another renderer by replacing `apps/api/src/proposal/export.ts`; storing export bytes adds a file under `<projectId>/exports/` keyed by the output id and the cited documents' hashes, which the erasure job must then remove with any document it cites. The CSV becomes XLSX by changing its writer only.

## Built (the print builder, phase 5 part A, 2026-10-05)

- **The printer** (`apps/api/src/proposal/export.ts`): `createPdfPrinter({ timeoutMs, idleCloseMs? })` with the planner's `PdfPrinter` interface; `ExportUnavailable` (code `export_unavailable`) with a `reason` code (`request_invalid`, `not_signed_in`, `page_failed`, `timeout`, `browser_unavailable`, `printer_closed`), never document text. As decision 2, plus: the request's web origin must be an http(s) origin with nothing after it and both ids UUIDs (`request_invalid`); a request with no session cookie is refused before a page opens; a print page that leaves the print route (to sign-in) is refused at once (`not_signed_in`), not at the time limit; a print route answering an error status is `page_failed`. The context lays out at A4's width (794 × 1123 CSS pixels), blocks service workers and downloads, dismisses dialogs, refuses off-origin requests and WebSockets, waits for `document.fonts.ready`, and prints with `preferCSSPageSize`, no header or footer template (no page number: prompt 3 section 7), a tagged PDF and no outline. The browser runs the installed headless shell with a 256 MB JavaScript heap for its renderer and one renderer process, is launched on the first print and relaunched if it went away, closed after two idle minutes and on `close()`. Prints queue one at a time. Measurements: ADR 0041 item 7. The API builder wires it (`ApiServices.printer`, `webOrigin`; `exportFile` maps any refusal to 503 `export_unavailable`).
- **The print route** (`apps/web/src/proposal/ProposalPrintPage.tsx`, `apps/web/src/proposal/print/PrintDocument.tsx`, `print.css`; the kit's `PrintFrame` and `PrintValue` in `packages/ui/src/components/print.tsx`): while shown, the document element carries `data-print-page`, which switches the tokens to the print scope; `data-print-ready` is `"true"` once the view rendered, `"failed"` when it could not be loaded (and on an id that is not one), absent while loading. The loading and failed states carry the demo line on the demo project from the project list (rule 10; G10-12's reading), with "Try again" for a person on screen.
- **The demo line on every printed page** is the kit's `PrintFrame`: a layout table (`role="presentation"`) whose header row holds the one `DemoLine` element; the browser repeats a table's header row at the top of every page the table breaks onto. Tried in Chromium build 1243 before choosing: an element fixed at the page's bottom repeats but overlaps the content; one fixed in the page margin is missing from the first page; an `@page` margin box repeats but holds the words in CSS, outside the page's elements, where the render test and assistive technology cannot read them. The header row reserves its room on every page, is first in reading order, and is an element the render test reads. Forced breaks inside the frame's cell hold (the cover ends its page; the appendix starts one). The page is the named page `sov-proposal` (A4; margins 14, 16 and 16 mm), so no other screen's printing is changed.
- **The print scope** (`packages/ui/src/tokens.css`, `:root[data-print-page]`): only Brand values in their light roles (white paper; ink #0D2E2B for every text role, 14.56:1; green #1F6B4A as the accent on light, 6.44:1; borders #0D2E2B at 12%; the light primary button). axe under the WCAG 2.2 AA tags found no violation on the printed document in screen and print media (the print builder's run of 2026-10-05). On paper the title is untracked: at the brand's -0.05em the PDF's text lost the space between its words. Rows are stacked (the name, then the value across the page's width): in a two-column row a long range wrapped and its badge was read after the range's second line in the PDF's text, so 2.8's "same line" did not hold in the export.
- **What the document shows, as decided here**: the cover (no logo, decision 7); the headline (the investment output's Price and "Still reading"; the open items are not repeated there); investment, control points (with rule 11's interface points), energy, operating cost and payback, measures, scope and exclusions, life safety, the basis, drafted paragraphs (tokens as their values); on a new page the appendix: every value of the view's `appendix.values`, named as the proposal names it (an output by the catalogue, an indicator by its name, a scope decision by its system, an investment figure through the Price component with the stage the server serves in it, an input by its measure's label), with its source line, badge, method lines and excerpts printed in full, never behind a disclosure; then "What we still need", the open items once (rule 7 read with 2.8 "Prominence": the appendix lists the open items, and they appear once). A price that cannot be produced prints its "Not available yet" line at the body's size.
- **Not decided here, listed**: an investment output that has no figure is named by nothing but its section, because the stored proposal's contract serves its stage label only with a figure (G10-11's reading for the outputs list names investment outputs by their stage labels; a served label for them is the view-model's and the contract steward's); the logo (P-5-PRINT-LOGO-UNREADABLE).
- **Proofs**: `apps/api/src/proposal/export.test.ts` (14 tests: a multi-page PDF read back with pypdfium2, the session cookie only, no request off the origin, failure, sign-in, no session, invalid request, not found, timeout, one print at a time, closed); `apps/web/src/proposal/ProposalPrintPage.test.tsx` (19); G10-5 (the page and the PDF, a TEST print view); G10-13 (the whole chain over a TEST database: Generate, export, download, every page of the demo's PDF carrying the demo line, none on another project's); four render-test screens of the print route in `tests/e2e/render/screens.ts` (the demo, a new project with nothing answered, loading, the view failing), passed on the e2e stack on 2026-10-05.

## Amended (closing phase 5, after the final verification, 2026-10-07)

- **Decision 2, one print per session (the final verification's item 3, A-7's residual; `apps/api/src/proposal/export.ts`):** the bounded queue had no cap per requester, so one member holding three downloads at once (one printing, two waiting) made every other member's Download answer 503 at once, for up to three print times. The printer now holds at most one print per session, waiting or printing: a second request from the same session while its first waits or prints is refused at once with the existing reason `printer_busy` (the route's `503 export_unavailable`, the web's existing "could not be prepared" line with Try again; no new wording, rule 7). The session is the request's session cookie as sent; a request without one is refused before it takes a place in the queue (`not_signed_in`, as before, only sooner). The session is freed when its print is answered: printed, failed, timed out, or left because its requester went away. The page's Download already sends one request per press while one is on its way, so one page never meets the cap; two tabs, or the proposal and Reports at once, can. Proof: `export.test.ts` "A-7 · … the final verification, item 3: one print per session …" (one member's second and third refused at once while another member's print waits and prints; the session prints again once answered; a waiting print holds its session; a print that leaves the queue frees it), run under the e2e lock; the earlier queue tests now ask from sessions of their own, so the queue's own bound is still what they prove. Not changed, still logged for the hosting step: Chromium's own sandbox (part B, above).

# 0027. The evidence verifier and the one ingestion path

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-26; amended 2026-09-30 (the phase 2 review: decisions 8 to 10; its third fix round: decisions 11 to 13)

## Context

- **Guardrails v1.6, rule 1 "Enforced by":** five checks over every evidence entry (the document belongs to the project; the content hash matches; the locator exists; the excerpt occurs there after normalising whitespace and diacritics; for `document`, the value parses from the excerpt). **2.1:** code decides between `document` and `ai_inference`. **2.4:** `Evidence.locator` holds page, sheet, cell and bbox only. **Rule 3:** confidence is capped by code; unverifiable evidence caps it at low. **Rule 13, rule 14.**
- **G1-13** (an IFC locator is refused at run time, logged as `evidence_not_found`, and the field stays unknown), **G1-10** (the AI never derives quantities), **G2-2** (a value not written literally is an inference).
- **Prompt 3 section 6:** one verifier serves the extractor and the AI. **Section 10, phase 2:** the one ingestion path creates `document` and `ai_inference` candidates only after the verifier passes; the model id is persisted with every AI candidate (owner answer, 2026-09-25: `claude-opus-5-5`; build-readiness 3 item 6).
- **ADR 0004:** `verifyProposal` was declared as a stub with a pending harness; **ADR 0022:** the extraction contract's `parseEvidenceLocator` refuses IFC keys with the code `ifc_field`.

## Decision

1. **`verifyProposal`** (`packages/domain/src/evidence.ts`) is pure and takes a `ProposalContext` the caller builds from the store: the project's documents, the text at a locator, the field definitions, and optionally the contract's strict locator parser. It runs, in order:
   - rule 1's first check over every entry, then the proposal's shape against its field (a known field, a value of its kind, a listed choice, never a candidate on an owner's decision), each shape problem an `ai_output_rejected` event;
   - checks 2 to 5, each over every entry before the next. Check 3 applies a **floor of its own** before the contract's parser: any key outside `EVIDENCE_LOCATOR_KEYS`, any IFC-like key (`ifc`, `globalId`, `guid`, `stepId(s)`, `step`, `path`, any case), page and sheet together, a cell without a sheet, or a bbox without a page or out of order is refused. A refused locator gives `evidence_not_found` with the reason `locator_exists.<problem>` and no candidate. So G1-13 holds even when the caller passes no parser.
   - Check 5 decides the source: a value that parses from an excerpt through the rule 8 parser is `document`; otherwise it is `ai_inference`, and an inferred quantity is accepted only as a direct count (a count field, unit `count`, a whole number, no alternative readings), else `inferred_quantity_not_direct_count`.
   - Confidence: an inference keeps the proposal's confidence or `low`, capped at `low` by any unverifiable entry; a document value with alternative readings is `low`.
2. **Alternatives hold every reading**, the quantity included, as the store's CHECK requires (at least two entries). The AI's output schema lists only the other readings; the verifier normalises them (`everyReading`). Listed for the integrator: the schema and the store should say the same thing.
3. **The one ingestion path** (`apps/api/src/ingestion/proposals.ts`, `ingestProposals`) resolves the field and subject, calls `verifyProposal` with the store-backed context, writes the guardrail events of a rejection (codes and ids only), and inserts the candidate only when it is accepted. When the proposal came from the AI it records the model id in `candidate_ai_origins`, a guarded, append-only table whose writer must be the candidate's own author (migration 0010).
4. **The extractor's output adds no candidate while `ifc-values` is closed.** Its text parts (page, cell and sheet text, visible only), coverage, findings and the model record are stored; the sealed IFC section is opened only through `openIfcValues`, which reads the gate, and nothing from it is stored today. Each embedded instruction gives one finding and one `embedded_instruction` guardrail event, and changes no state (G14-3).
5. **The AI extraction step** (`apps/api/src/ingestion/ai-extraction.ts`) runs through `packages/ai`'s boundary and feeds the same path. Without `ANTHROPIC_API_KEY` it reports `not running` and stores nothing; no recording is written by hand.
6. **The harness probe:** a call with no proposal still reaches the ADR 0004 stub, so the harness self-tests keep a declared stub to count. Retiring it is a harness change for the integrator.
7. **JSON from the sandbox** is read with the `yaml` package restricted to its JSON schema, as `packages/ai` does, because `JSON.parse` is banned by lint (ADR 0007).
8. **Checks 4 and 5 read whole tokens** (amended 2026-09-30, the phase 2 review's adversarial findings on fragments, rule 8 at verification, word-presence choices, evidence padding and the confidence cap; `packages/domain/src/evidence.ts`):
   - Check 4 matches an excerpt only on token boundaries: a match may not start or end inside a word or a number token (digits joined by `.` or `,`, or thousands groups joined by a space; a minus sign belongs to its number). A locator that names a whole sheet is read one cell (one line of the stored sheet text) at a time, so an excerpt cannot join a label cell to a number of another row.
   - Check 5 reads only whole standalone number tokens of the located text inside the matched span, through the injected reader, and keeps only each token's own readings (its digits and sign; a number glued to a tag, "CTA-01", states no quantity). Every evidence entry of a `document` value must bear it (`value_in_excerpt`, or `text_not_written` for text); a text not written in every excerpt is refused, never re-sourced.
   - Code, not the proposer, sets: the alternatives (every reading of the matched token; two readings set confidence low), `approximate` (from rule 8's words just before the number), the qualifier (only from rule 8's own words in the excerpt: the area-basis abbreviations and phrases, the level words and regim letters; otherwise unknown; a stated basis the proposal or the field does not match is refused) and `original` (the matched token as the located text writes it). The proposer's `original` is never stored.
   - A choice is `document` only through a label-value pattern the registry registers (`ProposalContext.labelValue`; none is registered, so none today). A choice whose every mention in the evidence is governed by a negation is refused (`choice_negated`). An `ai_inference` is capped at medium unless a non-negated excerpt names the chosen option (the glossary tier waits for `dataset-glossary`).
   - An inferred quantity is a whole count of at least 1, named `direct_count` when its excerpts hold digits; the verdict carries the `inference` kind decided. The AI boundary does not pass the kind the model names (`toCandidateProposal`), so every inferred count cited to excerpts that hold digits is refused: a sum the model named a direct count would otherwise pass, since neither the validator nor the verifier can count the items at a place. Passing it is proposal P-2-INFERENCE-KIND (build log, phase 2). Storing the kind with the candidate is not built (see Consequences).
   - The rule 8 qualifier words sit in the domain (`RULE_8_QUALIFIER_WORDS`), outside the loosening snapshot; moving them to the registry is proposal P-2-QUALIFIER-WORDS-REGISTRY (build log, phase 2).
9. **The API's reader hands the whole token to the rule 8 parser** (2026-09-30; `apps/api/src/ingestion/quantities.ts`): thousands groups joined by a space and a minus sign that belongs to the number are read as one number, as the verifier's tokens are, so "1 500 kW" and "-15 °C" can be document values.
10. **What an AI run searched is recorded by code** (2026-09-30, the review's finding on `searchedCoverage`; `apps/api/src/ingestion/ai-extraction.ts`, `apps/api/src/documents/coverage.ts`): each completed run stores a search record (the fields asked, the parts sent, and per accepted "not found" answer the sent parts it named) as the extracted-text part `ai:searched:<run id>`, keyed by project and content hash and erased with the document's text. `searchedCoverage` is the intersection of what the extractor read (`readCoverage`, the upper bound) and what a completed run searched for the field; with no run nothing counts as searched (rule 12). A dedicated table is proposal P-2-AI-SEARCH-TABLE.
11. **The stored excerpt is verbatim** (2.4, `Evidence.excerpt`: "required, verbatim, original language, never translated"; the phase 2 review's integrator item "Stored excerpts"). Check 4 matches the proposer's excerpt after normalising whitespace and diacritics, so a proposer's copy without the page's diacritics matched and was stored as the document's words. The verifier now stores, for each entry, the slice of the located text at the place check 4 matched, as that text writes it: its diacritics (with a combining mark after the last letter kept with it), case, line breaks and spaces; for a sheet read as a whole, the slice of the one cell it matched. Where an entry matched at several places, the one stored is the one that bears the value (the first number token that bears a `document` quantity, the first place that names the chosen option, the first that holds a `document` text), else the first. The proposer's copy is never stored, as its `original` never was (decision 8). Rule 13 is unchanged: the excerpt is still the document's own text, keyed by project and content hash, and the erasure replaces it with "[erased]". G13-3's case file needs no change: its fixture's page writes "Regim de inaltime: 2S+P+2E" without diacritics, the excerpt it cites, and its Expected cell holds. Proofs: `packages/domain/src/evidence.test.ts` ("2.4: the stored excerpt is verbatim", with a property that the stored excerpt is a slice of the located text and reads as the proposer's after normalisation).
12. **An inference's cap must hold again from what is stored** (rule 3; 2.3; ADR 0016 decision 22; case G3-18). Derive re-caps an inference against the evidence that remains, reading each stored excerpt on its own (`excerptNamesChoice`). An excerpt read on its own never sees more negations than its located text shows, so an entry that reads as naming the option only because its excerpt leaves out the negation its page writes ("este un hotel" cited from "Cladirea nu este un hotel.") would read higher on its own than it is. The verifier therefore caps an inference at medium when any entry does so, even beside another entry that names the option. Before, such a proposal was stored high, and after the naming entry's document was deleted it would still have read high. This lowers a stored tier in that case only; it refuses nothing and adds no question, gate, confirmation, badge or status line. Proof: `evidence.test.ts` ("the cap holds again from what is stored") and the property in `packages/domain/src/confidence.test.ts`.
13. **No "direct count" named by a proposer reaches the verifier from the ingestion path** (rule 1: "Sums ... are never produced by the AI"; P-2-INFERENCE-KIND stays a proposal; the phase 2 verifier's closing check, latent). The domain verifier accepts an inferred count cited to excerpts that hold digits when the proposal names it `direct_count` (G1-21's control pins that there), and the AI boundary drops every kind (`toCandidateProposal`, pinned in `packages/ai/src/boundary.test.ts`), so it was unreachable only while no other caller of `ingestProposals` passed a kind. `proposalForVerifier` (`apps/api/src/ingestion/proposals.ts`) now removes that one name from an inferred quantity before the verifier sees it, so from any caller such a count is refused as the boundary makes it. Only that name is removed: a direct count on a `document` proposal or on a value that is not a quantity is still refused as malformed, and a count named another kind is still refused, so nothing the verifier refuses is let through (a property in `apps/api/src/ingestion/ingestion.test.ts`). Applying P-2-INFERENCE-KIND means removing this function together with the boundary's drop, with the verifier check that proposal names.

## Consequences

- The verifier is the one gate for every candidate; nothing else in the API calls `insertCandidate`.
- A bbox-only locator names no stored text part, so its excerpt cannot be checked and the entry fails check 3 (listed as a limit: region evidence waits for a text part per region).
- The IFC value path behind the gate (ifc-input 6.2.1) is built behind the closed gates with its own verifier and store (ADR 0033); this verifier's 2.4 path still refuses every IFC locator (G1-13).
- The model's inference kind is neither passed to the verifier (P-2-INFERENCE-KIND; decision 13 keeps a named direct count from any caller) nor stored with the candidate (a column or `candidate_ai_origins` would hold it; "Next" in the build log).
- Stored excerpts are the located text as written (decision 11), so an excerpt shows the page's own diacritics, and a proposal whose excerpt differs from the page only by normalisation is stored with the page's words.

## How to reverse

- **A looser locator floor** (for example accepting IFC locators once 2.4 changes) is a guardrail change and a loosening; it needs the approver, and G1-13 names it.
- **Moving the verifier** into the extractor: the context is plain data, so the function moves unchanged.

# 0029. The demo seed: where it lives, what it writes, and how it reads "fixture sources only" for owner input

- **Status:** Accepted: default, reversible. Two readings in it are recorded for the owner (decisions 4 and 7).
- **Date:** 2026-09-26

## Context

- **Prompt 3 section 10, phase 2, "The demo seed":** "It creates the flagged demo project and pushes the fixture documents through the same pipeline. It may replay structured outputs from `fixtures/ai-recordings/` through the same validator and verifier; a replay never skips verification. A recording comes only from a real model run on a fixture, stored with the model id and date the API returned. Never write a recording by hand or label hand-written output with a model id. Without an API key there are no recordings: the demo has no AI-proposed values, and the phase report says so."
- **Prompt 3 section 7, "The demo is labelled and sourced":** the demo project is flagged `demo`; "Demo values come from fixture documents through the same pipeline, and are never verified (rule 10). The demo's owner answers (the four required fields, and steps 4 to 7) are `user` candidates that the seed writes from a committed fixture file, under a seed user labelled as demo input. List them in the build log, and tell the owner that rule 10's 'fixture sources only' is read this way for owner input."
- **Prompt 3 section 5.4:** "The API server and the demo seed refuse to start while any gate fails this check." Phase 0's "Next": "Call `assertGatesStartupSafe()` from the demo seed."
- **Guardrails v1.6:** rule 10, "Demo data" ("Labelled everywhere", "Fixture sources only. Demo values cite fixture documents that exist in the repo", "Never verified"); rule 13 ("The repo"; "Isolation"); rule 1; rule 3 ("Choices belong to the owner"; "A suggestion left in place counts as the owner's answer"); rule 7 (the four required fields); 2.1 (`user`: "The owner's or engineer's own action"; "The owner's own entry on a field whose `confirmBy` is `owner` or `either` gets a `user_confirmed` event when it is created").
- **PRD:** R-137 (the demo project), R-044 (the demo line; "every demo value's source line cites a synthetic fixture document in the repo"), R-026 (the demo's IFC models are synthetic fixtures, "Not analysed"); US-ADMIN-15, US-DOCS-23; F-INGEST-09. Open: who sees the demo (D-13), the demo floor structure and the `demo` profile of the IFC fixture (D-18; dashboards 8.4, build-readiness decision 7). OD-5: the demo is "Demo Hotel Bucharest", never the real hotel's name.
- **The store** (phase 1, ADR 0013, ADR 0015 decision 4): an account of kind `seed` creates only demo projects, and a demo project only by it; it acts as the owner only on a demo project (0006, `request_user_acts_as`); it never adds a member (0006, `add_project_member`: the operator's login adds a job's account).
- **Owner decisions of 2026-09-25 and 2026-09-26:** uploads accept fixture hashes only (ADR 0028); IFC data is read with web-ifc and IfcTester is not used, so the IDS model check waits (D-36); no `ANTHROPIC_API_KEY` is set.

## Decision

1. **Where it lives.** `apps/api/src/seed/` (`demo-seed.ts`, `owner-answers.ts`, `cli.ts`), run as `pnpm --filter @sovitech/api seed:demo [--no-analysis]`, not `packages/db/seeds/`: "the same pipeline" is the API's own upload service, analysis worker and documents service, which live in `apps/api`, and a package never imports an app (dependency-cruiser, `packages-do-not-import-apps`). `apps/` is read by lint:deps, the lint bans, the reserved-term check and the mockup-figure check (`tools/checks/scan-roots/roots.json`). Its tests: `apps/api/src/seed/owner-answers.test.ts` (no database) and `tests/api/demo-seed.test.ts` (a TEST database, the TEST data folder, and the real extractor in its sandbox when the image is present).
2. **Gates.** The CLI calls `assertGatesStartupSafe()` before it opens anything; `seedDemo` refuses any other gate source (`isStartupCheckedSource`), as `buildServer` does. Every gate is closed, and nothing in the seed reads or opens one except the worker's reading of `ifc-values` (closed: the IFC request asks for no values).
3. **Accounts.** On the operator's login: the demo seed account, kind `seed`, named "Demo seed (demo input, not a person)", created once and granted `owner` (audited); the extraction service account made a member of the demo project. On the app's login: the seed account creates the project, which the store flags demo because the seed made it.
4. **Owner answers, and the reading of rule 10 for them (for the owner).** The committed file `fixtures/demo/owner-answers.json` (generator `fixtures/demo/generate.ts`, listed in `fixtures/manifest.json`) holds the answers of steps 1, 4, 5, 6 and 7. The seed reads it as data and checks every answer against the production registry before writing anything: a field some step 1, 4, 5, 6 or 7 question asks; `confirmBy` owner (so never an engineer's field: no area, count, rating or protocol, and no figure); a choice among the field's options or one trimmed text; each field once; all four step 1 fields; every option of the step 4, 6 and 7 multi-selects; the working name "Demo Hotel Bucharest" (OD-5); an ISO 3166-1 country code. Each answer becomes a `user` candidate in the seed account's name, with a `user_confirmed` event in the owner's role and the reason `demo_input` (2.1). No `accepted_suggestion` event: the seed renders no screen, so nothing was suggested (rule 3). **Reading:** rule 10's "Fixture sources only. Demo values cite fixture documents that exist in the repo" has no document to cite for an owner answer (a `user` value carries no evidence, 2.1); it is read, as prompt 3 section 7 directs, as "the demo's owner answers come only from a committed fixture file, `fixtures/demo/owner-answers.json`, written by a seed account labelled as demo input".
5. **The answers written** (also listed in the build log):
   - Step 1: `project.name` "Demo Hotel Bucharest"; `project.type` renovation; `project.country` RO; `project.city` "Bucharest".
   - Step 4: `project.scope.*`: hvac, lighting, energy and access_control include; fire_safety, water, elevators and cctv exclude (Fire Safety stays opt-in, rule 11; its fire-alarm input and fire-mode status stay in the point list whatever the choice, G11-3).
   - Step 5: `building.type` hotel; `project.occupancy` mostly_occupied; `project.operatingSchedule` 24_7.
   - Step 6: `project.goal.*`: reduce_energy, occupant_comfort and reduce_operating_costs selected; lower_carbon, operational_efficiency, compliance and asset_lifespan not selected.
   - Step 7: `project.automation.*`: hvac, lighting and energy_management selected; water_management, security_access and predictive_maintenance not selected.
   They follow the approved step 8 summary's kinds of answer, made consistent where the mockups contradict themselves (onboarding-spec 6.1: the project type differs between step 1 and step 8; Energy Management is left unchecked although Energy is in scope). They are choices, not figures; none comes from `company/`.
6. **Documents, through the upload protocol.** `DEMO_DOCUMENTS`: the six PDF and two XLSX companions and two IFC models (ARH and MEP rev A) of the `test` profile (prompt 3 5.2, "Demo building"). MEP rev B and the IFC2X3 copy are left out: they are variants of rev A for the revision and schema cases (G4-13, G4-14, IFC-11, IFC-13), not more documents of the building; ground truth, IDS and expected-result files are no one's upload. Each file is hashed and checked against the owner's fixtures-only guard before anything is written (a drifted fixture writes nothing), then goes through `createUpload`, `appendUpload` in chunks and `completeUpload` in the seed's own request, where the same guard runs again, the file is stored under `<projectId>/<contentHash>/` and registered, and its analysis is queued (ADR 0019, 0025, 0026, 0028). Order: the step 1 answers, the documents, then steps 4 to 7, as an owner gives them.
7. **Analysis, and why the demo has no AI-proposed value (for the owner).** With a sandbox runner (the default of the CLI), the seed runs the analysis worker's own step (`AnalysisWorker.drain`, two attempts, no retry delay) with the Docker runner of ADR 0018 and no step after it. The draft IDS is not mounted: the IDS model check waits (owner decision 2026-09-26; D-36). The extractor stores the PDF and XLSX documents' text, coverage and findings; it maps no text to a field. **The two models are not read at all** (amended in the phase 2 review, the orchestrator's ruling on PRD R-023 and R-024 "Until decided": "Not built: no model is read"; ADR 0025 decision 4): their uploads queue no reader job, so the demo holds no engineer's model record and no finding from either model, and IFC values would wait behind `ifc-values` anyway. The IFC reader stays built and proven in tests until the owner decides D-01. PDF and XLSX values come only from the AI through the verifier, and the seed never calls the model: it may only replay recordings from `fixtures/ai-recordings/`. None exists, so the demo has no AI-proposed value, and the seed reports that; if recordings appear before a replay is built, it reports them as not replayed and replays nothing (fail closed). `--no-analysis` leaves the jobs queued for `pnpm --filter @sovitech/api worker`. The worker's claim is not project-scoped, so in a database with other queued jobs the seed runs those too, as the worker would.
8. **Once per database.** A second run finds the demo project the seed account made (the operator's login reads the audit events) and reports it, writing nothing. The store is append-only, so a fresh demo needs a fresh database.

## What the demo shows while every gate and dataset gate is closed and no key exists

- The project, flagged demo, named "Demo Hotel Bucharest" through its `project.name` answer.
- The 28 owner answers above, each the field's active value, "Provided by you" once phase 3 renders them, not provisional.
- Ten documents with their 2.8 status lines: the memoriu, the area table, the equipment list, the plan, the designer's note and both workbooks analysed in full; the specification "Partly analysed (37 of 40 pages)"; both models "Not analysed: IFC model stored, not analysed", and not read (until the owner decides D-01, no model is read: PRD R-023, R-024). The engineer's view holds the rule 14 findings of the PDFs (the embedded instruction in the note, the white text on the plan); it holds no model record and no model finding (the instruction and the switched-off layer in the MEP model are found only where models are read: the reader's tests and `tests/api/ifc-reader-gate-closed.test.ts`).
- No value from any document: every building fact (area, floors, rooms, zones, equipment, ratings) reads Unknown, and every output that needs one reads "Not available yet", naming what is missing. No estimate or price: the dataset gates are closed. No `engineer_verified` anywhere (the store refuses it on a demo project).

## Consequences

- Nobody but the seed account and the extraction service account is a member; who sees the demo is D-13, for phase 3 (a person holding a SOVITECH review role already reads it, as any project).
- Once a key exists and recordings are made, a replay path is needed: recordings through the output validator, the verifier and the one ingestion path, with the model id and date the API returned. It must also revisit the step 5 answers: a field the replayed documents then fill (the building type, if a document states it) would no longer be asked on step 5 (rule 5; the Speed Rule example), so the seed's answer on it would stand for a question for a known field, which GS-1 forbids. Today no document value exists, so step 5 asks it and the answer is the owner's.
- If the owner reads rule 10 more strictly for owner input (only document-cited values in the demo), the step 1 and step 4 to 7 answers go, and the demo's step 1 cannot exist (rule 7 needs the four fields).

## How to reverse

- Move the module elsewhere in `apps/api`; the entry is `seedDemo(deps)`.
- Change the answers in `fixtures/demo/generate.ts`, regenerate, and record the new hash in `fixtures/manifest.json`; the checks in `owner-answers.ts` still apply.
- Change `DEMO_DOCUMENTS` to add or drop fixtures (every one must be in the manifest).
- Build the replay of `fixtures/ai-recordings/` when recordings exist, through the same validator and verifier.

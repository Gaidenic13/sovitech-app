# 0036. The wizard API contract and the display objects

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-30

## Context

- **Guardrails rule 2, "Enforced by":** "UI code receives only resolved field objects, which carry the badge and the source line." Prompt 3 section 6: `apps/web` imports only `@sovitech/view-model/browser`, `@sovitech/ui` and `@sovitech/viewer`; "The API returns display objects only, so no candidate, event or bare engineering number reaches the browser". Section 7: every number in a 2.8 status line or a rule 7 count is bound to a value id derived from stored state; source and status lines render inside the value's element.
- **The render test** (ADR 0006; `tests/e2e/render/`) compares each value element with the display object the page received from the API: `{ text, lines?, parts?, evidence?, quotationRecordId? }` per value id. Phase 0 left `DISPLAY_OBJECT_ROUTE` and `parseServedDisplayObjects` for phase 3 to point at the real route and type.
- **dependency-cruiser** (`.dependency-cruiser.cjs`): browser-side code is `apps/web`, `packages/ui`, `packages/viewer` and `packages/view-model/src/browser(.ts|/)`; it may reach no server-side code (domain, registry, db, the view-model's other files). `apps/api` may import both view-model entries.
- **Phase 3 builds in parallel** (build log, phase 3 plan): API, view-model, UI components, web pages and e2e builders work at once, so they need one written contract.
- Sources: PRD R-001 to R-004, R-013, R-043 to R-047, R-051, R-133, R-136; F-VALUE-10, F-RENDER-01 to F-RENDER-06, F-QUESTION-01 to F-QUESTION-10; PRD D-32 (frontend), D-06 (the look of undesigned states).

## Decision

1. **Where it lives.** The contract is TypeScript with zod schemas under `packages/view-model/src/browser/contract/` (display.ts, common.ts, auth.ts, projects.ts, steps.ts, actions.ts, late-findings.ts, uploads.ts, routes.ts), exported by `@sovitech/view-model/browser`. It imports only zod, so it is browser-side code under the existing rules; no rule of `.dependency-cruiser.cjs` changes. The API validates its answers against the response schemas and the web parses every 2xx body with them.
2. **Display objects.** One type, `DisplayObject` (display.ts): a value id; `kind` `field` (a registry field's value or one fact of it), `record` (a document's file name, coverage, stage, revision; an upload's file name) or `line` (a standalone line or count holding a number); `text` (never empty, never a zero or dash standing for a missing value); `parts`; `shape` (`value`, `range`, `missing`) with `missing` (unknown, not provided yet, reading documents, not found in documents, not available yet, not applicable); one `badge` (id and label, from the registry); `measure` (label, unit, qualifier label: rule 8); `sourceLine`; `lines` (status and rule lines of the value); `evidence` excerpts; `actions` (edit, confirm, acknowledge, concern, resolve conflict, add, skip); `field`; `quotationRecordId` (never in phase 3). Every screen response carries `displayObjects`; views name values by value id only.
3. **The render projection.** `servedDisplayOf(display)` is the one projection onto what a value element may show (text; badge label when it differs; source line; status and rule lines; a confirmation's wording; an "Add" action's label; parts; evidence). The Value and StatusLine components render nothing with a number outside it, and the render harness reads served responses through it: `tests/e2e/render/api-display-objects.ts` intercepts the requests `isDisplayObjectRequest(method, path)` names (routes marked `servesDisplayObjects`), parses the body with the contract's schema and projects each object. A 2xx response of such a route without valid `displayObjects` fails the check; non-2xx responses are not read (the web renders no value from them).
4. **Value ids.** `<subject kind>:<subject id>.<field key without its subject prefix>[.<qualifier>]` for fields; `document:<id>.fileName|coverage|stage|revision`; `upload:<id>.fileName`; `project:<id>.documents.count`, `.documents.stillReading`, `.openItems.owner`, `.openItems.ownerMore`, `.openItems.engineer.<group>`, `.confirmations.count`, `.lateFindings.notice`, `.outputs.<output>`; `document:<id>.revisionNotice`; `building:<id>.detection.<system>`. Every path segment starts with a letter. The pattern equals the render contract's `VALUE_ID_PATTERN`.
5. **Copy.** Badge labels, 2.8 status lines, stage labels, the demo line and generated sentences come from the registry (`packages/registry/src/copy/`), and the rule lines the guardrails write word for word for the wizard (rules 4, 5, 7, 12, section 4) from its new `rule-lines.ts`; the view-model fills their slots and serves them. Fixed interface copy lives in the one UI catalogue, `apps/web/src/copy/en.json`, registered with the reserved-term check (`tools/checks/reserved-terms/catalogues.ts`). No string of the registries is repeated in the catalogue.
6. **Routes.** `ROUTES` in routes.ts lists every route with method, path, session, CSRF, schemas, refusal codes, whether it serves display objects, and the ids it serves. The phase 2 upload routes are listed unchanged. Refusals common to every route (401 `not_signed_in`, 403 `csrf_invalid`, 404 `not_found`, 400 `request_invalid`, 403 store refusal codes, 500 `internal_error`) are stated once. The API builder adds a unit test that Fastify's registered routes equal `ROUTES`.
7. **The server side** (`@sovitech/view-model/server`): the formatting module (`src/formatting/`, the ESLint rounding and coercion home), the resolver (`src/resolver/`) and the question engine (`src/intake/`), each with its signatures and rules written as doc comments for the view-model builder.
8. **Stepwise writes.** The owner's writes are the step's Continue (answers, the whole-question reading of multi-selects, visible suggestions, skips) and five field routes (edit, confirm, acknowledge, concern, resolve conflict, skip); each appends candidates and events through the store, never changes one (2.4).

9. **The API builder's decisions** (phase 3, B3):
   - **Listing a user's projects** is the store function `sovitech.request_user_projects()` (migration `0014_request_user_projects.admin.sql`): for the request's own user only, each project it is a member of, with its demo flag and creation time; a SECURITY DEFINER function of `sovitech_db_access`, registered as a guarded function, executable by the app's login only. Each project's values are then read in a request scoped to it, under row-level security. It is added under 0009's event trigger, never paused (`packages/db/src/migrate.test.ts`): the administrator's own default privilege drops PUBLIC's EXECUTE for the few commands that create, grant and hand over the function, and is put back in the same migration, so every command leaves every invariant true.
   - **One read per request.** `readProjectFieldInputs` (packages/db) reads every field of the project and its building at once; `readProjectState` (apps/api/src/wizard/project-state.ts) derives the 32 production fields with the one derive function and the production registry's lookups (no dataset approved: `datasetApproved` answers false; no calculated input derived before phase 5).
   - **The engine plans, the API appends.** Continue and the field writes call the question engine's planners (`planContinue` and `continueRecords`, `planConfirmation`, `planAcknowledge`, `planConcern`, `planConflictResolution`, `planSkip`; `parseOwnerAnswer` for an owner's value) and append their records in the owner's own request; an inline Edit's correction is the domain's `planOwnerCorrection`. The engine's refusals (`IntakeRefusal`) are answered with the status routes.ts names for each code (`apps/api/src/routes.ts`, INTAKE_STATUS).
   - **Defects are logged once per field**: `question_for_known_field` (from `questionsForKnownFields`) and `confirmation_budget_exceeded` (the budget's overflow), read back with `readGuardrailEvents` before a new one is written; `skipped` on every skip, `owner_corrected_inference` from each correction plan.
   - **Actions are the same on every screen** (G2-7): Edit on every field display; the confirmation while rule 5's test and budget show it; "Looks right" and "Something's wrong" on an engineer field's unanswered document or inferred value. A declined confirmation (left on Continue after its value arrived) takes no place in the budget.
   - **Additions to the contract** (the builder is its steward; each additive): the type `ContinueResponse`; `403 owner_only` among `projects.create`'s refusals; the value ids `project:<id>.outputs.equipmentCount` (step 3's HVAC assets row, "Not available yet" naming the missing taxonomy while `dataset-asset-taxonomy` is closed), `project:<id>.openItems.engineer.equipmentClassifications|siteSurvey|engineerValues` (the groups), and `project:<id>.confirmations.extractedFacts` (UD-45's count, apart from step 3's pill so one value id keeps one display).
   - **The development login** and its settings: ADR 0038 decisions 6 to 8.

10. **Amended 2026-10-01 (the integrator): the render adapter is built as decision 3 says.** `tests/e2e/render/api-display-objects.ts` intercepts every `/api/` request, lets through (`route.fallback()`) each one `isDisplayObjectRequest` does not name, and for a display-object request reads a 2xx body with `{ displayObjects: DisplayObjectSchema[] }` and projects each object with `servedDisplayOf`. One response may name a value id twice only with identical projections (one value id, one display: G2-7); two different displays for one id fail the check. Phase 0's placeholder route `/api/display-objects` is gone; `tools/checks/render/api-display-objects.test.ts` now proves the adapter against a TEST server on the step view route.

11. **Amended 2026-10-01 (phase 3 part B, the server fixes): additive contract changes**, each optional or a new export, so a client of decision 1's contract still parses every answer:
   - **The owner's text** (`common.ts`): `isBlankOwnerText` (text that shows nothing once white space, default-ignorable and format characters, U+180E, the Hangul fillers U+115F, U+1160, U+3164 and U+FFA0 and the Braille blank U+2800 are removed is empty: G7-9) and `holdsRefusedOwnerTextCharacter` (control characters, lone surrogates, and the bidirectional controls U+202A to U+202E and U+2066 to U+2069 are refused `answer_invalid`: G2-13). The API reads every owner text through them (project creation, Next on step 1, Edit, the question engine's `parseOwnerAnswer`), so the web may reuse them.
   - **`RefusalBody.fileName` and `RefusalBody.displayObjects`** (DR-10): a refused upload whose upload id exists (the fixtures-only guard's `not_a_fixture` at completion) names its file by the value id `upload:<id>.fileName`, whose display object the body carries; never in the message, never in the log. A format or size refused at creation has no upload id yet, so it names no file (no value id is invented).
   - **`FileRow.status` `{ kind: 'progress', line? }`** (DR-4): for a stored document being read (queued or analysing), the value id of its progress words, 2.8's pending wording "Reading documents…" (badge `reading_documents`), on `document:<id>.coverage` (the coverage line's own id, which the row carries only once the document is read). An upload still being sent has no line.
   - **`ReviewCard.skippedQuestions`** (V-6; G7-12): on step 8's systems, goals and automation cards, each skipped multi-select with rule 7's "You can provide this later." once; no option's display carries it (the resolver no longer puts it on a decision field). A multi-select card's rows are ordered chosen, then not chosen, then not provided.
   - **`OutputAvailability.label`** (G10-11): on the two investment outputs, the value id `project:<id>.outputs.<output>.label` of a `line` display object whose text and one `stage_label` line are 2.8's "Indicative range" (the benchmark output) or "Preliminary investment estimate" (the output from the project's data).
   - **Step 8's `proposal.stageLabel`** (US-INTAKE-16 AC2; G10-11): the value id `project:<id>.proposal.stage` of the stage the Proposal card names, derived from stored state (the view-model's `proposalStage`): "Indicative range" only where a first-estimate input is missing, the registry allows an Indicative range for it and its datasets are approved; otherwise "Preliminary investment estimate"; never "Formal quotation". `proposal.stage` stays null while no figure can be produced.
   - **`StepViewQuerySchema` with `add=<field key>`** (PRD R-012; G7-11), the `steps.view` route's `query`: on step 8, a first-estimate field with no eligible candidate has its inline ask served whatever its skip count (the owner asked for it: no skip limit, no `question_for_known_field`); any other key adds nothing; on another step the query is refused 400 `request_invalid`.
   - **`SkipRequest.step`** (G7-10): the step of the page that sent the skip. With it, a skip counts only where that step asks the question now (step 8: its inline ask, or the ask served on the owner's "Add"; steps 4 to 7: the question planned `ask` there), else 422 `answer_invalid`; a repeat (the fields already skipped since their last value) writes nothing and answers 200. Without it, the server reads the skip as the question's plan, step 8's inline ask or the owner's "Add" allows.
   - **`ProjectRow.projectType` and `ProjectRow.city`** (DR-22): the stored step 1 answers' display ids (`project:<id>.type`, `project:<id>.city`), resolved like the name; the rows are newest first by the store's creation time (`request_user_projects()` already returns it: no migration).
   - **Refusal codes in `ROUTES`**: `projects.create` 422 `answer_invalid` (G2-13); `steps.continue` and `fields.concern` 409 `shown_value_changed` (G4-36, G3-19); `fields.skip` 422 `answer_invalid` (G7-10); and the ids each route serves.
   - **Behaviour behind the same shapes:** an owner's answer (Edit, the step 8 inline ask, Next on step 1, a single-choice answer on Continue) must name in `corrects` every value the field shows now, unless it repeats the owner's own value, else 409 `shown_value_changed` and nothing is stored (G4-36); "Something's wrong" on an engineer_verified value is 409 `shown_value_changed` (G3-19); a quantity below zero of an area, volume or length is 422 `answer_invalid` (G8-22); a typed quantity is stored with its entry as written (`original`) and shown formatted (G8-23); a conflict line "Documents disagree on this. A SOVITECH engineer will check it." only when a value in the conflict is not a `user` entry (G4-36; proposal P-3B-CONFLICT-NO-DOCUMENT for the wording between two owner entries); Continue skips a confirmation only when the server shows it now (G7-10); each step view served is checked by `apps/api/src/wizard/defects.ts`, independent of the planner, and an ask for a field holding an eligible candidate logs `question_for_known_field` (reason `served_view`) once per field (G5-4).
12. **Amended 2026-10-01 (phase 3 part B, the integrator), two changes after the fixes were integrated:**
   - **`SkipRequest.step` is required** (not additive: a client that sends no step is refused 400 `request_invalid`). Every page of the web sends it (steps 4 to 7 their own number; step 8's Generate and "Generate without it" 8), so no skip reaches the API from no page, and a page-less skip of step 8's ask can no longer drop that ask (the residual the server fixer named under G7-10). The question engine's `planSkip` keeps its reading of a context with no step for unit use only.
   - **`Step4ViewSchema.subtitle` gains `no_documents`** (DR-25; US-SCOPE-01 AC10; rule 12): served when the project has no active document (the predicate step 3's intro uses), so step 4 never speaks of what documents say on a project with none; `none_named` stays for a project whose documents name no system, and `systems_named` waits for the detection fields (P-3-DETECTION-FIELDS). The web shows "No documents were uploaded, so no system was read from them." for it.
   - **`logPlanDefects`** (`apps/api/src/wizard/defects.ts`): the question engine's defects as planned (`question_for_known_field` with reason `question_engine`, `confirmation_budget_exceeded` with reason `budget`) are written there once per field, as before, so G5-3 runs the API's own logging over a TEST database (no contract change).
13. **Amended 2026-10-01 (phase 3, the fix round after part B's final verification; no contract shape changes):**
   - **The owner's writes of a project run one after the other.** `ownerState` (`apps/api/src/wizard/service.ts`), through which every owner write passes (Continue on steps 1 to 8, `fields/edit`, `confirm`, `acknowledge`, `concern`, `resolve-conflict`, `skip`), takes a transaction-level advisory lock keyed by the project (`lockProjectWrites`, `packages/db/src/scope.ts`, `sovitech.project_writes:<id>`) after `requireOwner` and before it reads the state, so a write sent together with another (two tabs, a double click) decides on the other's result, as a write sent alone does: a stale answer is refused `shown_value_changed` (G4-36, G4-38) and a repeated skip writes nothing (G7-10, G7-13). SERIALIZABLE was not used: the store's guards accept READ COMMITTED only (migrations 0008, 0009, 0011). `ensureBuildingSubject` takes the project's write lock before the building's own lock, so every request that takes both takes them in one order; advisory locks are re-entrant within a transaction, so an owner write that creates the building holds the write lock once.
   - **A repeated "Looks right" or "Something's wrong"** (amended 2026-10-02, phase 3, closing): `fields/acknowledge` on a candidate the requesting owner already acknowledged, and `fields/concern` on one they already rejected, answer 200 and append nothing (the planners read the stored candidate events under the same lock), as a repeated skip does; sent twice from a stale tab, one after the other or at once, each leaves one event. Another value, or the other action, is recorded as before.
   - **The served views' defect logging** (`logServedAsksForKnownFields`, `logPlanDefects`) takes the same lock before it reads the events it counts, and only when it has something to log, so views served together log a field once (G5-4, G5-3) and a view with nothing to log never waits.
   - **File names as served** (`servedFileName`, `apps/api/src/documents/file-names.ts`): every display object that names a file (`document:<id>.fileName`, `upload:<id>.fileName`, the refused upload's name, a source line, the revision notice, UD-45 and the proposal page) shows the stored name without its format characters (`\p{Cf}`) and bidirectional controls (`\p{Bidi_Control}`); a name with nothing left to show is no name (the resolver's missing wording). The stored name is kept and the upload accepted, so no new blocked state (G2-14). Not yet: the phase 2 raw route `GET /api/projects/:projectId/documents` (`servesDisplayObjects` false, not used by the phase 3 web) returns the stored name; phase 4's Documents view builds on `servedFileName`.
   - **Rule 4's routing line** ("Documents disagree on this. A SOVITECH engineer will check it.") is added by the resolver only when a candidate in the engineer-routed conflict has the source `document` or `ai_inference` (decision 11 said "not a `user` entry", which let a calculated or reference value carry it; none exists in phase 3). The owner-routed "Documents say <a>. You entered <b>. Which is right?" still reads every value that is not the owner's as the documents' (it cannot arise with a calculated or reference value before phase 5; the build log's "Next").
   - **`proposal.stageLabel`** stays served as decision 11 says (the stage the rules give for the investment figure), and the Proposal card names it only while the investment output carrying that stage is served as a range or `proposal.stage` is non-null; otherwise the card shows that output's "Not available yet" line (rule 7's `first_estimate` row, rule 10's stage 1; G10-11 as corrected). The doc comments of `Step8ViewSchema.proposal.stageLabel`, `proposalStage` and `proposalStageLabel` say so.
   - **Not refused, stated:** a skip that names step 8 is accepted whenever step 8 serves that ask now, worked out from stored state; the server keeps no record of the steps the owner visited (ADR 0039 decision 2; D-10), so it cannot tell a skip sent from step 8 before the owner reached it (an API call; no page sends one) from the owner's own "Generate without it". The ask returns through "Add <field>" (G7-11). Refusing it needs a stored visit record, which is D-10's decision (the build log's "Proposals").

## Consequences

- A change to what a screen shows is a change to a schema in one place, which both apps compile against; a response that drifts from it fails at the API's validation and at the web's parse.
- The render test and the components agree by construction on what a value element may show; the display object carries no field the render contract refuses, because the projection, not the object, is what the harness compares.
- The contract restates a few server constants (badge ids, accepted extensions, the size limit) for the browser; server-side tests keep them equal to their sources.

## How to reverse

Move the schemas into a new workspace package (for example `packages/api-contract`), add it to `WEB_ALLOWED` and `BROWSER_SIDE` in `.dependency-cruiser.cjs`, and re-export it from `@sovitech/view-model/browser`; nothing else changes. Replacing zod means rewriting the schemas with the same shapes.

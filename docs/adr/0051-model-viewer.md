## Decision

1. **One conversion per stored IFC model, for display only.** Every IFC document registered in a project (an upload's completion, Replace, or the demo seed, through the same path) queues one conversion of its bytes, keyed by project id and content hash. A second document of the same bytes in the same project reuses it; two projects that upload the same bytes get two conversions, and neither can load the other's file (G13-4). When the worker starts, it queues each current IFC model that has no conversion record, each whose conversion failed for a reason of the environment (`stale_image`, `sandbox_unavailable`, `output_unavailable`, `internal_error`), and each whose record reads "being prepared" with no conversion open (the one-open-job rule keeps it from queueing a second while one runs; the review's V-2 and A-5). Nothing is read from the model into any value, record or log beyond codes and counts; no candidate, finding or Documents line comes from a conversion, and Documents keeps "Not analysed: IFC model stored, not analysed" for a converted model (R-022, R-025; G1-30, G12-5, G14-5).
2. **The converter** is the spike's (`packages/viewer-spike/src/convert/`; the plan's move to a `packages/model-converter` package was not made in part 1: the production image builds from the spike package, and the API reads the converter's sources by path only, to hash them, so `viewer-spike-imported-by-nothing` is unchanged). Its view profile is ADR 0046 decision 6 with Finding 12's fix: shapes, GlobalIds and the spatial tree; no attribute but GlobalId; no property or quantity set, material, type or unit; the STEP header emptied; every item whose category is not an IFC class name deleted; a fixed model id; IFC2X3's electrical and equipment elements added; and, since the review (A-3), IfcAnnotation left out of the element classes, so lettering, dimensions or symbols modelled as an annotation's solid are not drawn (R-080: "no signage ... text is drawn"). Signage modelled as a building element's own shape (a proxy shaped as letters) is still drawn, and no check can tell it from a wall: P-V-CANVAS-UNREADABLE states that limit. It writes three files: `viewer.frag`, `storeys.json` and `summary.json` (codes, sizes, times and memory), and prints `model-converter: <code>` only. Exit statuses: 0 written, 2 arguments refused, 3 input refused, 4 conversion failed, 5 no geometry.
3. **The storey index is written at conversion and read by no page** (default, reversible). `storeys.json` holds the storeys in the order of their shapes' heights, each storey's GlobalId and its shaped elements' GlobalIds, and no name, elevation or count (ADR 0046 Finding 7: computed in the page it took minutes in software rendering). No page reads it while R-080 shows the whole model only; it is kept so that allowing storey stepping or an exploded mode later needs no reconversion (owner question 2 of the viewer step).
4. **The image** is `services/model-converter/Dockerfile` (moved from `services/viewer-spike/`), tagged `sovitech-model-converter:dev` (`SOVITECH_CONVERTER_IMAGE`), built by `services/model-converter/build.sh`. The build computes the SHA-256 of the converter's and plan cutter's sources, the package manifest and, since the review (V-7, A-8), what builds the image: its Dockerfile (base image, bundler and entrypoint flags), the lockfile and the workspace file it installs from. It refuses a mismatch with what it bundles, and records the hash as the label `org.sovitech.converter.source-hash`. Any change to the lockfile (any package's) therefore needs the image rebuilt, or every conversion fails with `stale_image` and the real-sandbox test fails where the image is built. Before each conversion the job compares the label with the same hash of the repository's sources and fails with `stale_image` on a difference, so an old converter never runs silently (the spike's image of 2026-10-02, from before Finding 12's fix, is refused this way). The setting is named `SOVITECH_CONVERTER_IMAGE`, not `..._MODEL_CONVERTER_...`: the API's guard against a model-reading switch refuses any setting matching `MODEL`, and that test is not loosened.
5. **The sandbox** is the extraction sandbox's confinement (`confinement`, defined in `apps/api/src/jobs/sandbox.ts` and used by `apps/api/src/jobs/model-view/sandbox.ts`): `--network none`, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--user 10001:10001`, `--pids-limit 256`, `--memory` equal to `--memory-swap` at 4g, `--cpus 2`, a 64 MB noexec `/tmp`, the stored file mounted read-only, one 512 MiB tmpfs output volume kept by a holder, a wall clock of 15 minutes. The three files are copied out by name through the Docker daemon (`copy-out.ts`, generalised to named entries with per-file bounds), and containers and volume are removed whatever happens. Both containers run the image the job inspected, by its digest, with `--pull never` (the review's A-7): a retag between the check and the run, or a missing tag, never runs another converter or a pulled one. The summary is read through the reviewed output reader (no new `JSON.parse`); the storey index is checked byte-wise to hold only its keys and GlobalIds (a GlobalId is kept as its author wrote it, so it can carry text in that alphabet, and no GlobalId is shown or logged while `ifc-values` is closed; A-9); the sizes must match the summary; anything else the container wrote is `output_refused`. Exit 2 reads as `stale_image`, 134 and 137 as `out_of_memory`, the wall clock as `timed_out`, a missing image or daemon as `sandbox_unavailable`. A copy-out that fails on the host's or the daemon's side (the job's folder gone, a file already there, a write error, no answer) is `output_unavailable` (A-4); view files the host cannot move into `derived/` are `output_unavailable` (a folder or file not there) or `internal_error` (any other error of the host), and so is any failure the job does not name (V-2, A-5, A-6). These four failures of the environment are retried after `retryAfterSeconds` (60 in `worker-main.ts`) while attempts are left (3), then recorded, and queued again at the worker's start. A folder an earlier run of the job left is cleared before the next run (A-4).
6. **The conversion record** is the append-only table `sovitech.model_view_events` (migration 0017): `queued`, `started`, `converted`, `failed` with a code (the model's own: `parse_failed`, `timed_out`, `out_of_memory`, `no_geometry`, `output_refused`; the environment's: `stale_image`, `sandbox_unavailable`, `output_unavailable`, `internal_error`) and `erased`. Each row holds the project, document and hash, the converter's name and source hash, the image digest, byte sizes and times, and no text. Row-level security on `project_id`; update, delete and truncate refused (G4-20); its writer guard `sovitech_guard.model_view_event_written` (SVX20) requires the request's own user, a stored IFC model, the project's service account for `started`, `converted` and `failed`, and nothing but `erased` after an erasure (SVE11, under the erasure lock taken shared). State is derived from the latest event. It is not a value (G1-30).
7. **A separate conversion queue** `sovitech_work.model_view_jobs` (ids and codes only, one open job per project and content hash, claimed with `SKIP LOCKED`), apart from the analysis queue of ADR 0026, and **one worker loop**: `worker-main.ts` runs one analysis step and one conversion step in turn, so only one sandbox runs at a time (the 4 GB container on the 8 GiB Colima VM) and neither queue waits on the other's backlog (default, reversible). An IFC upload makes the extraction service account a member of the project, because the job records its steps as that account; the account cannot add itself (SVR03), so the backfill does not reach an IFC-only project stored before this step until its next IFC upload.
8. **The locked write and erasure** (rule 13; ifc-input 6.2.16's stricter choice, D-89). The job checks under the project's write lock that a document still holds the bytes before recording `started`, runs the sandbox outside any transaction, then under the lock again checks the document, moves the files into `<root>/<projectId>/<sha256:…>/derived/` (never recreating the hash folder) and records `converted` in one transaction. `documents.delete` removes `derived/` with the hash folder when no other document of the project holds the bytes, drops the queued conversion, ends a running one (its job reads `failed` with `erased`), and records `erased`. Before recording or keeping anything, under the lock, the job checks that it still holds its job: a conversion finishing after an erasure stores and records nothing (the locked checks, and the store's SVE11 guard on its own), even when the same bytes were uploaded again meanwhile; that new document gets its own conversion, because the erasure freed the bytes' one open slot (the review's V-3 and A-1, where the erased run had recorded `output_refused` against the new document). The erased run's container still runs to its end, at most the 15-minute wall clock, reading its read-only mount of the erased file; its tmpfs output is removed with it and nothing of it is kept.
9. **Serving:** `GET /api/projects/:projectId/documents/:documentId/model-view` (`documents.modelView`; ADR 0044 as amended). It checks the session and membership under row-level security and answers only for a current, non-superseded IFC document of the project with a `converted` record: `application/octet-stream` with `Content-Length` and `X-Content-Type-Options: nosniff`. Every answer, refusals included, carries `Cache-Control: no-store`; anything else is 404, saying nothing of another project. The browser fetches it with `cache: 'no-store'` and keeps no IndexedDB or Cache Storage entry (default, reversible).
10. **The browser side, `packages/viewer`** (imported by `apps/web` only; in part 1 by no page):
    - **The graphics probe** (in the main bundle, a few lines; `probe.ts`) asks once per page for `webgl2` with `failIfMajorPerformanceCaveat`, reads the renderer's name (unmasked where offered) and treats SwiftShader, llvmpipe, softpipe, lavapipe, "Microsoft Basic Render Driver" or any name with "Software" as no hardware, then releases the context. It never measures a frame rate and has no override (owner decision: no slow view).
    - **The view is one lazily loaded chunk** (`React.lazy` over a literal `import()`), fetched only when the probe answers "hardware". On "none" the area reads its served "Not available yet" line and the chunk is never fetched.
    - **No `@thatopen/components`** (default, reversible): the view is built on `@thatopen/fragments` 3.4.7, `three` 0.186.1 and `camera-controls` 3.1.2 alone. Measured: the lazy chunk is 2,046,793 bytes, 430,359 gzipped (the spike's estimate for this trio was 683,413), against 1,080,282 with `@thatopen/components`, whose `SimpleRenderer` also draws That Open's logo (ADR 0046 Finding 2), so there is no vendor mark to remove.
    - **The Fragments worker comes from the app's own origin:** a static `?url` import of the package's minified worker (`worker.min.mjs`, 1,390,368 bytes, 278,189 gzipped), never `FragmentsModels.getWorker()`, which fetches from unpkg (ADR 0046 Finding 1). The import names the file path through the package's own `node_modules` link, because dependency-cruiser's resolver reads a query on a package export as part of the export's name (`"./worker?url" is not exported`); on a file path the edge stays visible. The bundler also emits Fragments' unminified worker (about 3.2 MB) as a fallback the library names with `new URL(...)`; it is never fetched (checked in `tests/proposed/model-view.test.ts`). No web-ifc WebAssembly is served; the browser never parses an IFC file.
    - **`no-computed-import` gains no Worker edges yet** (default, reversible): no code of ours constructs a Worker; Fragments constructs it inside `node_modules` from the URL passed in, and our edge to the worker file is a static import dependency-cruiser sees. The rule gains `new Worker(...)` and `new SharedWorker(...)` edges with the first app code that constructs one (phase 0's note).
    - **One canvas, a fresh one per engine** (default, reversible): each engine draws on a canvas created in the view's effect and is fully disposed (controls, the Fragments model and worker, geometry, `forceContextLoss`). A first design reused the canvas after its context was released, so React's double effect in development and any change of model reported "graphics" on a machine with hardware graphics. A lost context or a renderer that cannot start reports "graphics"; a failed or missing file reports "load".
    - **Token colours** (default, reversible): shapes are painted in `--sov-surface`, read from the CSS custom properties at run time as each material is made, never the model's colours, lit by a white ambient (2.5) and key light (6, three.js physical units). Only opaque tokens are usable: the translucent line tokens would need number parsing, which `no-number-coercion` bans. Fragments' grids, highlights and sections are never asked for; no raycaster, hover handler or picking of ours is installed.
    - **The first view and readiness:** a three-quarter view fitted to the bounding sphere (`fitToSphere`; `fitToBox` snaps to a face). The canvas stays hidden, with the loading line, until the whole model's tiles are in: Fragments drops an update asked for within its update interval (100 ms), so the engine waits out that interval and repeats until the model is no longer busy and has tiles (`settle.ts`). A model still busy after 600 tries (about a minute) is never shown in part: the view reports "load" and the area falls back to the stored model's line (default, reversible; the review's V-4, where the first build showed the view as it was after about 10 seconds; the minute is listed for part 2's design review).
    - **Keys and buttons:** the stage is one tab stop (`role="application"`, named by the document line through `aria-labelledby`, described by the visible key help); while it has focus the arrows turn and tilt, + and - zoom, W A S D pan, Home shows the whole model; Page Up and Page Down are not bound (R-080 wins over prompt 3 section 8's storey stepping); Ctrl, Alt and Meta combinations and Tab are left to the browser. A toolbar of seven icon buttons ("Turn left", "Turn right", "Tilt up", "Tilt down", "Zoom in", "Zoom out", "Show the whole model") is one tab stop with arrow keys, Home and End inside it, never disabled. Reduced motion makes moves instant; nothing moves by itself (G2-8).
    - **Audits for tests** (`@sovitech/viewer/testing`, counts only): sprites, points, textured materials (map slots and shader uniforms), text geometry, CSS2D and CSS3D objects; the stage holds one canvas and nothing else ("ifc-input 6.2.15 · no text in a view file or scene").
11. **The kit's model area** (`packages/ui/src/components/ModelArea.tsx`) gains the states `preparing`, `failed` (with its action), `no_graphics` and `viewable` beside `no_model` and `model_stored`. Its document line uses Documents' own display objects (the file name isolated in a `bdi`, Stage and Revision as served, the stored 2.8 line). Where the project has more than one current model, a chooser lists them by bound file name (prompt 3 5.2 "Several models": discipline cannot be used while a model's category reads Unknown, G1-26); choosing writes nothing (default, reversible). When the view says "graphics" the area shows the served no-graphics line; when it says "load" the area falls back to `model_stored`, keeping the document line and its stored 2.8 line (no new wording). Nothing is disabled, no dialog opens and focus is not moved (G7-23). A bare "Not available yet", or a state with no line, throws (G7-22). Step 3 moved onto this area with no visible change (pixel-identical at 515, 400 and 330 px in both of its present states).
12. **The draft copy is the owner's to approve** before part 2 mounts it: "Not available yet: hardware graphics support in this browser" (the plan's filler of rule 7's line), "View controls", the seven button names, the key help, "Loading the model view", and "Stage" and "Revision" as the document line's labels. The kit and the viewer take all copy as props; in part 1 it appears only in tests and harnesses. It holds no digit and no reserved term.

## Consequences

- **The owner sees no change on any screen in part 1.** The pipeline runs live (the demo's two models are converted at seed or worker start when the image is built), but no page mounts the view. The render test fails an unmarked canvas (`unreadable-pixels`), and the reviewed entry that would admit it is a loosening the approver decides (P-V-CANVAS-UNREADABLE; D-05 first). **The render test alone does not hold the mount** (corrected after the review's A-2): its headless Chromium renders with SwiftShader, so the probe answers "none", no canvas is ever made, and a mounted viewer would pass it. What holds the mount is a blocking test, `tools/checks/render/viewer-mount.test.ts`: no file of `apps/web` may import `@sovitech/viewer` while the render list holds no reviewed `model-view` entry naming `ModelView.tsx`. `tests/proposed/P-V-CANVAS-UNREADABLE.test.ts` shows the view failing today's render test only as unreadable pixels and passing with the proposed entry laid over the list and the marker set where the canvas is created.
- **Part 2 needs:** the approver's entry and snapshot; the marker set with a literal `setAttribute('data-render-unreadable', 'model-view')` in `ModelView.tsx`'s effect (the canvas is created there, not in JSX); the view-model's `modelArea` builder and the contract's model-area fields (ADR 0044); the mount on step 3 and System Scope; `viewer.css` imported by `apps/web`; catalogue keys for the draft copy; render screens for every state; the GPU measurements and the design review; third-party notices for the chunk (web-ifc's JavaScript, MPL-2.0, three, camera-controls and Fragments' dependencies; D-94).
- The e2e stack and `pnpm check`'s render step need the conversion image (`services/model-converter/build.sh`) beside the two analysis images (ADR 0037, amended).
- The chunk carries the string `unpkg.com` from `FragmentsModels.getWorker`, which is never called; no request left 127.0.0.1 in any run.
- A browser that hides its renderer's name and gives a software context without the performance caveat would draw slowly; an integrated GPU that passes the probe may still be slow on a large model (the office-laptop measurement is still missing, ADR 0046). Neither is masked by a frame-rate fallback.
- No GPU in CI: CI and the headless e2e runs see the no-graphics line only; the canvas path is proven in `tests/proposed/` (SwiftShader through an init-script patch, and the development machine's GPU Chromium).
- Rule 2 inside the canvas has no automated check beyond the converter's no-text test and the scene audits (ifc-input 6.2.15, D-46).

## How to reverse

- **Drop the viewer:** remove `packages/viewer`'s view and probe, the kit's four new states, and the `documents.modelView` route; the pipeline can stay or go independently.
- **Drop the pipeline:** stop queueing conversions in `apps/api/src/documents/service.ts` and the seed, remove `apps/api/src/jobs/model-view/` and its loop step in `worker-main.ts`, and leave migration 0017's tables (append-only records stay; a later migration may drop the queue). Erasure keeps removing `derived/` as it did before this step.
- **`@thatopen/components` instead of the trio:** swap the engine (`packages/viewer/src/model-view/engine.ts`) and remove the vendor logo as the spike did; the chunk grows by about 0.4 MB gzipped.
- **Storey index:** stop writing `storeys.json` in `cli.ts` and drop it from the copy-out names and the output check; nothing reads it.

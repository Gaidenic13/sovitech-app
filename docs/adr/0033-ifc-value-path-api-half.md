## Decision

1. **The IFC evidence locator is a domain type beside 2.4's, not a change to it** (packages/domain/src/ifc-evidence.ts). `IfcEvidenceLocator` holds the schema of the document's model record, the GlobalId, the STEP ids and the path (an attribute, a property or a quantity, on the occurrence or through its type object, or a relation). An `IfcEvidence` entry is a 2.4 `Evidence` whose 2.4 locator is empty (no page, sheet, cell or box) with the IFC locator beside it, and `check` always `text_match`. 2.4's `EvidenceLocator` is unchanged: the strict locator check (the domain's floor and the contract's schema) still refuses every IFC key on the 2.4 path (G1-13), and `insertCandidate` and `recordAssetAppearance` now refuse an IFC entry outright. Derive reads an entry's document and check only, so an IFC value takes part in rule 4, 2.3's revisions and deletion, and rule 13 like any other.
2. **The IFC verifier** (`verifyIfcEvidence`, checks 1 to 4; `verifyIfcProposal`, all five and the source). Check 1: the document is the project's. Check 2: the content hash is the stored revision's, and the schema the model record's. Check 3: the GlobalId is carried by a stored statement of that revision (its first attribute), each STEP id has a stored statement, and the path re-resolves (an occurrence attribute on the element's own statement; a type-object attribute on a type statement; a property or quantity statement of that name; a relation statement naming both elements). Check 4: the excerpt equals the stored statements after decoding STEP string escapes and normalising whitespace and diacritics (6.2.1). Check 5, for a direct read: the proposed value is the typed literal at the path's position in its statement (a single-value property's nominal value, a quantity's value, IfcRoot's Name and Description, IfcObject's ObjectType, an element's Tag or a spatial element's LongName, a storey's Elevation, a project's LongName and Phase, a type's ElementType, and PredefinedType as the last attribute); a number is read from the token through the rule 8 parser with the decimal point STEP fixes; a rating written as text (an IfcLabel) through the rule 8 parser, both readings of an ambiguous number kept, low. A direct read that fails check 5 is refused, never re-sourced as an inference. An interpretation (an IFC class, a glossary term, a relation read as a flag) is always `ai_inference`, capped at the table's confidence (low when none); a class of `IfcBuildingElementProxy` supports no type (6.2.9) and an inferred quantity is refused (rule 1).
3. **What the verifier reads is stored text, never the model file.** Opening an owner model is the sandbox's alone (prompt 3 section 8). So, with the gate open, the path first stores the statements the sandboxed reader quoted as the model's extracted text (`document_texts`, keyed by project id and content hash: `ifc:step:#<id>`, and `ifc:globalid:<GlobalId>` naming the statement that carries it), and verifies against those. The erasure deletes them with the rest of the document's text. Limitation: the unit a value declares is the reader's reading (its `IfcSIUnit` statement is not in the output), so it is not re-checked against text.
4. **Its own store** (migration 0013; packages/db/src/ifc-evidence.ts and ifc-reads.ts): `ifc_evidence` and `ifc_evidence_excerpts` (the entries of candidates and asset appearances), `ifc_elements` (which model element became which subject or appearance, and the storey or space containing it: ids and class names only) and `ifc_value_refusals` (the engineer's list of refused values: proposal, GlobalId, STEP ids, field and code, never text). Append-only for every role, project-scoped by row-level security, registered with the guards, rows only from the project's extraction service account in its own name and never for an erased document (0010's `ingestion_record_written`), an entry only for a document or inference candidate its writer wrote, and only with its excerpt. 0013 replaces three guard functions and changes nothing else in them: `candidate_has_evidence` and `appearance_has_evidence` count a (matched) IFC entry as evidence; `document_event_written`, which the erased event passes through inside `sovitech.erase_document` as the eraser, also erases the excerpts of IFC entries citing the document and withdraws the candidates whose IFC entries all cite removed documents (rule 13).
5. **The gate, in code.** Every writer of that store reads `ifc-values` through `readGate` first and throws `IfcValuesClosed` before it touches the request when it reads closed; the API path opens the sealed section through `openIfcValues` first and returns before it touches the store. The gate lives only in code (ADR 0005: gates are data in packages/registry/gates/, read through one function); the database holds no switch that could open it. The tables are left out of the store's shared Kysely type, so no other module writes them by a typed query.
6. **Subjects, assets and candidates from opened facts** (apps/api/src/ingestion/ifc-values.ts, called by `storeExtractionOutput` only when `openIfcValues` reads open): the project's building for the IfcBuilding; a level per storey and a zone per space or zone, per model, never matched across models (`ifc-identity`); with `ifc-identity` open, a model declared a revision of another keeps the other's subject for the same GlobalId (6.2.4, a declared revision chain only). An asset appearance per element an opened proposal names as equipment, joined to the asset of its tag only through an opened tag-source proposal (`ifc-identity`), the tag read from the verified statement; otherwise untagged, a possible duplicate, never counted (2.5; `ifc-untagged-count` and the engine for 6.2.5's count). A containing storey or space is kept in the element register, not as a candidate. Candidates: `document` for values written in the file, `ai_inference` for interpretations; nothing `calculated` (sums, counts and unit conversions are the engine's, phase 5; shapes are 6.2.7's, and no geometry is read: a geometry proposal is refused). Per mechanism, the contract's gates are read again. A declared unit maps only to the registry unit its SI name and prefix name exactly; any other (m³/s, J, absolute K, a derived or conversion-based unit) gives no quantity (`unit_unmapped` while `ifc-units` is closed, `unit_conversion_not_built` when open). A value that declares no unit (an IfcReal) gives no quantity (`unit_undeclared`). A quantity-set area carries its IFC basis only while `ifc-areas` is open and the field registers the basis (6.2.6). No candidate on the floor count comes from a model (prompt 3 section 8, "Storeys are not floors"). The project's own fields are the owner's (ifc-input 4.1 item 7). Hidden content gives nothing (rule 14; no release action exists, so `ifc-hidden-content` changes only the refusal's code). Every refusal is a guardrail event with codes and a row of the engineer's list.
7. **Mapping tables stay unapproved:** the API mounts none (6.2.10; `extractionRequestFor` sends `datasets: []`), so even with the gate open, the API's own request yields facts and no proposal. The proposed suite mounts a TEST table it writes.

## Consequences

- With every gate closed nothing of this path runs: no row in the four tables, no `ifc:` text part, no candidate or appearance from a model (proven by apps/api/src/ingestion/ifc-values.test.ts and packages/db/src/ifc-evidence.test.ts, blocking; and by tests/proposed/ifc-input-5.4-api.test.ts over a TEST database, non-blocking; and by the full-pipeline blocking test over a TEST database, tests/api/ifc-values-gate-closed.test.ts, placed by the integrator).
- tests/proposed/ifc-input-5.4-api.test.ts runs IFC-1 to IFC-11, IFC-13 and IFC-14 through this path; IFC-12 waits for the plan component (phase 4). What waits for the engine (IFC-2's cross-check and totals, IFC-3's "Incomplete", IFC-6's points, IFC-7's kW, IFC-8's conversion, IFC-10's count) is named in each title.
- CA-2.04 (the proxy whose `Tag` is an authoring id) has no asset, so its life-safety signal is refused and listed for the engineer, not stored: a tag source from `Name` is 6.2.4's and not built.
- **Not built here:** the streamed writer for large gated outputs (built since, in ADR 0034: the per-line section and the worker's line-by-line reading, returning the same sealed handle, so this path needed no change). The perf model's facts do not fit one JSON string; the writer (packages/ifc-reader/src/cli.ts), the contract's parser and seal (packages/extraction-contract) and the API's output reader (apps/api/src/jobs/read-output.ts) are other areas' files. This path consumes the sealed section through `openIfcValues`, so a streamed reader that returns the same sealed handle needs no change here. The per-element writes of this path are not batched either; the perf model's register (about 157,000 elements) is not measured.
- The erasure's audit record does not count IFC excerpts (its counts are `sovitech.erase_document`'s own).

## How to reverse

Delete apps/api/src/ingestion/ifc-values.ts and its call in `storeExtractionOutput`, packages/db/src/ifc-evidence.ts and ifc-reads.ts with their exports and the merge in reads.ts `evidenceFor`, packages/domain/src/ifc-evidence.ts with its export, and add an admin migration that restores 0009's three guard functions and drops the four tables (they hold no row while the gate is closed). The gates themselves are unchanged.

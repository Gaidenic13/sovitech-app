## Decision

1. **Which pages.** Built: Financial Overview (DB-02, R-088), CAPEX Breakdown (DB-13, R-089, an ordinary Metrics page: 5.2 "Configurator"), OPEX & Savings (DB-12, R-095 with D-27's "Until decided"), Payback Analysis (DB-21, R-096) and Lifecycle Analysis (DB-22, R-097), with R-087, R-090 to R-092, R-094 and the "Until decided" lines of R-098 to R-108. Not built: Phasing (DB-11; US-FIN-30, waiting on approval), Scenarios (DB-19; US-FIN-28, -29), the Metrics landing (UD-03; R-093 "Until decided"), UD-10, UD-11, UD-13, UD-23, UD-24, UD-25, UD-28, UD-29 (their requirements' "Until decided" lines or "Waiting on approval").
2. **Navigation** (ADR 0043 amended). The project sidebar keeps one flat list: the built project pages, then the five Metrics pages in the approved Metrics list's order and under its names (Financial Overview, CAPEX Breakdown, OPEX & Savings, Payback Analysis, Lifecycle Cost; R-093 "Until decided"), at `/projects/:projectId/metrics/<page>`. No "Metrics" item, group heading, landing, "← Back to Metrics", CAPEX / OPEX toggle or tab (R-093, R-146). Each page names itself in the document title.
3. **One snapshot per page, the proposal's own displays.** Financial Overview, CAPEX, Payback and Lifecycle read one stored version, the latest by default or the one `?snapshot=` names (the project's only; 404 otherwise). The API builds each from the stored proposal's own build input, and the view-model builds the stored proposal first and takes from it every value it also shows (the headline's price, the indicators, the outputs, the scope decisions as used), so one value id renders one display on every page (G2-7; US-FIN-03 AC8). Values only Metrics shows live under `proposal:<sid>.metrics.*` and `proposal:<sid>.series.*`. A project with no stored proposal reads "Not available yet: a generated preliminary proposal" with the action that opens the Proposal page (`open_proposal`, a new workspace action), and nothing else. OPEX & Savings reads the project's documents and decisions now (R-095: the building's cost before any BMS), never a snapshot.
4. **Series.** A chart is a series: an engine catalogue's declaration (`@sovitech/engine` `SeriesDeclaration`: a breakdown with its total, or a sequence; every point and the total outputs of one formula), read from one snapshot's rows (`seriesRowsOf`: one formula version, else refused). The production catalogue declares none (no production formula outputs lines by system, level, stream or year), so every Metrics chart reads one "Not available yet" line naming what its total waits for and "SOVITECH's method for <what it measures>", and draws no point, bar, axis, zero or dash (G1-31). TEST series prove the mechanism in the test runner (G1-5, G9-8, G9-9). A point the engine could not compute is a labelled gap: its display reads Unknown or "Not available yet: …" and it has no plot position (G1-5). No share is served: every v1.5 amount is a range, and US-FIN-05 AC3 lets a share of ranges be left out; with no shares, no donut is drawn (its arcs are shares), and the parts show as ranges beside their total (the design review compares this with DB-02 and DB-13).
5. **Charts as page elements.** Marks are inline elements (or inline SVG with no text) bound to their points' value ids; positions are layout, in thousandths of the plot, computed by the formatting module (`plotPositions`) from the numbers each point's label shows (`estimateAsShown`, `calculatedAsShown`: the central value to rule 9's significant figures, the bounds rounded outward; amended in part B, A-5), on an axis generated from those numbers (R-103 AC3), ranges never narrowed; no numeric tick or axis label is drawn; every chart has a table view listing each point's name and value display (prompt 3 sections 7 and 11). Colours: approved values only: the brand's mint accent (`--sov-accent`) for marks, the brand hairline (`--sov-border-hover`) for a gap's outline, text tokens for labels, and the served zero, the chart's only axis line, 2px in the muted text token (`--sov-text-muted`: 3:1 on dark, the ink on paper; amended in part B, V-8 and A-9: the track draws no line at its start); no system palette or chart extension colour until the owner's OK (D-19). A position is never shown as text, so no render allowlist or unreadable entry is added; that positions, numbers derived from engineering values, reach the browser outside display objects is listed for the approver as P-6-PLOT-POSITIONS (the build log, phase 6, "Proposals (not applied)").
6. **Labels.** "Building operating cost" (OPEX & Savings) and "BMS operating cost" (Financial Overview, and the proposal's own operating-cost indicator, relabelled) are two labels; "OPEX" never stands alone as a value's label (7.1.1-S8). Labels hold no digit or number word outside a bound value (the render test, rule 2): "square metre" for m², "carbon dioxide" for CO₂, no horizon in a label ("Net present value (NPV)").
7. **Export Report** (R-121). Payback and Lifecycle print their page from a print route, `/projects/:projectId/print/metrics/:page/:snapshotId`, on the brand's light values, through the API's one printer (ADR 0050, extended: a print path names a proposal or a Metrics page), with the requester's session only: a direct download (`GET …/exports/metrics/:page?snapshot=`), as the Equipment CSV is. No generated output is recorded and Reports does not list it: where an export lands and its lifecycle are undesigned (D-06) and proposal 7.2.25 (D-67). CAPEX's "Download Proposal" exports the stored proposal of the page's snapshot through phase 5's `proposals.export` (R-118; 7.1.1-P10).
8. **Not served, with the reason:** "Automation Level" (no approved function set: US-FIN-21 AC7); shares and the donut (decision 4); PROJECT CONTEXT (the sidebar's project card, R-049; R-088 Sources); VALUE DRIVERS, ROI, scenario bar, time scale, "By Phase", live values, benchmarks, achieved savings, savings opportunities, the ⓘ, "Configure", the "View … →" links, "Last <n> Months", monthly series, the cost callouts on a model (their requirements' "Until decided" lines).

9. **"Selected Systems"** (R-089; US-FIN-21 AC6; amended in part B, V-3: the first reading held it back as a calculated value needing a registered count formula, but ADR 0047 decision 7 concerns register counts by asset type, and the PRD defines this count). CAPEX's INVESTMENT SUMMARY shows the count of the include decisions as the snapshot used them, the very decisions "Systems" shows (G2-7), bound to `proposal:<sid>.metrics.selectedSystems` and rendered as the documents count is (the resolver's `resolveCount`: a count of stored decisions, not an engineering quantity). Its unknown policy is to refuse: while any decision as used was not recorded, it reads "Not available yet: systems in scope" with the owner's Add, as the stored proposal names the multi-select, never a count standing in for the decisions not made (rule 1; rule 7).
10. **The figures beside a chart** (G9-9; amended in part B, V-2 and A-4). A page names, for each chart, the outputs of the chart's own formula it shows beside it (`SeriesRequest.beside`: the payback beside a cash flow), and takes them from the same snapshot and formula version as the series; `{}` where only the total stands beside it, `null` where the page shows figures no formula of the series gives yet (the stored proposal's payback, NPV and IRR; the Metrics pages' savings and lifecycle lines). A series of a key whose page names `null` is refused once the stored version holds its rows, so no chart is ever drawn beside a figure of another formula or of none; a breakdown must total exactly the output the page shows beside it (G9-8). The page builders take their requests as a second argument (`METRICS_SERIES` by default; the API passes none), so the test runner can point one at a TEST series (G9-9's page half); a TEST series exists only in a TEST catalogue.
11. **What a series that cannot be drawn reads** (amended in part B). A snapshot that holds only part of a series' rows (an earlier formula version that output the total and no line: A-2) did not run that series: one "Not available yet" line, the page built. A series whose every point went out of date after generation keeps its points, each reading "Out of date, recalculating", with no axis (2.4; A-1). A line the formula gave for a system the version left out of scope is refused, never hidden from its total (G10-7; A-6). The parts of a priced total are served through the one Price, each with its stage (`SeriesPoint.price`; rule 10; A-3), and the engine refuses a breakdown whose total carries a stage and one of whose parts does not (`checkSeries`: `investment_part_without_stage`). A series is named by its label, never by its key (V-6).
12. **Every value id a Metrics view names is served** (part B, A-8): each Metrics response schema refuses a view that names a value id its response does not serve, so the API answers 500 and the page reads that it could not be loaded, never an empty tile or a row left off a printed report.

## Consequences

- Live, with no approved dataset and no key, every Metrics figure reads "Not available yet", naming the dataset, unit, method or open question it waits for, and every chart reads one such line; the mechanism (figures, ranges, gaps, one snapshot, one formula version, positions agreeing with labels) is proven with TEST series in the test runner only.
- The sidebar grows from seven items to twelve, flat.
- The proposal page's operating-cost row reads "BMS operating cost".
- A Payback or Lifecycle export is not listed on Reports and is printed again at each download, from today's state of the named snapshot (as ADR 0050 decision 3 prints the proposal).

## How to reverse

- Navigation: when D-02 is decided, group or move the five entries in `WORKSPACE_PAGES` and the web's `PAGE_SEGMENTS`; the pages do not change.
- Series: a production declaration joins `PRODUCTION_CATALOGUE.series` with the first approved dataset and the signature version that outputs the lines (P-6-SERIES-SIGNATURES). The page that draws it must then name the outputs of that formula it shows beside the chart (`METRICS_SERIES`' `beside`: the payback, NPV and IRR beside a cash flow, the savings total beside a savings breakdown, the lifecycle tiles beside the lifecycle charts), and the parts of an investment breakdown must be staged outputs (`OUTPUT_STAGES`); until both are done the page refuses the series (decision 10), so a declaration is not drawn "with no change" (corrected in part B, A-4).
- Shares and the donut: once amounts can be exact, or once the owner chooses share ranges, the engine serves shares as outputs of the same formula and the series gains them.
- Colours: once the owner approves the chart extension values (D-19), `tokens.css` gains them and the chart reads them by token.
- Export Report onto Reports: add an output kind to the contract's `OUTPUT_KINDS` and record it at export, as the proposal's is.

### The engine, view-model and API builder (2026-10-07)

1. **Series view** (`packages/view-model/src/metrics/series.ts` `seriesView`): a page asks for a series by its key, kind and total (or, for a series whose figure is no engine output of the stored version, by what that figure waits for: `SeriesRequest.waitsFor`, from `METRICS_MISSING`). A catalogue whose series `checkSeries` faults is refused. A series the catalogue does not declare, or whose rows the snapshot does not hold, reads one line: what its total waits for, as the stored proposal names it (`outputMissingOf`, the same names, Add actions and order as the output's own line), then "SOVITECH's method for <SERIES_LABELS' words>"; the owner's Add actions stay, and 2.8's "Add the <field> to see this." is left off, since the method is missing too. A declared series whose every point is a gap reads one line naming what its points and its total waited for (the "Add ... to see this." line only where every item named is an owner input). Otherwise each point's value is the stored proposal's own output display (`snapshotOutput`: the very builder the stored proposal uses, so one value id has one display: G2-7), its name a bound `line` display, a system the version excluded is no point (G10-7), and a point whose figure reads "Out of date, recalculating" is drawn as a gap (its label shows no figure, so no mark: G9-9). A total that is an investment output (`OUTPUT_STAGES`) is served as the stored proposal's price; any other as a value. A point named by a level is refused until a series by level exists (P-6-SERIES-SIGNATURES): its name needs the level register.
2. **Positions** (`formatting/plot.ts` `plotPositions`): decimal.js only; the axis runs over the drawn figures' bounds (and zero, for a breakdown); a low bound rounds down, a high bound up, a mark and an exact value to the nearest thousandth, the mark kept inside its range; zero is placed whenever the axis holds it and has a length; an axis of no length places everything at its start. Refused: an estimate not strictly inside its range, a value that is no finite number, a series of gaps only. The skeleton's `plot-errors.ts` (`FormattingNotBuilt`) is removed, unused.
3. **Page builders** (`metrics/index.ts`): each snapshot page builds the stored proposal (`proposalView`) and serves, under its own value ids, its headline price (the investment), its indicators, its scope decisions as used and its exclusions; values only Metrics shows are `proposal:<sid>.metrics.<item>` lines from `METRICS_MISSING`. 4. **OPEX & Savings** (`opexView`): `OpexBuildInput` holds the workspace's `WorkspaceProject` (not the planner's `current` fields), so a system's decision is System Scope's own display (`project:<id>.scope.<system>`: G2-7) and the rows are the systems whose stored owner decision is include (`storedDecision`). The new building's estimate names the catalogue's requirements of the formula whose outputs hold the annual energy consumption (production: "SOVITECH cost ranges and benchmarks"), then "the energy-price unit". Maintenance, staff and other costs are `record` displays reading Unknown.
5. **Services** (`apps/api/src/metrics/service.ts`): a named `?snapshot=` that is not one of the project's versions is 404 before any build (rule 13); none named reads the latest; the stored proposal's own build input (`proposalInputOf`) and envelope; the print views strip every action. 6. **DR-12's one step-of-field map**: `packages/view-model/src/intake/steps.ts` (`STEP_1_FIELDS`, `STEP_3_FACTS`, `STEP_5_FIELDS`, `productionStepOfField`) is read by the wizard's registry (`apps/api/src/wizard/registry.ts` re-exports it) and by the stored proposal's basis order.

# 0048. The stored proposal: Generate, the snapshot, its staleness, new versions, the price stage and the quotation record read

- **Status:** Accepted: default, reversible (decision 7's open-items reading and decision 9's landing are listed for the owner)
- **Date:** 2026-10-05

## Context

- **Guardrails** 2.4 ("A generated proposal keeps a snapshot of the candidate ids and formula versions it used"; "A calculated candidate whose inputs are no longer all active is stale. It renders as 'Out of date, recalculating' and never as current"), rule 3 ("A suggestion left in place counts as the owner's answer ... On Continue"; "Nothing hidden, collapsed or on another step is accepted this way"), rule 4 (nothing overwritten), rule 7 ("Analysis still running never blocks Generate: 'Still reading 2 files. Your estimate will update when they finish.'"; "In the proposal document. Open items appear once, in a 'What we still need' section"), rule 10 (the three stages; "Stage 3 is derived, not passed"; "A quotation goes stale when its inputs change"), rule 13, 2.8.
- **Prompt 3** 5.2 "After Generate" ("Generating state, then Overview. A stored proposal keeps its snapshot and shows its generation date. When its inputs change, Overview offers to generate again; nothing regenerates silently"), 5.2 "Generate before phase 5", section 9 (UD-01, UD-06, UD-07; UD-38: "phase 5 builds the record and its staleness"), phase 5.
- **PRD** R-109 (Generate, generating and failed states; S1), R-110 (snapshot, changed inputs, new versions: "stored only when the owner presses 'Generate Proposal' again ... or when analysis that was still running at Generate finishes"), R-111 (the stored proposal; AC10's landing interim), R-112, R-113, R-116 (Overview; "Until decided: No separate Overview page is built. After generation, and when the owner reopens a project that has a generated proposal, the owner is shown the stored proposal of R-111"), R-127 (the stage from stored records; S1), R-129 ("Until decided: No screen issues a quotation record, and no screen or export shows the 'Formal quotation' stage"). D ids: D-14, D-02, D-10, D-20, D-16, D-67 (proposal 7.2.25), D-09.
- **The store** (migration 0005): `proposal_snapshots` (id, inputs hash, created by, created at), `proposal_snapshot_candidates`, `proposal_snapshot_formulas`; `quotation_records` and `quotation_record_inputs` with no writer (`no_writer_decided`).

## Decision

1. **Generate** (`POST …/proposals`, owner only, CSRF, one request per press): the owner check, the project's write lock, the read; the engine runs over the derived state (ADR 0047); any candidate it produced is written as the engine's service account (the extraction service account's pattern, ADR 0013 and 0026: a service account made a member of the project on its first write; the API builder names the account in this ADR's "Built" section); the snapshot is recorded; nothing else is written: no owner answer, no skip, no accepted suggestion (rule 3; G3-23). Step 8's own Continue, before the POST, keeps doing what phase 3 built (its inline asks' skips, its visible suggestions on that step). Generation is synchronous: the web shows the generating state (UD-07: the title, an indeterminate progress bar, no figure, no partial total, no count-up; "Still reading <n> files…" where analysis runs) while the request is on its way, then the stored proposal; a failure shows UD-47 ("could not be generated", answers and uploads kept, Try again, Back to review). No dialog, no disabled button.
2. **The snapshot** (migration 0015, an admin migration on 0013's pattern that registers each new table with the append-only guard and the project tables): `proposal_snapshot_outputs` (snapshot, output key, formula id and version, the produced candidate or null, the missing items as codes, whether the total was incomplete), `proposal_snapshot_pending_documents` (the documents being read at generation), `proposal_snapshot_paragraphs` (AI-drafted paragraphs the validator accepted, with the model id: R-115), and `generated_outputs` (ADR 0050). Codes only (`dataset:<id>`, `method:<formula>`, `unit:<gate>`, `input:<subject>:<field>:<reason>`), never document text (rule 13). `proposal_snapshot_candidates` holds every candidate the run read and produced; `proposal_snapshot_formulas` the formulas whose body ran (none in phase 5). The inputs hash covers the inputs' states and deciding candidate ids, the formula versions and the dataset versions (ADR 0047).
3. **Read as generated.** A stored proposal shows its snapshot's outputs and the inputs as the snapshot used them, under the snapshot's own value ids (`proposal:<snapshotId>.inputs.*`), never the field's current id, so a value id keeps one display (G2-7) and no newer value is mixed in (US-PROPOSAL-03 AC3). Breakdowns and totals come from one snapshot id (G9-8).
4. **Changed inputs** (`snapshotChanges`): each output whose inputs changed since generation carries "Out of date, recalculating" and is never shown as current (2.4; G9-10; US-PROPOSAL-10). No status line marks the whole proposal (proposal 7.2.25, D-67) and nothing regenerates. In phase 5 every output reads "Not available yet", so no figure can go out of date; an input row of the basis whose field changed since keeps the snapshot's value with its badge and source as used, with no new wording (2.8 has none for it; listed for the owner and the approver with 7.2.25).
5. **New versions.** A new snapshot is stored only when the owner presses "Generate Proposal" (from step 8, reached by "Back to review" or a "Not available yet" action's step 8 inline ask: R-110, R-012), or, as the system, when the analysis of every document a snapshot recorded as pending has finished (US-PROPOSAL-11 AC6; rule 7's "Your estimate will update when they finish"; the worker's analysis job calls the API's regeneration after it records the result). Earlier versions keep their snapshots and stay readable (`/projects/:projectId/proposals/:snapshotId`; G4-45). Prompt 3 5.2's "Overview offers to generate again" is not built: R-110 and US-PROPOSAL-11 keep the way back to Generate through step 8 while D-14 and D-02 are open, and a regenerate action beside a stored output is proposal 7.2.25 (stricter; logged).
6. **The price stage from stored records** (`priceStageOf`): "Formal quotation" only from a stored quotation record that names the snapshot, is current and has a figure to name (the display then carries the record's id, G10-9); the output's own stage (`indicative_range` for the benchmark output, `preliminary_investment_estimate` for this project's data) when it has a figure, with "Superseded: inputs changed on <date>" and the stage 2 label when the record's inputs changed (G10-2); no stage while no figure exists (G10-11). The headline carries stage 2, or rule 7's stage 1 fallback (a first-estimate input missing, the registry allowing an Indicative range for it, its dataset approved: G7-2a), else stage 2's "Not available yet" line naming every missing input with its Add action (G7-2b). The Price component takes no stage of its own.
7. **The open items are the project's now** (a reading): "What we still need" and the headline's counts are computed from the current field states, as step 8 plans them (rule 7, "The review step computes open items from field states"), with the same value ids as step 8 (G2-7). They are what still needs doing, not figures; the figures stay the snapshot's. Listed for the owner.
8. **The quotation record read** (UD-38): the API reads the project's records and their inputs, and the engine's `quotationStanding` says current or superseded (with the date of the first change after issue). No route, screen, seed or script creates a record (R-129 "Until decided"; ADR 0005: no approval or record from code); the live app has none, so no screen shows "Formal quotation" or "Superseded". Tests insert TEST records (TEST accounts, never a real person) through the store's TEST machinery only.
9. **The landing** is the stored proposal page (`/projects/:projectId/proposal`: the latest version; phase 3's preview of what each output still needs while none is stored, with the way to step 8). UD-01's content (the stage label, the headline range or "Not available yet", the estimate's own open items) is the page's head; no separate Overview page or sidebar item is built (R-116, PRD 10.2 "Until decided"). The project list keeps opening a project at step 1: whether a generated project opens its stored proposal (R-009, R-111 AC10 interims) is D-14 and D-02, which the owner chose to decide in this phase's report ("3 Decide in phase 5"), so nothing here decides it.
10. **AI-drafted paragraphs** (R-115): only where the `ai-processor-route` guard allows drafting (the demo project's values only, while the gate is closed) and a key is set; the validator accepts or refuses each paragraph (tokens only, no digit, no reserved term, no life-safety control, no compliance claim); accepted ones are stored with the snapshot and rendered by code, each token as its value's own display. No key today: no paragraph, and Generate never waits on or fails for drafting. `prompts/`, the model id and the output schema do not change, so the evals' definition-of-done item stays as it is.

## Consequences

- Generate works on every project, with or without documents, and stores an honest record of what could and could not be produced.
- The demo and every new project show a stored preliminary proposal whose every output reads "Not available yet", naming the dataset or input, until SOVITECH's datasets are approved.
- Formal quotations, their staleness and figures out of date are proven with TEST data and stay unreachable in the live app.

## How to reverse

The landing (decision 9) is one route target in the web; making the project list open the stored proposal is one line in the project list once the owner answers D-14. The open-items reading (decision 7) moves to the snapshot by storing the items at generation (one more snapshot table). Regeneration after analysis (decision 5) is one call in the worker.

## Built (the web builder, phase 5 part A, 2026-10-05)

- **One POST per press, from the press** (decision 1; `apps/web/src/proposal/generation.ts`): step 8's "Generate Proposal" (and "Generate without it") skips the asks left open once, sends step 8's Continue (which opens the landing), then sends `proposals.generate` with `{}`; UD-47's "Try again" sends one new POST. The POST is never sent from a page's effect, so a reload, React StrictMode's double effects, the sidebar's "Proposal" or a stored version's page never send one. The generation state lives in the page session by project (module state): generating (UD-07: the title, a progress bar with no number, step 8's served "Still reading" display when the press came while files were being read), failed (UD-47: the sentence, "Try again", "Back to review"), else what is stored. A press while a POST is on its way sends its Continue and no second POST; a refused Continue sends no POST and step 8 says so. A failure stays until "Try again", "Back to review" or a new press (a reload forgets it and shows what is stored).
- **The landing** (decision 9; `apps/web/src/proposal/ProposalPage.tsx`) reads `proposals.list` (again after each generation of the page session) and shows the newest version through the same screen as `/proposals/:snapshotId` (`StoredProposalPage.tsx`), or, with none stored, phase 3's preview (`proposal.preview`) with "Go to the review". The project list still opens step 1 (D-14, D-02).
- **The head and the open items** (decision 7; rule 7, "Open items appear once"): the head shows the investment output's Price, the open items' count line with a link to "What we still need", and "Still reading"; the items themselves only in "What we still need", read-only with each item's own Add action where served. Rule 11's sentences show once each: the interface points in the points section, Fire Safety's sentence on its scope row, any other life-safety line in the life-safety section.
- **Prices** (decision 6): through the kit's Price only (ADR 0040 decision 8); the web shows the served `Price.stage` display apart from the figure only where the figure's own display does not carry it, and at the head only while a figure exists (G10-11); a stage 3 price must name the same stored record on the price and its display (G10-9), else the page refuses it and the frame keeps its sidebar and demo line. An investment output with no figure is named by a served stage label or measure label only; none is served for it today (B4 reached the same reading for the print route), so it shows its "Not available yet" line alone: listed for the view-model and the contract steward.
- **Proofs**: `apps/web/src/proposal/ProposalPage.test.tsx` (26 tests, among them the web halves of G7-18, G10-1, G10-2, G10-9 kept, G10-11 on the stored proposal, G11-12, G4-45, G3-23's "the POST writes no answer", G7-11 ported from phase 3), `apps/web/src/workspace/navigation.test.ts` (a stored version is the Proposal page's).

## Built (phase 5 part A: the API, the store and the view-model)

- **The engine's account** (decision 1; ADR 0047 decision 8): the system's service account, `SOVITECH_EXTRACTION_ACCOUNT_ID` (the extraction job's account, ADR 0013 and 0026), writes the engine's candidates. No new account or setting: one system account writes every non-`user` value. When a run produced a candidate (a TEST catalogue only: no production body exists), the owner's request makes the account a member of the project (as an upload does), the account writes the candidates in its own request (`apps/api/src/proposal/engine.ts` `writeEngineCandidates`; the store's SVX11 refuses anything else), superseding its earlier, not yet superseded value of the same output field as a system event (2.4 "Recalculation"; SVX13 allows it on calculated and estimated values only), then the owner's request stores the snapshot that names them. With the production catalogue (every live Generate), one request does it all, under the owner check and the project's write lock, and writes nothing but the snapshot.
- **Migration 0015** (`packages/db/migrations/0015_proposal_outputs.admin.sql`; decision 2): the four tables, append-only, project-scoped, registered with the guards and the shape recorded. Two guard functions, neither a definer: `snapshot_part_written` (SVX17: a part of a snapshot is written by its writer, the request's own user, in the snapshot's transaction, so a stored proposal is never added to after it commits) and `output_written` (SVX18: a generated output names the request's own user, acting as the owner). An output row holds codes only (a CHECK), names at least one missing item when it has no figure, none when its figure is complete, and its excluded items when the total is incomplete. `generated_outputs` reaches its project through its snapshot (the access tables belong to `sovitech_db_access`). A missing method's name is written as a code (characters outside a code's written `_`): the view names a missing method by the output's label, never by the code's text.
- **The store** (`packages/db/src/proposals.ts`): `recordGeneratedProposal`, `readProposalVersions`, `readProposalSnapshot`, `readPendingDocumentsBySnapshot`, `readQuotationRecords` (read only), `recordGeneratedOutput`, `readGeneratedOutputs`. TEST machinery: `insertTestQuotationRecord` (`@sovitech/db/testing`) writes a TEST record as the role `no_writer_decided` that the table's writer guard names, created in the throwaway TEST database only; no store login holds it, and the app, the seed and every script still cannot write a record (R-129).
- **Reading a version** (decisions 3, 4, 6, 7): the API reads the snapshot, its candidates (excerpts as stored, "[erased]" after erasure), the project's current derived state, the quotation records; the engine's `snapshotChanges`, `quotationStanding`, `priceStageOf` and `headlineOutputOf` read them; the view-model's `proposalView` and `proposalPrintView` resolve every value. An input shows the candidate the snapshot used under `proposal:<sid>.inputs.*`, with its badge as derived now (provisional status is computed on read, 2.4) and a 2.8 status line where it is no longer current ("Source document removed", "From a superseded revision"), never a newer value. A figure's lines: its stage label (from stored records), "Superseded: inputs changed on <date>" (G10-2), "Incomplete: excludes <names>" (the engine's coded notes, named by the fields' labels), the Provisional lines 2.8 and rule 4 write ("Provisional: depends on <n> equipment items not yet checked" for unverified asset inputs; "Provisional: two values for <field>"), the method line and rule 9's basis ("Based on <the inputs' labels, the datasets with their versions>"). An output with no figure reads "Not available yet", naming what was missing at generation (datasets by the catalogue's names, a method, a unit, an input; a multi-select once, by 2.6's words; a conflict as rule 4 names it), with an Add action only for a first-estimate input still missing now; rule 10's stage 2 output also names each first-estimate input the snapshot held no value for (as step 8 does: rule 7's `first_estimate` row). The headline's fallback is stage 1 only where `proposalStage` gives it (G7-2a). Open items and "Still reading" are step 8's (the same value ids and displays: G2-7).
- **Regeneration** (decision 5): `regenerateAfterAnalysis`, called by the worker's new `afterJobEnded` step (done, or failed for good; its failure is logged by code and never changes the job's end). As the system account, under the project's write lock: when the latest version recorded documents as still being read and none of them is being read now, a new version is generated; otherwise nothing.
- **Drafting** (decision 10): the services' `drafting` seam, unset by the entry points (no key). When set, Generate builds one request from the project's own values (a `summary` slot; `{{value:<field key>}}` tokens for inputs with a value and `{{calc:<output>}}` for outputs with a figure; the scope decisions as facts) and runs it through the boundary; the `ai-processor-route` guard refuses every project but the demo; accepted paragraphs are stored with the model id; a refusal or failure stores none and is logged by code, and Generate never fails for it. The view renders a paragraph as prose and value segments, leaving out a paragraph whose token names no display or whose prose holds a number.
- **Exports** (ADR 0050): `recordExport` (owner only, under the write lock); `exportFile` prints through the services' printer with the requester's Cookie header, and answers 503 `export_unavailable` with the owner's message when no printer or web origin is configured (`SOVITECH_WEB_ORIGIN`, loopback http(s) origins only) or the print fails (its reason logged as a code). The Equipment CSV (decision 4 of ADR 0050): six cells of three columns each (text, badge, source line), the cells as Equipment serves them, the count's line last, the demo line first on the demo (one quoted cell, RFC 4180), CRLF line ends, the apostrophe guard.
- **The demo seed** generates the demo's first version as the seed account (the demo's owner) and records one export by it (7.1.1-D6: a demo account, never a person).
- **Copy** (`packages/view-model/src/proposal/copy.ts`): section 5's Fire Safety sentence and rule 11's interface points sentence word for word; the indicators' names (draft); the outputs' measure labels (draft); the CSV's column heads (draft); the method-missing wording (draft). Step 8's dataset names now come from the engine's catalogue (`FORMULA_DATASETS`), so the savings output names "SOVITECH savings factors" there too (PRD R-099).

## Amended (the integrator, phase 5 part A, 2026-10-06)

- **The engine's refused answers** (`EngineRun.refusals`: a body's estimate outside its range, a figure on a field that forbids estimation, a unit of the wrong dimension, an undeclared or missing answer) are logged by Generate as `engine_answer_refused` with the refusal's code, the project id and the formula and output ids as codes (rule 13: no text). Guardrails section 8 lists no event type for them, so no guardrail event is written; proposal P-5-ENGINE-REFUSAL-EVENT (build log, phase 5) asks the approver for one. With no production body, none happens in the live app.
- **The landing after Generate:** the e2e flows wait for the stored proposal's head (`[data-proposal-head]`), not only for the render marker, which the generating state also sets (tests/e2e/support/wizard.ts `proposalSettled`).

## Amended (phase 5 part B: the API and the store, 2026-10-07)

- **Decision 5, "Still reading" at the head** (rule 7, "Your estimate will update when they finish"; R-110, "the version stored when running analysis finishes keeps the notice ... true"; US-PROPOSAL-11 AC6): a stored proposal's head carries step 8's line (`project:<id>.documents.stillReading`, the same value id, count and display: G2-7, G7-18) only when it is the latest version and at least one document its snapshot recorded as pending is still queued or analysing now. Then the promise is true: when that document finishes, the regeneration stores a new version, which records any document uploaded since as pending in its turn. Otherwise no line: a document uploaded after Generate, while none of the snapshot's own documents is read, regenerates nothing, so no version promises an update (G7-20). An earlier version, and its print view, never carry the line (G4-45). No new wording.
- **Decision 6, the headline read from the snapshot's rows** (R-110, "readable as generated"; 2.4): rule 7's `first_estimate` fallback is no longer read from today's answers, gates and catalogue (`proposalStage`), which let an earlier version's headline switch stage after it was generated. It is true when the snapshot's stage 2 row (`capex.preliminaryEstimate`) names, among what it was missing, an `input:` code whose registry field is a first-estimate field (`firstEstimateFallbackOf`, apps/api/src/proposal/service.ts). `headlineOutputOf` still takes stage 1 only when its row holds a complete figure, which exists only where its dataset was approved at generation (G7-2a). With the production catalogue nothing changes today: no output has a figure.
- **Decision 6, "Superseded" read one way** (rule 10; R-119; G2-7): each output row a reader builds carries `outOfDate` (engine `snapshotChanges`' `outOfDateOutputs` and `outOfDateOn`), so a current record over a figure whose inputs changed since generation (an input Unknown at issue, which the record could not list) reads "Superseded: inputs changed on <date>" (A-4). Reports reads a row's line from the stage 2 row of the snapshot it prints, through `priceStageOf` with the same records and standings as the proposal: a snapshot with no figure, or one whose record is current over inputs as generated, carries no line (V-4).
- **Decision 1, the engine's values under the lock** (2.4, "Recalculation"; rule 4): when a run produced values (TEST catalogues only), the system writes them in its own request under the project's write lock, reading the project again there and superseding every earlier engine value of each output field it finds, a concurrent Generate's among them; each output field keeps exactly one engine value nothing ended (G4-47). The snapshot is stored afterwards in the owner's request, as before; a snapshot stored after a later answer reads "Out of date, recalculating" (decision 4). Drafting still runs in that request (A-8 is logged for later).
- **Decision 2, who writes a snapshot** (migration `0016_snapshot_writers.admin.sql`; 2.4; rule 4): `proposal_snapshot_candidates` and `proposal_snapshot_formulas` now have 0015's writer guard too: a candidate id or a formula is written only with its snapshot, by its writer, in its transaction (SVX17); and `proposal_snapshots` refuses a row whose `created_by` is not the user making the request, or whose writer neither acts as an owner of the project (the demo seed on the demo) nor is the project's system service account (SVX19, `snapshot_not_from_the_requesting_writer`). Every writer the app has passes: the owner's Generate, the TEST path's snapshot request, the demo seed and the regeneration (G4-46). The migration tells the guard of each new trigger before the command that creates it and records the shape at the end; no guard is paused or unregistered.
- **Exports** (ADR 0050): a downloaded PDF is named `preliminary-proposal-YYYY-MM-DD-HHMM.pdf`, the digits of the printed snapshot's stored generation time (UTC, as stored; no arithmetic), so two versions never save under one name (DR-5). The file route hands the printer a signal aborted when the request's connection closes before its answer; the printer's queue is bounded and its time counts the wait (A-7; ADR 0050 decision 2, to be amended there).

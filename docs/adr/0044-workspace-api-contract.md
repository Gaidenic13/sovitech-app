# 0044. The workspace API contract, its display objects, and the API's registry seam

- **Status:** Accepted: default, reversible
- **Date:** 2026-10-02

## Context

- **Guardrails rule 2** ("UI code receives only resolved field objects, which carry the badge and the source line"), 2.8, rules 1, 3, 4, 7, 10 to 13; prompt 3 sections 6 and 7 (the API returns display objects only; every number in a line is bound to a value id). ADR 0036 fixed the contract's form for the wizard: zod schemas in `packages/view-model/src/browser/contract/`, the `ROUTES` table, display objects, value ids, the render projection `servedDisplayOf`, and the API's test that Fastify's routes equal `ROUTES`.
- **Phase 4 builds in parallel** (build log, phase 4 plan, "How the work is split"): the view-model, API, shell, page and e2e builders need one written contract.
- **Carried from phase 3:** "the registry seam in `apps/api/src/wizard` so G5-3 runs through the served view" (the build log's "Waiting": "Waits for a seam that takes the registry as a dependency (phase 4, with the API's next registry change)"); "phase 4's Documents page builds its display-object view of `documents.list` on `servedFileName`" (NP-4); the kit's Value action buttons' `aria-busy` and step 3's screen-wide guard (phase 3 "Next").
- **Sources by screen:** PRD R-016 to R-019, R-022, R-028 (DB-15); R-049, R-076, R-077, R-139, R-144 to R-146 (the frame); R-051 to R-055, R-058, R-072 (DB-16); R-065 to R-068, R-070 (DB-17, UD-08); R-060 to R-064 (DB-20); R-071 to R-075 (DB-08, DB-07, DB-10); R-078, R-080 to R-085 (model areas). D ids: D-02, D-03, D-04, D-01, D-06, D-09, D-18, D-24, D-51, D-54, D-60, D-61, D-64, D-65, D-90, D-92.

## Decision

1. **Where it lives.** `workspace.ts` beside the wizard's files, exported by `@sovitech/view-model/browser`; ten routes added to `ROUTES` with `phase: 4` (the type now allows 2, 3 or 4). Reads: `workspace.frame` (`GET /api/projects/:projectId/workspace`: the built pages, the project card, the footer, the level register), `workspace.documents` and `workspace.documents.deleteEffect`, `workspace.systemScope`, `workspace.equipment` and `workspace.asset`, `workspace.zones`, `workspace.topology`. Writes: `workspace.systemScope.decide` (`POST …/workspace/system-scope/decisions`) and `fields.concernMany` (`POST …/fields/concern-many`). Every phase 4 route serves display objects (the render test reads them by `isDisplayObjectRequest`). Every response is the envelope of `common.ts` (`asOf`, the project header with the demo line from the flag only, `displayObjects`) plus its view.
2. **Reused routes.** The project switcher reads `projects.list`. Documents' upload uses the phase 2 upload routes (`uploads.*`, step 2's resumable client), its revision declaration `documents.revisionOf`, its download `documents.file` (after the project access check), and its delete `documents.delete` (rule 13's erasure job), after `workspace.documents.deleteEffect` has stated the effect. A zone's correction (UD-09) is `fields.edit` on the zone's field. "Looks right" on a selection is `fields.acknowledge` (it takes many candidates). The phase 2 raw `documents.list` stays for tests and the demo seed; the web never reads it (it returns the stored file name; the new view serves names through `servedFileName`, G2-14).
3. **Value ids** added (the render contract's pattern; every segment starts with a letter): `document:<id>.kind` (the category), `document:<id>.deleteEffect`; `asset:<id>.tag|type|system|location|level|zone|points`, `asset:<id>.evidence<n>`, `asset:<id>.<field>.history<n>`; `zone:<id>.code|name|level|kind|area|systems|equipment|points`; `building:<id>.levels.<levelType>_<n>` (a level's label) and `building:<id>.levels.unstated`; `project:<id>.register.total[.<filter>…]`, `project:<id>.register.<system>[.<level>]` (equipment by type, one id per system and filter, shared by System Scope and Topology: G2-7), `project:<id>.points.<system>`, `project:<id>.levels.<system>`, `project:<id>.zones.<system>`, `project:<id>.topology.design`, `project:<id>.topology.noDecision`, `project:<id>.floors.missing`. The decisions, building facts and project answers keep phase 3's ids, so the card, System Scope, Topology, step 3 and step 8 show one display per value (G2-7).
4. **The registry seam** (the API builder; carried from phase 3). `ApiServices` gains a `registry` (the production registry's fields, questions and lookups, as `apps/api/src/wizard/registry.ts` reads them today) that `buildServer` and every wizard and workspace module read instead of module constants. `apps/api/src/index.ts` and `worker-main.ts` pass the production registry and nothing else; no environment variable or config can select another. Tests pass TEST registries they build in `tests/` (as `tests/guardrails/_support/view-model.ts` builds TEST fields today, never through the gate-opening `@sovitech/registry/test-utils`, which stays reachable only from `tests/proposed/`). A test proves the production entry serves the production registry. G5-3 then runs its twelve TEST values through the served step view (the build log's "Waiting" row closes), and the workspace's TEST states (zone and asset fields) run through the API in tests.
5. **The view builders** live in `packages/view-model/src/workspace/` (server side): pure functions from derived state, the registry and the closed gates to each view and its display objects, on the one resolver and the formatting module. The API reads the store in the user's own request (row-level security), calls them, and validates its answer against the contract (`answerWith`).
6. **Owner writes** (`workspace.systemScope.decide`, `fields.concernMany`, and the phase 2 `documents.delete` and `documents.revisionOf` the Documents page now calls) take the project's write lock (`lockProjectWrites`) after the owner check and before the state is read, in the lock order of ADR 0036 decision 13; a decision equal to the stored one writes nothing; the web sends one request per press (`useInFlight`) and never disables the control.
7. **No new dependency for tables or lists.** The Equipment register pages on the server (50 rows, previous and next only, no page numbers: R-017's reading applied to registers), so the 5,000-row budget (prompt 3 section 11; ADR 0041) needs no virtual list; Documents (tens of rows) filters, sorts and pages on the page.

## Consequences

- One schema per screen, compiled by both apps; a drift fails at the API's validation and the web's parse.
- The render test reads every workspace screen's values from the API with no change to its adapter.
- The API can serve TEST registries in tests only; production behaviour is unchanged by the seam.

## How to reverse

Each route is one entry in `ROUTES`, one schema in `workspace.ts`, one handler in `apps/api/src/workspace/routes.ts` and one builder in `packages/view-model/src/workspace/`; removing or reshaping one changes those four. The seam reverts by reading the production registry as module constants again (G5-3's served-view test then returns to "Waiting").

## Built (the view-model and API builder, 2026-10-02)

What the build decided within the decisions above, each reversible as they are:

- **The seam's form** (decision 4). `ApiRegistry` (apps/api/src/wizard/registry.ts) carries the bundle, its lookups, the step of each field (the production steps, plus the steps a TEST registry names for its own TEST fields, never moving a production field) and the suggestion rules (the production ones: none). `ApiServices.registry` is optional and `registryOf(services)` reads it, else the production one; src/index.ts sets `PRODUCTION_API_REGISTRY` explicitly. The worker (src/worker-main.ts) builds no `ApiServices`: its ingestion keeps reading the production registry, unchanged. The project state carries the registry it was read with, so every wizard module (the plan, the views, the displays, the answers, the defect logging) reads `state.registry`; a unit test (registry.test.ts) refuses a module-level import of the production bundle in apps/api/src/wizard and apps/api/src/workspace (the seam itself excepted). `tests/guardrails/_support/workspace-store.ts` builds TEST registries (the production bundle plus TEST fields), handed to `startTestApi({ registry })`.
- **Fields on level, zone and asset subjects.** The project state reads them only where the registry declares a field for that subject kind (none in production: ADR 0045 decision 1), keeps them apart from the question engine's fields (`subjectFields`; the planner never plans them), and the workspace resolves them with `resolveSubjectField`: a zone's fields carry Edit (UD-09: `fields.edit` on the zone's field, R-061) and, on an engineer field read from a document, "Looks right" and "Something's wrong"; an asset's and a level's fields carry no Edit (every asset is treated as possibly life-safety: prompt 3 5.2; ADR 0045 decision 5), and `fields.edit` on one is refused 400 `request_invalid`. `fields.acknowledge`, `fields.concern` and `fields.concernMany` find a candidate on any of the project's subjects.
- **The workspace's views** are built by `@sovitech/view-model/server` (packages/view-model/src/workspace) from a `WorkspaceProject` the API makes of the same project state the wizard reads (`workspaceProjectOf`), with one `resolve` that is the wizard's own resolution for the project's and the building's fields (`resolveWizardField`, its plan's confirmations and suggestions), so a value id shows one display on every page (G2-7). The envelope's project header is the wizard's.
- **The owner's writes** (decision 6): `workspace.systemScope.decide` and `fields.concernMany` take the owner check, the write lock, then read; System Scope's decisions are planned by `planScopeDecisions` and turned into records by the intake's `continueRecords` (no skip, ever, from here); the phase 2 `documents.delete` and `documents.revisionOf` now take the write lock too.
- **Documents' facts** the record does not hold: the date a document was added is the store's registration time (`readDocumentRegistrations`, packages/db/src/reads.ts, a read only); "Revision of" comes only from a person's `declared_revision_of` event, never code's proposed `supersedes`; `downloadable` is whether the stored original exists.
- **Not built from the orchestrator's brief, as the planner decided from the PRD:** no Property route (R-050, PRD 10.2 "Until decided") and no model-area route (no phase 4 page draws a model area: R-054, R-073, R-078; the owner's answer of 2026-10-02).

## Amended in part B (2026-10-02, the fix round for the API, store, view-model and contract)

Each reversible as the decisions above are; each with its proof.

- **The level register's conflict branch** (decision 1; finding V-4): `LevelRegisterSchema`'s `conflict` branch is `{ state: 'conflict', line, field, actions }`. `line` stays "Not available yet: two values for floors" (rule 4, "Until a conflict is resolved"); `field` is the floors field's own display as step 3 resolves it (`building:<id>.floors`: Two values, both readings with their sources, and rule 4's routing line where the conflict is routed to SOVITECH; G2-7); `actions` is `['enter_floors']` unless that display carries the routing line, then none (rule 4, "Routing"; `building.floors` is confirmBy engineer), so the line never appears alone (rule 7). Proofs: G7-16; contract.test.ts "V-4 · G7-16".
- **A zone's details** (decision 1; findings V-6 and V-9): `ZoneDetail.systemDecisions` is `[{ decision, systemId, lifeSafety }]`, the flag read from the catalogue (`SYSTEMS`), as System Scope's rows and Topology's groups carry it (rule 11; 7.1.1-L1; R-051), so the web keeps no list of its own; `ZoneDetail.fields` holds six fields in the order code, name, level, kind, area, description (`zone:<id>.description`: US-ZONES-03 AC1, R-061; Unknown while unregistered; stored text is data, rule 14), the row keeping five. Proofs: workspace.test.ts "V-6 · V-9"; tests/api/workspace-test-registry.test.ts; contract.test.ts "V-6".
- **"Revision of"** (the Built section's "Documents' facts"; finding A-5): served from the derive's own reading of the declarations (`DocumentStatuses.predecessor`, packages/domain/src/documents.ts, an additive export): one direction per pair, none on a cycle, none for a removed revision, never a raw declaration. No new refusal: the web's panel leaves out a document that would close a cycle through another document, and offers the reverse of a direct pair, a correction the derive applies (the final verifier's NP-2; `apps/web/src/workspace/pages/documents/revisions.ts`). Proofs: G4-44; documents.test.ts "G4-44 · A-5"; `tests/api/workspace-revision-correction.test.ts`.
- **The delete effect** (decision 1, `workspace.documents.deleteEffect`; findings A-2, A-3): the API derives the project again with the owner's withdrawal of the document added to the document events (every registered field with the one derive, the asset register with its own; nothing written) and the view-model counts the fields that hold a value now and none after, and the assets counted now and not after (ADR 0045 decision 7, amended). Proofs: G4-41, G4-42; G4-39 unchanged.
- **Owner writes and files** (decision 6; finding A-4): an upload's registration takes the project's write lock and, under it, moves its sealed copy in only when no original of those bytes is stored, keeping the copy until the registration commits; `documents.delete`'s file removal runs in a second request under the same lock and reads again the documents holding the bytes before it removes them (`removeUnheldFiles` takes the lock too). Proof: G13-10.
- **`fields.concernMany`'s answer** names a level and a zone as Equipment does (ADR 0045, amended), so the web's display set never holds the stored key or the zone's id for those value ids.
- **`projects.list`** (decision 2; finding V-5): each row is still read in the project's own request with the whole project state and the same resolver, so each display is identical to step 1's (G2-7, G13-9): row-level security sees one project per request, so no single read spans the user's projects without a migration, and a partial read would have to rebuild the question engine's plan and the searched coverage the step 1 displays read. The rows are read four at a time (`LIST_READS_AT_ONCE`), their displays collected in the list's order. Times in ADR 0041 item 6.
- **`RegisterState`**: on Equipment and Zones `no_documents` now means the project never had a document (a deleted one counts), else `none_read` (ADR 0045 decision 4, amended; G12-11); Documents keeps `no_documents` for no listed document.

## Amended in the viewer step (2026-10-07, part 1; ADR 0051)

- **`documents.modelView`** (`GET /api/projects/:projectId/documents/:documentId/model-view`), added to `ROUTES` (marked `phase: 5`, because the route type allows 2 to 5 only; the API's route-table test requires Fastify's routes to equal `ROUTES`). It checks the session and the project membership under row-level security and answers only for a current IFC document of the project (stored, not withdrawn, erased or superseded) whose bytes have a `converted` record, with the view file as `application/octet-stream`, `Content-Length` and `X-Content-Type-Options: nosniff`. Every answer, refusals included, carries `Cache-Control: no-store`; anything else is 404, saying nothing of another project (rule 13; G13-4; "ifc-input 6.2.16 · view files erased with their document"). It serves bytes, not display objects, so the render test reads no value from it.
- **Not yet in the contract:** the model area's fields (its state from the conversion record, the document line's value ids as Documents serves them, `document:<id>.fileName`, `.stage`, `.revision` and `.coverage`, the "Not available yet" lines and their action, the chooser and the view file's route). The view-model's `modelArea` builder and these fields are part 2's, served by the step 3 and System Scope views when the area is mounted there; the API exports `currentModels` and `modelViewState` (`apps/api/src/documents/model-view.ts`: none, preparing, converted, failed with a code) for it.

# 0014. Append-only storage, one writer per guarded row, and the guard invariants

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25 (amended after the phase 1 review rounds; round 5: decision 4's document withdrawal rule)

## Context

- **Guardrails 2.4:** "Candidates never change after they are written. Everything that happens to them later is an append-only event." "Storage has no update or delete method for candidates." Rule 4, "Enforced by": "Storage. Candidates are immutable, and events are append-only (2.4)." Rule 10: "No script, migration, seed, AI output or service account can write" `engineer_verified`. Rule 13, "Erasure": "This is the only path that alters stored evidence, and it cannot change a value."
- **Prompt 3 section 5.2, row "Database":** "`REVOKE UPDATE, DELETE, TRUNCATE` from the app role, plus raising triggers. [...] The only UPDATE or DELETE on any of these tables is one audited `SECURITY DEFINER` erasure function." Sources: `docs/build-readiness.md` 3 "Now" item 4; rule 13.
- **PRD R-157:** "No code path, script, seed, migration or service account can update or delete a stored candidate or a candidate, field, document or asset event; the store itself refuses the attempt." Its Sources: "Because rule 10 names migrations and scripts, which bypass app code, the refusal has to sit in the store, not only in the app." D id: none (PRD section 13, "The store").
- **New case G4-20** (prompt 3, "New case ids"): the app's database role updates, deletes or truncates a candidate, evidence (locator or excerpt) or event row; the statement fails, and the row is unchanged.

## Decision

1. **Privileges.** The app role holds `SELECT` and column-limited `INSERT` on the tables it writes, never `UPDATE`, `DELETE` or `TRUNCATE`, and the migrations revoke them explicitly. It cannot write any time column: the database sets every one. The operator's login holds no write privilege on a value-model table.
2. **Raising triggers on every table of the store**, for every role, the table owner included: `guard_change` (before update or delete, per row) and `guard_no_truncate` (before truncate) raise `SVA01`. Two tables have their own `guard_change`, the one exception rule 13 allows: an evidence excerpt may change only to `[erased]`, and extracted text may only be deleted, and only when the statement runs as `sovitech_db_eraser`, which only `sovitech.erase_document` runs as (ADR 0015).
3. **One writer per guarded row.** An `after insert` trigger refuses `engineer_verified` unless the statement runs as `sovitech_db_verifier` inside `sovitech.verify_candidate` for that candidate and that engineer (`SVV10`; being an `after` trigger, it reads the row exactly as stored). A `before insert` trigger refuses an `erased` document event outside `sovitech.erase_document` (`SVE10`). Accounts, role events, projects, members and audit events are written only by their functions, and the rule 10 stage 3 record has no writer at all until one is decided (D-20) (`SVR10`).
4. **Storage checks that rules 1, 2.4 and 2.5 need at the store.** At commit, a `document` candidate must have at least one evidence entry whose check matched (`text_match`, `ocr_match` or `region_rendered`: 2.1, "at a verified location"; unverifiable evidence alone only caps an inference's confidence, rule 1), an `ai_inference` candidate any evidence, each evidence entry its excerpt, each asset appearance its evidence, and each document its first analysis event (2.3 `DocumentRecord.analysis`; rule 12) (deferred constraint triggers, `SVX01` to `SVX03`, `SVX12`). Each alternative reading of a candidate is a quantity: an object with a number and a non-blank unit (`candidates_alternatives_shape`; rule 8). Evidence must name a document of the same project with the same content hash (a composite foreign key; the data-access layer turns its refusal into one `evidence_not_found` guardrail event with the reason `document_in_project` or `content_hash`, the store's side of G13-1). A candidate's method inputs, a resolution's chosen candidate and a related asset must be of the same project and field (`SVX04`, `SVX05`, `SVX08`). An asset event must come from the engineer making the request, a person holding `sovitech_engineer`, with a reason (`SVX07`; guardrails 2.5, "Only engineer accounts write them"). A guardrail event's reason must be a code (rule 13, "Logs [...] never contain document text"). `not_applicable` needs a named owner or engineer with a reason (2.4, "Field states").
   - **An event names the request's own user, in a role that user holds** (`SVX09`; 2.4; rule 4 routing, "Only the right person's resolution closes a conflict. Each resolution records who"; rule 3, who confirms; rule 10). A `before insert` trigger, `guard_event_actor`, on candidate, field and document events: an `owner` or `sovitech_engineer` event must name `sovitech.request_user_id()` as its actor, and `sovitech.request_user_acts_as` must hold for that role on the event's project: `sovitech_engineer` needs a person account holding the role; `owner` needs an account holding `owner` that is a member of the project, a person, or the demo seed on a demo project (prompt 3 section 7: the seed writes the demo's owner answers as `user` candidates, labelled as demo input); a `system` event needs a service account. The one exception is the erasure function, which withdraws, as the system, the candidates it leaves without a source during an owner's request (ADR 0015). The data-access layer still takes `by` and `role` from its caller; the store refuses any that are not the request's.
   - **A candidate names the request's own user as its author, from a source that user may create** (`SVX11`; 2.1, "Who can create it"). A `before insert` trigger, `guard_candidate_author`: `created_by` is `sovitech.request_user_id()`; a `user` value comes from an account that acts as `owner` on the project (a member; a person, or the demo seed on a demo project) or as `sovitech_engineer` (a person holding the role: an engineer's site survey entry, 2.1); `document`, `ai_inference`, `calculated`, `estimated` and `reference` values come from a service account that is a member of the project. So nobody writes a value in the owner's name, and no person writes an engine or extraction source. An engineer's `user` value does not need project membership: engineers review every project through their role (ADR 0013), and requiring membership would take their site entries away (listed for the approver).
   - **A candidate records the role its author acted in** (`candidates.author_role`; 2.1, "Who can create it"; rule 3, "Choices belong to the owner"; phase 1 review, round 4). The same trigger sets it from the request, never from the caller: `owner` when the request's user acts as the owner of the project (a member holding `owner`, or the demo seed on a demo project), else `sovitech_engineer` for an engineer's `user` value, and `system` for every other source; whatever the statement named is overwritten, and the app holds no INSERT on the column. A CHECK ties it to the source (`candidates_author_role_source`). The store does not know a field's kind, so an engineer's own entry on an owner decision is stored as the engineer's, and the domain's derive refuses it there (`choice_author_not_owner`, ADR 0016 decision 9; G3-16). A person who holds `owner` in the project and also `sovitech_engineer` acts as the owner there (listed for the approver with new Q36, one account holding two roles).
   - **The system writes only the candidate events the engine and the ingestion paths need** (`SVX13`): `superseded` on a `calculated` or `estimated` candidate (2.4, "Recalculation"), and `withdrawn` with the reason `document_erased` or `document_deleted` on a candidate every cited document of which carries a `withdrawn` or `erased` document event (2.3, "Deleting a document"); the erasure function's own withdrawals as before. A person withdraws only their own `user` candidate (`SVX14`; a correction is a rejection, rule 4). The domain's derive holds exactly these events (ADR 0016), so the store now refuses what derive would ignore.
   - **A document is withdrawn by the owner or an engineer, and by the system only as the job carrying out such a person's withdrawal, which it names; it is erased only by the erasure function** (2.3, `DocumentEvent` and "Deleting a document"; rule 13, "Erasure"; rule 4; phase 1 review, rounds 4 and 5). CHECK `document_events_withdrawn_by_person_or_request` takes a `withdrawn` document event in the role `owner` or `sovitech_engineer` (2.3's `DocumentEvent` names both; `guard_event_actor` binds the owner to a member holding `owner`, and an engineer to a person holding `sovitech_engineer`, member or not, as engineers read every project by role, ADR 0013), and in the role `system` only with `request_event_id`, which names that person's own `withdrawn` event on the same document (the trigger, SVX15; a composite foreign key keeps it in the same project and document). CHECK `document_events_request_only_on_system_withdrawal` keeps the column off every other event. So a job's service account never withdraws a document on its own, and SVX13 then refuses the system's withdrawal of its values; the owner's and an engineer's deletion, and the job carrying either out, are stored. Round 4 had held withdrawal to the owner alone (CHECK `document_events_withdrawn_by_owner`), which refused engineers what 2.3 gives them, a tightening beyond the rules as written; round 5 replaced it, and the owner-only rule is proposal P-1-DOCUMENT-REMOVAL-OWNER-ONLY (build log, phase 1). CHECK `document_events_erased_by_erasure` holds an `erased` event to the roles the erasure function writes, `owner` and `system`, and to its reason, `document_erased`; SVE10 keeps every other writer out. The domain reads the same events and no others (ADR 0016 decision 21, where the reasoning is written).
   - **Field events by role** (CHECK constraints): `conflict_resolved` only from `owner` or `sovitech_engineer` (`field_events_resolution_by_person`; rule 4), `skipped` only from `owner` (`field_events_skipped_by_owner`; 2.4, "The owner chose Skip for now"), `analysis_started` and `analysis_finished` only from `system` (`field_events_analysis_by_system`; rule 12).
   - **A resolution names the exact candidates it covered** (rule 4: "A conflict is put to someone only when values arrive without that person having seen both"). `field_events.covered_candidate_ids` is required on `conflict_resolved` and absent on every other type, holds at least one id, no null and no id twice, includes the chosen candidate, and each id is a candidate of the event's subject and field (CHECK constraints and `SVX10`). A candidate outside the set is not covered, whenever it was written; the domain reads the set instead of a time window (the domain's side is its own change).
5. **Every guard fires in every session:** the triggers are `ENABLE ALWAYS`, so a replica-mode session (`session_replication_role = replica`) does not skip them.
6. **The guard invariants and the event triggers.** `sovitech_guard.check_invariants()` lists every way a guard would be lost:
   - a required trigger missing, disabled or no longer the guard role's;
   - the recorded shape of a registered table or of any view of the schema changed: a recorded column dropped, retyped, or its collation, default, not-null, identity or generation changed (a collation decides how the guards compare text: a nondeterministic one made `BUILDING.ROOMS` equal `building.rooms`) (a default decides every time the database sets, so a default moved to 2000-01-01 would sort every new row before every resolution or revocation); a recorded constraint or unique index dropped or changed (the foreign key that keeps evidence in its project among them); a recorded policy dropped or changed; row-level security switched off or unforced; a recorded privilege of any role, on the table or a column, changed; a view's query or options (`security_barrier`) changed; or a policy, trigger, privilege or view added (an extra permissive policy would widen reads across projects; an extra trigger could alter rows as they are written; a `SELECT` or `INSERT` handed to the operator's login, which may name any engineer, would read and write across projects);
   - a default privilege of a role of the store, or granting to one, added, dropped or changed (`pg_default_acl`, recorded under the pseudo relation `(default privileges)`): a default privilege is a grant on every table or function created later, so one added by a migration would hand the next reviewed table to the app or the operator's login unseen, and one dropped could undo 0000's revoke of `EXECUTE` on functions;
   - a constraint or unique index added to a table the two guarded functions write (`candidate_events`, `document_events`, `evidence_excerpts`, `document_texts`, `audit_events`, `review_item_opens`): an added `CHECK (type <> 'withdrawn')` once stopped every owner's erasure; such a change is an admin migration that records the shape;
   - a collation, type or domain in schema `sovitech` or `sovitech_guard` other than the row types of its tables and views;
   - a rewrite rule on a table of the store; a table or view not owned by its registered owner (`sovitech_guard.relation_owners`: the access role for the relations the definer functions trust, the owner role for the rest; ADR 0013);
   - a table of the store joined to another by inheritance (a child's rows read as the parent's without passing its guards);
   - a login role holding `UPDATE`, `DELETE` or `TRUNCATE` on a table or a column;
   - a guarded function missing, replaced, not a definer, or callable by everyone; any function of schema `sovitech` that is not a registered guarded function; any definer function a `sovitech_db_` role owns outside the registry and the guard role's own schema;
   - a role other than the schema's owner allowed to create objects in `sovitech` or `sovitech_guard`;
   - a member of a definer role, or the app or operator login a member of any role; a store role that is a superuser or bypasses row security when it should not;
   - either event trigger missing or not always enabled.

   An event trigger on `ddl_command_end` runs it after every DDL command, in every session, and refuses the command when anything is listed (`SVG01`), so the command rolls back. A second event trigger, on `table_rewrite`, refuses any rewrite of a table of the store (`SVG02`): `ALTER COLUMN ... TYPE ... USING` or a volatile default would change stored rows without an `UPDATE`, so no row trigger would see it. The migration runner runs the check inside each migration's transaction, together with `sovitech_guard.unguarded_tables()`, so a migration that leaves a table of schema `sovitech` without registered guards rolls back; it runs both again after the run. The registry (`sovitech_guard.required_triggers`, `append_only_tables`, `project_tables`, `guarded_functions`, `recorded_shape`) is owned by the guard role; changing it takes an admin migration, which records the new shape with `sovitech_guard.record_shape()`.
7. **The runner's self-check** (`packages/db/src/self-check.ts`). Once the guards are installed, the runner performs one engineer verification and one erasure end to end on TEST rows (TEST accounts, project, document, text and document value), as the app and the operator's login would call them, in a transaction that is always rolled back: inside each admin migration's transaction (the migration rolls back when either path fails), after each ordinary migration commits (the migrator's transaction cannot act as the app or the operator, so the run fails naming the migration, and every later run fails until a new migration repairs it), and at the end of every run. A migration can add something that is a tightening on its face yet stops a guarded path; nothing is loosened, but people are blocked (rule 7), so the run must fail.
8. **What cannot be guarded.** A Postgres superuser can switch event triggers off or drop the guards. The superuser is the database administrator of ADR 0012, used only by the migration runner for admin files and never by the app, a seed or a script. An admin migration that weakened a guard would be a visible file in `packages/db/migrations/`, reviewed like any change to the guardrails.

## Consequences

- G4-20 passes: `UPDATE`, `DELETE` and `TRUNCATE` by the app role fail with `42501` on candidates, evidence locators and excerpts, and every event table (candidate, field, document, document analysis, asset, guardrail, audit, app role and opened-item events), and every row is unchanged. `packages/db/src/guards.test.ts` shows the same statements from the table owner fail with `SVA01`, and that `engineer_verified` is refused by every route: direct SQL as the app role, the operator's login, a seed through the data-access layer, a seed in SQL as the owner, the administrator in replica mode, and migrations that insert it, disable or drop the guard, replace the function, act as its role or try to join it.
- An ordinary migration may still add columns, and constraints and indexes on the tables the two guarded functions do not write. One that drops or disables a guard, grants or revokes any privilege or default privilege, adds a rule, a policy, a trigger, a view, a function, a collation, a type or a domain, sets or drops a column default or changes a column's collation, drops or retypes a recorded column, drops or changes a recorded constraint or unique index, adds a constraint or unique index to a table the guarded functions write, rewrites a table, joins a table by inheritance, opens the schema to another role or switches row-level security off fails and rolls back; one that touches the accounts, role events, current roles, projects or members fails for want of ownership (`packages/db/src/guards.test.ts`, "a migration cannot weaken a guard", each attempt matched to the problem the check names, and the same attempts on the migrator's own login outside the runner). A new column the app writes therefore comes with its grant in an admin migration that records the shape. A new table of schema `sovitech` comes with its guards in an admin migration; a table that must be updated (a job queue) belongs in another schema.
- Found in self-review before the phase report, and fixed with the recorded shape and the rewrite trigger: the first version of the check looked only for the named guards, so a migration could have added a permissive policy (reads across projects), rewritten candidate values with `ALTER COLUMN ... TYPE ... USING`, dropped the foreign key that keeps evidence in its project, or added a trigger, without a refusal.

- **Found by the phase 1 review (2026-09-25),** each confirmed against real Postgres, and fixed as above: the recorded shape held no view definitions, column defaults, privileges or functions, so an ordinary migration could replace the current-roles view (every account an engineer: cross-project reads and `engineer_verified` by a user with no role), move a time default to 2000-01-01, add a definer function granted to the app that wrote forged events, or grant the operator's login reads and writes on candidate events and excerpts, all with `check_invariants()` empty; and the store took an event's actor and role on the caller's word, so an owner's request could store an engineer's resolution, rejection or not-applicable mark, a system supersession, or a confirmation in another owner's name. `packages/db/src/access.test.ts` proves the event binding and the covered set.

- **Found by the phase 1 review, round 3 (2026-09-25),** each reproduced on a TEST database first (scratchpad `build/fix3/probe-before.json`; refused in `probe-after.json`): a commercial reviewer, an engineer or a co-owner stored a `user` value in the owner's name on the Fire Safety decision, and an owner stored a `calculated` value (the author and source were the caller's word); a service account stored a system supersession of a document value, a withdrawal with no removed document, a rejection and a conflict resolution, and an owner withdrew a document value; a document value on unverifiable evidence alone was stored; a document with no analysis event, and alternatives that were not quantities, were stored and then broke reads; an ordinary migration set default privileges for the owner (the next table would have granted the app `INSERT` and the operator's login `SELECT` and `INSERT`), changed a column's collation, created a nondeterministic collation, a domain and a type, and added a CHECK that stopped every erasure, each with `check_invariants()` empty. Decisions 4, 6 and 7 changed as above. Proofs: `packages/db/src/access.test.ts` (the candidate guard, with the controls: owner, co-owner, an engineer's site entry, a service account's engine and reference values; the system events and withdrawals), `store.test.ts` (evidence whose check matched, the analysis event, the alternatives), `guards.test.ts` ("a migration cannot weaken a guard": each attempt refused for its own reason, on the runner and on the migrator's own login, and a table created after the refused default privileges granting nothing), `self-check.test.ts` (an admin migration that records a constraint stopping erasure or verification is refused; an ordinary one that stops the paths the self-check drives fails the run). The store's stricter readings (a job's account that is not a member, the system events, the field-event roles, the invariants) stay proven by the store's own tests.

## How to reverse

- **Remove a guard:** an admin migration that drops the trigger and its row in `sovitech_guard.required_triggers` together, then calls `sovitech_guard.record_shape()`. Removing a guard lets more values through or involves fewer people, so it is a loosening under guardrails section 10 and waits for the approver's own words.
- **No event triggers:** an admin migration that drops `sovitech_guard_after_ddl` and `sovitech_guard_table_rewrite` and the invariant that names them. The row triggers stay; only the defence against a migration that disables them or rewrites a table goes. Also a loosening.
- **The event binding:** drop `guard_event_actor` and its three rows in `required_triggers` in an admin migration. The store would again take an event's actor and role on the caller's word; a loosening.
- **The candidate author and source guard, the system event limits, the analysis and alternatives checks:** drop `guard_candidate_author`, the `SVX13`/`SVX14` branches of `event_actor_written`, `guard_document_analysis`, `candidates_alternatives_shape` or the field-event role constraints in an admin migration that records the shape. Each lets more values or events through; a loosening.
- **The author role and the document removal checks:** drop `author_role` (with its CHECK and the lines of `candidate_author_written` that set it), or `document_events_withdrawn_by_person_or_request`, the SVX15 branch of `event_actor_written` or `document_events_erased_by_erasure`, in an admin migration that records the shape. Each lets an engineer's entry pass for the owner's choice, or lets a job remove a document on its own: a loosening. Holding withdrawal to the owner alone again (P-1-DOCUMENT-REMOVAL-OWNER-ONLY) is a tightening on engineers and waits for the approver's own words.
- **The self-check:** remove the `storeSelfCheck` calls from `migrate.ts`. Nothing is loosened by it, but a migration that stops erasure or verification would go unnoticed until someone tried either.
- **Stricter:** add a guard and its registry row in one admin migration. Tightening costs no owner time here.

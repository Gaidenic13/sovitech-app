# 0042. The view-model's readings: the resolver, the formatting module and the question engine

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-30

## Context

- **Guardrails** rule 2 ("UI code receives only resolved field objects, which carry the badge and the source line"), 2.8 (one badge, the first match in the table order; "The source always shows in the line below the value"), rules 1, 3, 4, 5, 6, 7, 8, 9, 12 and section 4. Prompt 3 section 6 places the one resolver, the formatting module and the question engine in `@sovitech/view-model/server`; ADR 0036 fixes the display objects they produce.
- **Where the rules leave a reading open**, the builder chose; each choice below keeps the Truth promise at least as strict as the text and adds no question, gate, confirmation, badge or status wording. Sources: F-VALUE-10, F-RENDER-04, F-QUESTION-01 to F-QUESTION-09, F-PROPOSAL-07; PRD R-002 to R-004, R-043, R-045, R-046, R-051; D-05 (approver), D-10, D-11, D-12, D-14, D-26, D-53, D-64, D-92.

## Decision

1. **Badges** are read from the derived state (`DerivedCandidate.verification` and `.confidence`, never `Candidate.confidence`: ADR 0016 decision 22) and chosen by the registry's `firstBadge`. Beyond 2.8's table as written: an engineer's own `user` entry not yet verified reads **SOVITECH will check** (phase 1 R5-6: "Provided by you" is "Owner entered or accepted"); an ambiguous reading (rule 8, "low confidence") on an owner field reads **Please check**; a design-stage document reads **From design drawings** only on an existing building or a BMS modernization (2.3), and on an engineer field **SOVITECH will check** comes first (2.8's order).
2. **Source lines**: "Found in <file>, page <n>" (or sheet and cell) for a document value; "Inferred from <file>, page <n>" for an inference; 2.8's generated sentences once confirmed or verified (the verified one only with the event's date); "<stage> <revision> (<year>): <file>, page <n>" for design drawings; "(stage unknown)" after a document of unknown stage on an existing building or BMS modernization project, and on a value from a superseded revision (2.3); none for the owner's own answer, whose badge names its source. *Part B, 2026-10-01 (V-8), the reading recorded:* 2.3's "When the stage is unknown, the source line says so" sits in the bullet "Old-only values stay visible", so its literal scope is a value only a superseded revision had; "(stage unknown)" shows there, and also on every document value of the two project types 2.3's "Stage matters more than date" names. That is a superset of the literal scope, so this reading does not narrow the text; the wider reading (every document value of every project) stays the build log's proposal P-3-STAGE-UNKNOWN-SCOPE, not applied.
3. **Values**: a document value as written (rule 9), its approximate word kept and no "about" added (the original carries it; rule 8 and US-REVIEW-02 AC7 read together); the owner's quantity every digit they typed; an estimate "about <value> (<low> to <high>)" to rule 9's figures, rounded outward; a calculated count exact; a calculated quantity only with the significant figures of its inputs, else refused; an ambiguous reading a range over its readings; a stale calculated or estimated value reads "Out of date, recalculating" in place of its figure (2.4: "never as current"). Enum, decision, qualifier and stage words live server side (`resolver/labels.ts`), because a display object carries the whole text its element shows; `labels.test.ts` keeps them equal to the UI catalogue's option labels.
4. **Value ids** beyond ADR 0036: a multi-fact field's facts are `<field id>.<qualifier>` (`unknown` for a fact whose qualifier no one stated), a value with an unknown qualifier that rule 4 compared is `<field id>.unqualified<n>`, and each value of a conflict is `<field id>.value<n>`, which the `resolve_conflict` action names.
5. **Number formats and dates** (formatting module): English separators by default ("45,600"), Romanian ("45.600") behind the `ro` option (D-26); decimal.js arithmetic from numbers, never from text; a date is the calendar day its ISO timestamp writes, in the zone it carries, as "D MMM YYYY" in a `<time>`.
6. **Rule 5's test**: "the value matters now" reads `affects` outputs under `capex.` or `scope.`; a fact in conflict is put to its person by rule 4, never through a confirmation; a value already user_confirmed (on another source) or engineer_verified is not uncertain. Ties within the budget keep a fixed order (field key, candidate id).
7. **Continue** reads a multi-select as a whole (PRD R-051 interim): with none ticked and none suggested the question is skipped, except that an option the owner had chosen and has now unticked records the other option (the owner's own change, never a decision taken for them). A suggestion the page reports is accepted only when the server makes it now; any other is counted and ignored.
8. **Suggestions** pass one guard whatever rule made them: only a decision field, or the occupancy or schedule (rule 3), with no value and no skip, never a life-safety system or one never preselected (rule 11; D-64). No production rule exists (P-3-DETECTION-FIELDS; D-11, D-12).
9. **Step 8**: an inline ask per missing first-estimate slot, allowed while the slot holds no more skips than its earlier questions (one for building type and the systems, none for the area). Output availability names the SOVITECH datasets each declared formula waits for, by gate (cost ranges and benchmarks; point templates), and the SOVITECH function set, which no gate opens (rule 9), plus each missing first-estimate input with its Add action. *Amended 2026-10-02 (phase 3, closing):* the output that carries rule 10's stage 2, "Preliminary investment estimate", waits for every first-estimate input, not only those its formula reads (rule 10's table gives stage 1 the figure "when first-estimate data is missing"; rule 7's `first_estimate` row, "or else 'Not available yet' with the missing item and an action to add it"), so the Proposal card, which shows that output's line, names the gross floor area with "Add gross floor area" when it is the only input missing.
10. **Late findings** are dotted on step 3 for the building's quantities and counts and on the step of the question that asks any other field (ADR 0039 decision 3).
11. **One rule line added**: `yes_building_type_vowel`, "Yes, it's an {buildingType}", the same words as section 4's "Yes, it's a hotel" with the article a vowel needs ("Yes, it's an office").

## Consequences

- One pure function per display: two screens that read the same stored state show the identical display (G2-7), and the render contract's projection (`servedDisplayOf`) agrees with the components by construction.
- A value the rules cannot show honestly is refused in code (a calculated quantity without its inputs' precision, an estimate outside its own range, a stage 3 label from a parameter) rather than shown.
- The server holds the words of options and qualifiers as well as the UI catalogue; the drift test fails when they part.

## How to reverse

Each reading is local to one function in `packages/view-model/src/{resolver,formatting,intake}/`, with its tests; change the function and its test together. Readings 1, 6, 7 and 8 decide what the owner is shown or asked: making any of them looser (a badge later in 2.8's order, a confirmation where rule 5's test fails, a suggestion on a fact or a life-safety system) is a loosening under guardrails section 10 and needs the approver's own words.

# 0012. The store: Postgres, Kysely, hand-written SQL migrations and UUIDv7 ids

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25

## Context

- **Prompt 3 section 5.2, row "Database"** (sources: `docs/build-readiness.md` section 3 "Now" item 4; guardrails rule 13): Postgres (local Docker; Testcontainers in tests), Kysely, hand-written SQL migrations, UUIDv7 generated in app code, and row-level security on `project_id`; candidates, evidence locators and every event table append-only; excerpt text and extracted document text in their own tables keyed by project id and content hash; one audited `SECURITY DEFINER` erasure function as the only path that alters stored evidence.
- **Build-readiness 3 "Now" item 4:** "Postgres, in local Docker and in CI with Testcontainers, using Kysely and hand-written SQL migrations", with `REVOKE UPDATE/DELETE` plus raising triggers, row-level security on `project_id`, one guarded writer of `engineer_verified` (G10-3), UUIDv7 generated in app code.
- **PRD:** R-157 (candidates and events never changed; one guarded writer) and R-158 (documents stay with their project) require the behaviour; section 13 "Build recommendations for prompt 3's ADRs", row "The store", records the mechanism as Proposed with D id **none**. The owner decided no D row as of 2026-09-25, so the 5.2 default applies with this ADR.
- **Guardrails:** 2.1 to 2.5 (the value model), rule 4 ("Storage. Candidates are immutable, and events are append-only"), rule 10 ("Engineer verification is an authenticated action"), rule 13 ("Isolation", "Erasure").
- **Downloads approved by the owner** (build log, "The owner's answers", item 2): the Postgres and Testcontainers ryuk images from Docker Hub, pinned by digest.

## Decision

1. **Postgres 18.6** (Debian bookworm), pinned by the multi-architecture index digest `postgres:18.6-bookworm@sha256:3725f4e2499eef5134592b3b4ab79a543ed7f8e533b05b5b637af926630f6650` (pulled 2026-09-25; 649 MB). `packages/db/src/images.ts` holds it; `docker-compose.yml` runs the same image for local development, and `packages/db/src/images.test.ts` fails when the two differ.
2. **Testcontainers in tests.** `@sovitech/db/testing` (`packages/db/src/testing/index.ts`) starts a throwaway Postgres per test file with `testcontainers` 12.0.1, applies every migration and opens a store per login role. The reaper is pinned too, through `RYUK_CONTAINER_IMAGE`: `testcontainers/ryuk:0.14.0@sha256:7c1a8a9a47c780ed0f983770a662f80deb115d95cce3e2daa3d12115b8cd28f0` (4.3 MB), the version 12.0.1 starts. When `DOCKER_HOST` is unset, the helper asks the docker CLI for its current context, so Colima works without setup. The data directory is a tmpfs and fsync is off: test data only. Start-up is about 3 s per file on the development machine.
   - **Version pins.** testcontainers 12.1.0 needs Node 22.22 and 12.0.2 to 12.0.4 need undici 8 (Node 22.19); the machine runs Node 22.17.1 (`.node-version` pins 22), so 12.0.1 (undici 7) is pinned. `@testcontainers/postgresql` is not used: its 12.x releases depend on `testcontainers ^12.0.1`, which resolves to 12.1.0. `GenericContainer` with a log wait strategy does the same job.
   - **Build scripts.** testcontainers brings `ssh2` with the optional native add-ons `cpu-features` and `protobufjs`. pnpm 12 refuses an install until each build script is allowed or denied; `pnpm-workspace.yaml` denies all three (`allowBuilds: false`), so they never run. They serve Docker over SSH, which the tests do not use.
3. **Kysely 0.29.6 on `pg` 8.23.0.** `openStore(url)` (`packages/db/src/connection.ts`) opens a pool whose sessions run in UTC and whose type parsers return timestamps as ISO 8601 strings with six fractional digits (so they order as text and keep the database's microseconds), `date` columns as written and `uuid[]` as string arrays. Kysely is scoped to schema `sovitech` (`withSchema`). Quantities are stored as `double precision`: the same double the domain holds, so the store neither rounds a value nor coerces one in app code (rule 9 "Stored values are never rounded"; the lint bans on `Number()` apply to `packages/`); the text as written stays in `original_text` (rule 8).
4. **Hand-written SQL migrations** in `packages/db/migrations/`, one transaction each, recorded with their SHA-256 in `sovitech_meta.schema_migrations`. A file that changed after it was applied stops the run: write a new migration instead. Two kinds, by file name:
   - `NNNN_name.admin.sql` runs on the database administrator's connection (a superuser): roles, the functions owned by the definer roles, the guards and the event trigger (ADRs 0013 to 0015);
   - `NNNN_name.sql` runs as `sovitech_db_migrator` acting as `sovitech_db_owner` (`SET LOCAL ROLE`): tables, indexes, grants and policies.

   Inside each migration's transaction, and again after the run, the guard invariants must hold and every table of schema `sovitech` must have registered guards (`sovitech_guard.check_invariants()`, `unguarded_tables()`; ADR 0014), or the migration rolls back and the run fails. Once the guards are installed, the runner's self-check also performs one engineer verification and one erasure on TEST rows, always rolled back (`src/self-check.ts`; ADR 0014, decision 8). The runner sets the login roles' passwords on every run and never prints one. `pnpm --filter @sovitech/db migrate` applies them to the local database from `.env` (template: `.env.example`).
5. **UUIDv7 in app code**: `newId()` (`uuid` 14.0.2, `v7`). Every row the data-access layer writes gets its id before it is written. The erasure function writes one `withdrawn` event per affected candidate, whose number only the database knows at that moment; those ids come from Postgres 18's `uuidv7()`, still UUIDv7.
6. **The data-access layer** (`packages/db/src/`): `withRequest` (the request scope, ADR 0013), append-only writes (`writes.ts`: no update or delete method exists in the package), calls to the guarded functions (`guarded.ts`), and reads that return the domain's own types for `derive` and `deriveAssetRegister` (`reads.ts`, `mapping.ts`). A read that feeds `derive` passes `subjectId` and every document event of the project (`readFieldInputs`, `deriveContextFor`); `readAssetRegisterInputs` passes the project's document statuses and every evidence entry of each appearance, so an appearance stays evidence while any of its entries cites a document that is not withdrawn or erased (2.3, "A candidate or asset with evidence from other active documents keeps that evidence"). `insertCandidate(request, candidate, field)` runs the registry's unit check (`checkQuantityUnit`; 2.7, rule 8) on the quantity and every alternative reading before it writes, and returns `refused` with the reason (`unit_unknown`, `dimension_mismatch`, `field_takes_no_quantity`) and nothing stored; `recordAssetAppearance` takes one or more evidence entries. Refusals raised by the database carry their own SQLSTATE (`SVA01`, `SVV0n`, `SVE0n` and `SVE1n`, `SVR0n`, `SVX0n` and `SVX1n`, `SVG01`) and reach callers as `StoreRefusal` with a code (`errors.ts`).
8. **No stored text in errors or the server log** (rule 13, "Logs and error reports never contain document text"). A database error can carry stored text: the failing row of a CHECK violation or the key of a unique or foreign-key violation in its DETAIL (Postgres leaves the row out on tables with row-level security, but the account and role tables have none), and the input itself in the message of an input error ("invalid input syntax for type uuid: ..."). So:
   - nothing the data-access layer throws keeps the database's error: a refusal becomes `StoreRefusal` with the store's own message, any other database error becomes `StoreError` with only its SQLSTATE and the constraint, table and column it names (`scrubbed` in `errors.ts`, applied by `refusing`, `insertCandidate` and `withRequest`, which also covers the deferred checks at commit);
   - migration 0000 sets `log_error_verbosity = terse` (no DETAIL, hint or context in the server log) and `log_min_error_statement = panic` (no failing statement) on the database, for every session; both are superuser settings, so no login role can switch them back. `docker-compose.yml` passes the same two settings to the server.
7. **Scope of the schema** (migrations 0001 to 0005): accounts, app role events, projects and members, audit events; subjects; documents, document events, document analysis events (the record is written once; its analysis status and coverage are events) and extracted text; candidates, evidence locators, evidence excerpts, candidate and field events (a `conflict_resolved` event names the exact candidates it covered, `covered_candidate_ids`, ADR 0014); asset identities (unique per project and normalised tag), appearances and asset events; guardrail events (section 8 types; the reason is a code, never document text); the opened-item record; the rule 10 stage 3 record with one row per input candidate hash; proposal snapshots with their candidate ids and formula versions.

## Consequences

- Every guardrail case that touches the store runs against real Postgres with the real migrations: G4-20, G10-3, G10-8 and G13-5 in `tests/guardrails/`, and the route-by-route tests in `packages/db/src/guards.test.ts` and `store.test.ts`. `pnpm test` therefore needs Docker running, as prompt 3 section 1 item 3 requires. CI needs a Docker service for Testcontainers (a GitLab `docker:dind` service with `DOCKER_HOST` set); `.gitlab-ci.yml` does not provide one yet.
- A document's kind, stage and revision are recorded at registration. If phase 2 detects them after registration, it adds them as candidates on the document subject (2.2 lists "the stage of document M-001" as a field) or through a new migration; the record is never updated.
- The `documents.content_hash` column accepts only `sha256:` and 64 hex digits, so a content hash can serve as a storage path segment under the project (phase 2) without escaping it.
- Rows are never updated or deleted, so tables grow. Retention and backups are D-35 (PRD section 11).
- **Left open by decision 8:** the server still logs an error's message, and an input error's message holds its input. The layer sends only ids generated in code and typed values into typed columns, so no stored text reaches such a message by any path it offers; a caller that passed document text as an id would put it in the server log (never in what the layer throws). Suppressing error lines in the server log (`log_min_messages`) would hide every database error from whoever runs the server, so it is not done.
- `packages/db/src/access.test.ts` proves decision 8: a CHECK violation whose failing row holds TEST text, and an input error echoing TEST text, leave the text out of the thrown error, and the server log carries the violation's name but not the text.

## Phase 1 review (2026-09-25)

The verifier and the adversarial reviewer found, confirmed against real Postgres, that a CHECK violation on the account table carried the failing row, TEST text included, in the error the layer re-threw and in the server log. Decision 8 was added; the column of decision 7 and the document statuses of decision 6 came with the fixes recorded in ADRs 0013 to 0015.

## Phase 1 review, round 3 (2026-09-25)

The verifier's round 3 and the adversarial reviewer found, each reproduced on a throwaway TEST database before the fix (scratchpad `build/fix3/probe-before.json`, and `probe-after.json` after): `insertCandidate` stored a quantity in `banana`, or in kW on an area field, because the unit check ran only on read; `readAssetRegisterInputs` passed only the first evidence entry of an appearance, so an asset shown in two documents dropped when the first was deleted; and a malformed alternative reading, or a document with no analysis event, could be stored and then broke every read of its field or project. Decision 6 changed as above; the store's side is in ADR 0014. `packages/db/src/store.test.ts` proves each: the unit refusals on the quantity and on an alternative, with nothing stored; the asset seen in two documents counted until both are removed; the alternatives CHECK and the analysis check. Indexed at integration (guardrails 1.6): G4-31 (its store half) and the store assertions added to G8-4 (the unit refusal) and G1-14 (unverifiable evidence alone).

## How to reverse

- **Another database:** the domain does not depend on the store. Replace `packages/db` and port the guards; the case files G4-20, G10-3, G10-8 and G13-5 state what must still hold.
- **Another query layer:** only `packages/db/src/{connection,request,writes,reads,guarded}.ts` use Kysely; the SQL migrations and guards do not.
- **An ORM or generated migrations:** keep the admin files as hand-written SQL: the guards depend on who owns each object.
- **Another Postgres version or image:** change `images.ts` and `docker-compose.yml` together (the test fails otherwise), and re-run the store tests. Postgres 17 lacks `uuidv7()`: generate those ids in app code first.

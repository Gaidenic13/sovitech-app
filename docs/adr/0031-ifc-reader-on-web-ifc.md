# 0031. The IFC reader on web-ifc: its package, its division of labour with the STEP text reader, its sandbox, and the dispatch

- **Status:** Accepted: owner decision 2026-09-26 for the parser ("web-ifc instead (Recommended)"; ADR 0018). Accepted: default, reversible, for the rest: where the reader lives, how it uses web-ifc and the in-house STEP text reader, its image, and the worker's dispatch. **For the approver and the owner, listed below:** the reader's exchange-structure check recorded in the contract's `schemaCheck` (decision 5), and "placed outside the site's extent" not checked in this phase (decision 6).
- **Date:** 2026-09-26; amended 2026-09-30 (the phase 2 review: decisions 2, 4, 8 and 9, and the Consequences)

## Context

- **The owner's decision of 2026-09-26** (build log, "Owner answers during the run"): IfcOpenShell 0.8.5's and IfcTester 0.8.5's PyPI wheels bundle CGAL packages published under the GPL (ADR 0018, "The stop"). Asked how the app should read IFC models, the owner answered **"web-ifc instead (Recommended)"**: IFC data is read with web-ifc (MPL-2.0) in the no-network sandbox, as the viewer will in phase 4; the in-house STEP reader stays only for word-for-word evidence excerpts; IfcOpenShell, its schema validator and IfcTester are not used, so the IDS model check waits (a recommendation, D-36); counsel still reviews MPL-2.0 (D-94). ADR 0024's in-house schema tables are superseded.
- **Prompt 3 section 8** (the IFC pipeline): code reads IFC, not the AI; every job that opens an owner model runs in a container with no network, a read-only input mount, and memory and time limits; the order is header and schema, units, spatial tree, groups and systems, elements with types and property sets, geometry last; a file with problems is read where it can be, and the problems are stored with the document for the engineer, never hidden; logs carry codes, GlobalIds and STEP ids only; web-ifc is wasm32, so 4 GB is its ceiling. **Section 11**: the extraction budget (a `perf` IFC4 file of about 100 MB: the data pass within 5 minutes and under 4 GB). **Section 12**: packages from npm, pinned, with lockfiles.
- **ifc-input** 2.2 (the stack; its IfcOpenShell recommendation is superseded by the owner's decision), 4.1 (the verbatim STEP line is the excerpt; units from the file), 5.3 to 5.5 (the fixtures and cases), 6.2.13 (hidden content, a proposal).
- **ADR 0022**: the extraction contract, one JSON Schema; an IFC file is always `stored_only` with "IFC model"; typed STEP literals as text tokens; the sealed `ifcValues`; `Producer.name` is the constant `sovitech-extractor`. **ADR 0024**: the Python extractor, whose IFC data pass (on its own schema tables) this replaces with the same stages, codes and output. **ADR 0018** decision 4: the pinned `node:22.17.1-bookworm-slim` base. **ADR 0020**: the worker runs `docker run` with ADR 0018's flags; jobs carry ids only.
- **PRD**: R-022 to R-024 (models stored "Not analysed"; the engineer's record; model text as findings), R-027 to R-041 (the gated value path), D-01 (parsing scope), D-36 (the IDS check), D-94 (licences).
- **Guardrails v1.6**: rule 1 (evidence checked by code; the content hash), rule 8 (the reader never parses a number out of text), rule 12 (coverage by code), rule 13 (logs never hold document text; derived files keyed by project), rule 14 (embedded instructions and hidden content are findings and change nothing).

## Decision

1. **Where it lives: `packages/ifc-reader`** (`@sovitech/ifc-reader`), a workspace package in TypeScript, rather than a new `services/ifc-reader`. `services/**` is scanned only by the Python checks (tools/checks/scan-roots/roots.json), so a TypeScript service there would sit outside ESLint and the lint bans (`Number()`, zero fallbacks, `JSON.parse`, totals), dependency-cruiser, the reserved-term and mockup-figure scans, the root typecheck and Vitest; under `packages/` it gets all of them by the existing configuration. It is server-side only: dependency-cruiser's `SERVER_SIDE` names it, so no browser code reaches it (the browser never parses the owner's IFC, prompt 3 section 8). Its image is built from `services/ifc-reader/Dockerfile`, beside the Python extractor's `services/extractor/Dockerfile`: under `packages/` the reserved-term check would have to read a Dockerfile as copy, or list it as non-copy, which is an exception for the approver; `services/` is where the sandboxed services' images live.
2. **web-ifc 0.0.78**, pinned in `pnpm-lock.yaml` (npm registry, integrity `sha512-LGKMNYFV…`), MPL-2.0: the licence check reports it as MPL. It reads the model: the schema family (`GetModelSchema`; IFC2X3, IFC4 and IFC4X3 with their aliases), the header lines, every instance's class (`GetLineType`, `GetNameFromTypeCode`), its attributes by name in schema order and their values (`GetLine`), and the classes' inheritance (`InheritanceDef`), which sorts instances into the data pass's kinds (project, site, building, storey, space, zone, system, type object, element). It is initialised once per process, single-threaded (no worker threads in the sandbox), with its own logging off. A one-off search of `web-ifc-node.wasm` for the CGAL GPL package symbols the licence check's binary search uses (ADR 0018 decision 6) found none. Since the phase 2 review (2026-09-30) the licence check itself searches every `.wasm`, `.node`, `.so`, `.dylib` and `.dll` of installed npm packages for those markers, and lists web-ifc's bundled CDT (MPL-2.0), glm (MIT) and tinynurbs (BSD-3-Clause) for the notices page in `tools/checks/licences/bundled-notices.json` (D-94; ADR 0009).
3. **The division of labour.** web-ifc decides everything about the model. The in-house STEP text reader (`src/step-text.ts`, the TypeScript copy of `services/extractor/src/sovitech_extractor/ifc/step.py`) is used only for word-for-word evidence: the verbatim statement of an instance, from "#" to ";" (a fact's excerpt), and its literal tokens (`430000.`, `+007`, a string's token with its escapes beside its decoded text), which web-ifc does not give back as written. An instance is read only when **both readers see the same statement**: the same number of attributes, and every literal the same (a real's text, an integer's digits, a string's decoded text, an enumeration or logical, a binary, a reference). Otherwise it is not read, with a code: `step.syntax` (the text reader cannot read the statement), `step.attribute_count`, `step.readers_disagree`, `step.not_read_by_web_ifc`, `step.unresolved_reference`. web-ifc hands some values out bare (IFC2X3 logicals as `true`, `false` or nothing; integers inside aggregates as numbers; an unset reference as `{value: null}`; a derived attribute as a reference to 0); the agreement check reads each form. The two text readers read one TEST corpus, `src/step-text-corpus.json`, the same way (`step-text.test.ts`; `services/extractor/tests/test_step_text_parity.py`); the Python one gained one fix from it (trailing whitespace after the last statement was read as unexpected text). STEP ids are web-ifc's integers: identifiers it reads, never digits turned into numbers, so the Python STEP-id helper and its proposed exception to the bans (ADR 0024 decision 10) are gone.
4. **The data pass** (`src/reading.ts`) keeps ADR 0024 decision 6's stages, codes and results: header and schema; the project's unit assignment and the units values name themselves; the spatial tree; zones and systems with their members and the buildings a system serves; elements with containment, type objects, property and quantity sets (on the occurrence and through the type) and control links; presentation layers switched off as hidden content; geometry last, not processed (`geometry.not_processed`). The register (`src/register.ts`) names an IFC2X3 generic occurrence by its type object's class, as ADR 0024 did. **What IFC2X3 cannot express is recorded in coverage** (amended 2026-09-30, the phase 2 review; ifc-input 5.3, "recorded in coverage"): `ifc2x3.kind_written_as_user_defined` per element whose USERDEFINED kind is written as an enumeration value, `ifc2x3.class_not_expressible` per IfcElectricDistributionPoint whose function IFC4 moves to IfcUnitaryControlElement, and one `ifc2x3.system_kind_not_expressible` entry naming every IfcSystem; IFC4 models have none (`src/ground-truth.test.ts`, IFC-11). The gated values (`src/values.ts`, `src/proposals.ts`, `src/datasets.ts`) are built only when the request asks for them, from mounted TEST or approved `ifc-mapping` datasets in the same format. **Checked:** on the four synthetic models, gate closed and gate open (with the TEST table), the reader's outputs equal the Python data pass's, key by key, except the producer's libraries, the schema check (decision 5) and the site-extent coverage entry (decision 6); the ground truth of all four models passes (`src/ground-truth.test.ts`), and IFC-11 holds at reader level.
5. **Output** (`src/output.ts`), the contract's JSON exactly, checked by the contract's own strict parser and `outputAnswersRequest` before it is written: an IFC file is `stored_only` "IFC model" (G12-5); the engineer's record holds the header's schema as written, the authoring tool, the IfcProject GlobalId, the classes present (as web-ifc names them), `processing` (`partial` while geometry is not processed), and the schema check; there is **no IDS result** (the IDS model check waits, D-36: an IDS the request names is checked for its hash and not run); findings are `embedded_instruction` (Name, Description, ObjectType, LongName, text property values and the header, with the Python extractor's detector, English and Romanian), `hidden_content` (`hidden_content.layer_off`, naming the element and the layer) and `schema_error` (each parse problem by its code and STEP ids: `step.unexpected_text`, `step.duplicate_id`, `step.complex_instance`, `step.no_endsec`, `step.non_ascii_text` and the codes of decision 3). `Producer.name` stays `sovitech-extractor` (the contract's constant), with the reader named among the libraries: `sovitech-ifc-reader`, `web-ifc 0.0.78`, `sovitech-step-text`. **For the approver:** the contract says schema problems are `schema_error` findings, and its invariant ties those findings to `schemaCheck.outcome` `problems`. No schema validator runs (the owner's decision leaves `ifcopenshell.validate` unused, and web-ifc validates nothing), so the reader records its own **exchange-structure check** there, named as such (`tool: sovitech-step-exchange-check`): `problems` when it found any, `no_problems` otherwise. It checks ISO 10303-21 and the two readers' agreement on each instance read; it checks no type, WHERE rule or inverse cardinality, and the engineer's record must not read it as a schema validation. The alternative, parse problems in coverage only, would leave them unstored: the API stores findings and the model record, not `coverage.ifc`.
6. **Hidden content "placed outside the site's extent"** (ifc-input 6.2.13) is **not checked in this phase**: it needs the site's extent and the elements' placements, which are geometry (phase 4, with the viewer's conversion), and the distance is the approver's ("by more than a registered distance"; none is registered). Coverage says so, per site: `hidden_content.site_extent_unknown` when no site has a shape, `hidden_content.site_extent_not_checked` otherwise. The synthetic sites have no shape.
7. **The command line** (`src/cli.ts`, `src/bin.ts`) takes the Python extractor's arguments and exit statuses (`--request --document --out [--datasets] [--ids]`; 0 written, 2 request refused, 3 job refused, 4 internal error), so the worker runs either reader the same way. The request and datasets are read with the YAML reader restricted to JSON (the `no-json-parse` ban); output.json is written atomically. While a job runs, the standard streams' writers and the console point nowhere; the log lines (JSON: level, code, and at most a class name, a count, STEP ids and GlobalIds) go to the writer kept aside (rule 13). A sealed section too large for one string is refused (`output.too_large`, exit 4), never truncated. Since ADR 0034 (2026-09-30) a request that asks for IFC values gets `output.json` as lines (the output, a stream header, each STEP statement once, the facts, the proposals), written through a file stream; every other output stays one JSON text.
8. **The sandbox image** (`services/ifc-reader/Dockerfile`), built from the repository root (`docker build -f services/ifc-reader/Dockerfile -t sovitech-ifc-reader:dev .`), with a root `.dockerignore` that lets in only the lockfile, the workspace manifests and the four packages' sources. The build stage, on the pinned `node:22.17.1-bookworm-slim` digest, installs pnpm 12.6.0 from the npm registry (corepack 0.33 cannot unpack pnpm 12's per-platform executables), installs from the committed lockfile with `--frozen-lockfile --filter "@sovitech/ifc-reader..."`, and bundles the reader into one file with esbuild 0.28.2 (the lockfile's). The run-time stage, on the same digest, holds Node, the bundle, and web-ifc's Node build (`web-ifc-api-node.js`, `web-ifc-node.wasm`, its package.json, LICENSE.md and README.md); npm and corepack are removed; it runs as uid and gid 10001 with `node --max-old-space-size=2048 --disallow-code-generation-from-strings`. The API's runner applies ADR 0018's flags (`--network none --read-only --cap-drop ALL --security-opt no-new-privileges --pids-limit 256 --memory 4g --memory-swap 4g --cpus 2`, a 64 MB noexec tmpfs, the document and request read-only, one writable output place, a wall-clock kill). **Amended 2026-09-30 (the phase 2 review, attacks on the writable mount):** `/output` is a per-job Docker volume, a tmpfs sized to the output limit plus 16 MiB, `noexec,nosuid,nodev`, owned by uid 10001 with mode 0700 and backed by no host folder, kept mounted by a holder container; every container runs with `--user 10001:10001`; the runner copies `/output/output.json` out through `docker cp` and takes only one regular USTAR entry of that name within the limit, written `O_EXCL|O_NOFOLLOW` on the host (links, FIFOs, devices, folders, pax headers and oversize entries are refused as `sandbox_output_refused`); the output reader opens with `O_NOFOLLOW|O_NONBLOCK`, requires a regular file and reads at most its size plus one byte; the work folders are 0700 (`apps/api/src/jobs/copy-out.ts`, `read-output.ts`; `jobs.test.ts` with real Docker). **Probed:** network closed (`ENETUNREACH`), root read-only (`EROFS`), uid 10001, output written. The Python extractor's sandbox definition names the image too (`sandbox.IFC_READER`).
9. **The dispatch.** A job's reader is chosen by its stored format (`readerFor`: `ifc` to the IFC reader, everything else to the Python extractor), carried on the sandbox job (`SandboxJob.reader`), and the Docker runner takes one image per reader (`SOVITECH_IFC_READER_IMAGE`, default `sovitech-ifc-reader:dev`; `.env.example`). The Python extractor refuses an IFC job (`job.ifc_read_by_ifc_reader`, exit 3), so a model is never half-read by the wrong reader; its `ifc/` package keeps only `step.py` (ADR 0024). **Amended 2026-09-30 (the orchestrator's ruling on PRD R-023 and R-024, "Until decided": "Not built: no model is read"; ADR 0025 decision 4):** until the owner decides D-01, the live app queues no reader job for a model, and the worker ends a model's job that reaches it anyway with `model_reading_not_decided` before any sandbox runs. The dispatch and the reader stay built and are reached only through the tests-only switch `readModelsForTests()` (`apps/api/src/documents/model-reading.ts`), in `tests/guardrails`, `tests/api` and `tests/proposed`.

## Consequences

- **In the live app no model is read until the owner decides D-01** (decision 9, amended 2026-09-30): an uploaded model is stored and hashed with "Not analysed: IFC model stored, not analysed", and has no engineer's record, coverage or finding (`tests/api/ifc-models-stored-only-until-d01.test.ts`). Where the tests switch reading on, nothing from a model becomes a value while `ifc-values` is closed (G12-5, G12-6, G14-3 and G13-4 hold end to end through the API with the real reader: `tests/api/ifc-reader-gate-closed.test.ts`; the indexed cases keep their scripted outputs). D-01 now also decides whether the live app reads models for the engineer.
- Two parsers read a model, and they must agree on every instance the data pass reads. A statement web-ifc reads loosely (a missing comma, which web-ifc accepts) is a `step.syntax` problem and is not read: stricter on Truth; on a real export it may leave an element unread, with its code, for the engineer.
- The schema check the engineer sees is the reader's exchange-structure check (decision 5), not a schema validation; a schema validator waits for the owner (ADR 0018).
- **The gated value path does not scale to the `perf` model**: 741,528 facts, whose JSON exceeds V8's longest string, so the reader refuses the output (`output.too_large`); the API's reader also refuses outputs over 256 MB. Before `ifc-values` opens, the sealed section needs a streamed writer and a streamed reader (or relation facts that do not repeat a long relation line per member). The live path is unaffected. Built since in ADR 0034: the per-line section, read line by line by the worker; the `perf` model now goes through the whole gated path in `tests/proposed/` (ADR 0034, "Measurements").
- The data pass holds the file's text in memory beside web-ifc's copy, so memory is higher than the Python pass's, and still under half the 4 GB limit on the `perf` model.
- The IDS model check and a schema validator are not built (D-36; ADR 0018).

## How to reverse

- **Back to IfcOpenShell** (the owner's call; ADR 0018 options (a), (b) or (d)): rebuild the data pass in the Python extractor on IfcOpenShell with this reader's stages, codes and tests, make `readerFor` send `ifc` to the extractor, and retire this package and its image.
- **Another web-ifc version:** change the pinned version in `packages/ifc-reader/package.json`, `pnpm install`, rebuild the image, and re-run the ground-truth, oracle and `perf` measurements; the agreement check (decision 3) shows where its value shapes changed.
- **Services instead of packages:** move the folder to `services/ifc-reader` and add a TypeScript entry for it to the scan roots, the lint and type configurations and Vitest.
- **The schema check slot:** record `not_run` (with `ifcopenshell.validate`) and keep parse problems in coverage only, accepting that the API does not store them; or add a contract field for exchange-structure problems (a contract change, both languages).

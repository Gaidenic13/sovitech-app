## Decision

1. **The engineer workspace is not built while D-16 is open.** R-128's "Until decided" line does not keep options open, and it differs from prompt 3 5.2's "Reviews and roles" default. It is the stricter: nothing is verified or resolved in the app, so engineer-field values stay unverified and dependent results stay provisional, which blocks no owner (rule 7) and claims nothing (rules 3 and 10). So UD-15, UD-48, UD-49 and UD-44 are not built, and no route verifies, rejects, resolves a conflict, writes an asset event or records a survey. The guarded function (`sovitech.verify_candidate`) and its role, demo and opened-item checks stay as built in phase 1 (D-16's interim). The plan the engineer workspace would follow if the owner decides D-16 for it is written in the build log, phase 7, "Plan", "Track E", ready for a builder; no code of it is written.
2. **What phase 7 builds live:** the development-only admin area (UD-39 to UD-41) in the forms the PRD's lines give; the development accounts of the four app roles (ADR 0038, amended); the landing by role; G3-7's display through the existing guarded function and resolver; rule 3's correction counts (ADR 0054); GS-1 end to end on the demo; the definition-of-done report for the whole build.
3. **"Development-only."** The admin area exists only while the development login is on (ADR 0038 decision 6: development accounts set AND the fixtures-only upload guard). Otherwise each admin route answers 404 `admin_off` before the session or the role is read, so the area can never run where a real owner document could be stored (R-133 "Guardrail behaviour").
4. **Reached by role.** R-144's line forbids another menu entry, so the admin area is reached by role: `/` sends a user holding `sovitech_admin` and not `owner` to `/admin/accounts`, and every other user to the project list (`apps/web/src/admin/landing.ts`). The project list shows "New project" only to a user holding `owner` (the store refuses anyone else's owner answers: ADR 0013; a dead button otherwise), and a user without `owner` reads one line saying what their role does in this build (draft copy, `projects.roleLines`; the engineer queue waits for D-16, the commercial review for D-20 and D-16). An admin who also holds `owner` lands on the project list, which offers "Open the admin area".
5. **Who may read the admin area.** A person holding `sovitech_admin` now, read from the roles table in the user's own request (never from the request), else 403 `admin_only`. Holding `sovitech_admin` never permits verification (G10-3 already refuses an admin and a commercial reviewer at the guarded function).
6. **How the admin reads across projects.** One admin migration, `0018_admin_reads.admin.sql`, modelled on 0014: guarded definer functions, registered with the guard, not executable by PUBLIC, executable by the app's login only, each refusing every request but one by a person holding `sovitech_admin` (a new refusal code), returning ids, codes, counts, times and the stored texts the admin manages (an account's name, a role event's reason) only. Never a candidate's value, an evidence entry, an excerpt, extracted text, a file name or a project's name (rule 13, "Project boundary"; ADR 0013 decision 5; new cases G13-15 and G13-16). They write nothing.
7. **What each page shows** (the contract: `packages/view-model/src/browser/contract/admin.ts`):
   - **UD-39**: accounts with their current roles and the date of each grant; every role event (granted or revoked, by an account or the operator's login, when, the reason as recorded); projects by id, with the demo line on the demo's row, their creation date and their members; and "No processor is chosen. No owner document or excerpt is sent to any external service." (R-143 "Until decided"). No control.
   - **UD-40**: each dataset a gate waits for (`waitsFor[].kind: dataset`) and each dataset the registry declares (none in production), with its version ("No version received" while none is), its approval status read through the registry's one resolver ("No approval record" while no approver is named) and the gates and D id that wait for it. TEST datasets never appear; no IFC mapping table is listed as a dataset (R-132 "Until decided"). No review, approval, edit or import control.
   - **UD-41**: counts per section 8 event type for each project and in all (a count read from the store is a count, including none); "By release: not counted yet" (no release is recorded with the events); each speed metric next to its truth metric for each project, a metric no stored event records reading "not counted yet" and every target "Target not set" (D-34's interim; the owner correction rate on inferences counted from the owner's confirmations and corrections of inferences, with its basis); rule 3's corrections per tier and item type, and each tier's wording as shown (ADR 0054); and the erasure log, one entry per `erased` document event with who asked (the owner's account name, or the system), the role, when, the document's id and what was removed (counts), never document text or an excerpt. No control that widens a tolerance, allows estimation, raises the budget or changes a threshold.
8. **Every number is bound.** Counts, ids, dates and stored texts are display objects under the contract's value ids, so the render test reads no digit outside a bound element; no allowlist or unreadable entry is added.

## Consequences

- The owner's request "SOVITECH engineers can do the work that turns 'SOVITECH will check' into verified facts" is not met in this build: it waits for the owner's D-16 (and, for quotation records, D-20). Every engineer-field value stays unverified, every result that depends on one stays provisional, every engineer-routed conflict stays open, and no figure can reach stage 3. This is stated in the phase 7 report and the final report.
- The development engineer and commercial reviewer accounts exist (ADR 0038, amended) and sign in, with no work surface of their own; their landing says so. They keep the read surface their roles give them in the store (ADR 0013 decision 5: a person holding `sovitech_engineer` or `sovitech_commercial_reviewer` reads every project by role, a member or not): every project route that serves display objects (the steps, the extracted values, the workspace, the proposal, Documents with its file names), and, for the engineer, the engineer record of a document. They write nothing in the app: every owner write answers 403 `owner_only`, and since part B so does a revision declaration (A-3; it was the one write an engineer could make, on any project and on the demo), while D-16 is open.
- The admin's cross-project reads add definer functions to the store's guarded set; the runner's invariant check covers them.

## How to reverse

- **D-16 decided for an engineer workspace in this app**: build the build log's "Track E" (phase 7 plan); amend decision 1. Nothing here needs removing.
- **D-16 decided against** (engineers work elsewhere): nothing to remove; record the decision and drop "Track E".
- **The admin area beyond development**: lift decision 3 only with the production sign-in (D-13; R-153) and the processor route (D-09).
- **A menu entry for the admin area**: once D-10 and D-02 settle the menu (R-144), add it and keep the landing by role.

## Built (web, phase 7)

- **The area's frame** (`apps/web/src/admin/AdminLayout.tsx`): the app's shell, the area's three pages as links in the kit's SideNav (the project sidebar's grammar), and once for the whole area, with a lock, the draft line "Development only. Everything here is read-only: …". A user who does not hold `sovitech_admin` sees the app's not-found page and nothing of the area: no navigation, no admin title (the route's title reads "Page not found" for them: `apps/web/src/routes.tsx`, `adminPage`, the title now takes the viewer's roles), and no request is sent. A page whose request the API refuses (403 `admin_only`, 404 `admin_off`) hides the area the same way and sets the same title (decisions 3 and 5).
- **The pages** (`AccountsPage.tsx`, `DatasetsPage.tsx`, `GuardrailEventsPage.tsx`, shared parts in `admin-view.tsx`): each the title, one sentence, then one section per question, each a heading, a sentence and a ruled table with headers (the kit's RegisterTable, or a native table with `scope` and, on the speed and truth table, explicit `headers` per cell). Every count, id, date and stored text is the served display object, bound (the kit's Value, StatusLine, or the served text in one bound element for ids and names); the web formats, counts and names nothing of its own. No control anywhere in the page column: no button, form field, form or link (decision 7; prompt 3 5.4). States: loading (one polite line, no figure), failed ("This page could not be loaded." with "Try again"), each table's empty state in words, and "not for your role" as above.
- **Speed and truth** (UD-41): each row one pair, the speed metric's name, value and target on the left half and the truth metric's on the right, split by a hairline under the column-group headings "Speed" and "Truth" (guardrails section 4, "Each speed metric is read next to a truth metric").
- **The demo line on admin rows** (G10-10): drawn by `ProjectCell` from the row's served `demoLine`, on `isDemo` rows only (`rowDemoLine`). When the web was built the contract's admin rows carried `isDemo` and no line, and the web holds no words of 2.8's demo line, so no admin row showed it; the integrator's reconciliation below serves the line with each row.
- **The landing by role** (decision 4): sign-in returns to the page the visitor came from, else to `/`, which lands by role (`landing.ts`); the project list shows "New project" to `owner` only, one draft line per SOVITECH role to a user without `owner` (and no "start a new one" wording), and "Open the admin area" to a holder of `sovitech_admin`.
- **Not built**: no engineer page (UD-15, UD-48, UD-49, UD-44) and no verify, correct, merge, split, remove or survey control (decision 1).

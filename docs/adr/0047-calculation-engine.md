# 0047. The calculation engine: catalogue, versions, hash manifest, unknown policies, intervals and results as candidates

- **Status:** Accepted: default, reversible
- **Date:** 2026-10-05

## Context

- **Guardrails** 2.1 (`calculated`: "A deterministic formula over this project's values that adds no assumption of its own"; `estimated`: "Points from per-room tables, CAPEX from €/point, and consumption from capacity × hours are always estimated"; both "The calculation engine only"), 2.4 ("Formula versions are immutable"; "A generated proposal keeps a snapshot of the candidate ids and formula versions it used"; "Calculated candidates are transparent"; "When any input's active candidate changes, the engine appends a new calculated candidate and supersedes the old one"), rule 1 ("Formulas declare how they handle unknowns, and the default is `refuse`"; "Unknown propagates"; "Ranges need a basis"; "Material exclusions"), rule 4 ("Until a conflict is resolved": a formula never runs on one of the values), rule 7, rule 8 ("Points ... are never summed into one priced total"), rule 9 ("Arithmetic lives in code"; "Rounding happens only when a value is displayed"; "Ranges come from the method ... low < value < high"), rule 10 (stages), section 6 ("Calculation engine: Versioned formulas, `unknownPolicy`, ranges, stale detection, and provisional status derived automatically").
- **Prompt 3** section 6 ("engine/: Versioned formulas with unknownPolicy, a hash manifest, decimal.js intervals: counts, points, pricing stages, the proposal snapshot. TEST formulas in test-formulas/"), section 7 ("Only `engine` creates `calculated` and `estimated` candidates"; "Arithmetic runs only in code, with decimal.js"), phase 5 ("Write no production formula for a method no source defines: the app shows 'Not available yet' and names what is missing"; engine cases against TEST datasets and TEST formulas in the test runner).
- **PRD** R-112, R-114 ("Until decided: No point or CAPEX candidate is created ... the formulas may be built and tested on synthetic fixture templates and cost ranges in tests only", D-92), R-111 (operating cost, payback, NPV and IRR "Not available yet"), R-127. D ids: D-92 (SOVITECH datasets), D-05 (the approver), D-47 (approval records), D-07 and D-48 (`financial-indicators`), D-44 (`units-7.2.22`).
- **Phase 1** declared the six formula signatures every `affects` names (`packages/registry/src/production/formulas.ts`) and the unknown-policy planner (`planFormulaRun`); the domain's derive refuses a calculated or estimated candidate whose formula is undeclared or TEST outside the test runner (G1-16). Phase 3's view-model names each output's missing datasets (`FORMULA_DATASETS`).

## Decision

1. **One catalogue.** `PRODUCTION_CATALOGUE` (`packages/engine/src/catalogue.ts`) holds each declared signature (from the registry, never restated), what it waits for besides its inputs (a dataset with its gate and the name its gate's "Waits for" gives it; a unit the registry lacks), the registry field each output's candidate is written on, and its body where a source defines the method. The view-model reads the same catalogue for the names it shows, so the proposal, step 8 and the print route say the same words.
2. **No production body in phase 5.** All six signatures are estimated methods only SOVITECH can define from datasets no one has approved, so every production run answers "not available" for every output, naming what is missing. No output field is registered and no production candidate is written. The function set has no gate (prompt 3 5.4 lists none); it is named as missing.
3. **A body, when one exists, is a file.** Each production body lives in `src/bodies/<id>@<version>.ts`; `manifest.json` holds each file's SHA-256; `checkManifest` fails on a body without an entry, an entry without a body, a changed body without a new version, an undeclared or TEST id, or a body outside `src/bodies/` (2.4; case G9-11). The manifest is empty today.
4. **Exact arithmetic.** decimal.js intervals (`interval.ts`): sums, products and the hull of options as interval arithmetic; an estimate is a central value strictly inside its range, refused otherwise (rule 9; case G9-12); a JavaScript number appears only at the candidate's boundary (`toCandidateNumber`, refused when it would not read back as the same decimal). Nothing rounds in the engine; the view-model's formatting module rounds at display, ranges outward.
5. **Runs.** `runEngine(catalogue, input, options)` reads only derived state (the one derive), loaded datasets (`loadDataset`: an approval record that resolves) and the closed gates (`readGate`). Per output: requirements first (a closed gate or no approved version: missing); then the inputs by the declared `unknownPolicy` (`refuse` by default, G1-9; `range_over_options` over an unknown enum's or decision's options, else refused for want of a basis; `exclude_and_count` leaving out and counting, an excluded item that is not `minorForTotals` making the total "Incomplete: excludes <item names>" with no headline, payback or ROI, G1-2); an input in conflict or read two ways: a range over its values where the formula takes one, else "Not available yet: two values for <field>" (G4-12); then the body, or "method" missing when none. A result is a candidate (`calculated` or `estimated` by the signature; `method` with the exact input candidate ids, the policy, the assumptions and the dataset versions; the range from the body) or the missing items. Never a zero for an unknown, never a value on an output field the registry does not declare.
6. **TEST formulas stay in the test runner.** `packages/engine/test-formulas/engine.ts` builds a `test` catalogue: the six signatures mirrored with `TEST-<id>` ids (so a TEST candidate never passes as a production one, G1-16) and the TEST formulas the cases need (G1-2, G1-7, G7-1, G10-6, G11-3), reading only `fixtures/datasets/TEST-*`, writing only TEST output fields, with their own manifest. dependency-cruiser's `test-formulas-and-fixtures-only-from-tests` keeps app and package source away from them; `runEngine` refuses a `test` catalogue outside the test runner.
7. **Counts from the register wait.** Equipment counts by asset type need the asset type field and the approved taxonomy (`dataset-asset-taxonomy`; ADR 0045 decisions 1 and 2), and zone counts the zone fields (D-09): no count formula is declared in this phase; the pages keep "Not available yet: SOVITECH asset taxonomy". The register-count formula joins the catalogue with the fields it reads.
8. **Who writes the engine's candidates.** The engine returns candidates; the API writes them through the store's service-account path (2.1 "The calculation engine only"; ADR 0013: every source but `user` from a service account that is a member of the project), never in the owner's name (G2-9). The account is ADR 0048's.

## Consequences

- The live app shows every proposal output as "Not available yet", naming the SOVITECH dataset, the method, the unit or the owner's missing input, with the owner's action where there is one; nothing invented, nothing zero.
- The mechanism (ranges, policies, incomplete totals, stages, snapshots, staleness) is proven before any SOVITECH dataset exists, with TEST data that cannot reach the app.
- Writing a SOVITECH formula later is: the dataset approved (its gate opened by the approver's record), the output fields registered at the 5.2 policy (estimation allowed only where 2.1 and rule 10 name the method), the body file, its manifest entry; the signature's version moves if its inputs or outputs change.

## How to reverse

The catalogue is one file; a body is one file and one manifest line; a formula's requirements are one table. Moving to another arithmetic library changes `interval.ts` only.

## Built (the engine builder, phase 5 part A, 2026-10-05)

What the skeleton left open, decided here; each is reversible in `packages/engine` alone unless it says otherwise.

1. **Exact decimals.** `interval.ts` works in one decimal.js constructor (`EngineDecimal`, precision 1,000,000 significant digits), so `plus` and `times` never round; operands of another constructor are read into it first (decimal.js constructors share one prototype, so the check is the instance's own constructor). Nothing divides: a percentage is a product with 0.01 (`percentOf`), a midpoint a product with 0.5 (`midpoint`). A sum or a hull of nothing is refused (rule 1, "Zero is a value"). `toCandidateNumber` refuses a decimal no JavaScript number holds without rounding; the run records that refusal (`not_representable`) and the output reads "Not available yet" naming the method.
2. **Reading an input** (`reading.ts`). From derived state only: unknown, pending, skipped and not applicable as derived; a known field whose active engine value is stale reads `out_of_date`; an engine total with material exclusions reads `incomplete` (G1-2: nothing is computed from it); a quantity the plausibility check holds back reads `please_check` (rule 8; G8-10); a field in conflict, or read two ways, is handed as a range over its values only to a formula whose policy is `range_over_options`, and otherwise reads `conflict` or `ambiguous` (rule 4; G4-12), under every other policy, `exclude_and_count` included. `MissingInputReason` gains `please_check`, `incomplete` and `out_of_date` (the view-model names each).
3. **What a body is handed.** `BodyInputs.readings` (new): per usable input, the active value of each fact, or every value a range runs over, as exact decimals with their units and qualifiers. A body never reads a field's candidates for a value of its own. `BodyOutput`'s `excluded` kind gains `range` and `qualifier`.
4. **Benchmarks make estimates.** A dataset requirement is a benchmark unless marked `reference` (the function set is); the engine refuses a catalogue pairing a benchmark with a signature not declared `estimated` (2.1; G9-4). The source of every candidate comes from the signature, never the body; a body answer of the wrong kind, an estimate not strictly inside its range (G9-12), an undeclared or missing output, a unit of another dimension, or an output field that forbids estimation is refused, with no candidate, and recorded in the run's new `refusals` list for the API's guardrail event.
5. **The method records its basis.** A candidate's `method.assumptions` carry coded notes (`notes.ts`): `dataset:<id>@<version>`, `range_over_options:`, `range_over_values:`, `excludes:`, `excludes_minor:`, `excludes_item:` and `note:<text>` for the method's own words. The domain's `CandidateMethod` has no other place for the dataset versions, the ranges' basis or the exclusions (rule 9: "what it is based on"); the view-model reads them with `methodNotesOf` and names them in the owner's words.
6. **Output fields.** The engine writes a candidate only on a field it can find the registry entry of: `EngineInput.fieldDefinition` (optional, new), else the entry of that field as `fields` hands it.
7. **The inputs hash** covers every field handed to the run (key, subject, derived state, deciding candidates: `decidingCandidateIds`), every formula ref of the catalogue, and the dataset versions read. `candidateHashOf` hashes a candidate's content in a canonical key order (rule 10's "hash of every input candidate").
8. **Staleness** (`staleness.ts`). A field changed when the candidates that decide it now differ from the snapshot's candidates of that field. The change is dated by the earliest record of the field after generation: a candidate's `createdAt`, a candidate or field event's `at` (`CurrentInputs` gains optional `fieldEvents` and `documentEvents`), or a document event on a document its candidates cite; null when no such record exists. A quotation record is current while each input it lists keeps the content its hash names and still decides a known field with no conflict; a date-only issue day reads as its start (UTC); with no dated record of the change, the "Superseded" date is the issue day, the earliest the change can have happened. `storedSnapshotOf` and `inputsOfOutput` (the `readsOf` of a catalogue) are new helpers.
9. **The stage.** "Formal quotation" only for the stage 2 output (this project's data), only for a complete figure, from the latest-issued current record naming the snapshot; a benchmark-only figure (stage 1) never becomes one. With no current record, the latest-issued superseded record gives the "Superseded" date. The headline never names an incomplete figure (G1-2).
10. **The manifest.** `checkManifest` takes the manifest's kind (production refuses TEST ids; TEST refuses ids without "TEST") and the refs of the catalogue's formulas that carry a body (`body_outside_bodies`). `src/manifest.test.ts` checks the empty production manifest; G9-11 checks the TEST manifest (`test-formulas/test-manifest.json`, sixteen bodies).
11. **F-CALC-06 (exact unit conversions).** No conversion candidate is written on the field it converts: a second candidate of one field in another unit compares as `units_differ` under rule 4 and would put the field in conflict. A formula that needs another unit of the same dimension converts inside its body by the registry's exact factors (`inBaseUnit`) and says so in a `note:`; a stored converted value, when a page needs one, is a `calculated` candidate on a field registered for it. No phase 5 body converts.
12. **The TEST catalogue** (`test-formulas/engine.ts`, README there). TEST formulas carry version `1.0.0`, not `1`: it is the version the TEST lookups of `tests/guardrails/_support/builders.ts` already declare, so their candidates derive in any case's context. The stage 1 mirror reads no area (rule 7's fallback is for a missing area; see the second finding below). `TEST-measurePriority` has no body: its output is an order of measures, which no engine candidate (a quantity) holds. Eleven extra TEST formulas serve the cases. The TEST tables they read are the new `TEST-engine-tables` dataset (`fixtures/datasets/generate.ts`, numbers 9001 to 9099 only, in `fixtures/manifest.json`).

**Findings for the integrator and part B** (none changes a rule; each is listed in the engine builder's report):
- `derive` reads an engine figure computed over a field in conflict as stale ("Out of date, recalculating"), because its inputs in conflict are not active; rule 4 says such outputs read "Provisional: two values for <field>" with a range. A clarification for the approver (which line wins), or the store not writing such candidates and the proposal showing them from the snapshot.
- `capexIndicativeRange@1` reads the gross floor area under `refuse`, so it can never be rule 7's stage 1 fallback when the area is the missing first-estimate input (G7-2a); the signature needs a version without the area when the cost ranges arrive.
- `pointsEstimate@1` declares hardware I/O as one output; rule 8 splits it into AI, AO, DI, DO and UI, and integration by protocol (G9-3). The signature's next version, with the point templates, should declare those outputs (`TEST-pointsByType` shows the shape).
- `measurePriority@1`'s output is an order, not a quantity; no engine candidate can hold it as the candidate model stands.

**Cases** (each in `tests/guardrails/`, titles starting with their ids): G1-2, G1-7, G1-28 (proposed), G4-4, G4-12, G7-1, G8-7, G8-8, G8-10 (extended, Expected unchanged), G9-3, G9-4, G9-7, G9-10 (proposed), G9-11 (proposed), G9-12 (proposed; with the rounding-outward property beside it), G10-2, G10-6, G10-7, G11-3; G1-9 and G1-16 kept. Unit and property tests in `packages/engine/src/*.test.ts` (exactness, interval containment, determinism of runs and of the inputs hash, notes, snapshot, staleness, stage, manifest).

## Amended (part B, phase 5 fix round, 2026-10-07)

Each item is reversible in `packages/engine` alone; no rule text and no case's Expected changed.

1. **Decision 3, the manifest's hash input (V-7).** The manifest held the SHA-256 of the body file alone, while all sixteen TEST bodies import helpers outside their own file (`../../src/interval`, `../lib`, `../engine-lib`, `../datasets`, `../fields`, `../points`), so a helper could change a formula's figures under the same version and the check stayed green; `src/bodies/README.md` claimed the file's hash covered everything that decides its figures. A body's entry is now the SHA-256 of `bodyHashInputOf`: the body and every file it loads through relative value imports, transitively, sorted by path from the repository root, each as its path, its length and its bytes. `import type` and `export type` load nothing at run time and are left out; packages imported by name (`@sovitech/registry`, `decimal.js`) are pinned by their versions and are not hashed here (superseded when phase 5 closed, below: a workspace package has no version, and the reader missed imports); an import the reader cannot resolve to a file fails the check. One helper, `manifest.ts` (`relativeValueImports`, `bodyClosureOf`, `bodyHashInputOf`, `bodyFilesOf`), serves `src/manifest.test.ts` and case G9-11 (extended: a helper a body imports changed under the same version fails the check, proven in memory). `test-formulas/test-manifest.json` was re-recorded once under the new input (no body or helper changed); the production manifest stays `{}`. A dependency-cruiser rule limiting `src/bodies/` imports to `../interval` and a type-only `../catalogue` was considered and left out: every rule there needs a seeded import in `tools/` (not this package's), and the closure hash already covers whatever a body imports.
2. **Built item 8, staleness (V-2, A-3, A-4).** Every moment `snapshotChanges` and `quotationStanding` answer is an ISO 8601 date-time with a zone: a superseded record with no input, with an input the caller cannot place, or with a changed hash and no dated change used to answer its issue day as stored (a DATE column, `YYYY-MM-DD`), which the formatting module refuses, so the stored proposal, its print view and Reports failed; it now answers `<issue day>T00:00:00Z`, by text only (`timestampOf`, `issuedAtOf`). `SnapshotChanges` gains `outOfDateOn`: for each out-of-date output, the first dated change after generation among the changed fields it reads, or null.
3. **Built item 9, the stage (A-4, V-4).** `SnapshotOutputRow` gains an optional `outOfDate` (`{ changedOn } | null`), set by the reader from `outOfDateOn` and never stored. `priceStageOf` never answers "Formal quotation" for a row whose `outOfDate` is set: with a current record naming the snapshot, a complete stage 2 figure that is out of date answers stage 2 with that record's "Superseded" on the later of the change and the issue day (the issue day when the change is not dated). Rule 10: "If any input changes after issue, it shows 'Superseded: inputs changed on <date>', and the figures return to stage 2 labels"; the record could not list an input that was Unknown at issue, so its standing alone read current. Stage 1, and an incomplete stage 2 total, never carry "Superseded" (no quotation covers them). Rows without `outOfDate` behave as before.

## Amended (closing phase 5, after the final verification, 2026-10-07)

Reversible in `packages/engine` alone; no rule text and no case's Expected changed.

1. **Decision 3, the closure fails closed (the final verification's item 1).** Part B's reader found imports with a pattern anchored at the start of a line: of `import { a } from './a'; import { h } from '../helper';` it read `./a` only, it missed a template-literal ``import(`../helper`)``, and packages imported by name were not hashed at all (the TEST bodies' `@sovitech/registry` is a workspace `link:`, pinned by no version), while the code said an import the hash cannot cover fails the check. Now:
   - `valueImportsOf` finds every import, export-from, `import x = require()`, `import()` and `require()` with the TypeScript parser (`typescript`, already the repository's; no dependency added), wherever it stands. An `import()` or `require()` whose module is not a plain string literal, `require` used any other way, or a source that does not parse fails the check. `import type`, `export type` and type positions are still left out, by design (they load nothing at run time).
   - An import by name passes only when the import policy names it. `PRODUCTION_IMPORT_POLICY` names `decimal.js` alone (a body's arithmetic, through `../interval`), pinned by its exact version in `pnpm-lock.yaml` for the importing package (`lockedVersionOf`, a line reader of pnpm's layout); that version is part of the hash input (`package:decimal.js@10.6.0`), so a new locked version fails the check like a changed helper. A package with no exact locked version (a range, a `link:`, no entry), a workspace package, a Node built-in or any other name fails the check.
   - TEST bodies read the production registry's keys and the TEST dataset generator, which no locked version pins, so `TEST_IMPORT_POLICY` (`packages/engine/test-formulas/engine.ts`) names four imports it lets stand unhashed, each with its reason (`@sovitech/registry`; `node:fs`, `node:path`, `node:url` of `fixtures/datasets/generate.ts`'s script run), recorded in the hash input by name only (`unhashed:<specifier>`). TEST only: hashing the registry's sources would tie every TEST body's version to every registry change, and a production body may import none of them.
   - The manifest's check has its own entry, `@sovitech/engine/manifest` (`package.json` `exports`); the engine's index no longer re-exports it, so the API's run never loads the compiler. Its readers are tests: `src/manifest.test.ts`, `test-formulas/engine.ts` and case G9-11.
   - `test-formulas/test-manifest.json` was re-recorded a second time, because the hash input grew (the locked version and the unhashed names); every TEST body's closure holds the same files as before (compared body by body), and no body or helper changed. The production manifest stays `{}`.
   - Proofs: `src/manifest.test.ts` (each probe shape of the final verification moves the hash or fails the check: two imports on one line, after a comment, an import split over lines, `export * from`, a template-literal, computed or concatenated `import()` and `require()`, an alias of `require`, a source that does not parse, a type-only import left out, `decimal.js` by its locked version, every other name refused); G9-11 extended (a helper imported on the same line as another import, changed under the same version: the check fails for each body that loads it; with part B's reader the same change passed).

## Amended 2026-10-07 (phase 6 planner): chart series

- **Series** (`src/series.ts`; docs/adr/0052 decision 4): a catalogue may declare series, each a breakdown (its points and its total) or a sequence (its points), every one an output of **one formula**, so one run of one formula version in one snapshot gives them all (G9-8, G9-9). The engine stores nothing new: a point is a snapshot output row like any other, and a row with no candidate is a labelled gap the view-model draws as such (G1-5). `checkSeries` refuses a declaration whose formula is not in the catalogue, whose total or a point is not an output of that formula, whose ids or keys are not value-id safe or repeat, a breakdown without a total, a sequence with one, a TEST series in production or a production one in a TEST catalogue; `runEngine` refuses such a catalogue. `seriesRowsOf` reads a series' rows from one snapshot and refuses rows of two formula versions.
- **The production catalogue declares no series** (`series: []`): no production formula outputs lines by system, level, stream or year, and writing one is a method only SOVITECH can define from datasets no one has approved (prompt 3 phase 5). The TEST catalogue declares the TEST series the phase 6 cases need (`capex.TEST_bySystem` with one formula under `range_over_options` over the scope decisions, for G1-5, G9-8 and G10-7: corrected by the integrator from this line's first wording, `exclude_and_count`, to what the builder built and why, "Built" item 3 below; `cashFlow.TEST_cumulative` with the payback estimate beside it, for G9-9), in the test runner only.
- How to reverse: remove `series` from `FormulaCatalogue` and `src/series.ts`; nothing stored changes.

## Built (phase 6, the engine and view-model builder, 2026-10-07): chart series

Each item reversible in `packages/engine` alone; no rule text and no case's Expected changed.

1. **`checkSeries`** (`src/series.ts`) answers every problem of every declaration, each with its series id, code and message: an id that is not value-id safe dotted segments (the contract's SERIES_KEY_PATTERN, restated, since the engine may not import the view-model) or that repeats; a formula the catalogue does not hold; a total or a point output that is not an output of that formula, or drawn twice (the total again as a point included); a point key that is not one lower-case value-id segment, or repeats; a breakdown with no total, a sequence with one; no point; in the production catalogue a series whose id or formula carries "TEST"; in a TEST catalogue a series whose id carries no "TEST" (so a TEST series can never be drawn under a production key a page asks for). `runEngine`'s `assertCatalogue` refuses a catalogue with any problem before any formula runs, naming each code (as it refuses a misdeclared benchmark: G9-4).
2. **`seriesRowsOf`** reads the total's and each point's row by output from one snapshot's rows: null when the snapshot holds none of them (generated with a catalogue that did not declare the series) or only part of them (generated by an earlier version of the formula that did not output them all: the series did not run there; amended in phase 6 part B, A-2, where the first reading refused it and so failed every page of an earlier version once a next signature version adds lines beside a stored total); refused (`EngineInputError`) when it holds two rows for one output, rows of two formula refs (G9-9), or rows of another formula than the declared one. A row with no candidate stays in the answer with its missing codes (G1-5). `checkSeries` also refuses a breakdown whose total carries a rule 10 stage (`OUTPUT_STAGES`) and one of whose parts does not (`investment_part_without_stage`; phase 6 part B, A-3).
3. **The TEST series** (`test-formulas/series.ts`, bodies `TEST-capexBySystem@1.0.0` and `TEST-cashFlow@1.0.0`, recorded in `test-manifest.json` as two new entries; no other entry changed). `testCatalogue({ extra })` declares the TEST series of the extra formulas it includes, and no other. Their output fields are TEST fields declared in `series.ts`, not in `fields.ts`, and the bodies read only the existing TEST engine tables, so no existing body's closure (and hash) changed and `fixtures/datasets/generate.ts` did not change (the plan had foreseen extending it and re-recording the manifest; a helper changed under the same versions would have meant re-recording sixteen entries, which the README forbids). `test-formulas/inputs.ts` reads the series' output fields by default.
   - `capex.TEST_bySystem` (G1-5, G9-8, G10-7): one line per system (the TEST per-building range of the engine tables for the building type) and the total. **Deviation from the plan** (which named `exclude_and_count`): the formula declares `range_over_options`. Under `exclude_and_count` the engine marks every output of a formula that left out a material input as `incomplete`, so a known system's line would have read "Incomplete: excludes System in scope: CCTV" although it reads no such input; under `range_over_options` an unknown or conflicting decision is handed with its options, the body answers that system's line "not available", naming the decision (the labelled gap), and ranges the total over the system's two options (nothing for exclude, its line for include), as the savings mirror ranges an area. An excluded system's line is not available (method), and the view-model lists the system among the exclusions, never as a gap.
   - `cashFlow.TEST_cumulative` (G9-9): `TEST-cashFlow` (`refuse`) gives the cumulative cash flow of TEST years 0 to 10 (n times the engine tables' `perLineItem` range less the TEST investment, the included systems' TEST per-building ranges; interval arithmetic, no division) and, from the same run, a TEST payback counted in TEST years (unit `count`: no duration unit exists, 7.2.22), from the last TEST year whose range is below zero to the first whose range is at or above it, its central value their midpoint; the central values cross zero within it by construction.
4. **Tests:** `src/series.test.ts` (each problem code over a seeded bad declaration, the production catalogue's empty series, the refusal by `runEngine`, the rows read and refused); the engine halves of G1-5 and G9-9 (`tests/guardrails/`); G9-11 passes with the two new entries.

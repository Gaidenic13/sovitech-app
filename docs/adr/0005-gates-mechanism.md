# 0005. Gates, the loosening check and registry validation

- **Status:** Accepted: default, reversible
- **Date:** 2026-09-25 (revised 2026-09-25 after the phase 0 review, and again after its second round)

This ADR records the mechanism only: prompt 3's own design (section 5.4 for gates; section 10, "Phase 0", for registry validation, the sensitivity test and the loosening snapshot). The registry values that "unapproved baseline v0" holds are a separate decision with status "Proposed", as prompt 3 section 5.2 ("Registry values") asks: see [ADR 0010](0010-registry-values-unapproved-baseline.md).

## Context

- **Prompt 3 section 5.4 (gates).** A gate is a named switch stored as data in `packages/registry/gates/`, with its id, what it waits for (proposal ids, dataset ids, decision numbers), its behaviour while closed, and one approval reference per item, each starting empty. Every gate starts closed. Code reads gates through one function that takes a gate source; production builds the source only from `packages/registry/gates/`; the override that opens a gate exists only in a test-utils entry that dependency-cruiser forbids everywhere except `tests/proposed/`; no environment variable or config file can open a gate. The loosening check fails when a gate is open without references that resolve to a change-log row in `docs/guardrails.md` naming the approver in its "Approved by" cell (or to a dataset approval record citing such a row), and, for an owner decision, to the decision recorded with its date and the owner's words in `docs/product/prd.md` section 15 or `docs/build-readiness.md`. While the approver table in section 10 is empty, any open gate fails. The API server and the demo seed refuse to start while any gate fails the check. The starting set has 18 gates.
- **The guardrails.** Rule 6 "Enforced by" (registry validation checks that each named consumer exists and reads the field; the sensitivity test runs in CI); section 10 "What counts as loosening", "Who approves" ("What counts as approval": the approver's own words about that specific change) and "Versioning" (CI compares the loosening-sensitive properties with the last approved snapshot and fails on any loosening without an approval record); G1-12 (a dataset with no approval record fails the loosening check); G6-1 and G6-2.
- **build-readiness 3 "Now" item 2** (harness first: registry validation with the loosening snapshot). PRD R-156 (the harness comes first; F-REGISTRY-01, F-QUESTION-03, F-REGISTRY-06).
- **PRD D rows.** D-05 (name the approver; nothing can be approved until then), D-47 (how approval records for datasets, mapping tables and registry snapshots reach the app: open, no recommendation), D-33 (the tooling defaults, dependency-cruiser among them; ADR 0001). Each gate's items carry their own D ids (below). The values the snapshot holds cite D-05, D-53 and D-93 in ADR 0010. No D row was decided as of 2026-09-25.
- **Phase 0 review (2026-09-25).** A verifier and a read-only adversarial reviewer found four gaps in the first version of this mechanism: a gate could be opened by a relative import of `packages/registry/src/gates/source.ts`, whose issuing functions were exported and which no dependency-cruiser rule covered; `buildServer()` built the API without the start-up gate check; a change-log row counted as approved whenever its "Approved by" cell mentioned the approver's name ("Pending <name>'s review" would have counted); and the registry check had no floor for an empty scope. Decisions 2, 3 and 4 below record the fixes; each comes with seeded bad inputs that the first version let through.
- **Phase 0 review, round 2 (2026-09-25).** Five more gaps: the test-utils rule forbade only a direct import, so `apps/api` or an indexed case reached the override through a `tests/proposed/` helper (high); a computed dynamic import reached `issueTestOverrideSource` outside Vitest and `readGate` read the gate open, because `readGate` did not check the source kind and the `VITEST` variable in the test-utils entry was the only barrier (low); approvals resolved from the working-tree text of `docs/guardrails.md` and the PRD, so a row the build wrote, committed or not, counted, and a placeholder such as "TBD" read as an approver (medium); an "Approved by" cell dated in the future counted (minor); and every exception list the checks use (the render allowlist and unreadable list, the ESLint allowlist, the reserved-term allowances and machine-key lists, the document homes, the third-party skills, the figure lists) was a code constant `pnpm check` accepted at any size (medium). Decisions 2, 3 and 6 record the fixes; each probe was reproduced first, fails now, and is kept as a seeded bad input.

## Decision

### 1. Gates as data

- `packages/registry/gates/<id>.yaml`, one file per gate of the starting set (`GATE_IDS` in `packages/registry/src/gates/schema.ts`): `id`, `open` (all `false`), `waitsFor`, `closedBehaviour` (the "While closed" text of the 5.4 table), `source`. Each `waitsFor` item names the `item` (source id), its `kind` (`guardrail-proposal`, `dataset` or `owner-decision`), its PRD `dId`, a `dataset` id for dataset items, and `approvalRef: ''`.
- The D ids, from PRD section 15's source-id column: ifc-input 6.2.1 D-38, 6.2.2 D-39, 6.2.3 D-40, 6.2.10 D-37, IFC mapping tables (GAP-I) D-37, build-readiness decision 4 D-01, 6.2.9 D-42, 6.2.4 D-41, 6.2.5 D-74, 6.2.6 D-49, 6.2.7 D-50, 6.2.11 D-63, 6.2.13 D-59, proposal 7.2.8 D-45, ifc-input 6.2.15 D-46, the five SOVITECH datasets D-92, proposal 7.2.22 D-44, dashboards 8.6 D-07, proposal 7.2.12 D-48, dashboards 8.1 D-28, proposals 7.2.1 D-76, 7.2.2 D-80, 7.2.11 D-75, 7.2.16 D-79, 7.2.33 D-85, build-readiness decision 2 D-09.
- Adding a gate means adding its id to `GATE_IDS`, its file, and recording it in the unapproved baseline (section 5 below; ADR 0010). Add one only where gated code is written (5.4).

### 2. One read function; sources issued only inside the gate source module

- `readGate(source, id)` in `@sovitech/registry/gates` is the only way code reads a gate. It returns a frozen reading (`open`, `closedBehaviour`, what it waits for) and throws on an unknown id or on a source the module did not issue (sources are tracked in a module-private `WeakMap`, so a look-alike object is refused).
- **Who issues a source.** Every source is created by one module-private function in `packages/registry/src/gates/source.ts`. Nothing exported there takes a kind or a gate list from the caller. The module exports exactly: `productionGateSource`, `assertGatesStartupSafe`, `isProductionSource`, `isStartupCheckedSource`, `readGate`, `checkProductionDefinitions` (the fail-closed test on definitions; it returns definitions and issues nothing), `GateApprovalError`, `issueTestOverrideSource` (below), and, since round 2, `PROPOSED_RUNNER_SETUP_FILE`, `armTestOverridesForProposedRunner` and `disarmTestOverrides` (below). A unit test pins that list.
- `productionGateSource()` builds the source only from `packages/registry/gates/` (a fixed path; no parameter, environment variable or config file). It **fails closed**: when any gate file says `open: true`, it reads the approval documents and refuses to build unless every gate passes the approval check. No gate code reads `process.env`; a unit test greps for it.
- `assertGatesStartupSafe()` reads the gate files, runs the gate part of the loosening check against the repository documents (a missing gate of the starting set, an open gate without approval, or any reference that does not resolve fails it) and throws, or returns a **new production source over the definitions it checked, marked as start-up checked**. `isStartupCheckedSource()` is true only for a source it returned: not for `productionGateSource()`, not for a test override, not for a look-alike.
- **The API cannot be built without the check.** `buildServer({ gates })` in `apps/api/src/server.ts` throws unless `gates` is start-up checked, and keeps it as `app.gates` for routes. `apps/api/src/index.ts` calls `buildServer({ gates: assertGatesStartupSafe() })`. So a worker, the demo seed or a test that builds the API goes through the same check. A test-override source is refused too, so an API with a gate open cannot be built, even in `tests/proposed/`; gated behaviour is tested at function level there.
- **The test override.** `openGateForTest(id, base?)` in `@sovitech/registry/test-utils` returns a new in-memory source with that gate open. It writes no file, leaves the production source closed, and reaches the gate source module through one internal function, `issueTestOverrideSource(base, id)`, which can only issue kind `test-override`, over a copy of a source the module issued, with one known gate open. The gates entry does not re-export it.
- **A test override exists only inside the `tests/proposed/` runner** (round 2). The gate source module holds a module-private flag: the test file it is armed for. `issueTestOverrideSource` refuses unless the module is armed for the file the runner runs now, and `readGate` refuses any source that is not a production source on the same condition, so a test-override source read in a production context (outside that runner, or after its test file ended) throws. Only `packages/registry/src/test-utils/proposed-runner-setup.ts`, registered in `setupFiles` of `vitest.proposed.config.ts`, arms it (and disarms it after the file). Arming reads Vitest's worker state, not an environment variable: the worker's current file must lie under `tests/proposed/` of its root, and its setup files must include that setup file; in a plain Node process, in the blocking `unit` and `guardrails` projects, or for a file outside `tests/proposed/`, it throws. No environment variable or config value arms it; `VITEST` plays no part. The limit, stated plainly: code in the same process that forges Vitest's worker state can arm it; the lint ban on non-literal `import()` in `apps/` and `packages/` (the lint-bans check's area) and review stay the barriers against that.
- **Who may import what** (dependency-cruiser, `.dependency-cruiser.cjs`; unit tests):
  - `gate-test-utils-only-from-proposed` forbids reaching the test-utils entry from outside `tests/proposed/` (and the entry's own folder), by package name or by path, directly or through any chain of imports (`reachable: true`, since round 2);
  - `proposed-tests-only-from-proposed` forbids importing anything under `tests/proposed/` from outside it, and `no-tests-from-apps-or-packages` forbids importing anything under `tests/` from `apps/` or `packages/` (both round 2);
  - `package-internals-only-through-exports` (added after the review) forbids importing any file under `packages/<pkg>/src/` from outside that package unless the file is an entry of that package's `package.json` `exports`; the entry list is read from the package files when the configuration loads. So `packages/registry/src/gates/source.ts` is out of reach from `apps/`, `tests/`, `tools/` and the other packages;
  - inside the registry package, a unit test (`packages/registry/src/gates/gates.test.ts`) allows only the gates entry, the test-utils entry, the proposed runner's setup file and the tests of those two folders to import `gates/source.ts`.
  The seeded imports that prove the four rules are in `tools/checks/loosening/seeded/boundary-imports/`, with, for each fix, the earlier configuration rebuilt from the repository's one (rules removed, `reachable` switched off) and the probes it let through (`expectations.json`, `before`; proven by `tools/checks/loosening/boundary-seeds.test.ts`, the lint-bans self-test and `tools/eslint-rules/depcruise.test.ts`).

### 3. Approval references

A reference is one of three forms, and only people write them:

- `guardrails-changelog:<version>` resolves only when the approver table of `docs/guardrails.md` section 10 names someone, the change log has that row, its "Approved by" cell records an approval by a listed approver, and its Change cell names the approved item (the proposal number as a whole token, so "6.2.1" is not found in "6.2.10"; for ifc-input items, "ifc-input 6.2.N"). The last condition is stricter than 5.4 asks: it stops a reference to an unrelated approved row from opening a gate.
  - **What an "Approved by" cell must hold** (`approverOfCell` in `packages/registry/src/approvals/index.ts`; revised after the review): the whole cell is either the approver's name as the section 10 table writes it, or that name followed by ", " and a calendar date written YYYY-MM-DD. Only whitespace and Markdown emphasis are ignored; case and wording are compared as written. A cell that merely mentions the name records nothing: "Pending <name>'s review", "Not approved by <name>", "<name> declined this on <date>", "<name>, pending", a name inside a longer phrase, a date that does not exist. Section 10 counts only the approver's own words about that specific change as approval; a mention is not that.
- `dataset-approval:<dataset>@<version>` resolves only through a dataset approval record that cites a resolving change-log row naming the dataset. How records reach the app is D-47, which is open, so no loader exists and no such reference resolves.
- `owner-decision:<D-id>` (or `owner-decision:build-readiness-<n>` for a build-readiness item) resolves only when that D row of PRD section 15 has a cell starting "Decided" with an ISO date and the owner's words, quoted, or build-readiness section 5 item n says "Decided <date>" followed by quoted words. The reference must name the item's own D id or decision. The section 15 table of settled parts and an "owner direction" (build-readiness decision 4 today) are never read as a decision.

While the approver table is empty, nothing resolves, and any open gate fails even with every reference filled.

**Where approvals are read from** (round 2). The repository's approval documents (`docs/guardrails.md`, `docs/product/prd.md`, `docs/build-readiness.md`) are read from git, at `git merge-base refs/heads/main HEAD` (`packages/registry/src/approvals/git.ts`): a change-log row, an approver-table row or a recorded owner decision counts only when it exists in a commit reachable from main that is not part of the build branch's own history. Rows added on the build branch, or left in the working tree, never count; a row the approver commits on main counts once main is in the build branch's merge base. Git runs with every `GIT_*` variable removed from its environment and with replace objects switched off; the branch name and the paths are fixed. Where no merge base exists (no main, a shallow clone without it, no git), nothing resolves and the loosening check fails, naming the reason: a safe failure.

**The tripwire** (round 2; `approvalDocumentEdits`). The loosening check also compares the working tree with that merge base and fails when the build branch or the working tree adds, edits or removes an approver-table row; edits an "Approved by" cell, or any cell of a row that records an approval; adds a change-log row whose "Approved by" cell is anything but the build's own "<what>: allowed without approval (section 10)" with no approver's name in it; or records an owner decision in PRD section 15 or build-readiness section 5 that main does not hold. The build's own rows (prompt 3 section 12) pass.

**Placeholders and dates** (round 2). An approver-table cell names a person only when it holds a letter and none of the placeholder forms ("TBD", "TBA", "n/a", "pending", "unknown", "none", "to be named", "to be confirmed", a cell of dashes, dots or "x"). An "Approved by" cell of the form "<name>, <YYYY-MM-DD>" counts only when the date is no later than the day the check runs (local time).


### 4. Registry shape, validation and the sensitivity test

- `@sovitech/registry/validation` defines a registry version: units, fields (guardrails 2.6 plus `estimatedMethod`, `requiredSlot`, `firstEstimateSlot`, `confirmByBasis`, `referenceDatasets`, `options` and per-property `approvals`), questions (`fieldKeys`, optional `affects` that must be a subset of their fields'), declared formula signatures (id, version, inputs, outputs, `unknownPolicy`, `estimated`), template slots, datasets and the approver settings. The production registry (`packages/registry/src/production/`) holds the settings only in phase 0; phase 1 adds fields, questions and signatures.
- `validateRegistry(registry, { scope })` checks, in the production scope: every `affects` entry is `formula:<id>@<version>` or `template:<slot>`, declared, reading the field, with a declared output (a category such as "proposal" fails, the G6-2 shape); every field names at least one output; estimation `allowed` names a method from the guardrails' closed list; no tolerance, plausible range or `minorForTotals` without an approval reference; `required` only on the four slots of rule 7, `first_estimate` only on the proposed set, each slot once (systems in scope excepted, one decision field per system); `confirmBy` owner or either names the rule 3 owner fact; identity only on the project name; reference datasets declared; unique `impactRank`; units present with the declared dimension; no TEST id; settings equal to the values the guardrails state unless they carry an approval reference. The test scope allows TEST ids, tolerances and plausible ranges, for cases. The values this validation holds the production registry to are ADR 0010's.
- `runSensitivityTest(registry, suite)` varies each field of each question across its options (or the fixture's probes, at least two), evaluates only the consumers the field declares, passes each consumer only its declared inputs, and fails a field when no declared output changes (the G6-1 shape), when a TEST implementation is missing, or when it throws. Datasets passed in must carry "TEST". Phase 0 proves it on in-test registries; the registry check fails as soon as the production registry has a question and `tools/checks/registry/sensitivity-suite.ts` supplies no suite (phase 1 fills it with the synthetic fixture project, TEST formulas and TEST datasets).
- `tools/checks/registry` runs validation, the gate files' shape and set, and the sensitivity test.
- **No pass on an empty scope** (revised after the review). The registry check fails when `packages/registry/gates/` is missing, and when it holds fewer gate files than the 18 of prompt 3 section 5.4's starting set. The floor is counted from the files, not from `GATE_IDS`, and a unit test ties the number and the ids to the prompt's table, so a shorter list in code cannot shrink what is checked. **Phase 1 adds the registry's own floor:** once the production registry holds fields, the four required fields of rule 7 (project name, project type, city, country) must exist, so an empty or partial field list fails too. Until then the summary reports "0 fields".

### 5. The loosening snapshot and check

- **What a snapshot holds.** Per field: estimation and its method, tolerance, plausible range, criticality and its slot, `confirmBy` and its rule 3 basis, identity, reference datasets, `impactRank`, `minorForTotals`, `qualifierRequired`; the `impactRank` order; the settings (confirmation budget, calibration threshold, first-estimate set, required list, identity list, document-stage order); every gate with what it waits for and its closed behaviour. Plausible ranges, `minorForTotals`, `qualifierRequired`, the order and the closed behaviour go beyond section 10's list because each lets more values through or shows fewer labels when changed (section 10, "What counts as loosening").
- **Directions.** Estimation forbidden→allowed, a tolerance added or widened, a plausible range removed or widened, a lower criticality, `confirmBy` away from engineer (and owner→either), identity added, a reference dataset added, `minorForTotals` set, `qualifierRequired` dropped, a removed field or gate, a raised budget, a member removed from the first-estimate or required set or added to the identity list, and an opened gate or an item it no longer waits for are loosenings. A change whose direction is unclear (the calibration threshold, the stage order, the `impactRank` order, a closed-behaviour text, a changed method or basis) counts as a loosening ("When unsure, treat the change as loosening").
- **The base.** The last approved snapshot whose `approvalRef` resolves; while none exists, "unapproved baseline v0" (`packages/registry/src/snapshots/unapproved-baseline-v0.json`). Its values, and their status, are ADR 0010's.
- **The check** (`tools/checks/loosening`) fails on: any loosening without a resolving reference; against the unapproved baseline, any value it does not hold (a new field, a tightening), because nothing approves it; a baseline holding a value the strict policy does not allow (any tolerance, plausible range, reference dataset, `minorForTotals`, estimation without a method, an owner field without a basis, a slot outside its list, an open gate, settings other than the guardrails' values, a status other than unapproved); a closed list or proposed value in `packages/registry/src/validation/policy.ts` whose sentence is no longer in `docs/guardrails.md` (the policy anchors, which stop a code constant and the baseline from being changed together); an open gate without approval, or any reference anywhere that does not resolve; a field taking reference data from a dataset with no approval record (G1-12). It lists every value waiting for approval in its details (`pnpm checks -- --only loosening --verbose`).
- **The writer** (`tsx tools/checks/loosening/write-baseline.ts`, `--check` for a dry run) records the current registry and gates as the unapproved baseline. It refuses when registry validation fails, when a gate is open or any reference is filled in, when anything is looser than the baseline on disk, or when the result breaks the strict policy. The unapproved baseline can therefore only gain strict values. The writer is not a check and is not run by `pnpm check`.

### 6. Exception lists in the snapshot (round 2)

- **What is recorded.** Every list that lets something past a check (an allow list) or names what a check must catch (a deny list), read from the module that uses it (`EXCEPTION_LISTS` in `tools/checks/loosening/exception-lists.ts`): the render allowlist entries and the reviewed unreadable list; the ESLint allowlist (one entry per rule and file pattern); the shadow values and theme files the lint bans accept; the reserved-term allowances and machine-key lists; the fixture-manifest document homes and never-read paths (allow), document extensions and content signatures (deny); the scanning checks' default ignores; dependency-cruiser's excluded paths; the third-party skills in `skills-lock.json`; `tools/checks/mockup-figures.txt` and `tools/checks/company-figures.txt` (deny; the second is optional and reads as empty while absent). The values are ADR 0010's.
- **Where.** The exception-list part of "unapproved baseline v0", `packages/registry/src/snapshots/exception-lists/unapproved-baseline-v0.json`, and any approved exception-list snapshot beside it. Each entry is stored as a key and a SHA-256 of its content, with the day it was recorded; figure lists are keyed by a hash of the figure, so no mockup figure, company figure, SAUTER name or hotel name is written into `packages/` (prompt 3 section 14, item 3; the `dataset-sauter-catalogue` gate).
- **The check.** Against the base (the approved exception-list snapshot of highest version whose reference resolves, mentioning "exception lists v<n>", else the unapproved baseline), it fails on an entry added to an allow list, an allow entry whose content changed (a direction that is unclear counts as a loosening), an entry removed from a deny list, a list no longer read or whose direction changed; each is a loosening with no approval reference. Against the unapproved baseline it also fails on a tightening (an allow entry removed, a deny entry added, a new list) until the writer records it. A list that cannot be read (a moved file, a renamed export) fails the check; it is never read as empty. Allow entries are listed as waiting for approval.
- **The writer** records the lists with the registry baseline, refuses every loosening, refuses to record the lists again when the file is missing but committed in HEAD (or git cannot tell), and prints each entry it records for the first time, for the build log.


## Consequences

- `pnpm checks -- --only registry,loosening` passes on the repository in phase 0, and each check fails on every seeded bad input for its own seeded reason (`pnpm check:selftest`). After the review: the loosening self-test has three more seeds (`approval-cell-pending-review`, `approval-cell-not-approved-by`, `approval-cell-name-then-refusal`), each a gate opened with a reference to a row whose "Approved by" cell only mentions the approver; the first version let all three through as approved loosenings. The registry self-test has two more (`gates-folder-missing`, `gates-fewer-than-starting-set`).
- No loosening can pass until the approver is named, and then only one change-log row at a time, whose "Approved by" cell holds the approver's name alone or with a date. No gate can open before that, whatever the PRD records.
- A relative import into another package's internals now fails `pnpm lint:deps` and the lint-bans check. When the rule was added it found three such imports outside the gates code: `tools/checks/reserved-terms/{scan,check,cases}.ts` import `packages/registry/src/reserved-terms.ts` by path. The fix, importing `@sovitech/registry/reserved-terms` (whose entry re-exports that module), belongs to that check's folder.
- The seeds in `tools/checks/loosening/seeded/boundary-imports/` follow the format of `tools/eslint-rules/fixtures/seeded/depcruise/`, so the lint-bans self-test and `tools/eslint-rules/depcruise.test.ts` ("proves every forbidden rule with at least one seeded import") can read them as they are. Those two files belong to the lint-bans check; the new rule counts as proven there once they read these seeds or a copy of them.
- Round 2: the loosening self-test gained 24 seeds that the earlier code let through: seven git scenarios built in a temporary repository (a row only in the working tree, a row committed on the build branch, the approver named on the build branch, a row on main after the branch point, an "Approved by" cell edited on the build branch, an owner decision recorded on the build branch; and a control, `good-git-approval-on-main`, that must pass), a placeholder approver ("TBD"), a future-dated cell, the runtime probe `gate-override-outside-proposed-runner` (run with tsx in a plain Node process, `VITEST=true`), and 15 exception-list seeds (an added render entry, unreadable canvas, ESLint allowlist entry, document home, reserved-term allowance, machine-key list, third-party skill and default ignore; a changed allow entry; a removed mockup figure and document extension; a list no longer read; the baseline missing; an unrecorded tightening; an approved snapshot whose reference does not resolve). The boundary seeds gained the two chains through a `tests/proposed/` helper and imports of test code from `apps/` and `packages/`.
- Round 2: the loosening check now needs a `main` branch that shares history with HEAD. In CI the `checks` and `checks:selftest` jobs set `GIT_DEPTH: "0"` and fetch `main` as a local branch when it is missing (`.gitlab-ci.yml`, wired at integration); without it the check fails, naming the reason.
- Round 2: `vitest.proposed.config.ts` registers `packages/registry/src/test-utils/proposed-runner-setup.ts` in `setupFiles` (wired at integration), so a `tests/proposed/` case can open a gate there. The integrator checked it with a throwaway TEST case under `tests/proposed/` that opened `ifc-values` and read it open, then removed the file; `tests/proposed/` holds no case yet.
- Round 2, at integration: nine more lists joined the exception-list snapshot (ADR 0010), each with a seed, so the loosening self-test runs 53 seeds.
- Round 2: any later change to an exception list is visible in the snapshot's diff. Adding an entry within rule 2's categories, which prompt 3 section 7 lets the build do with a listing for the owner, now needs an approved exception-list snapshot as well; until the approver is named (D-05), such an entry (the viewer's canvas in phase 4, for example) waits for approval and the check stays red.
- The owner-decision reader depends on how the PRD will record a decision ("Decided …" with a date and quoted words, the PRD's own legend). If the owner's decisions are recorded in another form, no reference resolves and the gate stays closed: a safe failure.
- `assertGatesStartupSafe()` runs in `apps/api/src/index.ts` before the app is built; `buildServer()` refuses any other source. The demo seed calls it too once it exists (phase 2).

## How to reverse

- **Gates as YAML files:** replace the loader in `packages/registry/src/gates/load.ts`; `readGate` and the check keep their contract.
- **Approval-reference forms:** once D-47 is decided, add the loader for dataset approval records to `loadRepoApprovalContext`, and change the reference grammar in `packages/registry/src/approvals/index.ts`. The "Change cell names the item" condition, and the two forms of the "Approved by" cell, can be relaxed there if the approver prefers; either lets more rows count as approval, so each is a loosening and needs the approver.
- **Start-up checked sources:** `buildServer` could take the plain production source again (drop the `isStartupCheckedSource` test in `apps/api/src/server.ts`). That lets an entry point skip the start-up check, so it needs the approver.
- **The package-internals rule:** remove `package-internals-only-through-exports` from `.dependency-cruiser.cjs`, with its seeds. That reopens the review's probe, so it needs the approver.
- **Snapshot properties beyond section 10's list:** remove them from `packages/registry/src/validation/snapshot.ts`; that is a loosening and needs the approver.
- **The runner guard on test overrides:** drop the `assertInsideProposedRunner` calls in `packages/registry/src/gates/source.ts`. That lets a test-override source be issued and read outside `tests/proposed/`, so it needs the approver.
- **Approvals from git:** read the documents from the working tree again (`loadRepoApprovalContext`), or drop the tripwire from `tools/checks/loosening/core.ts`. Either lets a row the build writes count, so each needs the approver.
- **The chain rules:** switch `reachable` off, or remove `proposed-tests-only-from-proposed` or `no-tests-from-apps-or-packages`; each reopens a round 2 probe and needs the approver.
- **Exception lists:** remove a list from `EXCEPTION_LISTS`, or accept additions without an approved snapshot; each is a loosening and needs the approver.
- **Registry values:** see ADR 0010.

- **The production registry** (phase 1) holds 32 fields: the project's answers, the building's facts (`building.floors` by level type, `building.rooms`, `building.zones` with their qualifiers) and the decisions. It registers no asset, zone or level field. The AI is asked only about the project's and the building's fields (`fieldsForAi`, apps/api/src/ingestion/ai-extraction.ts), so even a registered asset or zone field would get no value until the AI is asked about it, which changes what the AI is asked and needs the guardrail evals at 5 of 5 (CLAUDE.md, definition of done item 2): impossible while no API key is set (D-09). - **Prompt 3 phase 5** builds the engine: "counts from the register (calculated, provisional through their inputs)".

## Decision

1. **No asset, zone or level field is added to the production registry in this phase.** The pages are built over the registry (each column, cell and editor resolves its field from the registry the API serves: ADR 0044 decision 4), so they show Unknown where no field is registered and are proven with TEST registries in tests. Registering the asset attributes (location, system, configuration, interface, ratings), the zone fields (id as written, name, kind, area with basis, level) and the level fields (name as written, function) waits for the AI request that fills them, with its evals (D-09), and is listed in the build log's "Waiting" table. The asset type waits for the approved taxonomy (`dataset-asset-taxonomy`; adding the taxonomy as a field's reference dataset is a loosening, guardrails section 10).
2. **Counts stay the engine's.** Equipment counts are counts by asset type (2.5), so every one (the Equipment total, System Scope's and Topology's per-system lines, a zone's equipment) reads "Not available yet: SOVITECH asset taxonomy" while the gate is closed; the rows of the register are listed (an identity per tag; the tag as written from its evidence, From document). Zone and level counts are not shown before the phase 5 engine (no count header on Zones). Rule 7's open-item lines stay lines derived from stored state, as in phase 3. Reading: a count shown as Calculated before the engine exists would carry a source no formula produced (2.1); listed for the owner.
3. **The level register is derived on read, by one function, from `building.floors`' facts** (R-076): one level per counted level in building order (below ground, semi-basement, ground, mezzanine, upper, setback or technical, attic, roof plant); each label from one label function in the regim's notation and numbering where the registry has its letter (S, P, Mz, E, Er; "Etaj 1 is the first floor above parter"), and the level type's registered qualifier label otherwise; level types no source states named once as Unknown (rule 8). No level comes from a sheet count, a model's storeys, the building type or a mockup. While the floor field is in conflict no list is built (rule 4). With nothing known: "Not available yet: floor structure", with "Upload a document" and "Enter the floors" (G7-14). Level labels are listed for D-18.
4. **Register states are said truthfully.** A register with no row says why, from stored state: no documents; reading; documents read and nothing of this register came from them (never "not found": no completed AI run searched them, G12-8, G12-10); or rows. "Not found in the analysed documents (<coverage>)" appears only over what a completed AI run searched.
5. **An asset whose type is Unknown or unverified is treated as possibly life-safety for every purpose** (prompt 3 5.2): nothing beyond view, log and documents is offered on it; the owner sees no new label. The owner's only responses on equipment are "Looks right" and "Something's wrong", alone or for a selection (R-065), where a candidate exists to answer.
6. **Document categories:** the fixed mapping from `kind` to chip (D-24 open; this default): architectural → Architectural; mep, electrical → MEP; existing_bms, energy_bill → Operational; certificate → Regulatory; specification, boq, photo, other → Other. A document whose kind no classifier set reads **Unknown** in its Category cell and appears under "All Documents" only (G1-26): the upload stores `kind: 'other'` because 2.3's record has no `unknown`, and showing "Other" would present a stored default as a reading (rule 1). Every document of this build is unclassified (no classifier, US-DOCS-08). Listed as a near miss for the guardrails change log, with proposal P-4-DOCUMENT-KIND-UNKNOWN (an `unknown` kind in 2.3) for the approver.
7. **The delete effect** (UD-42; 7.1.1-D4): "<n> values will return to Unknown" counts the fields whose every eligible candidate cites only that document (2.3: a candidate with evidence from another active document keeps it; G4-39), derived from stored state, bound to `document:<id>.deleteEffect`. The words are 7.1.1-D4's and US-DOCS-21 AC1's (not a 2.8 status line: a confirmation's statement), kept in the view-model's server copy with their source, and a test that they occur in design/dashboards-spec.md.
8. **No preview image** on Documents (US-DOCS-14 AC2 applies to "a document with a preview"): an image of a page holds digits the render test cannot read, so a preview needs a `render.unreadable` entry, a loosening (proposal P-4-DOCUMENT-PREVIEW).

## Consequences

- With no API key, every register but Documents is empty in the live app, and says why; the demo shows its documents, its decisions and its answers. The pages, filters, editor and detail views are proven with TEST registries and TEST data.
- No value or count appears that a source, an approved dataset or the engine does not produce.

## How to reverse

Registering the asset, zone and level fields is a registry addition at the strict policy, re-recorded in unapproved baseline v0 by its writer (only strict values gained), together with the AI request change and its evals. Counts move to the engine in phase 5. The category mapping is one table in `workspace.ts` (`KIND_TO_CATEGORY`). The level label function is one function in `packages/view-model/src/workspace/`.

## Built (the view-model and API builder, 2026-10-02)

- **The field keys the pages read** (decision 1), declared by no production registry entry: on assets `asset.type`, `asset.system`, `asset.location`, `asset.level`, `asset.zone`; on zones `zone.code`, `zone.name`, `zone.level`, `zone.kind`, `zone.area` (packages/view-model/src/workspace/inputs.ts). A key the registry does not declare reads Unknown. A filter matches only an asset or a zone whose own stored value says so: an asset's system holds a catalogue system id, its level a level key (`upper_3`), its zone a zone subject id; an unknown value matches no filter (rule 1). Registering them for real fixes what their values hold, with the AI request that fills them (D-09).
- **Counts** (decision 2): equipment counts by type (the Equipment total, System Scope's and Topology's per-system lines, a zone's equipment) read "Not available yet: SOVITECH asset taxonomy" and points "Not available yet: SOVITECH point templates"; with either gate open, the view-model refuses (throws) rather than count, since counts are the phase 5 engine's. A system's levels and zones in System Scope's detail panel list only what its equipment's stored values name, else Unknown.
- **Level labels** (decision 3; D-18): the regim's letter where the floor notation reads one (S, P, Mz, E, Er; the parser's letters), the upper floors always numbered (E1 …), a level type counted once keeping its letter alone (S, Mz, Er), more than once numbered from the ground (S1 is the nearest the ground, listed deepest first: S3, S2, S1); a level type with no letter by its registered label ("Semi-basement", "Attic 2", "Roof plant"). A count above 999 for one level type, or no qualified count at all, reads "Not available yet: floor structure"; a fact in conflict or read two ways reads "Not available yet: two values for floors" (rule 4).
- **The asset detail's history** (R-068) lists each registered field's candidates (the value as its display formats it, the role that wrote it, when), never a person's name. Candidate events (acknowledged, rejected, verified) are not listed yet: their words would be new history wording, which 2.8 does not write; listed for the design review.
- **Near miss, G9-6** (found writing it): a rooms count read from a document is stored with its qualifier unknown whatever the proposal says, because the verifier reads a qualifier only from the rule 8 words it holds, and it holds none for rooms (packages/domain evidence.ts). That is stricter than G9-6's Expected for a document; the case proves the Expected on the owner's own entry (step 3's Edit names what the count counts) and the document path as stricter. Which words state "all spaces", "guest rooms" or "keys" in a document is the glossary's (rule 8, "Abbreviations"; `dataset-glossary`).

## Amended in part B (2026-10-02, the fix round for the API, store, view-model and contract)

- **Decision 4, the register state** (finding A-10): `no_documents` ("No documents were uploaded, so no equipment was read from them.") only when the project never had a document, withdrawn and erased ones counting; a project whose every document was deleted reads `none_read` ("No equipment has come from your documents yet."). No new wording. Proof: G12-11.
- **Decision 7, the delete effect, derived** (findings A-2, A-3): the count is what Delete does, derived, never guessed by an evidence heuristic. The API derives the project with the owner's withdrawal of the document added to the document events (the one derive for every registered field; the asset register's derive), so a value only this document holds is withdrawn, the document's revision declarations no longer supersede an older value, and an asset only it shows leaves the count. The count is (i) each field that holds a value now (known or in conflict) and none after (unknown, or skipped, which "stays unknown", 2.4), and (ii) each asset counted now and not after: its tag, a value of the asset (2.5, `tag?: FieldRef`) read only from this document, returns to unknown with it, so the same sentence covers it ("<n> values will return to Unknown"; no new wording). An asset leaving the register is 2.5's counting (G4-28) and gets no "Source document removed" line. A field left `pending` or `not_applicable` after is not counted (it shows "Reading documents…" or "Not applicable", not Unknown). Deleting a declared newer revision brings the older value back and counts nothing. Proofs: G4-41, G4-42; G4-39 unchanged.
- **Levels and zones named** (decision 3; findings V-1, A-12): an asset's or a zone's level field keeps its own display (value id, badge, source line, actions) with its text set to the level register's label for the stored key (E1 for `upper_1`), and an asset's zone field its text set to the zone's name as written, else its code, else the missing wording, never the stored key or the zone's id (rule 8 "Floors"; 2.2; R-077; US-ASSETS-05 AC2; US-ZONES-02 AC2; 7.1.1-E4). Listed with D-18. Proof: G8-24.

# 0023. The AI boundary: request building, the processor-route guard, the output validator and the eval runner

- **Status:** Accepted: default, reversible. The model id inside it is the owner's decision of 2026-09-25 (ADR 0021).
- **Date:** 2026-09-26; amended 2026-09-30 (the phase 2 review: decisions 10 to 14)

## Decision

1. **One call path** (`packages/ai/src/boundary.ts`): build the context from one project; run the route guard; send; refuse a response that names another model than `MODEL_ID`; validate every item; hand what passes to the evidence verifier as proposals that carry the model id and the time the API returned. The app and the eval runner use the same path; the runner's policy (`EVAL_POLICY`) differs only in one call per sample and in allowing a TEST glossary.
2. **The context** (`context.ts`, `blocks.ts`): every input carries its project id, and any item of another project refuses the whole request before anything is built (`CrossProjectContextError`, ids only; G13-2). Documents are sent verbatim (the verifier compares excerpts with the stored text), each in blocks whose tags carry a nonce derived from the whole request (SHA-256 prefix), so a document cannot close its own block; a request whose text holds its own nonce is refused. State reaches the model only as the structured fields `verifications` and `pricingStage`. The project's name is never sent (rule 1). Owner decisions are never asked of the AI (rule 3). Code records which blocks of which revision were sent (rule 12).
3. **The route guard** (`guard.ts`) reads the gate through `readGate` and, while it is closed, allows a document only when `fixtures/manifest.json` lists its SHA-256, and project values (owner texts, drafting facts and tokens) only from the demo project. Refusals are logged by code and id. **Reading recorded for the owner:** a drafting eval sends a fixture file that the manifest lists, re-read and re-hashed by the guard (`fixture_values`). The gate's first sentence is "sends only fixture content", and prompt 3 section 13 item 3 allows "Evals that send fixtures to the Anthropic API"; no project's values are sent that way, and in the app a drafting request that names a fixture file as its source is refused (`APP_POLICY.fixtureProvenance` is false). If the owner reads "the demo project only" as excluding drafting evals, G11-1 and G11-4 cannot run until the demo project exists.
4. **The request** (`transport.ts`, the only file that imports the SDK; a unit test pins that): `claude-opus-5-5`, `max_tokens` 64,000 on a stream, effort `high` set explicitly (this model's default is `medium`), adaptive thinking left alone, the system prompt from `prompts/sovitech-ai-system.md` read at run time (its developer comment removed) with a cache breakpoint, the documents as plain text blocks. No tools, no Citations, no Files API, no fallbacks. The output schema is sent as zod's JSON Schema with the keywords structured outputs do not take removed and `enum` and `const` kept, so the API itself holds `source` to `document` and `ai_inference`: the SDK 0.128.0 helper (`zodOutputFormat`) moves `enum` and `const` into descriptions, which would have left the sources to the validator alone. The SDK only reads the response's JSON; SDK errors become codes (their messages, which may echo content, are dropped). The boundary is held by the ESLint block `sovitech/anthropic-sdk-boundary` (static import, re-export, `import()`, `require()` plain, through `module` or `createRequire`, and TypeScript's import-equals) and, for a specifier computed at run time, by the lint ban `sovitech/no-computed-import`, which refuses every computed specifier in apps/ and packages/. Outside those folders (tools/, tests/, evals/, fixtures/) no lint rule sees a computed specifier; there, the guard is the source-text scan in `packages/ai/src/transport.test.ts`, which finds the SDK's package scope in no script but the transport. No runtime guard stops a module from loading the SDK later (phase 2 fix round 3).
5. **The output schema** (`schema/`, hashed into every eval record): candidates (field key, subject reference, value as quantity with alternatives, enum key or text, original text, source `document` or `ai_inference`, inference kind, confidence, evidence with page, sheet or cell and a verbatim excerpt), not-found answers with what was searched, missing field keys, findings (`embedded_instruction`, `hidden_text`, `claim`, `unreadable`, with locations only) and notes for the engineer or the SOVITECH team. No field holds a verification, a stage label, a price or a question. Drafting outputs are one paragraph per slot the request names.
6. **The output validator** (`validator/`), the same for the app and the evals, refuses an item, with its rule codes and a guardrail event (`ai_output_rejected` with its reason, `reserved_term_blocked`; `embedded_instruction` for each accepted finding of that kind), never text:
   - the schema, again, on receipt;
   - fields not requested, owner decisions, subject and value kinds that do not fit the field, choices, qualifiers and units the field or the unit registry does not list;
   - evidence that is missing, empty, outside the blocks the request sent of that revision, or in a block flagged hidden (rule 14);
   - sources and inferences: an inference with no kind or confidence, a `document` value carrying one, and every `ai_inference` quantity that is not a direct count (a whole number of zero or more, unit `count`, on a count field, with no alternative; rule 1); the verifier checks this again;
   - SAUTER model numbers and product names in a value that no approved catalogue lists, flagged for the engineer with their locations (G1-3); with the catalogue gate closed, every one;
   - in every text the AI writes (paragraphs, notes, suggestions, inferred text values): tokens that are unknown, malformed or name a product with no approved catalogue; digits outside tokens, except a year written as a year ("in 2019", "(2007)"), a document or sheet name the request carries, and a standard identifier from an approved standards dataset (none today, build-readiness decision 9); numbers written as words and percent signs; ranges built from two tokens; arithmetic on tokens ("T per room", "T plus T", "the sum of T and T"); reserved terms with no allowance; the brand followed by a product name or code outside a token; a clause where the BMS, as actor, commands life-safety plant (a control verb after it or a control noun anywhere, unless negated); a BAC class named without "aims to support"; compliance claimed in other words; and any question mark (rule 6).
   These text checks read words, not meaning, and fail closed; the evals cover the wording the model should use.
7. **Retries never lead** (rule 12): an unusable output (another model, a refusal, a cut-off, no JSON) is asked for again with the identical request; fields whose items were refused are asked for again with the same documents and only those fields listed, with no word of what failed; a field refused in both attempts stays unknown, with `failed_validation_twice`.
8. **The eval runner** (`evals/`, `pnpm evals [<ID> ...]`): reads each `evals/guardrails/<ID>.yaml` with its own strict schema and a closed assertion language (documented in `evals/guardrails/README.md`), refuses any fixture the manifest does not list with its bytes, runs 5 samples in a synthetic project `eval-<ID>`, and passes a sample only when the response names `MODEL_ID`, the validator refused nothing (unless the case allows it) and every assertion holds. It writes one record per case that ran, passed or not, with `id`, `samples: 5`, `passed`, the prompt hash, the model id the responses named, the schema hash, the time, the runner, the case and fixture hashes and each sample's outcome as codes. It hashes the prompt and schema folders exactly as the index check does (a test proves it on this repository). No transport can be handed to it, so a record comes only from real calls. Without a key it reports every E id of section 7 as "not running: ANTHROPIC_API_KEY not set", builds no client and writes nothing; the API refusing the key stops the run the same way.
9. **The key** is read as ADR 0021 says (the environment or the root `.env`, that variable only) and prints as a redaction in every form.
10. **Every prose check also reads a checked form of the text** (amended 2026-09-30, the phase 2 review: homoglyphs and number glyphs passed). `validator/text.ts`'s `checkedText` applies NFKC per character, drops format characters and maps Cyrillic, Greek and Armenian look-alike letters to Latin; each prose check runs on the text as written and on that form, and an issue in either counts. A new rule, `mixed_script`, refuses a word that mixes scripts, unless it is a document name the request carries. Digit runs are `\p{N}` (a superscript 2 or 3 right after a letter, as in m² and m³, stays exempt); a Roman numeral before a counted noun ("XII floors", "XII etaje") is a number (`number_word`), a letter after a label word ("wing C", "level II") is not. Latin letter forms that NFKC keeps (small capitals such as ᴠ and ꜰ, letters with a stroke or hook, negative circled and squared letters, regional indicators; `validator/latin-forms.ts`, generated from Unicode names) read as ASCII letters, and letter-spaced words (three or more single letters: 'c o m p l i a n t') are read joined for the reserved terms and numbers in words (fix round of 2026-09-30). Since the third fix round (2026-09-30, scratchpad `build/fix4/`; the closing verification's finding that 'It is a q u o t e.' was read 'aquote'), every stretch of three to twenty-four letters inside such a run is also read joined on its own, within the words around it, for the reserved terms (`letterStretches`), so a term right after a one-letter word ('a', 'o', 'I') or before another spaced word is found; a stretch is read only when some reserved term holds its letters, so a long run costs little. Ordinary single letters and one-letter words ('a b c' lists, 'I am') still pass. A side effect, a refusal only: any letter-spaced word one of whose stretches is a listed term is refused while its unspaced form passes, for example 'c o n f i r m a t ă' (the unspaced form waits for proposal 7.2.29), 'f i n a l i z e d', 'q u o t e d', 'o f f e r e d' and 'e x a c t l y'. A word split into two or three parts ('ve rified', 'veri fied') is not letter-spaced and is not read joined; 2.8 matches whole words. 'I c o n f i r m it.' passes, as 'I confirm it.' does: 'confirm' is not on 2.8's list.
11. **Rule 11's check is an allowlist** (amended 2026-09-30, the phase 2 review: the first reading was a denylist and passed the passive, nominalisations, verbs off its list and Romanian inflections; `validator/life-safety.ts`). A clause is checked when it mentions the BMS in any position (subject, "by/via/through the BMS", "prin BMS", "de sistemul BMS", "BMS-controlled", object, negated, "it" standing for the BMS, after "BMS logic:") and its sentence carries the fire or life-safety context (a clause qualified as normal mode does not inherit it). In such a clause every action word must be a read verb (monitor, display, show, log, record, read, receive, alarm, raise an alarm, and the Romanian forms), be negated, or be given to the fire system or a hardwired interlock; otherwise it is refused. The first reading's list (`life-safety-list.ts`) still runs beside it, so nothing it refused passes; letting the allowlist decide alone is proposal P-2-LS-READ-COMPLEMENTS, and reading "show", "record", "read", "receive" and "raise an alarm" as the four verbs' plain forms is the wording clarification P-2-LS-READ-SYNONYMS (build log, phase 2). Amended again in the fix round of 2026-09-30 (the verifier's 'rule 11 residuals'): a verb of provision or scope, a noun of scope or charge held by the BMS, and the BMS said to be or have a life-safety function are actions unless the fire system is their actor or every life-safety function the clause names is a read; and a clause whose sentence names the fire context, with the BMS as a party (not overridden, not negated), must say what the BMS may do (a read word or status noun, a negation of its part, the fire system's reaction, a connection of reads only), so verbless pairings ('Fire dampers: BMS.') are refused. These only add refusals (a 10,417-sentence differential against the earlier check: none loosened). Amended again in the third fix round of 2026-09-30 (scratchpad `build/fix4/`; the closing verification's findings that the check recognised the BMS only by its listed names, and that its residual was broader than its examples): `lifeSafetyControl` reads each text twice, the plain reading being the check as it stood and the wide reading adding the BMS spelled letter by letter ('B.M.S.', 'B M S', 'B-M-S') and other letter-spaced words joined in place; the BMS's other names (BAS, BEMS, GTC, SCADA, 'building controls', 'controls system', 'head-end', 'sistem(ul) de control / de automatizare / de management al clădirii', 'gestiunea tehnică a clădirii', 'tablourile de automatizare') and generic names of its parts ('controllers', 'automation') where no fire-system or life-safety name holds them; 'this system', 'that system', 'the same system', 'this same system', 'the said system', 'the system', 'acest sistem', 'același sistem', 'sistemul acesta', 'sistemul respectiv' and 'respectivul sistem' (`SYSTEM_ANAPHORS`) as 'it' is read; a clause that refers back to the BMS only through 'its' or 'there' (its control verbs on the lists, its nouns of control held through 'its', and its words of provision, scope, charge and signal); a signal, output or instruction from the BMS that life-safety plant acts on; 'move', 'follows', 'happens' and the like; and a life-safety name with a predicate of its own after a finite read verb and 'and'. A clause either reading refuses is refused, so the wide reading only adds refusals (a 23,717-sentence differential against the check before the round: 0 loosened, 4,948 newly refused; 6,191 generated read-only sentences: 0 newly refused). Residual, word for word in the header of `life-safety.ts` and pinned in `prose.test.ts`: a verb on no list, in no verb position, beside a read ('The BMS logs the fire alarm and then smoke extraction kicks in.'); in a clause that names the BMS only through 'its' or 'there', a verb on no list found only by its position or a noun of charge on no list ('The BMS monitors the fire alarm; smoke extraction is arranged from its workstation.', 'The BMS covers HVAC. Smoke extraction is also arranged there.', 'The BMS monitors the fire alarm; smoke extraction is its call.'); Romanian possessives ('BMS-ul monitorizează alarma de incendiu; desfumarea este sarcina sa.'); and a name of the BMS that no list holds ('The plant controls stop the AHUs on fire alarm.'). The closing verification of the third round found the same family in a clause with no actor after a read sentence: 'The BMS monitors the fire alarm; smoke extraction then takes place.', '... smoke extraction then follows.' and the same as two sentences are accepted (the 'and then ... takes place' form is refused); they are listed with the residual in the build log. The evals are the second layer: G11-1's `excludesAll` now also holds the round's new forms (12 patterns, its Expected cell unchanged), and no eval runs while no API key is set.
12. **One `ai_output_rejected` event per rule** (2026-09-30): a rejection with several rules was logged with the reason `rules.join('+')`, which the store's reason CHECK (migration 0005) refuses, failing the whole step's transaction.
13. **Document names are set by code while `ai-processor-route` is closed** (2026-09-30, the phase 2 review: the owner-typed file name reached the model inside the document block for any project). `guard.ts`'s `nameForModel` sends the fixture's manifest basename, else the document id; the typed name is sent only once the gate is open. The route item `document` carries its name, and while the gate is closed the guard refuses a name that is not code-set (`document_name_not_fixture`), except for the demo project and an eval fixture file that states the name itself.
14. **Eval records carry their provenance** (2026-09-30, the phase 2 review; `tools/checks/index/eval-runs.ts`): a record counts only when its `caseSha256` equals the SHA-256 of the current case file, it names every fixture the case names with the manifest's SHA-256, and its `sampleOutcomes` hold exactly five entries numbered 1 to 5, each passed with no failure and naming the current `MODEL_ID`. Four seeded bad records prove each gap (the index check's self-test).

## Consequences

- Candidates the AI proposes carry the model id in `AiProposal.modelId`; the ingestion path stores it in `candidate_ai_origins` (migration 0010; ADR 0027). The inference kind the model names is not passed to the verifier (`toCandidateProposal`; proposal P-2-INFERENCE-KIND) and not stored.
- The validator's direct-count check still allows a count of zero; the verifier refuses an inferred count of 0 (rule 1, "A count of 0 needs a document, the owner or an engineer saying so"; case G1-22).
- The extraction contract (ADR 0022) says the API never sends hidden blocks to the AI. The boundary accepts blocks flagged hidden and refuses any value that cites one; the API should keep to ADR 0022 and send none, and code makes the hidden-text finding. Evals may send a flagged block (G14-2 tests the model on one).
- The guard trusts a document's content hash as the store holds it: the upload path computes it by code at "complete", and the local app accepts only uploads whose hash `fixtures/manifest.json` lists (the owner's decision of 2026-09-25). The boundary cannot re-hash a document's extracted text against its file.
- Strict text checks can refuse wording a person would accept (for example a revision "Rev. 02" in a note); a refused item is dropped with its reason, and in the evals such a sample fails. That keeps the Truth promise at some cost to eval pass rates, and it is visible in the records.
- While no key is set, no eval is real; the index check counts every E case with a file as pending at most, and a full case file without `status: pending` fails the index check until it has a 5-of-5 record.
- The validator's word lists (life-safety terms and verbs, number words, compliance words, generic nouns after the brand) are code, not registry data: widening them to let more through is a loosening in the sense of guardrails section 10.

## How to reverse

- **The schema sender:** switch `outputFormat` back to `zodOutputFormat` from the SDK (the enum then travels as a description only; the validator still refuses other sources). Run the evals 5 of 5.
- **The drafting-eval reading (decision 3):** drop the `fixture_values` route item; G11-1 and G11-4 then wait for the demo project.
- **Retries:** set `APP_POLICY.maxAttempts` to 1.
- **Any text check:** only by removing its rule from `validator/`, which lets more through: the approver's decision (guardrails section 10).
